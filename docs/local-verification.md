# 手元の検証を関連テストに絞り、全件を CI に任せる

原本を変えるときの手元の検証を、構文・MANIFEST・関連テスト・Markdown の確認に絞る。テストの全件は、PR の CI が macOS と Ubuntu で流す結果で確認する。

この文書は、手元で流す検証の範囲、関連テストの選び方、手元で全件を流す条件、同じ PR で全件を流したあとの直しの選び方、リーダーの依頼の書き方、報告の形と、その理由を書く。決まりの正本は、`AGENTS.md` の完了の条件、`CONTRIBUTING.md` の「変更の進め方」と「テストを流す」、検証スキル `squadkit-verify` の `and00/multica-squad-kit` の節の 3 か所である。リーダーの依頼の書き方だけは、配布する squad-handoff のリーダーの手順に置く（[変える場所](#変える場所)）。

## 目的と範囲

今は、すべての変更で手元の `bash tests/run.sh` の全件を流すことが完了の条件である。全件は手元で 1 時間ほどかかり、同じ全件を CI も PR ごとに両方の OS で流すので、二重になっている。関係ない失敗の切り分けにも時間を使う。待つのは実装・修正の役と、その利用枠を払い結果を読む人間である。次の 4 つを目的にする。

1. 手元の検証の時間を、変更の大きさに比例させる
2. 全件の結果を、CI の 1 か所で読めるようにする
3. 多くのテストに効く変更では、今までどおり push の前に手元で全件を流す
4. 同じ PR の中で、手元の全件を繰り返さない。全件の条件に当たる直しが続いても、手元の全件は最初の 1 回にとどめる（[全件を流したあとの直し](#全件を流したあとの直し)）

4 つ目は、あとから足した。共通のスタブを変えた PR で、CI の失敗を直すたびにスタブを変え、そのたびに全件の条件に当たって手元の全件を流し直した。リーダーの依頼と受け入れ条件も、手元の全件の結果を求めていた。全件の条件そのものは変えず、繰り返しと、依頼で全件を求めることだけを止める。

次は対象にしない。

- テストの遅さそのものの改善。別のタスクで扱う
- 関係ない失敗や不安定なテストの扱いの見直し
- 全件の条件の中身と、`tests/run.sh` の並列数の既定。どちらも今のままにする
- 実装と修正の役の指示と `skeleton/`。役の指示は「AGENTS.md の完了の条件」を指すだけなので、変えなくても新しい条件に従う。配布するひな形のうち変えるのは、リーダーの手順の 1 項目だけである（[リーダーの依頼](#リーダーの依頼)）
- 要件を決める役が受け入れ条件に何を書くか。受け入れ条件が手元の全件を求めたときの扱いは[残る危うさ](#残る危うさ)に書く
- CI のワークフロー。CI は今のまま全件を流す
- リーダーの「同じワークフローの失敗が直しのあとも続けば人間へ返す」決まり

## 手元で必ず流す検証

変更の大きさによらず、次の 4 つを手元で流す。CI が流さない markdownlint と、push の前に分かるほうが安い構文と MANIFEST の確認を、手元に残す。

| 検証 | 流すとき | 成功の基準 |
| --- | --- | --- |
| 構文の確認 `bash scripts/check.sh` | いつも | 終了コード 0 |
| MANIFEST の作り直しと差分の確認 | いつも | 作り直してコミットしたあと、もう一度作り直しても差分がない |
| 関連テスト `bash tests/run.sh <ファイル…>` | いつも。全件の条件に当たるときは全件に替える | 終了コード 0 |
| markdownlint | Markdown を変えたとき | 終了コード 0 |
| `tests/doc-lines-test.sh` | `README.md`・`manual.md`・`CONTRIBUTING.md` を変えたとき | 終了コード 0。関連テストに加えて流してよい |

今の 2 つの例外は、関連テストのときも全件のときも残す。setup-tag-test は、エージェントの実行ではホストの `git push` の関所に止められるので流さない。混入の検査は、非公開の語の一覧が CI の Secret にしかないので流さない。どちらも「未実行。CI で確認する」と報告する。

## 関連テストの選び方

関連テストは、変えたテストのファイルと、変えたファイルの名前を含むテストのファイルである。名前はパスの最後の部分で、パスで参照するテストも名前を含むので、ここで選ばれる。

変えたファイルは、PR の base（ふつうは `main`）から分かれたところと、作業ツリーとの差分に、まだ Git に加えていないファイルを足したものにする。名前を変えたファイルは、前と後の両方の名前を入れる。消したファイルも入れる。そのファイルを参照するテストが、消したことで落ちるかを確認するため。

`MANIFEST` は、変えたファイルから除く。作り直すと毎回変わり、名前を含むテスト（`setup-test` や `install-test` など 6 本）が毎回選ばれてしまう。中身の正しさは、MANIFEST をコミットした内容と照合して判断する。

選んだテストから、setup-tag-test を除く（[例外](#手元で必ず流す検証)）。関連テストが 1 本も選べないときは、選べなかったことを報告し、テストは CI で確認する項目に書く。たとえば、`docs/` の設計文書だけを変えたときは、名前を含むテストがないので 1 本も選ばれない。

## 手元で全件を流す条件

次のどれかに当たるときは、関連テストの代わりに手元で全件を流す。多くのテストが読むので、名前で選ぶと漏れが大きいものを並べた。

| 条件 | 当たるファイル |
| --- | --- |
| テストの仕組み | `tests/run.sh`、`tests/run-one.sh`、`tests/run-hook.sh` |
| 多くのテストが共有するスタブと補助 | `tests/` の直下で、名前に `fixture` か `lib` を含み、`-test.sh` で終わらないファイル。`tests/fixtures/` の下のすべて |
| 多くのテストが読む共通の部品 | `setup.sh`、`lib/ui.sh`、`lib/check.sh`、`lib/project.sh`、`lib/render.sh`、`common/monitor/squad-cli-lib` |
| CI の定義 | `.github/workflows/` の下のすべて |
| 数と自信 | 関連テストが 10 本を超えるとき。または、選び方に自信が持てないとき |

`lib/` の共通の部品は、`lib/` のほかの 4 つ以上のファイルが関数を呼ぶものにした。今は `check.sh`（11 ファイル）、`ui.sh`（9 ファイル）、`project.sh`（6 ファイル）、`render.sh`（4 ファイル）で、ほかは 3 ファイル以下である。`lib/` にファイルを足すか、呼ぶ関係を変えたときは、この一覧を見直す。

`setup.sh` は `lib/` をすべて読むので、共通でない `lib/` のファイルも、名前を含まないテストに効くことがある。この漏れは CI で分かり、修正の役へ回す往復が 1 回増える。毎回 1 時間の全件より小さいと見て、名前で選ぶ形にとどめる。

「選び方に自信が持てない」の例は、名前を含まずに読み込まれるファイルを変えたとき（ディレクトリをまとめて読む、名前を組み立てて読むなど）である。全件を流したときは、どの条件に当たったかを報告に書く。

## 全件を流したあとの直し

同じ PR で手元の全件を一度流したら、その後の直しでは、全件の条件に当たっても全件を流し直さない。全件を流したコミットを起点に、変えたファイルの関連テストと、変えたスタブや補助を読むテストを流す。全件は CI に任せる。

全件の条件は、push の前に広い壊れを見つけるためにある。一度全件が通ったあと、または落ちたテストが分かったあとは、壊れうるのは起点からの直しが届く範囲だけである。そこは名前と補助をたどれば選べ、漏れは毎回 CI の全件で分かる。直しのたびに 1 時間の全件を手元で流すより、選び漏れで CI から修正へ回す往復のほうが小さいと見る。

### 全件を流した記録

全件を流した役は、報告に `全件:` の行を書き、結果・起点・当たった条件を入れる。形は `全件: 成功。起点 <完全な SHA>。条件: <当たった条件>` か、`全件: 失敗（<N> 本）。起点 <完全な SHA>。条件: <当たった条件>` である。実装と修正の役は検証の結果をタスクのコメントに 1 件 1 行で書くので、この行もタスクのコメントに残る。1 タスクは 1 PR なので、同じタスクのコメントが同じ PR の記録になる。

起点は、全件を流した作業ツリーをコミットし、push したコミットである。同じ実行の中で、全件のあとに直してからコミットしたときも、そのコミットを起点にする。全件のあとの直しは、下の選び方で確認してあるため。

全件を最後まで流せば、成功でも失敗でも記録になる。落ちたテストは、直したあとにファイルを指定して流すので、全件を流し直す必要がない。時間の上限や実行の停止で途中で止まった全件は、記録にしない。

次の役は、タスクのコメントから `起点` のある `全件:` の行を探し、新しいものから順に、起点が今の HEAD の祖先であるものを使う。祖先かは `git merge-base --is-ancestor <起点> HEAD` で確認する。記録がない、またはどの起点も祖先でない（履歴を書き換えた）ときは、通常の選び方と全件の条件に戻る。

人が手で変えるときは、全件を流したコミットを PR の確認に書いておき、同じ選び方を使う。

### 選び方

変えたファイルは、通常の選び方の起点（PR の base から分かれたところ）を、全件を流したコミットに替えて求める。作業ツリーとの差分、Git に加えていないファイル、名前を変えたファイルの前と後、消したファイルを入れ、`MANIFEST` を除くのは通常と同じである。

次の和を流す。

1. 変えたテストのファイル
2. 変えたファイルの名前を含むテストのファイル。通常の関連テストと同じ
3. 変えたスタブや補助を読むテストのファイル。`tests/` の直下で `-test.sh` で終わらないファイル（`test-weights` を除く）を補助と呼ぶ。変えたファイルの名前を含む補助を集め、その補助の名前を含む補助も、新しく増えなくなるまで集める。集めた補助の名前を含むテストを選ぶ
4. 直す前に落ちていたテストのファイル。CI のログか、前の全件の報告にあるもの

全件の条件は使わない。数が 10 本を超えても、選び方に自信が持てなくても、全件には替えない。選べたテストが 1 本もないときは、選べなかったことを報告し、CI で確認する。setup-tag-test は、通常と同じく除く。

3 で補助をたどるのは、スタブの多くが別の補助を通して読まれるためである。たとえば `tests/cli-fixture-lib.py` は、名前を含むテストが 1 本だけだが、`cli-stub.py` などの補助を通して 23 本のテストに読まれる。名前だけで選ぶと、合意した「変えたスタブを読むテスト」を落とす。通常の選び方でこれをしないのは、スタブを変えたときは全件の条件に当たり、全件で確認するからである。`test-weights` を除くのは、すべてのテストの名前を並べたファイルで、たどると関係ないテストまで選ぶため。

今のリポジトリで、3 までの選び方が選ぶ本数は次のとおり。

| 起点のあとに変えたファイル | 選ぶ本数 | たどった補助 |
| --- | --- | --- |
| `tests/cli-fixture-lib.py` | 23 本 | `cli-stub.py`、`gh-fixture.py`、`multica-fixture.py`、`cli-mode-test-lib.sh` など 12 個 |
| `tests/setup-fixture.sh` | 7 本 | なし |
| `tests/project-test-lib.sh` | 6 本 | なし |
| `tests/run.sh` | 4 本 | `run-one.sh`、`stop-session.py` |
| `lib/webhooks.sh` | 4 本 | なし。通常の関連テストと同じ |

起点のあとに `main` を取り込んだときは、取り込んだ変更も変えたファイルに入り、選ぶテストが増える。多く流す側に倒れるので、そのままにする。コンフリクトを解消したときの検証は、[コンフリクトの解消の設計](conflict-resolution.md)の決まりのままで、この節を使わない。

## リーダーの依頼

リーダーは、実装や修正の依頼に、手元で流す検証の範囲を書かない。範囲は作業先の `AGENTS.md` の完了の条件と検証スキルが決める。とくに、手元でテストの全件を流すことや、その結果を返すことを求めない。全件の結果は、マージへ回す前に CI で読む今の決まりで確認する。

依頼が手元の全件を求めると、役は依頼に従い、検証スキルの選び方が効かなくなる。全件を流した記録があっても、依頼のたびに全件を流し直す。そこで、依頼を書くときにリーダーが読む squad-handoff の `references/leader-flow.md` の「依頼の書き方と受け渡し」に、1 項目を足す（[リーダーの手順に足す項目](#リーダーの手順に足す項目)）。

この項目は、どのプロジェクトにも配るひな形に入る。そのため、このリポジトリの全件の条件は書かず、「範囲は作業先の決まりに任せる」とだけ書く。手元の全件を求める決まりのプロジェクトでは、役が検証スキルに従って全件を流すので、動きは変わらない。人間がコメントで手元の全件を求めたときは、役は全件を流す。人間の明示した求めは、リーダーの依頼とは分けて扱う。

## 報告

報告は、コマンドごとに成功・失敗・未実行を分けて 1 件 1 行で書く。読み手が、手元で確認した範囲と CI に任せた範囲を見分けられるようにする。

- 関連テストは、選んだファイルと選んだ理由を 1 件 1 行で書く。理由は「`lib/webhooks.sh` の名前を含む」「変えたテストのファイル」のように書く
- 全件を流したときは、[全件を流した記録](#全件を流した記録)の形で、結果・起点・当たった条件を書く
- 全件を流したあとの選び方を使ったときは、使った起点を書く。補助をたどって選んだテストは、理由に補助の名前と、たどり始めたファイルを書く
- 全件の条件に当たったが、全件を流した記録があるので流さなかったときは、そのことを書く
- 関連テストが選べなかったときは、選べなかったことを書く
- 手元で流さなかった全件は「CI で確認する」と書き、成功に数えない
- 実装と修正の役は、CI の結果を待たずに引き継ぐ

## CI の失敗を修正へ回す流れとの整合

CI の見張りがリーダーへ知らせ、リーダーが修正の役へ回す今の流れは変えない。関連テストの選び漏れは、この流れで直る。

修正の役は、CI で失敗したテストのファイルを `bash tests/run.sh <ファイル…>` で手元で流し、直ったことを確認する。そのうえで、自分の変更についてテストを選んで流す。全件を流した記録があれば[全件を流したあとの直し](#全件を流したあとの直し)の選び方を使い、なければ通常の選び方と全件の条件を使う。全件の成功は、リーダーが人間のマージへ回す前に CI の結果を読む今の決まりで確認する。

## 変える場所

決まりの正本は、今の 3 か所（`AGENTS.md` の完了の条件、`CONTRIBUTING.md` の「変更の進め方」、検証スキル）のままにする。エージェントの正本は検証スキルで、人が手で変えるときの正本は `CONTRIBUTING.md` である。人は Multica のスキルを読めないことがあるので、条件は両方に書き、変えるときは両方をそろえる。

| 場所 | 今の役目 | このたび変えること |
| --- | --- | --- |
| `AGENTS.md` の完了の条件 | 手元で必ず流す 4 つ、全件は CI で確認すること、正本が検証スキルにあること | 変えない。「全件を流す条件に当たるときだけ流す」は、全件を流したあとの直しと食い違わない |
| `CONTRIBUTING.md` の「変更の進め方」 | 人向けのコマンド、関連テストの選び方、全件の条件 | 全件の条件の表のあとに、[全件を流したあとの直し](#contributingmd-に足す段落)の段落を足す |
| `CONTRIBUTING.md` の「テストを流す」 | 手元では関連テストを選び、全件は CI が流すこと | 変えない |
| `.github/pull_request_template.md` の確認 | 関連テストか全件かと、CI で確認する全件を書く欄 | 変えない。全件を流したコミットは、この欄の説明に書く |
| 検証スキル `squadkit-verify` の `and00/multica-squad-kit` の節 | エージェント向けの選び方・全件の条件・報告の形 | 「変更に応じて選ぶ検証」と「結果の報告」を、[検証スキルの新しい本文](#検証スキルの新しい本文)に置き換える |
| `common/skills/squad-handoff/references/leader-flow.md` の「依頼の書き方と受け渡し」 | リーダーが依頼を書くときの決まり | [リーダーの手順に足す項目](#リーダーの手順に足す項目)を足す |
| `tests/agent-templates-test.sh` | リーダーの手順の参照が、決まった語句を持つかの確認 | `leader-flow.md` の語句の確認に、足す項目の語句を足す |

実装と修正の役の指示、`skeleton/`、CI のワークフローは変えない。

### CONTRIBUTING.md に足す段落

全件の条件の表のあと、「手元で流さなかった全件は…」の段落の前に、次の段落を足す。文は[文書の改行](../CONTRIBUTING.md#文書の改行)に従って 1 行 1 文にする。

```markdown
同じ PR で手元の全件を一度流したら、その後の直しでは、全件の条件に当たっても全件を流し直さない。  
全件を流したコミットを PR の確認に書き、その後は、そのコミットからの差分でテストを選ぶ。  
選ぶのは、関連テストと、変えたスタブや補助を読むテストと、直す前に落ちていたテストである。  
補助は、`tests/` の直下で `-test.sh` で終わらないファイル（`test-weights` を除く）を指す。  
変えたファイルの名前を含む補助を、名前でたどって集め、その名前を含むテストを選ぶ。  
選び方とコマンドは、[手元の検証の設計](docs/local-verification.md#全件を流したあとの直し)にある。
```

`CONTRIBUTING.md` から設計の文書へ結ぶのは、たどるコマンドが長く、人向けの手順に写すと 2 か所で食い違いやすいためである。エージェントは検証スキルの同じコマンドを使う。

### リーダーの手順に足す項目

`leader-flow.md` の「依頼の書き方と受け渡し」の 1 つ目の項目（依頼には対象・頼む範囲・返してほしいものを書く）のすぐあとに、次の項目を足す。

```markdown
- 依頼に、手元で流す検証の範囲を書かない。範囲は、作業先の `AGENTS.md` の完了の条件と検証スキルが決める。手元でテストの全件を流すことや、その結果を返すことは求めない。全件の結果は CI で読む
```

`tests/agent-templates-test.sh` の `leader-flow.md` の語句の確認（`'作業先' '同じ誤り' '原因'`）に、`'手元でテストの全件を流すこと'` を足す。項目を消したり言い換えたりしたときに、テストで気づけるようにする。

### 検証スキルの新しい本文

検証スキルはリポジトリの外の Multica のスキルなので、この PR では本文だけを示す。人間がこの本文を承認したあとに、スキルの `and00/multica-squad-kit` の節へ反映する。

置き換えるのは「変更に応じて選ぶ検証」と「結果の報告」の 2 つの小見出しの中身である。今の本文との違いは、「手元で全件を流す条件」の末尾の 1 文、新しい「全件を流したあとの直し」、「CI で失敗したテストを直すとき」の選び方、「結果の報告」の全件の行の 3 項目である。「実行の前提」「サービスやデータを使う検証」「E2E と画面の確認」「依存ライブラリの脆弱性の確認」「片付け」は変えない。

````markdown
### 変更に応じて選ぶ検証（and00/multica-squad-kit）

手元では、変更の大きさによらず下の「手元で必ず流す検証」を流す。テストの全件は PR の CI が macOS と Ubuntu で流すので、手元では「手元で全件を流す条件」に当たるときだけ全件を流す。AGENTS.md の完了の条件が、この節を選び方と全件の条件の正本として指している。CONTRIBUTING.md の「変更の進め方」にも人向けに同じ条件があるので、変えるときはそろえる。

#### 手元で必ず流す検証

| 変えたもの | コマンド | 成功の基準 |
| --- | --- | --- |
| すべての変更 | `bash scripts/check.sh` | 終了コード 0 |
| すべての変更 | `bash scripts/manifest.sh` で作り直してコミットし、もう一度作り直して `git diff --exit-code -- MANIFEST` | 終了コード 0 |
| すべての変更 | 下の選び方で選んだ関連テストを `bash tests/run.sh <ファイル…>` で流す。全件の条件に当たるときは全件に替える | 終了コード 0 |
| Markdown のファイル | `npx markdownlint-cli2 '**/*.md' '#tmp/**'` | 終了コード 0 |
| README.md・manual.md・CONTRIBUTING.md | 関連テストに `tests/doc-lines-test.sh` を加える | 終了コード 0 |

> 例外 1: エージェントの実行では、setup-tag-test はホストの `git push` の関所に止められて失敗する。関連テストからも全件からも除き、「関所のため未実行。CI で確認する」と報告する。全件は `bash tests/run.sh $(ls tests/*-test.sh | grep -v setup-tag-test)` で流す。関所を避ける設定や呼び方はしない。
>
> 例外 2: 混入の検査は非公開の語の一覧が要り、CI の Secret にしかない。流さずに「一覧がないため未実行。CI で確認する」と報告する。一覧を探したり作ったりしない。
>
> markdownlint は CI が流していないので、ここで確認する。manual.md の節名を変えたときは、CONTRIBUTING.md の「画面に出す文」にある grep で参照を合わせる。

#### 関連テストの選び方

関連テストは、変えたテストのファイルと、変えたファイルの名前（パスの最後の部分）を含むテストのファイルである。変えたファイルは、PR の base（ふつうは main）から分かれたところと作業ツリーとの差分に、Git に加えていないファイルを足したものにする。名前を変えたファイルは前と後の両方、消したファイルも入れる。MANIFEST は、作り直すと毎回変わるので除く。

原本のルートで次を流すと、全件の条件に当たるファイル（`全件:` の行）と、関連テストの一覧が出る。`全件:` の行が 1 行でも出たら、全件を流す。

```bash
git fetch -q origin main
changed=$({ git diff --name-only --no-renames "$(git merge-base origin/main HEAD)"; git ls-files --others --exclude-standard; } | grep -vx MANIFEST | sort -u)
printf '%s\n' $changed | grep -E '^(tests/run(-one|-hook)?\.sh|setup\.sh|lib/(ui|check|project|render)\.sh|common/monitor/squad-cli-lib)$|^(tests/fixtures|\.github/workflows)/|^tests/[^/]*(fixture|lib)[^/]*$' | grep -v -- '-test\.sh$' | sed 's/^/全件: /'
for f in $changed; do
  case $f in tests/*-test.sh) [ -f "$f" ] && echo "$f" ;; esac
  grep -lF -- "${f##*/}" tests/*-test.sh
done | grep -vx tests/setup-tag-test.sh | sort -u
```

関連テストが 1 本も選べないときは、テストを流さず、選べなかったことを報告する。テストは CI で確認する項目に書く。

#### 手元で全件を流す条件

次のどれかに当たるときは、関連テストの代わりに全件を流す。

| 条件 | 当たるファイル |
| --- | --- |
| テストの仕組み | `tests/run.sh`、`tests/run-one.sh`、`tests/run-hook.sh` |
| 多くのテストが共有するスタブと補助 | `tests/` の直下で、名前に `fixture` か `lib` を含み、`-test.sh` で終わらないファイル。`tests/fixtures/` の下のすべて |
| 多くのテストが読む共通の部品 | `setup.sh`、`lib/ui.sh`、`lib/check.sh`、`lib/project.sh`、`lib/render.sh`、`common/monitor/squad-cli-lib` |
| CI の定義 | `.github/workflows/` の下のすべて |
| 数と自信 | 関連テストが 10 本を超えるとき。または、選び方に自信が持てないとき（名前を含まずに読み込まれるファイルを変えたときなど） |

`lib/` の共通の部品は、`lib/` のほかの 4 つ以上のファイルが関数を呼ぶものである。`lib/` にファイルを足したり、呼ぶ関係を変えたりしたら、この一覧を見直す。

同じ PR で全件を流した記録があるときは、この条件を使わず、下の「全件を流したあとの直し」に従う。

#### 全件を流したあとの直し

同じ PR で手元の全件を一度流したら、その後の直しでは、全件の条件に当たっても全件を流し直さない。全件を流したコミットを起点に選んだテストを流し、全件は CI で確認する。リーダーの依頼や受け入れ条件に「全件」とあっても、この節に従い、全件を流さなかったことを報告に書く。人間がコメントで手元の全件を求めたときは、全件を流す。

記録は、このタスクのコメントにある `全件:` の行のうち、`起点 <完全な SHA>` を含むものである。新しいものから順に、`git merge-base --is-ancestor <起点> HEAD` が成功する最初の記録を使う。記録がない、またはどの起点も祖先でないときは、上の選び方と全件の条件に戻る。最後まで流した全件は、成功でも失敗でも記録になる。途中で止まった全件は記録にしない。

原本のルートで、`base` に記録の起点を入れて次を流すと、たどった補助（`補助:` の行）と、流すテストの一覧が出る。

```bash
base=<記録の起点>
git merge-base --is-ancestor "$base" HEAD || echo '起点が HEAD の祖先でない。上の選び方に戻る'
changed=$({ git diff --name-only --no-renames "$base"; git ls-files --others --exclude-standard; } | grep -vx MANIFEST | sort -u)
helpers=$(find tests -maxdepth 1 -type f ! -name '*-test.sh' ! -name test-weights)
keys=$(printf '%s\n' $changed | sed 's#.*/##' | sort -u)
while :; do
  next=$({ printf '%s\n' $keys; for k in $keys; do grep -lF -- "$k" $helpers; done | sed 's#.*/##'; } | sort -u)
  [ "$next" = "$keys" ] && break
  keys=$next
done
printf '%s\n' $changed | sed 's#.*/##' | sort -u | comm -13 - <(printf '%s\n' $keys) | sed 's/^/補助: /'
{ for f in $changed; do case $f in tests/*-test.sh) [ -f "$f" ] && echo "$f" ;; esac; done
  for k in $keys; do grep -lF -- "$k" tests/*-test.sh; done; } | grep -vx tests/setup-tag-test.sh | sort -u
```

出た一覧に、直す前に落ちていたテスト（CI のログか、前の全件の報告にあるもの）を足して、`bash tests/run.sh <ファイル…>` で流す。数が 10 本を超えても、全件には替えない。1 本も選べないときは、選べなかったことを報告し、CI で確認する。

起点のあとに main を取り込んだときは、取り込んだ変更も選ぶ対象に入る。コンフリクトを解消したときは、この節ではなく、コンフリクトの解消の決まりに従う。

#### CI で失敗したテストを直すとき

修正の役は、CI のログで失敗したテストのファイルを `bash tests/run.sh <ファイル…>` で手元で流し、直ったことを確認する。そのうえで、全件を流した記録があれば「全件を流したあとの直し」で、なければ上の選び方と全件の条件でテストを選んで流す。全件の成功は、リーダーが人間のマージへ回す前に CI の結果で確認する。

### 結果の報告（and00/multica-squad-kit）

実行したコマンド、確認した対象、成功・失敗・未実行とその理由を分けて報告します。

> コマンドごとに、成功・失敗・未実行を分けて 1 行で書く。
>
> - 関連テストは、選んだファイルと選んだ理由を 1 件 1 行で書く。例: `tests/webhooks-test.sh: lib/webhooks.sh の名前を含む`、`tests/ui-test.sh: 変えたテストのファイル`
> - 全件を流したときは、結果・起点・当たった条件を 1 行で書く。起点は、全件を流した作業ツリーをコミットし、push したコミットの完全な SHA である。例: `全件: 成功。起点 <完全な SHA>。条件: tests/run.sh を変えた（テストの仕組み）`、`全件: 失敗（3 本）。起点 <完全な SHA>。条件: …`
> - 全件を流したあとの直しで選んだときは、`起点: <SHA>（全件を流した記録）` と書く。補助をたどって選んだテストの理由は、例: `tests/setup-test.sh: cli-stub.py の名前を含む（tests/cli-fixture-lib.py から補助をたどった）`
> - 全件の条件に当たったが、記録があるので流さなかったときは、`全件: 条件に当たるが、起点 <SHA> で流したので流さない。CI で確認する` と書く
> - 関連テストが選べなかったときは、`関連テスト: 選べなかった（変えたファイルの名前を含むテストがない）。CI で確認する` と書く
> - 手元で流さなかった全件は `全件: CI で確認する` と書き、成功に数えない。CI の結果は待たずに引き継ぐ
> - CI で失敗したテストを直したときは、そのファイルと手元の結果を書く
> - setup-tag-test、混入の検査、pwsh がないときの wsl.ps1 の構文の確認は、未実行と理由を書き、成功に数えない
> - 失敗したテストは、run.sh が最後に出す失敗した場所と直前のケースを添える
````

## 確認の方法

受け入れ条件の例を、変えたあとの正本に当てて確認する。今のリポジトリで、上のコマンドが出す結果は次のとおり。

| 場面 | 変えたファイル | 選ばれるテスト | 手順 |
| --- | --- | --- | --- |
| 記録なし | `lib/webhooks.sh` だけ | `completion-colors-test`、`project-followup-test`、`project-issues-test`、`webhooks-test` の 4 本 | 関連テストを流す |
| 記録なし | `tests/run.sh` だけ | 3 本（数は使わない） | 全件を流し、`全件:` の行に起点を書く |
| 記録なし | `tests/cli-fixture-lib.py` だけ | 1 本（数は使わない） | 全件を流し、`全件:` の行に起点を書く |
| 記録なし | `docs/` の設計文書だけ | 0 本 | 選べなかったと報告し、CI で確認する |
| 記録あり | 起点のあとに `tests/cli-fixture-lib.py` | 補助 12 個をたどり 23 本 | 23 本と、直す前に落ちていたテストを流す。全件は流さない |
| 記録あり | 起点のあとに `tests/setup-fixture.sh` | 7 本 | 7 本を流す |
| 記録あり | 起点のあとに `docs/` の設計文書だけ | 0 本 | 選べなかったと報告し、CI で確認する |
| 記録あり、起点が祖先でない | 履歴を書き換えたあと | — | 通常の選び方と全件の条件に戻る |

ほかに、次を確認する。

- `common/` の差分が、`leader-flow.md` の 1 項目だけである。`skeleton/`、`.github/` には差分がない
- `tests/agent-templates-test.sh` が、足した語句の確認を含めて通る
- 変えた文書が、markdownlint、`tests/doc-lines-test.sh`、[文書の改行](../CONTRIBUTING.md#文書の改行)を通り、MANIFEST を作り直してある
- 検証スキルの節が、人間の承認のあとに、[検証スキルの新しい本文](#検証スキルの新しい本文)と同じになっている

## 残る危うさ

関連テストを名前で選ぶので、名前を含まずに効くテストは手元で漏れる。`setup.sh` が読む共通でない `lib/` のファイルと、リポジトリのファイルをまとめて走査するテスト（語の検査の `terms-test` など）がこれに当たる。漏れは CI で分かり、修正の役へ回す往復が 1 回増える。リーダーの差し戻しの決まりは変えないので、往復が続けば人間へ返る。

全件を流したあとの直しでは、補助を名前でたどるが、`tests/fixtures/` のようにディレクトリをまとめて読むものや、名前を組み立てて読むものは、たどれない。通常の選び方なら全件の条件に当たる変更でも、記録のあとは全件を流さないので、この漏れは CI で初めて分かる。同じ PR で一度は全件が通っているか、落ちたテストが分かっているので、漏れは直しが届く範囲に限られると見る。

要件を決める役が、受け入れ条件に「手元で全件が通る」と書くことは止めていない。検証スキルは、依頼や受け入れ条件に全件とあっても全件を流したあとの直しに従うと書くので、役は全件を流し直さない。受け入れ条件との食い違いは、報告の「流さなかった」の行で人間とリーダーに見える。要件の役の指示を変えるかは、同じことが続いたときに別のタスクで考える。

条件が、検証スキルと `CONTRIBUTING.md` の 2 か所にある。片方だけを変えると食い違うので、どちらにも「そろえる」と書く。全件を流したあとの選び方のコマンドは、検証スキルと、この文書の[検証スキルの新しい本文](#検証スキルの新しい本文)にあり、`CONTRIBUTING.md` はこの文書を指す。

検証スキルはマージを待たずに Multica で効く。反映してからマージまでの間は、`main` の `CONTRIBUTING.md` と検証スキルが食い違う。反映を実装の最後に回し、間を短くする。この間に全件を流し直さなかった変更も、CI が全件を流すので確認は漏れない。

`leader-flow.md` は配布するひな形なので、導入済みのプロジェクトには、バージョンを上げて更新したときに届く。届くまでは、そのプロジェクトのリーダーは今の書き方のままである。

## 検討した案

### 選び方をどこに置くか

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 検証スキルにコマンドを書く | 合意した 3 か所の中で済む。コードとテストが増えない | 長いコマンドを写して流す | 選んだ |
| 選ぶスクリプトを `scripts/` に置く | 1 行で呼べる。テストで選び方を確認できる | 合意した範囲の外で、コード・テスト・重みが増える | 選ばない。選び漏れが続くときに別のタスクで考える |

全件を流したあとの選び方も、同じ理由で検証スキルにコマンドを書く。

### 差分の起点

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| PR の base から分かれたところ | レビューの役が同じ PR で同じ一覧を得る。ローカルのブランチ名によらない | 前のフェーズの分も毎回選ぶので、後のフェーズほど本数が増える | 通常の選び方で選んだ |
| 前に push したところ | 本数がそのフェーズの分だけになる | レビューの役では差分が空になる。checkout したブランチ名が PR のブランチと違い、起点を決めにくい | 選ばない |
| 全件を流したコミット | 全件で確認した先からの差分だけを選べる。コミットの SHA なので、ブランチ名によらず次の役が同じ起点を使える | 記録を残し、読む手間が増える | 全件を流したあとの直しで選んだ |

### 何を「一度全件を流した」と数えるか

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 手元で全件を最後まで流したときだけ | 起点のコミットと結果を、流した役が確かに書ける | 最初の 1 回は、条件に当たれば手元で流す | 選んだ |
| PR の CI が全件を流したときも数える | 手元の全件が 1 回もいらなくなる | CI は push のたびに流すので、最初の push のあとは全件の条件が効かなくなる。合意した「一度全件を流したら」が、「手元では流さない」に変わる | 選ばない |
| 成功した全件だけを数える | 起点で全件が通っていると言える | 落ちた全件のあとの直しのたびに、全件を流し直す。今回止めたい繰り返しが残る | 選ばない |

### 変えたスタブを読むテストの選び方

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 名前を含むテストだけ（通常の選び方） | コマンドが今のまま | 補助を通して読まれるスタブを落とす。`tests/cli-fixture-lib.py` では 1 本しか選ばない | 選ばない |
| 補助を名前でたどる | 補助を通して読むテストも選べる。今のリポジトリでは最も多いスタブで 23 本 | コマンドが長くなる。ディレクトリでまとめて読むものはたどれない | 選んだ |
| スタブを変えたら全件 | 漏れがない | 今回止めたい繰り返しそのもの | 選ばない |

### 選ぶ鍵から除くもの

`MANIFEST` を鍵に入れると、毎回 6 本が選ばれ、重い `setup-test` も入る。中身は MANIFEST をコミットした内容と照合して判断するので、除いた。`lib/` のすべてを全件の条件にする案は、`setup.sh` がすべてを読むので漏れは減るが、共通でない 1 ファイルの変更でも全件になり、目的と合わないので選ばない。補助をたどるときに `test-weights` を除くのは、すべてのテストの名前を並べたファイルで、たどると関係ないテストまで選ぶためである。
