# 手元の検証を関連テストに絞り、全件を CI に任せる

原本を変えるときの手元の検証を、構文・MANIFEST・関連テスト・Markdown の確認に絞る。テストの全件は、PR の CI が macOS と Ubuntu で流す結果で確かめる。

この文書は、手元で流す検証の範囲、関連テストの選び方、手元で全件を流す条件、報告の形と、その理由を書く。変えるのは、`AGENTS.md` の完了の条件、`CONTRIBUTING.md` の「変更の進め方」と「テストを流す」、検証スキル `squadkit-verify` の `and00/multica-squad-kit` の節の 3 か所である（[変える場所](#変える場所)）。

## 目的と範囲

今は、すべての変更で手元の `bash tests/run.sh` の全件を流すことが完了の条件である。全件は手元で 1 時間ほどかかり、同じ全件を CI も PR ごとに両方の OS で流すので、二重になっている。関係ない失敗の切り分けにも時間を使う。待つのは実装・修正の役と、その利用枠を払い結果を読む人間である。次の 3 つを目的にする。

1. 手元の検証の時間を、変更の大きさに比例させる
2. 全件の結果を、CI の 1 か所で読めるようにする
3. 多くのテストに効く変更では、今までどおり push の前に手元で全件を流す

次は対象にしない。

- テストの遅さそのものの改善。別のタスクで扱う
- 関係ない失敗や不安定なテストの扱いの見直し
- 配布するひな形（`common/` の役の指示、`skeleton/`）。実装と修正の役の指示は「AGENTS.md の完了の条件」を指すだけなので、変えなくても新しい条件に従う
- CI のワークフロー。CI は今のまま全件を流す
- リーダーの「同じワークフローの失敗が直しのあとも続けば人間へ返す」決まり

## 手元で必ず流す検証

変更の大きさによらず、次の 4 つを手元で流す。CI が流さない markdownlint と、push の前に分かるほうが安い構文と MANIFEST の確認を、手元に残す。

| 検証 | 流すとき | 成功の基準 |
| --- | --- | --- |
| 構文の確認 `bash scripts/check.sh` | いつも | 終了コード 0 |
| MANIFEST の作り直しと差分の確認 | いつも | 作り直してコミットしたあと、もう一度作り直しても差分がない |
| 関連テスト `bash tests/run.sh <ファイル…>` | いつも。全件の条件に当たるときは全件に替える | 終了コード 0 |
| markdownlint | Markdown を変えたとき | 終了コード 0 |
| `tests/doc-lines-test.sh` | `README.md`・`manual.md`・`CONTRIBUTING.md` を変えたとき | 終了コード 0。関連テストに加えて流してよい |

今の 2 つの例外は、関連テストのときも全件のときも残す。setup-tag-test は、エージェントの実行ではホストの `git push` の関所に止められるので流さない。混入の検査は、非公開の語の一覧が CI の Secret にしかないので流さない。どちらも「未実行。CI で確かめる」と報告する。

## 関連テストの選び方

関連テストは、変えたテストのファイルと、変えたファイルの名前を含むテストのファイルである。名前はパスの最後の部分で、パスで参照するテストも名前を含むので、ここで選ばれる。

変えたファイルは、PR の base（ふつうは `main`）から分かれたところと、作業ツリーとの差分に、まだ Git に加えていないファイルを足したものにする。名前を変えたファイルは、前と後の両方の名前を入れる。消したファイルも入れる。そのファイルを参照するテストが、消したことで落ちるかを確かめるため。

`MANIFEST` は、変えたファイルから除く。作り直すと毎回変わり、名前を含むテスト（`setup-test` や `install-test` など 6 本）が毎回選ばれてしまう。中身の正しさは、MANIFEST の差分の確認で確かめる。

選んだテストから、setup-tag-test を除く（[例外](#手元で必ず流す検証)）。関連テストが 1 本も選べないときは、選べなかったことを報告し、テストは CI で確かめる項目に書く。たとえば、`docs/` の設計文書だけを変えたときは、名前を含むテストがないので 1 本も選ばれない。

## 手元で全件を流す条件

次のどれかに当たるときは、関連テストの代わりに手元で全件を流す。多くのテストが読むので、名前で選ぶと漏れが大きいものを並べた。

| 条件 | 当たるファイル |
| --- | --- |
| テストの仕組み | `tests/run.sh`、`tests/run-one.sh`、`tests/run-hook.sh` |
| 多くのテストが共有するスタブと補助 | `tests/` の直下で、名前に `fixture` か `lib` を含み、`-test.sh` で終わらないファイル。`tests/fixtures/` の下のすべて |
| 多くのテストが読む共通の部品 | `setup.sh`、`lib/ui.sh`、`lib/check.sh`、`lib/project.sh`、`lib/render.sh`、`common/monitor/squad-cli-lib` |
| CI の定義 | `.github/workflows/` の下のすべて |
| 数と自信 | 関連テストが 10 本を超えるとき。または、選び方に自信が持てないとき |

`lib/` の共通の部品は、`lib/` のほかの 4 つ以上のファイルが関数を呼ぶものにした。今は `check.sh`（11 ファイル）、`ui.sh`（9 ファイル）、`project.sh`（6 ファイル）、`render.sh`（4 ファイル）で、ほかは 3 ファイル以下である。`lib/` にファイルを足すか、呼ぶ関係を変えたときは、この一覧を見直す。

`setup.sh` は `lib/` をすべて読むので、共通でない `lib/` のファイルも、名前を含まないテストに効くことがある。この漏れは CI で分かり、修正の役へ回す往復が 1 回増える。毎回 1 時間の全件より小さいと見て、名前で選ぶ形にとどめる。

「選び方に自信が持てない」の例は、名前を含まずに読み込まれるファイルを変えたとき（ディレクトリをまとめて読む、名前を組み立てて読むなど）である。全件を流したときは、どの条件に当たったかを報告に書く。

## 報告

報告は、コマンドごとに成功・失敗・未実行を分けて 1 件 1 行で書く。読み手が、手元で確かめた範囲と CI に任せた範囲を見分けられるようにする。

- 関連テストは、選んだファイルと選んだ理由を 1 件 1 行で書く。理由は「`lib/webhooks.sh` の名前を含む」「変えたテストのファイル」のように書く
- 全件を流したときは、当たった条件を書く
- 関連テストが選べなかったときは、選べなかったことを書く
- 手元で流さなかった全件は「CI で確かめる」と書き、成功に数えない
- 実装と修正の役は、CI の結果を待たずに引き継ぐ

## CI の失敗を修正へ回す流れとの整合

CI の見張りがリーダーへ知らせ、リーダーが修正の役へ回す今の流れは変えない。関連テストの選び漏れは、この流れで直る。

修正の役は、CI で失敗したテストのファイルを `bash tests/run.sh <ファイル…>` で手元で流し、直ったことを確かめる。そのうえで、自分の変更について関連テストを選んで流す。全件の成功は、リーダーが人間のマージへ回す前に CI の結果を読む今の決まりで確かめる。

## 変える場所

3 か所を同じ内容にそろえる。エージェントの正本は検証スキルで、人が手で変えるときの正本は `CONTRIBUTING.md` である。人は Multica のスキルを読めないことがあるので、条件は両方に書き、変えるときは両方をそろえる。

| 場所 | 変えること |
| --- | --- |
| `AGENTS.md` の完了の条件 | 手元で必ず流す 4 つ、全件は CI で確かめること、選び方と全件の条件の正本が検証スキルにあること |
| `CONTRIBUTING.md` の「変更の進め方」 | PR の前に流すコマンドを、全件から関連テストに替える。関連テストの選び方と全件の条件を書く |
| `CONTRIBUTING.md` の「テストを流す」 | 手元では関連テストを選んで流し、全件は CI が流すことを書く |
| `.github/pull_request_template.md` の確認 | `bash tests/run.sh` の欄を、関連テストか全件かを書く欄に替える |
| 検証スキル `squadkit-verify` の `and00/multica-squad-kit` の節 | 「変更に応じて選ぶ検証」と「結果の報告」を、[検証スキルの新しい本文](#検証スキルの新しい本文)に置き換える |

PR テンプレートは合意した 3 か所の外だが、確認の欄に全件の `bash tests/run.sh` が残ると、`CONTRIBUTING.md` と食い違う。`.github/workflows/` ではないので、CI の定義は変えない。

### AGENTS.md の完了の条件

「完了の条件」の最初の段落を、次の 2 段落に替える。2 つ目と 3 つ目の段落（合格の基準、未実行を成功にしない）は残し、3 つ目に「手元で流さなかった全件」の 1 文を足す。

> 変更の大きさによらず、手元で次を流します。構文の確認、MANIFEST の作り直しと差分の確認、変えたファイルに関係するテスト（関連テスト）、Markdown を変えたときの markdownlint です。`README.md`・`manual.md`・`CONTRIBUTING.md` を変えたときは `tests/doc-lines-test.sh` も流します。テストの全件は PR の CI が macOS と Ubuntu で流すので、手元では全件を流す条件に当たるときだけ流します。
>
> 関連テストの選び方、全件を流す条件、実行する場所・道具・コマンド・例外・報告の形・片付けの正本は、プロジェクトの検証スキル `squadkit-verify` の `and00/multica-squad-kit` の節です。人が手で変えるときの同じ手順は[変更の進め方](CONTRIBUTING.md#変更の進め方)にあります。別のリポジトリの手順は流用しません。
>
> （3 つ目の段落に足す文）手元で流さなかった全件は「CI で確かめる」と報告し、成功に数えません。CI の結果は待たずに引き継ぎます。

### CONTRIBUTING.md の「変更の進め方」と「テストを流す」

「変更の進め方」の PR の前に流すコマンドを次に替え、その下に関連テストの選び方と全件の条件を書く。文は[文書の改行](../CONTRIBUTING.md#文書の改行)に従って 1 行 1 文にする。

```bash
bash scripts/check.sh
bash scripts/manifest.sh
bash tests/run.sh tests/webhooks-test.sh     # 関連テスト。選び方は下に書く
npx markdownlint-cli2 '**/*.md' '#tmp/**'    # Markdown を変えたとき
SQUAD_KIT_FORBIDDEN_FILE=/path/outside/terms.txt bash tests/check-content.sh
```

コマンドの下には、次を書く。

- 関連テストは、変えたテストのファイルと、変えたファイルの名前を含むテストのファイルである。`MANIFEST` は変えたファイルに数えない
- `README.md`・`manual.md`・`CONTRIBUTING.md` を変えたときは、`tests/doc-lines-test.sh` も流す
- 全件を流す 5 つの条件を、[手元で全件を流す条件](#手元で全件を流す条件)と同じ対象で書く。全件は `bash tests/run.sh` で流す
- 手元で流さなかった全件は、PR の確認に「CI で確かめる」と書く。全件は CI が両方の OS で流す
- エージェントは、検証スキルの同じ条件に従う。条件を変えるときは、検証スキルとそろえる

「テストを流す」の「CI も同じコマンドを流す。」は、「手元では、変更の進め方に従って関連テストを選んで流す。全件は CI が流す。」に替える。コマンドの例は変えない。

````markdown

#### 手元で必ず流す検証

| すべての変更 | `bash scripts/check.sh` | 終了コード 0 |

#### 関連テストの選び方

関連テストは、変えたテストのファイルと、変えたファイルの名前（パスの最後の部分）を含むテストのファイルである。変えたファイルは、PR の base（ふつうは main）から分かれたところと作業ツリーとの差分に、Git に加えていないファイルを足したものにする。名前を変えたファイルは前と後の両方、消したファイルも入れる。MANIFEST は、作り直すと毎回変わるので除く。

原本のルートで次を流すと、全件の条件に当たるファイル（`全件:` の行）と、関連テストの一覧が出る。`全件:` の行が 1 行でも出たら、全件を流す。

```bash
git fetch -q origin main
changed=$({ git diff --name-only --no-renames "$(git merge-base origin/main HEAD)"; git ls-files --others --exclude-standard; } | grep -vx MANIFEST | sort -u)
printf '%s\n' $changed | grep -E '^(tests/run(-one|-hook)?\.sh|setup\.sh|lib/(ui|check|project|render)\.sh|common/monitor/squad-cli-lib)$|^(tests/fixtures|\.github/workflows)/|^tests/[^/]*(fixture|lib)[^/]*$' | grep -v -- '-test\.sh$' | sed 's/^/全件: /'
for f in $changed; do
  case $f in tests/*-test.sh) [ -f "$f" ] && echo "$f" ;; esac
  grep -lF -- "${f##*/}" tests/*-test.sh
done | grep -vx tests/setup-tag-test.sh | sort -u
```

関連テストが 1 本も選べないときは、テストを流さず、選べなかったことを報告する。テストは CI で確かめる項目に書く。

#### 手元で全件を流す条件

次のどれかに当たるときは、関連テストの代わりに全件を流す。

| 条件 | 当たるファイル |
| --- | --- |
| テストの仕組み | `tests/run.sh`、`tests/run-one.sh`、`tests/run-hook.sh` |
| 多くのテストが共有するスタブと補助 | `tests/` の直下で、名前に `fixture` か `lib` を含み、`-test.sh` で終わらないファイル。`tests/fixtures/` の下のすべて |
| 多くのテストが読む共通の部品 | `setup.sh`、`lib/ui.sh`、`lib/check.sh`、`lib/project.sh`、`lib/render.sh`、`common/monitor/squad-cli-lib` |
| CI の定義 | `.github/workflows/` の下のすべて |
| 数と自信 | 関連テストが 10 本を超えるとき。または、選び方に自信が持てないとき（名前を含まずに読み込まれるファイルを変えたときなど） |

`lib/` の共通の部品は、`lib/` のほかの 4 つ以上のファイルが関数を呼ぶものである。`lib/` にファイルを足したり、呼ぶ関係を変えたりしたら、この一覧を見直す。

#### CI で失敗したテストを直すとき

修正の役は、CI のログで失敗したテストのファイルを `bash tests/run.sh <ファイル…>` で手元で流し、直ったことを確かめる。そのうえで、上の選び方で関連テストも流す。全件の成功は、リーダーが人間のマージへ回す前に CI の結果で確かめる。

### 結果の報告（and00/multica-squad-kit）

実行したコマンド、確かめた対象、成功・失敗・未実行とその理由を分けて報告します。

> コマンドごとに、成功・失敗・未実行を分けて 1 行で書く。
>
> - 関連テストは、選んだファイルと選んだ理由を 1 件 1 行で書く。例: `tests/webhooks-test.sh: lib/webhooks.sh の名前を含む`、`tests/ui-test.sh: 変えたテストのファイル`
> - 全件を流したときは、当たった条件を書く。例: `全件: tests/run.sh を変えた（テストの仕組み）`
> - 関連テストが選べなかったときは、`関連テスト: 選べなかった（変えたファイルの名前を含むテストがない）。CI で確かめる` と書く
> - 手元で流さなかった全件は `全件: CI で確かめる` と書き、成功に数えない。CI の結果は待たずに引き継ぐ
> - CI で失敗したテストを直したときは、そのファイルと手元の結果を書く
> - setup-tag-test、混入の検査、pwsh がないときの wsl.ps1 の構文の確認は、未実行と理由を書き、成功に数えない
> - 失敗したテストは、run.sh が最後に出す失敗した場所と直前のケースを添える
````

## 確かめ方

受け入れ条件の例を、変えたあとの 3 か所の正本に当てて確かめる。今のリポジトリで、上のコマンドが出す結果は次のとおり。

| 変えたファイル | 全件の条件 | 選ばれる関連テスト | 手順 |
| --- | --- | --- | --- |
| `lib/webhooks.sh` だけ | 当たらない | `completion-colors-test`、`project-followup-test`、`project-issues-test`、`webhooks-test` の 4 本 | 関連テストを流す |
| `tests/run.sh` だけ | テストの仕組み | 3 本（数は使わない） | 全件を流す |
| `tests/cli-fixture-lib.py` だけ | 共有のスタブと補助 | 1 本（数は使わない） | 全件を流す |
| `docs/` の設計文書だけ | 当たらない | 0 本 | 選べなかったと報告し、CI で確かめる |

ほかに、次を確かめる。

- `common/`、`skeleton/`、`.github/workflows/` に差分がない
- 変えた文書が、markdownlint、`tests/doc-lines-test.sh`、[文書の改行](../CONTRIBUTING.md#文書の改行)を通り、MANIFEST を作り直してある
- 検証スキルの節が、人間の承認のあとに、[検証スキルの新しい本文](#検証スキルの新しい本文)と同じになっている

## 残る危うさ

関連テストを名前で選ぶので、名前を含まずに効くテストは手元で漏れる。`setup.sh` が読む共通でない `lib/` のファイルと、リポジトリのファイルをまとめて走査するテスト（語の検査の `terms-test` など）がこれに当たる。漏れは CI で分かり、修正の役へ回す往復が 1 回増える。リーダーの差し戻しの決まりは変えないので、往復が続けば人間へ返る。

条件が、検証スキルと `CONTRIBUTING.md` の 2 か所にある。片方だけを変えると食い違うので、どちらにも「そろえる」と書く。

検証スキルはマージを待たずに Multica で効く。反映してからマージまでの間は、`main` の `AGENTS.md` と検証スキルが食い違う。反映を実装の最後に回し、間を短くする。この間に関連テストだけで済ませた変更も、CI が全件を流すので確かめは漏れない。

## 検討した案

### 選び方をどこに置くか

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 検証スキルにコマンドを書く | 合意した 3 か所の中で済む。コードとテストが増えない | 長いコマンドを写して流す | 選んだ |
| 選ぶスクリプトを `scripts/` に置く | 1 行で呼べる。テストで選び方を確かめられる | 合意した範囲の外で、コード・テスト・重みが増える | 選ばない。選び漏れが続くときに別のタスクで考える |

### 差分の起点

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| PR の base から分かれたところ | レビューの役が同じ PR で同じ一覧を得る。ローカルのブランチ名によらない | 前のフェーズの分も毎回選ぶので、後のフェーズほど本数が増える | 選んだ |
| 前に push したところ | 本数がそのフェーズの分だけになる | レビューの役では差分が空になる。checkout したブランチ名が PR のブランチと違い、起点を決めにくい | 選ばない |

### 選ぶ鍵から除くもの

`MANIFEST` を鍵に入れると、毎回 6 本が選ばれ、重い `setup-test` も入る。中身は MANIFEST の差分の確認で確かめるので、除いた。`lib/` のすべてを全件の条件にする案は、`setup.sh` がすべてを読むので漏れは減るが、共通でない 1 ファイルの変更でも全件になり、目的と合わないので選ばない。
