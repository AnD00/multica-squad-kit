# PR をタスクに自動で紐付ける

PR を作った役が、作った直後に共通スクリプトを呼び、タスクの画面で URL を指定したときと同じ紐付けを Multica の API で行う。人間の手作業は、スクリプトが紐付けられなかったときだけに残す。

この文書は、スクリプトと、それを呼ぶ役の手順の設計と、その理由を書く。利用者が確認する前提は `manual.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

今は、`squad-handoff` が「タスクの画面で URL を指定して紐付ける」と決めているが、CLI に紐付けのコマンドがなく、役はこの手順を実行できない。そのため、タスクに PR が紐付かず、PR をマージしてもタスクが `done` に移らない。Multica は、手で紐付けた PR もマージでタスクを移す判定に入れる。PR 本文の `Closes` は紐付けるだけで、判定には関わらない。

`squad-dependabot-merge` は、人間に回す Dependabot の PR を、すでに API で紐付けている。この方法を共通のスクリプトに取り出し、PR を作る役からも使う。次は対象にしない。

- タスクの識別子を、PR のタイトル・ブランチ名・本文に入れて自動で紐付かせること。識別子を PR へ持ち出さない決まりを保つため
- この変更より前に作られた PR の紐付けを補うこと。人間が画面で紐付けられるため
- 紐付けた PR の外し方と付け替え。人間の画面操作に任せる
- 前提の設定（[前提](#前提)）を、セットアップが自動で変えること。ワークスペース全体の動作を変えるため、人間が画面で確認する
- エージェントの実行からスクリプトを名前で呼べない問題。別のタスクで扱う。この設計では、呼べないときも紐付けの失敗として扱い、作業を止めない

## 前提

次の 2 つが満たされていないと、PR をタスクに紐付けられないか、紐付けてもマージでタスクが `done` にならない。スクリプトはこの 2 つを確認しない。読むための CLI がなく、ワークスペースの設定は人間が画面で確認するものだから。

- Multica の GitHub 連携が、作業先のリポジトリにつながっている。つながっていないと、紐付けそのものができない
- ワークスペースの設定「After PRs merge, move the issue to」が Done である。Done でないと、紐付けてもマージでタスクが `done` にならない

GitHub 連携は、紐付けの API の前提でもある。サーバーは、リポジトリが連携につながり、PR が同期されるまで、その PR を知らない。その間は、紐付けの API が 404 を返し、タスクの画面から URL を指定しても紐付けられない。404 の応答の本文は、`pull request not found; it appears here once its repository is connected and the PR has been synced` である（連携していないリポジトリの PR を渡して確認した）。スクリプトは、404 で待ち切れたときの警告で、この前提を確認するよう案内する（[警告の内容](#警告の内容)）。

## 置くもの

原本の `common/monitor/` に、スクリプトと共有の関数を置く。`common/monitor/` の `squad-*` は、ホストの準備がエージェントの `bin` に置き、エージェントの `PATH` に入るため、役の実行から名前で呼べる。`squad-usage-read` と `squad-usage-check` が `squad-usage-lib` を共有するのと同じ形にする。

| ファイル | 役目 |
| --- | --- |
| `common/monitor/squad-pr-link-lib` | 紐付けの関数。API を呼び、見つからない間は待ち、成功したら metadata に `pr_url` を書く |
| `common/monitor/squad-pr-link` | 役が呼ぶコマンド。引数を確認し、タスクを読み、関数を呼び、失敗したら警告を出す |
| `common/monitor/squad-dependabot-merge` | 今の `link_pull_request` の中身を、共有の関数を呼ぶ形に置き換える |
| `tests/squad-pr-link-test.sh` | スタブの `multica`・`curl`・`sleep`・`date` で、紐付け・紐付け済み・待ち・失敗・トークンを確認する |

## コマンドの I/F

```bash
squad-pr-link <タスク> <PR の URL>
```

- `<タスク>` は、タスクの ID か識別子。`multica issue get` が受け取る形ならよい。役は、実行に渡されたタスクの ID を渡す
- `<PR の URL>` は `https://github.com/OWNER/REPO/pull/番号` の形だけを受け取る。末尾の `/files` やクエリ、フラグメントは受け取らない。紐付けの重複を見分ける値を 1 つの形にそろえるため

| 終了コード | 意味 | 呼んだ役の扱い |
| --- | --- | --- |
| 0 | 紐付けた。または、metadata に `pr_url` があり、紐付けずに飛ばした。どちらかは標準出力の行で分かる | そのまま進む。紐付けたかは、終了コードでなく標準出力の行で読む |
| 1 | 紐付けられなかった。標準エラーに警告を出した | 止まらずに引き継ぐ。警告の内容を引き継ぎのコメントに書く |
| 2 | 引数の誤り。使い方を標準エラーに出した | 引数を直して呼び直す |

コマンドが見つからないとき（終了コード 127）も、役は 1 と同じに扱う。

標準出力には、紐付けたときと、`pr_url` があり飛ばしたときに、1 行の結果を出す。行の先頭の語で、紐付けたかどうかが分かるようにする。PR の URL は、どちらも引数に渡された URL を書く。

| 場合 | 標準出力の行 |
| --- | --- |
| 紐付けた | `紐付けました: <識別子> <PR の URL>` |
| `pr_url` があり、飛ばした | `紐付けていません: <識別子> <PR の URL>（metadata に pr_url があるため、API を呼びませんでした。紐付いているかは multica issue pull-requests で確認してください）` |

飛ばしたときも終了コードは 0 のままにし、行で紐付けていないことを示す。理由は [紐付け済みの判定と、役が書く `pr_url`](#紐付け済みの判定と役が書く-pr_url) にある。

## 処理の順序

1. PR の URL の形を確認する。合わなければ、終了コード 2 で終える
2. `multica issue get <タスク> --output json` で、タスクの ID・識別子・metadata を読む。読めなければ、失敗として警告を出す
3. metadata に `repository` があり、URL の `OWNER/REPO` と大文字・小文字を区別せずに違うときは、紐付けずに失敗として警告を出す。別のリポジトリの PR を取り違えて紐付けないため
4. metadata に `pr_url` があれば、API を呼ばず、`紐付けていません:` の行を出して終了コード 0 で終える。人間が画面で外した紐付けを戻さないため。`pr_url` が渡した URL と違うときは、そのことを標準エラーに 1 行書き、紐付けは変えない
5. トークン（`MULTICA_TOKEN`）、サーバーの URL（`MULTICA_SERVER_URL`）、`curl` のどれかがなければ、失敗として警告を出す
6. タスクの画面と同じ API（`POST <サーバーの URL>/api/issues/<タスクの ID>/pull-requests`、本文は `{"url": "<PR の URL>"}`）を呼ぶ。`MULTICA_WORKSPACE_ID` があれば、`X-Workspace-ID` の見出しに入れる
7. 応答が 200 なら、`multica issue metadata set <タスクの ID> --key pr_url --value <PR の URL> --type string` で残し、`紐付けました:` の行を出して終了コード 0 で終える。metadata を書けなければ、失敗として警告を出す
8. 応答が 404（サーバーが PR をまだ取り込んでいない）なら、[見つからないときの待ち](#見つからないときの待ち)に従って呼び直す
9. それ以外の応答と、通信の失敗は、待たずに失敗として警告を出す

失敗したときは、metadata に `pr_url` を書かない。

手順 3 と 4 は、`repository` と `pr_url` の鍵の有無で決まる。タスクは CLI の出力の約束を通して読み、約束はこの二つの鍵を補わない。詳しくは [review-wait.md の鍵の有無で決まる動作](review-wait.md#鍵の有無で決まる動作)にある。

## 見つからないときの待ち

PR を作った直後は、GitHub から Multica への Webhook が届く前で、サーバーが PR を知らず 404 を返すことがある。404 の間は、10 秒ごとに呼び直し、最初に呼んだときから 120 秒を過ぎたら、待つのをやめて失敗として警告を出す。

- 上限を 120 秒にするのは、Webhook はふつう数秒で届き、2 分を過ぎても届かないときは、連携が切れているなど待っても直らない原因が多いため。役の 1 回の実行は 30 分ほどに収めるので、待ちはその 1 割に満たない長さにとどめる
- 間隔を 10 秒にするのは、ふつうの遅れなら 1 回か 2 回の呼び直しで済み、上限までに呼ぶのが 12 回以内にとどまるため
- 上限には HTTP の通信時間も含める。通信の前に残り時間を確認し、通信は 30 秒と残り時間の短い方、待ちは 10 秒と残り時間の短い方に制限する。応答が期限以降に返ったら、200 でも成功にせず、metadata を書かない
- 経過は `date +%s` で測り、待ちは `sleep` で行う。テストは両方をスタブにして、実際には待たない
- 待ちの値は、スクリプトの中の定数にする。役ごとや導入先ごとに変える要件がないため、設定にはしない

`squad-dependabot-merge` も、共有の関数を通して同じ待ちを使う。Dependabot の PR は、人間に回す時点で作られてから時間がたっているので、ふつうは待たずに終わる。

## 警告の内容

警告は標準エラーに出す。紐付けられなかったタスクの識別子、PR の URL、理由、人間が紐付ける手順を書く。

```text
タスク <識別子> に PR <URL> を紐付けられませんでした（<理由>）。タスクの画面の PR の欄で、この URL を指定して紐付けてください。
```

- 理由は、「サーバーが PR を見つけられない（120 秒待った）」「応答の状態コード <番号>」「トークンがない」「metadata の repository と違う」などの短い語にする
- 応答の本文は出さない。サーバーの返す本文に、何が入るかを決められないため
- 1 行目の文は、理由によらず同じ形のまま保つ。役と人間は、この行で紐付けの失敗を見分けるため

### 404 で待ち切れたときの案内

404 で待ち切れたときだけ、1 行目に続けて、GitHub 連携と PR の同期を確認する案内を 2 行目に出す。`<OWNER/REPO>` には、PR の URL のリポジトリをそのまま入れる。

```text
タスク <識別子> に PR <URL> を紐付けられませんでした（サーバーが PR を見つけられない（120 秒待った））。タスクの画面の PR の欄で、この URL を指定して紐付けてください。
サーバーは、<OWNER/REPO> がワークスペースの GitHub 連携につながり、PR が同期されるまで、PR を見つけられません。ワークスペースの設定のコードの画面で、<OWNER/REPO> がつながっていることを確認してから紐付けてください。つながっていないと、タスクの画面からも紐付けられません。
```

- 案内は、スクリプトの中の決まった文にする。404 の意味は、サーバーが応答の本文で示している（[前提](#前提)）。ただし本文の文言はサーバーのバージョンで変わり得るので、本文を読んで出し分けたり、そのまま出したりはしない
- 待ち切れたことは、共有の関数が理由の文とは別の値（`PR_LINK_NOT_FOUND`）で返す。呼び出し側は、理由の文を照合して出し分けない。文を直したときに案内が黙って消えるのを防ぐため
- 待ち切れるのは、少なくとも 1 回 404 を受けて待ったあとだけである。最初の通信は 30 秒で打ち切るので、120 秒の上限には届かない。このため、上限による打ち切りはすべて 404 の続きとして扱い、`PR_LINK_NOT_FOUND` を立てる
- Webhook がふつうより遅れただけでも、この案内は出る。案内は「つながっていない」と言い切らず、「つながり、同期されるまで見つけられない」と前提を述べ、確認の方法を示す形にする
- 404 以外の失敗（状態コード、通信、トークン、`repository` の不一致など）では、案内を出さない。連携と関係のない原因で、人間に連携を確認させないため
- `squad-dependabot-merge` の警告には、案内を足さない。Dependabot の見張りは次の回で紐付けを補うので、1 回の 404 で人間を連携の確認に向かわせる必要が薄いため。`PR_LINK_NOT_FOUND` は読まない
- `squad-dependabot-merge` は、今の警告の文（「次に同じ PR を回すときに補います」を含む）を変えない。次の回で補う動きが Dependabot の見張りにだけあるため。共有の関数は成否と理由だけを返し、警告の文は呼び出し側が作る

## トークンの扱い

トークンは、コマンドの引数・PR・タスクのコメント・ログに出さない。

- `curl` へは、`Authorization` の見出しを `curl --config -` の標準入力で渡す。引数に入れると、同じホストのプロセスの一覧から読めるため
- 応答の本文は `-o /dev/null` で捨て、状態コードだけを読む
- スクリプトは `set -x` を使わない。警告と結果の行には、識別子・URL・状態コードだけを書く
- 一時ファイルにトークンを書かない

テストは、スタブの `curl` が受け取った引数、標準出力、標準エラー、一時のディレクトリのどれにもトークンの値がないことを確認する。

## 紐付け済みの判定と、役が書く `pr_url`

紐付け済みかどうかは、metadata の `pr_url` で決める。`multica issue pull-requests` の一覧で決めると、人間が画面で外したあとに呼ばれたとき、紐付けを戻してしまうため。

スクリプトが失敗したときは、PR を作った役が自分で metadata に `pr_url` を書く。`squad-handoff` は、次の担当と見張り（`squad-pr-watch`）が対象を取り違えないよう `pr_url` を置くことを求めており、紐付けの成否にかかわらず必要なため。この順序なので、失敗のあとにスクリプトを呼び直しても、API を呼ばずに飛ばす。紐付けは、警告に従って人間が画面で行う。役がスクリプトを呼ぶのは PR を作った直後の 1 回だけなので、呼び直しで補う動きは要らない。

### 飛ばしたことを出力で示す

`pr_url` があることは、紐付いていることを意味しない。役が失敗のあとに自分で書いた値かもしれず、人間が画面で外したあとかもしれない。そこで、飛ばしたときの標準出力の行は `紐付けていません:` で始め、紐付いているかを `multica issue pull-requests` で確認するよう添える（[コマンドの I/F](#コマンドの-if)）。紐付けたときの行も `紐付けました:` で始め、2 つの行を先頭の語で読み分けられるようにする。

飛ばしたときの終了コードは 0 のままにする。理由は次の 2 つである。

- 手順どおりなら、役は PR を作った直後の 1 回だけ呼び、`pr_url` はまだない。飛ばすのは手順の外の呼び直しだけで、そこで要るのは結果を読み違えないことである。出力の行で足りる
- 0 以外にすると、`squad-handoff` の「0 以外なら `pr_url` を自分で置き、人間に紐付けを頼む」に当たる。スクリプトが紐付けたあとの呼び直しでも、人間に不要な紐付けを頼むことになる

スクリプトは、飛ばしたときに `multica issue pull-requests` を読まない。読むと、今の紐付きを出力で答えられる。しかし、その一覧は CLI の出力の約束（[review-wait.md](review-wait.md)）にまだなく、約束に足す変更が要る。紐付きの確認は、リーダーが「[紐付いていないことを見落とさない](#紐付いていないことを見落とさない)」で一覧を読んで行うので、スクリプトは紐付けていないことを示すだけにする。

`squad-dependabot-merge` は、失敗したときに `pr_url` を書かない。次の回で同じ PR を回すときに、もう一度紐付けを試すため。今の動きのままにする。

## 役の手順

`squad-handoff` の「PR を作る・実装を積む」の「タスクの画面で URL を指定して紐付ける」を、次の手順に改める。

- PR を作ったら、すぐに `squad-pr-link <タスク> <PR の URL>` を呼ぶ
- 終了コードが 0 なら、metadata の `pr_url` はスクリプトが書いたので、`branch` だけを置く
- 0 以外なら、止まらずに `branch` と `pr_url` を自分で置き、引き継ぎのコメントに「PR をタスクに紐付けられなかったので、タスクの画面で紐付けてほしい」ことを書く。タスクの画面で URL を指定して紐付ける手作業は、この失敗のときの扱いとしてだけ残す

失敗したときの引き継ぎのコメントには、標準エラーの警告の文もそのまま写す。404 で待ち切れたときの連携の案内を、人間に届けるため。`squad-handoff` の「スクリプトを呼ぶのは PR を作った直後の 1 回だけにする」の理由の文も、「`pr_url` があると、紐付けずに飛ばすため」に改める。飛ばしたことを、紐付け済みと読ませないため。

「タスクの識別子・作業番号・進行の記録は Multica 側に置き、PR の本文やコミットメッセージへ持ち出さない」決まりは、そのまま残す。

PR を作る役の指示にも、PR を作った直後にこの手順を行うことを書く。

| 指示 | 変えるところ |
| --- | --- |
| `common/agents/designer.md` | draft PR を作るところに、`squad-handoff` の紐付けの手順を行うことを足す |
| `common/agents/claude-implementer.md`、`common/agents/codex-implementer.md` | 設計の役がないときや不具合の修正で、自分で PR を作るときに、同じ手順を行うことを足す |

修正の役は既存の PR に積むだけで PR を作らないので、変えない。`common/autopilots.md` の Dependabot の見張りの指示（紐付けを自分で API で行わない）も、`squad-dependabot-merge` に任せる形のままなので変えない。

## 導入と更新

スクリプトと共有の関数は `common/monitor/` の `squad-*` なので、ホストの準備（`lib/host.sh` の `prepare_host`）が、新しい導入でも流し直しでもエージェントの `bin` に置く。流し直しでは、原本の印がある既存のファイルを新しい中身で置き換える。セットアップの手順は変えない。

`tests/host-test.sh` は、`common/monitor/` の `squad-*` のすべてが置かれることをすでに確認している。新しいファイルについても、新しい導入で置かれること、流し直しで印のある古い中身が置き換わることを確認する行を足す。

[飛ばしたことを出力で示す](#飛ばしたことを出力で示す)と [404 で待ち切れたときの案内](#404-で待ち切れたときの案内)の変更も、同じ仕組みで届く。導入済みのプロジェクトは、セットアップを流し直すと、新しいスクリプトと共有の関数、`squad-handoff` の新しい文に置き換わる。エージェントやオートパイロットの登録は変わらない。流し直すまでは、今の出力のまま動く。

## 利用者向けの文書の変更

`manual.md` の「GitHub 連携とリポジトリの紐付け」に、[前提](#前提)の 2 つを確認する手順と、満たさないときに起きることを書く。今の `manual.md` は、2 つを「マージでタスクを `done` にするための前提」とだけ書いている。GitHub 連携が紐付けそのものの前提であることを、次のとおりに書き分ける。節の名前は変えない。

- GitHub 連携: ワークスペースの設定 → コードで、作業先のリポジトリがつながっていることを画面で確認する
- マージ後の移動先: ワークスペースの設定の「After PRs merge, move the issue to」が Done であることを画面で確認する
- GitHub 連携がないときは、スクリプトもタスクの画面も PR を紐付けられない。役の引き継ぎに「サーバーが PR を見つけられない」とあれば、まず連携を確認し、つないでから画面で紐付ける
- 移動先が Done でないときは、PR がタスクに紐付いても、マージでタスクが `done` にならない。人間がタスクを `done` にする

セットアップの導入の確認には入れない。CLI からワークスペースの設定を読めず、画面での確認になるため。`manual.md` は、1 文 1 行の決まり（`CONTRIBUTING.md`）に従う。

## 紐付いていないことを見落とさない

紐付けに失敗した報告を、リーダーが確認せずに進めると、CI の見張りがタスクに紐付いた PR を見つけられず、人間のマージの待ちまで動かない。次の 2 つを足す。

- PR を作った役は、紐付けに失敗したことを、引き継ぎのコメントの先頭（結論の行のすぐ次の行）に書く。人間への依頼として扱い、成果物や確認したことの後ろに埋もれさせない
- リーダーは、PR を受け取ったとき、人間のマージへ回す前、返事を待つ回を始める前に、`multica issue pull-requests <タスク> --output json` の `pull_requests` が空でないことを確認する。空なら、人間にタスクの画面で紐付けてもらうよう頼んで止まる

一覧は、紐付け済みかどうかをスクリプトが決めるためではなく、リーダーが今の状態を確認するためだけに読む。スクリプトを呼ぶ判定は、上のとおり metadata の `pr_url` のままにする。

## 検討した案

- タスクの識別子を PR のタイトル・ブランチ名・本文に入れ、Multica に自動で紐付かせる案。CLI も API も要らないが、識別子を PR へ持ち出さない決まりに反するので選ばなかった
- 紐付けを各役の指示に `curl` で書く案。トークンの渡し方や待ちを役ごとに書くことになり、誤るとトークンが引数やログに出るので、スクリプトにまとめた
- `squad-pr-link` と `squad-dependabot-merge` で、紐付けをそれぞれに持つ案。待ちとトークンの扱いが 2 か所に分かれ、片方だけ直す誤りが起きるので、共有の関数にした
- 紐付け済みを `multica issue pull-requests` の一覧で判定する案。人間が外した紐付けを戻してしまうので、metadata の `pr_url` で判定した
- `pr_url` があり飛ばしたときに、0 以外の新しい終了コードを返す案。スクリプトから読み分けやすいが、役の「0 以外なら人間に紐付けを頼む」に当たり、紐付け済みの呼び直しでも人間に手作業を頼むことになるので、出力の行で示すことにした（[飛ばしたことを出力で示す](#飛ばしたことを出力で示す)）
- 飛ばしたときの行だけを変え、紐付けたときの行は今の `<識別子> <URL>` のまま残す案。変更は小さいが、識別子と URL だけの行は紐付けたとは読めず、今回の読み違えと同じことが逆向きに起きるので、両方の行に先頭の語を付けた
- 飛ばしたときに `multica issue pull-requests` を読み、今の紐付きを出力で答える案。正確だが、CLI の出力の約束に一覧を足す変更が要り、リーダーの確認と重なるので選ばなかった
- 404 で待ち切れたときに、サーバーの応答の本文をそのまま警告に出す案。案内がサーバーの言葉になるが、本文に何が入るかを決められず、英語の本文を人間への依頼に混ぜることになるので、決まった文の案内にした
- 404 以外の失敗にも連携の案内を出す案。連携の切れを見落としにくくなるが、状態コードやトークンの不足など、連携と関係のない原因で人間を連携の確認に向かわせるので、404 で待ち切れたときに限った
- 404 を待たずに失敗にする案。PR を作った直後は Webhook が届く前のことがあり、ふつうの遅れで人間の手作業が増えるので、上限を決めて待つことにした
