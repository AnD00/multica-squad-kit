# 記入が足りずに止まるときの返し方

導入したプロジェクトで、検証スキルの節やプロジェクトの説明が未記入のまま役が止まったとき、報告に、セットアップが起票した記入のタスクを示す。報告を受けた人間とリーダーが、止まった理由と次の手（先に記入のタスクを片付ける）を、すぐ分かるようにする。

この文書は、共通スキル squad-handoff に足す返し方の設計と、その理由を書く。使う人への案内は `manual.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

セットアップは、検証スキルとプロジェクトの説明の `[記入: …]` を自動で補わず、代わりに記入のタスクを起票する（[導入後の自動の作業と起票の設計](setup-completion.md#二重に作らないための判定)）。記入のタスクが終わる前に検証の要るタスクを振ると、役は決まりどおり推測で検証せずに止まる。今の報告は不足している欄だけを書くので、人間はセットアップの不備と受け取りやすく、リーダーは古い報告を引いて「未記入です」と返すことがある。

そこで、止まり方は変えずに、報告の中身を変える。報告には、記入のタスクの識別子・タイトル・今の状態を書き、先にそのタスクを片付けるよう案内する。止まる前には、その実行で受け取った内容で未記入かを確かめ直す。

次は対象にしない。

- セットアップが欄を自動で下書きすること。`[記入: …]` を自動で補わない今の設計と、検証の正本を人が確かめる方針に反するため
- 記入のタスクが終わるまで、ほかのタスクの振り分けを止める仕組み
- `AGENTS.md` と作業別のルールの未記入の扱い。別のタスクで扱う
- 未記入なら推測で検証しない、未記入や未実行を成功にしない、という決まりの変更。決まりは今のまま残す
- 役に検証スキルが割り当てられていない、取り込めていないなど、記入とは別の不足。今までどおり不足を書いて止まる

## 置き場所

返し方は、共通スキル squad-handoff の新しい節「記入が足りずに止まるとき」に書く。節は「人間を呼んで止まるとき」の直前に置き、最後はその節の手順で止まる。

共通スキルに置くのは、実装・修正・レビュー・QA・リーダーなど、スキルを使うすべての役に一度で効くため。セットアップは、取り出したタグの URL から共通スキルを更新するので、原本を更新すれば導入済みのプロジェクトにも届く（`manual.md` の「更新と、途中で止まったあとの再実行」）。各プロジェクトの検証スキルと説明は、セットアップが書き換えないので、ここには頼らない。

| ファイル | 変えること |
| --- | --- |
| `common/skills/squad-handoff/SKILL.md` | 節「記入が足りずに止まるとき」を足す（[返し方](#返し方)） |
| `skeleton/.agents/skills/verify/SKILL.md` | 未記入なら止まる決まりの文のあとに、返し方は squad-handoff の同じ節に従う、という 1 文を足す。決まりの文は変えない |
| `manual.md` | 「プロジェクトのひな形を記入する」に 1 段落を足す（[利用者向けの文書の変更](#利用者向けの文書の変更)） |
| `tests/agent-templates-test.sh` | 節と決まりの文が残っていることを確かめる（[テスト](#テスト)） |
| `MANIFEST` | 作り直す |

検証スキルのひな形の 1 文は、新しく導入するプロジェクトにだけ届く。導入済みのプロジェクトでは、squad-handoff の節だけで同じ動きになるようにし、ひな形の文に頼らない。役の指示（`common/agents/`）は変えない。どの役も、止まるときは squad-handoff に従うとすでに書いてあるため。

## 未記入かを確かめる

止まると報告する前に、その実行で受け取った内容だけで、未記入かを確かめる。前の報告、タスクのコメント、リーダーの依頼文にある「未記入」は根拠にしない。記入はほかの実行の間に進むので、前の報告は古くなっているおそれがあるため。

| 確かめる対象 | 未記入とみなすとき |
| --- | --- |
| 検証スキル | その実行で受け取った本文に、作業先の `` ## `OWNER/REPO` `` の節がない。または、今回の検証に使う欄に `[記入:` が残る |
| プロジェクトの説明 | その実行で受け取った説明の、今回の作業に要る箇所（リポジトリごとの役割の行など）に `[記入:` が残る |

今回の検証に使わない欄の `[記入:` では止まらない。検証スキルの「今回の検証に必要な欄」の決まりと合わせるため。記入済みなら止まらずに進める。

リーダーと、要件・設計の役は検証スキルを受け取らないので、検証スキルが未記入かを自分では決めない。プロジェクトの説明は受け取るので、説明についてだけ確かめる。

## 記入のタスクの探し方

記入のタスクは、セットアップが起票のときに書く metadata の印で探す。印は、セットアップが二重に作らないための判定と同じもので、人がタイトルを直しても変わらない。タイトルの一致では探さない。

| 足りないもの | 探すタスク | 選び方 |
| --- | --- | --- |
| 検証スキルの、作業先の節がない | `squad_kit_task=repository-change` | `squad_kit_targets` に `added:<作業先>` を含むもの。なければ下の `project-instructions` |
| 検証スキルの欄、プロジェクトの説明 | `squad_kit_task=project-instructions` | プロジェクトに 1 つ |

探すときは、「このプロジェクトの値」のプロジェクト ID を使い、`multica issue list --project <プロジェクト ID> --metadata squad_kit_task=<種類> --output json` を流す。状態は絞らず、完了と取り下げも読む。複数あれば、当てはまるものをすべて報告に書く。

一覧を読めなかったときは、見つからなかったときと分けて、読めなかったことと理由を報告に書く。ないと決めつけると、人間が記入のタスクを探さなくなるため。

## 返し方

止まる報告は、「人間を呼んで止まるとき」の形で書き、呼ぶ人間をメンションしてタスクを `in_review` にする。1 行目に、未記入で止まったことと、先に片付ける記入のタスクを書く。

報告には次を書く。

1. 足りない欄。検証スキルの節の見出しと欄の名前、またはプロジェクトの説明の箇所
2. 確かめた内容。その実行で受け取った検証スキルか説明で確かめたこと
3. 記入のタスク。識別子（タスクへのリンク）、タイトル、今の状態
4. 次の手。記入のタスクを先に片付け、記入を終えたらこのタスクに返事をすれば再開すること

記入のタスクが `done` か `cancelled` なのに未記入のときは、状態をそのまま書き、記入が反映されていないので確かめてほしいと添える。記入した内容を Multica のスキルや説明に反映し忘れている場合があるため。

記入のタスクが見つからないとき（人が消した、印のない古いバージョンで導入したなど）は、今までどおり足りない欄を書いて止まる。あわせて、記入のタスクが見つからなかったことと、探した印を書く。

レビューや E2E の依頼で、`返事を待つ役:` の行がある実行は、人間を直接呼ばない。上の 1〜4 を結果の中に書き、その検証は未実行として、「レビューと E2E の返事を返す」の手順で返す。待ちの仕組みが、全員の返事をそろえてリーダーへ渡すため。

## リーダーの扱い

リーダーが未記入の報告を受けて人間へ返すときや、人間の返事で再開するときは、前の報告に書かれた状態を写さない。記入のタスクをその実行で探し直し、今の状態を書く。

報告のあとに記入のタスクが `done` になっていれば、人間を呼ばず、止まった役にもう一度確かめるよう頼む。記入を終えたあとの古い報告で、人間に「未記入です」と返さないため。報告より前から `done` だったときは、記入が反映されていないおそれがあるので、人間を呼んで止まる。同じ役が同じ理由で 2 回止まったときも、人間を呼んで止まる。

## テスト

導入済みのプロジェクトに届くことは、テストで確かめる。届く仕組みは今のテストがすでに確かめているので、新しいテストは、原本の共通スキルに節と決まりが入っていることだけを足す。

| 確かめること | テスト |
| --- | --- |
| squad-handoff に、節「記入が足りずに止まるとき」があり、2 つの印、見つからないときの報告、その実行で確かめること、推測で検証しないこと、未記入や未実行を成功にしないことが書いてある | `tests/agent-templates-test.sh` に足す |
| 検証スキルのひな形に、推測して実行しないこと、未記入や未実行を成功にしないこと、squad-handoff の節への案内がある | `tests/agent-templates-test.sh` に足す |
| 原本の共通スキルが、タグが変われば同じ ID のまま更新される | 今の `tests/workspace-test.sh` |
| 既存の検証スキルの中身を、更新で書き換えない | 今の `tests/setup-runtimes-test.sh` |
| 編集したプロジェクトの説明を、更新で書き換えない | 今の `tests/project-test.sh` |

文の確かめは、節の見出しと、決まりの要の語句（`squad_kit_task=project-instructions`、`repository-change`、`見つからなかった` など）の有無だけにする。文全体を固定すると、文言の手直しのたびにテストを直すことになるため。実機で、記入のタスクが終わる前に検証の要るタスクを振り、報告に識別子と状態が出ることは、人が確かめる。

## 利用者向けの文書の変更

`manual.md` の「プロジェクトのひな形を記入する」の最後に、次を 1 段落で足す。設計の理由は写さない。

- このタスクを終える前に、検証が要るタスクを振ると、役は推測で検証せずに止まること
- そのとき報告には、このタスクの識別子と状態が書かれること
- 先にこのタスクを片付け、止まったタスクに返事をすれば再開すること

`skeleton/README.md` と `CONTRIBUTING.md` は変えない。`CHANGELOG.md` と `VERSION` は、次にバージョンを上げる PR で扱う。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 検証スキルのひな形だけに書く | 新しく導入するプロジェクトにしか届かない。セットアップは既存の検証スキルを書き換えない |
| リーダーの指示だけに書く | 役が人間を直接呼んで止まったときに効かない |
| 記入のタスクをタイトルの一致で探す | 人がタイトルを直すと見つからない。セットアップの判定とも食い違う |
| 印で見つからないとき、タイトルでも探す | 人が作った似たタスクを拾うおそれがある。見つからないことを報告すれば、人が判断できる |
| 役の指示（`common/agents/`）にも同じ手順を書く | 同じ決まりを複数の場所に写すことになる。役の指示は、止まるときは squad-handoff に従うとすでに書いてある |
| 前の報告の「未記入」を引き継いで止まる | 記入はほかの実行の間に進むので、古い報告で止まることになる |
| 導入済みに届くことを手引きの手順だけで確かめる | 届く仕組みは今のテストで確かめられており、内容の有無もテストで確かめられる。手で確かめる手順を増やさない |
