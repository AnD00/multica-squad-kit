# レビューと E2E の返事がそろったあとに次へ進む

レビューと E2E の返事がそろったら、スクワッドのメンションでリーダーの実行を起こし、`proceed` の記録で 1 つの実行だけが次へ進む。どの実行が進むかは、実行の種類ではなく、`proceed` の最も早い記録だけで決める。

あわせて、見張りのスクリプトが読む CLI の出力の欄を、実物の出力で確かめる決まりを置く。読む欄が出力にないときは、その欄の名前を出して失敗する。開始時の確認（`squad-preflight`）でも同じ欄を確かめる。

この文書は、その仕組みと理由を書く。返事を待つ回の始め方（`watch` と `返事を待つ役:` の行）、役が結果を返す手順（`report`）、待つ上限と失敗の見張りは、今のとおりにする。

## 目的と範囲

返事がそろったあと、リーダーが「次に進む」まで進めずに止まることが続いた。止まるたびに人間が手で再開している。この変更で、返事がそろってから次へ進むまでを、人間の手を借りずに通す。

次は対象にしない。

- Multica の CLI やプラットフォームに、リーダーの実行かどうかを示す欄を足してもらうこと。この原本の中で直せるため
- 返事を待つ回の始め方と、待つ上限・失敗の見張りの仕組みを変えること
- `proceed` で最も早く記録した実行が、そのあと止まったときに、別の実行が代わりに進むこと。[残る危うさ](#残る危うさ)に書く

## 止まっていた理由

止まった理由は 3 つ重なっていた。どれか 1 つを直しても、残りで同じように止まる。

1. `leader-check` が読む `issue runs` の `is_leader_task` の欄が、CLI 0.7.0 の出力にない。jq は欠けた欄を `null` と読むので、「今の実行が一覧にない」という別の理由に見える説明で止まった
2. 「返事がそろいました」の知らせは、リーダーのエージェントを名前でメンションしていた。エージェントのメンションと wakeup で始まる実行は、リーダーの実行（スクワッドのメンションで始まる実行）にならない。だから、`leader-check` が欄を読めても、リーダーの実行は来なかった
3. テストの CLI の出力は手書きで、実物と比べていなかった。`is_leader_task` を含むデータでテストは通り、実物では失敗した

## 返事がそろった知らせ

`report` が書く「返事がそろいました」の知らせは、本文の先頭をスクワッドのメンションのリンクにし、エージェントのメンションを含めない。スクワッドのメンションで、そのスクワッドのリーダーの実行が始まるため。

知らせの 1 行目は `[@<スクワッドの名前>](mention://squad/<スクワッドの ID>) 返事がそろいました。` にする。返した役の一覧は、今のとおり名前だけで書き、メンションのリンクにしない。

### メンションするスクワッドの決め方

メンションするスクワッドは、回のコメントを書いた進行役をリーダーとするスクワッドにする。`multica squad list` の出力のうち、`leader_id` が回のコメントの `author_id` と同じで、`archived_at` が `null` のものを選ぶ。回を始めたのはそのスクワッドのリーダーなので、知らせはそのリーダーの実行に届く。

当てはまるスクワッドが 1 つでなければ、知らせを書けない。`report` は、結果を投稿する前にスクワッドを決め、決められなければ投稿せずに失敗する。回がないときと同じく、呼び出した役は squad-handoff の「引き継ぐとき」で返す。結果だけが `/note` で残り、誰も起きずに止まることを防ぐため。

失敗のメッセージには、見つかった数（0 か 2 以上）と、回のコメントを書いたエージェントの ID を書く。

### 拾い直しの知らせ

知らせがないまま全員が返していたときに `proceed` が書く拾い直しの知らせは、今のとおりメンションを付けない。拾い直しは、すでに動いている進行役の実行が書くので、別の実行を起こす必要がないため。

## 次へ進む実行の決め方

返事がそろったあと次へ進むのは、`proceed` を呼んだ実行のうち、同じ回の記録（`返事の待ち: この回を次へ回します`）を最も早く書いた実行だけにする。リーダーの実行かどうかは確かめない。どの実行が `proceed` を呼んでも、進むのは必ず 1 つになる。

記録の順は、Multica がコメントに付ける時刻と、同じ時刻なら ID の順で決める。すべての実行が同じ一覧を読むので、同じ 1 つを選ぶ。

### proceed の流れ

`proceed <タスク> <きっかけのコメント>` は、次の順に進める。

1. 最新の回を読む。回がない、返していない役がいるときは、何もしない
2. その回の記録がすでにあれば、`返事の待ち: 回ごと済み` を返す。2 つ目以降の実行は、ここで止まる
3. 知らせがなければ、拾い直しの知らせを書く
4. 記録を書き、そのコメントの ID を覚える
5. `REVIEW_WAIT_RECHECK_SECONDS`（20 秒）待ってから、回を読み直す。新しい回があれば、何もしない
6. 自分の記録が読めれば、最も早い記録が自分のものなら `返事の待ち: 次に進む` を返して回の見張りを消す。そうでなければ `返事の待ち: 回ごと済み` を返す
7. 自分の記録が読めなければ、もう 1 回だけ待って読み直す。それでも読めなければ、記録のコメントの ID を添えて失敗する

`返事の待ち: リーダーを再度起こす` の出力はなくす。進む実行を決めるのに、別の実行を起こす必要がなくなったため。7 の失敗は、自分の記録が Multica から読めない異常なので、進行役は人間へ返す。

5〜7 の待ちは最大 40 秒なので、進行役は `proceed` のコマンドの時間切れを 90 秒以上にする。

### status の判定

`status` は、全員が返していて、その回の記録がまだないときに、`proceed` へ進む判定を返す。知らせの有無は問わない。知らせのあとにリーダーの実行が止まっても、待つ上限の見張りや人間の返事で起きた実行が、次へ進められるようにするため。

| 回の状態 | status の判定 |
| --- | --- |
| 回がない | 何もしない |
| 記録がある | 次へ回し済みなので何もしない |
| 全員が返していて、記録がない | `proceed` へ進む |
| 返していない役が失敗・取り消し | 人間を呼ぶ |
| 返していない役が待ちか実行中 | 待つ。上限を過ぎていれば記録する |

`proceed` へ進む判定の行は、知らせの有無で分けず、`返事の待ち: 返事がそろっていて、まだ次へ回していない` の 1 つにする。

### コメントと指示に書く前提

`proceed` の冒頭のコメントと、関数の前のコメントから、「記録を書くのはリーダーの実行だけ」という前提を消す。代わりに、どの実行が呼んでも、最も早い記録の実行だけが進むことを書く。進行役の指示にも、同じことを書く（[進行役の指示](#進行役の指示)）。

### leader-check をなくす

`squad-review-wait` から `leader-check` のサブコマンドと、使い方の文、冒頭のコメントを消す。実行の種類に頼らずに進む実行を決めるので、使う場面がなくなるため。テストの `leader-check` のケースと、手書きの `is_leader_task` のデータも消す。

`CHANGELOG.md` の過去の版の節にある `leader-check` は、その版の記録なので残す。この変更の版の節は、版を上げる PR で書く。

## 進行役の指示

`common/agents/orchestrator.md` の「レビューと E2E の返事」の、`返事がそろいました` で起きたときの手順を、次に置き換える。

- `leader-check` を流す手順と、終了コードごとにリーダーを再度起こす・人間に返す分岐を消す
- `返事の待ち: リーダーを再度起こす` が返ったときの手順と、`返事がそろいました: リーダーを再度起こす` の wakeup を作る手順を消す
- `返事がそろいました` で起きたら、すぐに `squad-review-wait proceed <タスク> <きっかけのコメント>` を流す。きっかけのコメントには、今のとおり知らせのコメントの ID を渡す
- `返事の待ち: 次に進む` を返した実行だけが進む。`回ごと済み` なら何もしない。スクリプトが失敗したら、出力を添えて人間へ返す
- どの実行が `proceed` を呼んでも進むのは 1 つだけなので、実行の種類を確かめずに呼んでよいことを書く

`squad activity` の扱いは今のとおりにする。リーダーの実行でない実行で記録が失敗したら、流し直さず、最後の返答に 1 行書く。

「受け渡しと人間を待つところ」の `squad activity` の項目から、`返事がそろいました` で起きたときの確かめを参照する文を消す。

## CLI の出力の欄

見張りのスクリプトが読む Multica の CLI の出力の欄は、一か所に一覧にする。スクリプトは、その一覧を通して CLI を読み、欄が出力にないときは、その欄の名前を出して失敗する。テストのデータと開始時の確認も、同じ一覧を使う。

### 読む欄の一覧

一覧は、見張りと同じ `common/monitor/` に、読み込んで使うライブラリ `squad-cli-lib` として置く。`squad-usage-lib` と同じく、セットアップが関所のディレクトリに置く。

一覧の 1 項目は、読み取りの名前、呼ぶコマンド、読む欄の組にする。読み取りの名前は、テストのデータのファイル名と開始時の確認の出力にも使う。

| 読み取りの名前 | コマンド | 読む欄 |
| --- | --- | --- |
| `issue-get` | `multica issue get <タスク> --output json` | 見張りが読む欄 |
| `issue-comments` | `multica issue comment list <タスク> --full --output json` | 各要素の欄 |
| `issue-runs` | `multica issue runs <タスク> --output json` | 各要素の欄 |
| `issue-wakeups` | `multica issue wakeup list <タスク> --output json` | 各要素の欄 |
| `agent-get` | `multica agent get <エージェント> --output json` | 見張りが読む欄 |
| `squad-list` | `multica squad list --output json` | 各要素の欄 |

表は、今の見張りが読むものの例である。項目と欄の確定は、見張りの見直し（[見張りのスクリプトの見直し](#見張りのスクリプトの見直し)）で行う。

欄は、出力にその名前の鍵があるかで確かめる。値が `null` でも、鍵があればよい。jq の `.欄` は、鍵がないときも `null` を返すので、値で確かめると欠けを見落とすため。出力が配列なら、すべての要素で確かめる。空の配列は、確かめる要素がないので通す。

`metadata` のように、中の鍵が利用者の値で決まる欄は、その欄の鍵だけを確かめ、中の鍵は確かめない。

### 欄がないときの失敗

ライブラリの読み取りの関数は、CLI を呼び、出力の欄を確かめてから、出力を返す。欄がなければ、出力を返さずに失敗する。メッセージは次の形にし、標準エラーに出す。

```text
CLI の出力に欄がありません: issue-runs の trigger_comment_id（multica 0.7.0）
```

欠けた欄がいくつあっても、すべて 1 行ずつ出す。CLI の版は `multica version` の 1 行目から読み、読めなければ版を省く。終了コードは 1 にし、呼び出した役は、ほかのスクリプトの失敗と同じく人間へ返す。

見張りは、一覧にある読み取りを、必ずこの関数を通して呼ぶ。一覧にない欄を読む変更は、先に一覧に欄を足す。

### テストのデータ

テストが使う CLI の出力のデータは、実物の出力から取る。取ったデータは、`tests/fixtures/multica/<読み取りの名前>.json` に置く。取った CLI の版は、`tests/fixtures/multica/VERSION` に `multica version` の 1 行目をそのまま書く。

データを取るのは、`tests/capture-multica-fixtures.sh <タスク> <エージェント>` で行う。実物の CLI で一覧の読み取りを流し、公開してよい値に置き換えてから書き出す。置き換えるのは次の値で、鍵と値の型は残す。

- メールアドレス、人の名前、アバターの URL
- コメントの本文、エージェントとスクワッドの指示、実行の結果と要約など、自由に書いた文
- 作業ディレクトリのパス

テストの各ケースは、このデータを元にして、値だけを変えて組み立てる。鍵を足したり消したりしない。テストの関数は、組み立てたあとの鍵の集まりがデータと同じかを確かめ、違えば失敗する。手書きの欄が入ることを、テストで防ぐため。欄を消すのは、欄がないときの失敗を確かめるケースだけにする。

CLI の版を上げたときは、データを取り直す。差分に消えた欄があれば、その欄を読む見張りを直す。

### 開始時の確認

`squad-preflight` は、関所と見張りの解決先を確かめたあと、読む欄も確かめる。引数にタスクを取れるようにし、`squad-preflight [<タスク>]` にする。

| 引数 | 確かめる読み取り |
| --- | --- |
| なし | `squad-list` と、`MULTICA_AGENT_ID` の `agent-get` |
| タスク | 上に加えて、そのタスクの `issue-get`、`issue-comments`、`issue-runs`、`issue-wakeups` |

欄がなければ、ライブラリと同じメッセージを出して 1 で終わる。空の配列で確かめられなかった読み取りは、`確かめられない（空）` と 1 行出し、失敗にしない。

進行役は、タスクを付けて呼ぶ。CI の見張り・Dependabot のマージ・使用上限の見張りは、今のとおり引数なしで呼ぶ。squad-handoff の確認の節も、タスクのある実行はタスクを付けて呼ぶように書く。

`squad-preflight` は、PR #30 で入る。この変更の `squad-preflight` の部分は、PR #30 のマージのあとに積む。

### Multica 以外の CLI

`gh` の `--json` で欄を指定する読み取りは、一覧に入れない。`gh` は、指定した欄がないとき、その欄の名前を出して失敗するため。`gh api`、`claude`、`codex` の出力を読む箇所は、見張りの見直しで実物と比べ、結果を PR に書く。

## 見張りのスクリプトの見直し

`common/monitor/` のすべてのスクリプトを見直す。見直しの結果は、スクリプトごとに、読む欄、実物で確かめたこと、直したもの、直さない理由を、PR のコメントに表で書く。PR の本文の確認の行から、そのコメントへリンクする。

見直す観点は次の 2 つである。

1. 読む欄が、今の CLI の実物の出力にあるか。Multica の CLI の読み取りは、一覧に載せて確かめる
2. 実際には始まらない種類の実行を当てにしていないか。エージェントのメンションや wakeup で起こした実行に、リーダーの実行だけができること（`squad activity` の記録など）を期待していないか

今わかっている箇所は次のとおりで、見直しで扱いを決める。

| スクリプト | 箇所 | 扱いの方針 |
| --- | --- | --- |
| `squad-pr-watch` | `ci-check` の CI の失敗の知らせが、進行役をエージェントでメンションする | 返事の知らせと同じく、進行役をリーダーとするスクワッドのメンションに変える。スクワッドが決まらなければ、今のエージェントのメンションで知らせる |
| `squad-pr-watch` | `conflicts` と `ci` の wakeup が、進行役の実行を起こす | wakeup はスクワッドのメンションを作れない。起きた実行は振り分けだけをし、リーダーの実行を要らないので、直さない理由として残す |
| `squad-review-wait` | `watch` の wakeup が、進行役の実行を起こす | 起きた実行は `status` と `proceed` だけを流し、どの実行でも進めるので、直さない理由として残す |
| `squad-pr-watch` | `ci-check` が `issue runs` と `comment list` の欄を読む | 一覧に載せる |

スクワッドを決める処理は、`squad-review-wait` と `squad-pr-watch` で同じものを使う。ライブラリ `squad-cli-lib` に置く。

## 検証用の issue での実証

実際の Multica で、レビュー待ちを始めてから返事がそろうまでを動かし、人間の手を借りずに「次に進む」まで進むことを確かめる。結果は PR のコメントに書き、PR の本文の確認の行からリンクする。

### 手順

1. 人間が、動いているタスクがないときに、この変更のブランチを取り出して `bash setup.sh --no-checkout` を流す。見張りと役の指示が、この変更のものに入れ替わる
2. 検証用の issue を、スクワッドを担当にし、ラベル `検証` を付けて作る。本文で、変更のない小さな対象のレビューを 1 役に頼み、返事がそろったら人間に回して止まるよう依頼する
3. 進行役が回を始め、役が `report` で返し、知らせでリーダーの実行が始まり、`proceed` で次へ進むまでを、人が手を出さずに待つ
4. 次の記録を集めて、PR のコメントに書く

### 集める記録

| 確かめること | 記録 |
| --- | --- |
| 知らせがスクワッドのメンションで始まる | 知らせのコメントの ID と 1 行目 |
| 知らせでリーダーの実行が始まった | `multica issue runs` のうち、`trigger_comment_id` が知らせのコメントの ID の実行の ID |
| その実行がリーダーの実行である | `multica issue timeline` の `squad_leader_evaluated` で、`details.task_id` がその実行の ID のもの |
| 次に進んだ | 記録のコメントの ID と、`proceed` が `返事の待ち: 次に進む` を返したことを書いたその実行の最後のコメント |
| 人間が手を出していない | 回のコメントから次に進むまでの、人が書いたコメントがないこと |

リーダーの実行であることは、`squad activity` が受け付けられて timeline に残ったことで示す。`squad activity` はリーダーの実行でなければ受け付けられないので、外から確かめられる事実になる。

検証用の issue は、確かめが終わったら人間が閉じる。

## 残る危うさ

`proceed` で最も早く記録した実行が、そのあと次の工程の依頼を書く前に止まると、その回は誰も進めない。2 つ目以降の実行は `回ごと済み` で止まり、`status` も記録があるので待たない。止まった実行は Multica の失敗として残るので、人間が気づいて再開する。

この場合に別の実行が代わりに進むには、記録の実行が終わったかを実行の一覧で調べる必要がある。二重に進めない決まりとの兼ね合いがあり、今回の要件にないので、扱わない。

## 検討した案

### スクワッドの決め方の案

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 回を始めた進行役をリーダーとするスクワッド（採用） | 回を始めたリーダーに必ず届く。役の指示を変えずに済む | `squad list` の欄に頼る。欄は一覧で確かめる |
| タスクの担当のスクワッド | 1 回の読み取りで済む | オートパイロットが作るタスクなど、担当がスクワッドでないことがある |
| 回のコメントにスクワッドの ID を書く | 読み取りが要らない | 進行役の書く行が増え、書き誤ると別のスクワッドを起こす |
| `report` の引数で役が渡す | 読み取りが要らない | すべての役の指示と呼び出しが変わり、渡し誤る箇所が増える |

### 進む実行の決め方の案

`squad activity` の記録や timeline で、リーダーの実行かを確かめてから進める案もある。確かめるために書き込むと、その実行がコメントを投稿できなくなった経緯があり（`squad activity no_action` の件）、読み取りだけで確かめる欄も CLI にない。`proceed` の記録はすでに 1 つだけを選べるので、実行の種類を確かめずに記録だけで決める。

### 欄を確かめる場所

欄を確かめるのを、テストのデータだけにする案もある。データは CLI の版を上げるまで変わらないので、ホストの CLI だけが上がったときに気づけない。実行のたびのライブラリの確かめと、開始時の確認を足し、実物の CLI で毎回確かめる。

## 利用者向けの文書の変更

`CONTRIBUTING.md` の「テストを書く決まり」に、CLI の出力のデータを実物から取ること、取り方、版を上げたときに取り直すことを足す。`manual.md` は、進行役と役の使い方が変わらないので変えない。
