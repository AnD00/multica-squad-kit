# レビューと E2E の返事がそろったあとに次へ進む

レビューと E2E の返事がそろったら、スクワッドのメンションでリーダーの実行を起こし、`proceed` の記録で 1 つの実行だけが次へ進む。どの実行が進むかは、実行の種類ではなく、`proceed` の最も早い記録だけで決める。

あわせて、見張りのスクリプトが読む CLI の出力の欄を、必須・条件付き・省略可能に分けて一か所に書く。分け方は実物の出力から決め、テストで実物と合うかを確かめる。正常な省略は受け入れ、あるはずの欄がないときだけ、その欄の名前を出して失敗する。

この文書は、その仕組みと理由を書く。返事を待つ回の始め方（`watch` と `返事を待つ役:` の行）、役が結果を返す手順（`report`）、待つ上限と失敗の見張りは、今のとおりにする。

## 目的と範囲

返事がそろったあと、リーダーが「次に進む」まで進めずに止まることが続いた。止まるたびに人間が手で再開している。この変更で、返事がそろってから次へ進むまでを、人間の手を借りずに通す。

次は対象にしない。

- Multica の CLI やプラットフォームに、欄を足したり、省かずに出したりしてもらうこと。この原本の中で直せるため
- 返事を待つ回の始め方と、待つ上限・失敗の見張りの仕組みを変えること
- `proceed` で最も早く記録した実行が、そのあと止まったときに、別の実行が代わりに進むこと。[残る危うさ](#残る危うさ)に書く

## 止まっていた理由

止まった理由は 3 つ重なっていた。どれか 1 つを直しても、残りで同じように止まる。

1. `leader-check` は、`issue runs` の `is_leader_task` を `true` か `false` で分けていた。CLI 0.7.0 は、この欄をリーダーの実行にだけ `true` で出し、それ以外では省く。jq は省かれた欄を `null` と読むので、「今の実行が一覧にない」という別の理由で止まった
2. 「返事がそろいました」の知らせは、リーダーのエージェントを名前でメンションしていた。エージェントのメンションや wakeup で始まる実行は、リーダーの実行になるとは限らない。実物では、エージェントのメンションで始まったリーダーの実行 6 件のうち 3 件が、リーダーの実行でなかった
3. テストの CLI の出力は手書きで、実物と比べていなかった。手書きのデータは `is_leader_task` を必ず持ち、欄が省かれる形を含まなかった

1 と 3 の根は、読む側が、欄がないことを正常か異常か区別できないことにある。設計 v1 は欄を一律に必須としたが、これも同じ根から出た誤りだった。人のコメントに `source_task_id` はなく、直接開始の実行に `trigger_comment_id` はない。どちらも正常な省略で、一律に必須とすると、正常な出力で止まる。[CLI の出力の欄](#cli-の出力の欄)で、欄ごとに省略が正常かを決めて直す。

## 返事がそろった知らせ

`report` が書く「返事がそろいました」の知らせは、本文の先頭をスクワッドのメンションのリンクにし、エージェントのメンションを含めない。スクワッドのメンションで、そのスクワッドのリーダーの実行が始まるため。

知らせの 1 行目は `[@<スクワッドの名前>](mention://squad/<スクワッドの ID>) 返事がそろいました。` にする。返した役の一覧は、今のとおり名前だけで書き、メンションのリンクにしない。

### メンションするスクワッドの決め方

メンションするスクワッドは、回のコメントを書いた役をリーダーとするスクワッドにする。`multica squad list` の出力のうち、`leader_id` が回のコメントの `author_id` と同じで、`archived_at` が `null` のものを選ぶ。回を始めたのはそのスクワッドのリーダーなので、知らせはそのリーダーの実行に届く。

当てはまるスクワッドが 1 つでなければ、知らせを書けない。`report` は、結果を投稿する前にスクワッドを決め、決められなければ投稿せずに失敗する。回がないときと同じく、呼び出した役は squad-handoff の「引き継ぐとき」で返す。結果だけが `/note` で残り、誰も起きずに止まることを防ぐため。

失敗のメッセージには、見つかった数（0 か 2 以上）と、回のコメントを書いたエージェントの ID を書く。

### 拾い直しの知らせ

知らせがないまま全員が返していたときに `proceed` が書く拾い直しの知らせは、今のとおりメンションを付けない。拾い直しは、すでに動いているリーダーの実行が書くので、別の実行を起こす必要がないため。

## 次へ進む実行の決め方

返事がそろったあと次へ進むのは、`proceed` を呼んだ実行のうち、同じ回の記録（`返事の待ち: この回を次へ回します`）を最も早く書いた実行だけにする。リーダーの実行かどうかは確かめない。どの実行が `proceed` を呼んでも、進むのは必ず 1 つになる。

記録の順は、Multica がコメントに付ける時刻と、同じ時刻なら ID の順で決める。すべての実行が同じ一覧を読むので、同じ 1 つを選ぶ。

### proceed の流れ

`proceed <タスク> <きっかけのコメント>` は、次の順に進める。

1. 最新の回を読む。回がない、返していない役がいるときは、何もしない
2. その回の記録がすでにあれば、`返事の待ち: 回ごと済み` を返す。2 つ目以降の実行は、ここで止まる
3. 知らせがなければ、拾い直しの知らせを書く
4. 記録を書き、そのコメントの ID を覚える
5. `REVIEW_WAIT_RECHECK_SECONDS`（20 秒）待ってから、回を読み直す。新しい回があれば、何もしない
6. 自分の記録が読めれば、最も早い記録が自分のものなら `返事の待ち: 次に進む` を返して回の見張りを消す。そうでなければ `返事の待ち: 回ごと済み` を返す
7. 自分の記録が読めなければ、もう 1 回だけ待って読み直す。それでも読めなければ、記録のコメントの ID を添えて失敗する

`返事の待ち: リーダーを再度起こす` の出力はなくす。進む実行を決めるのに、別の実行を起こす必要がなくなったため。7 の失敗は、自分の記録が Multica から読めない異常なので、リーダーは人間へ返す。

5〜7 の待ちは最大 40 秒なので、リーダーは `proceed` のコマンドの時間切れを 90 秒以上にする。

### status の判定

`status` は、全員が返していて、その回の記録がまだないときに、`proceed` へ進む判定を返す。知らせの有無は問わない。知らせのあとにリーダーの実行が止まっても、待つ上限の見張りや人間の返事で起きた実行が、次へ進められるようにするため。

| 回の状態 | status の判定 |
| --- | --- |
| 回がない | 何もしない |
| 記録がある | 次へ回し済みなので何もしない |
| 全員が返していて、記録がない | `proceed` へ進む |
| 返していない役が失敗・取り消し | 人間を呼ぶ |
| 返していない役が待ちか実行中 | 待つ。上限を過ぎていれば記録する |

`proceed` へ進む判定の行は、知らせの有無で分けず、`返事の待ち: 返事がそろっていて、まだ次へ回していない` の 1 つにする。

### コメントと指示に書く前提

`proceed` の冒頭のコメントと、関数の前のコメントから、「記録を書くのはリーダーの実行だけ」という前提を消す。代わりに、どの実行が呼んでも、最も早い記録の実行だけが進むことを書く。リーダーの指示にも、同じことを書く（[リーダーの指示](#リーダーの指示)）。

### leader-check をなくす

`squad-review-wait` から `leader-check` のサブコマンドと、使い方の文、冒頭のコメントを消す。実行の種類に頼らずに進む実行を決めるので、使う場面がなくなるため。テストの `leader-check` のケースと、手書きの `is_leader_task` のデータも消す。

`CHANGELOG.md` の過去のバージョンの節にある `leader-check` は、そのバージョンの記録なので残す。この変更のバージョンの節は、バージョンを上げる PR で書く。

## リーダーの指示

`common/agents/orchestrator.md` の「レビューと E2E の返事」の、`返事がそろいました` で起きたときの手順を、次に置き換える。

- `leader-check` を流す手順と、終了コードごとにリーダーを再度起こす・人間に返す分岐を消す
- `返事の待ち: リーダーを再度起こす` が返ったときの手順と、`返事がそろいました: リーダーを再度起こす` の wakeup を作る手順を消す
- `返事がそろいました` で起きたら、すぐに `squad-review-wait proceed <タスク> <きっかけのコメント>` を流す。きっかけのコメントには、今のとおり知らせのコメントの ID を渡す
- `返事の待ち: 次に進む` を返した実行だけが進む。`回ごと済み` なら何もしない。スクリプトが失敗したら、出力を添えて人間へ返す
- どの実行が `proceed` を呼んでも進むのは 1 つだけなので、実行の種類を確かめずに呼んでよいことを書く

`squad activity` の扱いは今のとおりにする。リーダーの実行でない実行で記録が失敗したら、流し直さず、最後の返答に 1 行書く。

「受け渡しと人間を待つところ」の `squad activity` の項目から、`返事がそろいました` で起きたときの確かめを参照する文を消す。

## CLI の出力の欄

見張りのスクリプトが読む CLI の出力の欄は、読み取りごとに一か所に書く。これを欄の約束と呼ぶ。見張りは約束を通して CLI を読み、約束にない読み方をしない。テストのデータ、テスト、開始時の確認も、同じ約束を使う。

### 欄がないことの意味

Multica の CLI 0.7.0 は、値が空か偽の欄を出力から省く。省かれる欄は、要素の種類や状態で決まる。たとえば `issue runs` の `is_leader_task` は、リーダーの実行にだけ出る。欄がないことは、異常とは限らない。

一方で jq の `.欄` は、欄がないときも `null` を返す。読む側が `// 既定値` で補うと、あるはずの欄の欠けを見落とす。読む欄を一律に必須にすると、正常な省略で止まる。どちらも、欄ごとに省略が正常かを知らないことから起きる。

欄がないことと、値が `null` であることが、違う意味を持つ読み取りもある。PR の紐付けは、metadata に `pr_url` の鍵があれば、値によらず紐付けない。人間が画面で外した紐付けを戻さないため（[PR の紐付けの処理の順序](pr-link.md#処理の順序)）。整形が鍵を補ったり除いたりすると、この区別が消える。設計 v2 は、省略可能な欄に `null` を補い、約束にない `repository` を除いていた。

そこで、欄ごとに、省略が正常かを実物の出力から決めて約束に書く。整形は鍵を補わず、読む欄を除かない。読む側は、約束にない補い方をしない。

### 欄の分け方

欄は次の 3 つのどれかに分ける。どれに当たるかは、実物の出力の見本で決める（[見本とテストのデータ](#見本とテストのデータ)）。

| 分類 | 欄がないとき | 例 |
| --- | --- | --- |
| 必須 | 欄の名前を出して失敗する | `issue runs` の `id` |
| 条件付き | 条件に当たる要素なら失敗する。当たらなければ `null` を入れる | `issue runs` の `trigger_comment_id`（`kind` が `comment` のとき） |
| 省略可能 | 鍵を補わずに、そのまま通す | `issue get` の `metadata.pr_url` |

省略可能の欄と、条件に当たらない条件付きの欄には、既定値を置かない。読む側の `.欄` は、鍵がなければ `null` を返すので、値を読むだけなら補う必要がない。鍵の有無で動作を変える読み方（`has` など）は、補わないことで実物と同じに働く。

条件は、同じ要素の必須の欄の値で書く。条件に使う欄を必須にするのは、条件に当たるかが、欠けた欄で変わらないようにするため。

必須と条件付きの欄は、値が `null` でよいかも書く。`null` を許さない欄が `null` のときも、欄がないときと同じく失敗する。

`metadata` のように、中の鍵が利用者の値で決まる欄は、欄そのものを必須にする。中の鍵は、見張りが読むものだけを省略可能として書く。

### 読む欄の一覧

約束は、見張りと同じ `common/monitor/` に、読み込んで使うライブラリ `squad-cli-lib` として置く。`squad-usage-lib` と同じく、セットアップが関所のディレクトリに置く。

約束の 1 項目は、読み取りの名前、呼ぶコマンド、欄の分類の組にする。読み取りの名前は、テストのデータのファイル名と開始時の確認の出力にも使う。今の見張りが読む Multica の読み取りは次のとおりである。分類は、8 件のタスクの実物の出力で確かめた。

| 読み取りの名前 | コマンド |
| --- | --- |
| `issue-get` | `multica issue get <タスク> --output json` |
| `issue-comments` | `multica issue comment list <タスク> --full --output json` |
| `issue-runs` | `multica issue runs <タスク> --output json` |
| `issue-wakeups` | `multica issue wakeup list <タスク> --output json` |
| `issue-labels` | `multica issue label list <タスク> --output json` |
| `issue-metadata` | `multica issue metadata list <タスク> --output json` |
| `issue-search` | `multica issue search <語> --include-closed --output json` |
| `agent-get` | `multica agent get <エージェント> --output json` |
| `squad-list` | `multica squad list --output json` |
| `label-list` | `multica label list --output json` |
| `member-list` | `multica workspace member list --output json` |

| 読み取りの名前 | 必須（null 可は括弧） | 条件付き | 省略可能 |
| --- | --- | --- | --- |
| `issue-get` | `id`、`identifier`、`status`、`status_category`、`metadata`、（`assignee_type`、`assignee_id`） | なし | `metadata.repository`、`metadata.ci_watch_thread`、`metadata.pr_url` |
| `issue-comments` | `id`、`author_type`、`author_id`、`content`、`created_at`、（`parent_id`） | `source_task_id`（`author_type` が `agent` か `system`） | なし |
| `issue-runs` | `id`、`agent_id`、`kind`、`status`、`created_at`、`delivered_comment_ids`、（`error`） | `trigger_comment_id`（`kind` が `comment`） | なし |
| `issue-wakeups` | `id`、`agent_id`、`mode`、`enabled`、`instruction`、（`condition`、`paused_reason`） | `condition.type`（`condition` が `null` でない）、`condition.event`（`condition.type` が `pull_request`） | なし |
| `issue-labels` | `id` | なし | なし |
| `issue-metadata` | なし | なし | `repository`、`pr_url` |
| `issue-search` | `issues`、`issues[].id`、`identifier`、`title`、`created_at`、（`project_id`） | なし | なし |
| `agent-get` | `id`、`name`、（`archived_at`） | なし | なし |
| `squad-list` | `id`、`name`、`leader_id`、（`archived_at`） | なし | なし |
| `label-list` | `id`、`name`、`resource_type` | なし | なし |
| `member-list` | `user_id`、`name`、`email` | なし | なし |

`issue-search` の `project_id` は、プロジェクトのないタスクで `null` になる。同じ種類の `parent_issue_id` と `due_date` は、8 件の実物で `null` で出ていた。Dependabot のマージは、ワークスペースの全体を検索するので、ほかのプロジェクトのタスクも読む。

書き込みのコマンドの応答から読む欄も、同じ約束に入れる。`issue comment add` の `id`、`issue create` の `id` と `identifier`、`issue wakeup create` の `id` を必須にする。

`--compact` は、欄を読む呼び出しに使わない。0.7.0 の `--compact` は、`--full` で出る `source_task_id` や `issue_id` も省くため。返り値だけを使う呼び出し（スレッドがあるかの確かめなど）は、欄を読まないので約束に入れない。

### 確かめて整える

ライブラリの読み取りの関数は、CLI を呼び、約束で出力を確かめて整えてから返す。順番は次のとおりで、どの見張りも同じ関数を通す。

1. 必須の欄が、すべての要素にあるかを確かめる。値ではなく、鍵があるかで見る
2. 条件付きの欄が、条件に当たる要素にあるかを確かめる
3. 約束にない欄を除いて返す。省略可能の欄と、条件に当たらない条件付きの欄は、鍵がなければないまま返す

3 で、見張りは約束にない欄を読めなくなる。欄を読むには、先に約束に分類を書くことになる。見張りは `// 既定値` で欄を補わない。

約束にない欄を読む変更は、`null` を読む。値を使う読み方なら、テストの結果が変わって気づける。しかし、欄がなければ確かめを飛ばす読み方は、`null` でも止まらず、確かめだけが黙って消える。設計 v2 では、紐付けの `repository` の照合がこうして消えた。そこで、見張りのテストで、整形の前と後の動作を比べる（[約束のテスト](#約束のテスト)）。

欠けた欄は、すべて 1 行ずつ標準エラーに出し、終了コード 1 で失敗する。メッセージには、読み取りの名前、欄、条件付きなら条件、要素の `id`、CLI のバージョンを書く。

```text
CLI の出力に欄がありません: issue-comments の source_task_id（author_type が agent のとき、要素 01a1…）（multica 0.7.0）
CLI の出力の欄が null です: issue-runs の kind（要素 01a1…）（multica 0.7.0）
```

CLI のバージョンは `multica version` の 1 行目から読み、読めなければバージョンを省く。呼び出した役は、ほかのスクリプトの失敗と同じく人間へ返す。

### 見本とテストのデータ

テストが使う CLI の出力のデータは、実物の出力から取る。読み取りごとに `tests/fixtures/cli/<読み取りの名前>.json` に置き、取ったバージョンを `tests/fixtures/cli/VERSION` に書く。バージョンは `multica version` と `gh --version` の 1 行目である。

データは `tests/capture-cli-fixtures.sh <タスク>...` で取る。複数のタスクを渡し、約束の読み取りを実物の CLI で流す。要素は、次の見本の形ごとに選び、約束にない欄も含めてそのまま残す。

- 条件付きの欄ごとに、条件に当たる要素と当たらない要素。たとえば、人・エージェント・システムのコメントと、コメントで始まった実行・直接始まった実行
- 省略可能の欄ごとに、欄がある要素とない要素
- 約束に足した形。担当のないタスクの `issue-get` と、書き込みの応答

見本の形が出力にないときは、どの形がないかを書いて失敗する。足りない形は、ラベル `検証` の見本用のタスクを作って形をそろえ、そのタスクも渡して取り直す。CLI だけでは作れない形は、約束に「見本なし」と書き、取り込みは失敗せずに一覧で知らせる。

公開してよい値への置き換えは、鍵と値の型を残して行う。置き換えるのは次の値である。

- メールアドレス、人の名前、アバターの URL
- コメントの本文、エージェントとスクワッドの指示、実行の結果と要約など、自由に書いた文
- 作業ディレクトリのパス
- UUID 形式の ID。同じ採取の全見本で共通の対応表を作り、元の文字列の順に、固定桁の連番を持つ UUID 形式でない文字列へ置き換える。同じ ID は同じ値、別の ID は別の値にし、ファイル間の同一性と ID 同士の比較順を保つ。対応表と元の ID は公開物に残さない

### 約束のテスト

約束が実物と合うかは、テストのデータから機械的に確かめる。読む欄を足すたびに手でケースを書かないので、確かめが漏れない。

1. 必須の欄が、データのすべての要素にある。1 つでもない要素があれば、その欄は必須に分けられない
2. 条件付きの欄が、条件に当たるデータのすべての要素にある
3. 約束が求める見本の形が、データにすべてある。「見本なし」の形は、件数とともに出力に書く
4. 必須と条件付きの欄を 1 つずつ消すと、ライブラリがその欄の名前で失敗する
5. 省略可能の欄と、条件に当たらない条件付きの欄をすべて消した最小の形でも通り、消した鍵はないまま返る

見張りのテストの各ケースは、データの要素を元に、値だけを変えて組み立てる。テストの関数は、データにない鍵を足したケースを失敗にする。手書きの欄が入ることを防ぐため。欄を消してよいのは、省略可能の欄と、条件に当たらない条件付きの欄と、4 のケースだけにする。見張りのテストは、ライブラリを通した出力で動かす。

見張りのテストの各ケースは、整形の前と後の 2 通りで流し、動作が同じことを確かめる。整形の前は、必須と条件付きの欄を確かめただけで、欄を除かない出力である。終了コード、標準出力、呼んだコマンドと引数のどれかが違えば、見張りが約束にない欄を読んでいる。ライブラリは、このために、欄を除かない切り替えをテストにだけ開く。読む欄が約束から落ちても、黙って確かめが消えずに、テストで気づける。

CLI のバージョンを上げたときは、データを取り直す。1〜3 が、欄の省き方が変わったことを見つける。

### 鍵の有無で決まる動作

PR の紐付けは、metadata の 2 つの鍵の有無で動作を決める。`squad-pr-link` は `issue-get` の `metadata` を読む。Dependabot のマージは `issue-metadata` を読む。どちらも同じ共有の関数に渡す。どちらも約束を通し、次の性質を保つ。順序は [PR の紐付けの処理の順序](pr-link.md#処理の順序)のとおりにする。

| metadata | 動作 |
| --- | --- |
| `repository` があり、PR の `OWNER/REPO` と違う | 紐付けを拒む。API も metadata の書き込みも呼ばない |
| `repository` がない、または PR と同じで、`pr_url` がない | 初回の紐付けをする。API を呼び、成功したら `pr_url` を書く |
| `repository` がない、または PR と同じで、`pr_url` がある | 何もしない。値によらず紐付け済みとみなし、人間が外した紐付けを戻さない |

テストは、`issue-get` と `issue-metadata` の見本から、2 つの鍵のあり・なしの組をすべて作る。両方のスクリプトで、上の表を確かめる。ケースは約束を通した出力で流し、API と `metadata set` のスタブが呼ばれたかで判定する。見本には、`repository` のないタスクと、`pr_url` のないタスクの両方を入れる。

### 開始時の確認

`squad-preflight` は、関所と見張りの解決先を確かめたあと、読む欄も確かめる。引数にタスクを取れるようにし、`squad-preflight [<タスク>]` にする。

| 引数 | 確かめる読み取り |
| --- | --- |
| なし | `squad-list` と、`MULTICA_AGENT_ID` の `agent-get` |
| タスク | 上に加えて、そのタスクの `issue-get`、`issue-comments`、`issue-runs`、`issue-wakeups` |

確かめはライブラリと同じで、必須と条件付きの欄が欠けていれば、同じメッセージで 1 で終わる。正常な省略では失敗しない。空の配列は、確かめる要素がないので `確かめられない（空）` と 1 行出し、失敗にしない。

ホストの `multica version` が、約束を確かめたバージョンと違えば、そのことを 1 行出す。失敗にはしない。約束を確かめたバージョンは、テストのデータの `VERSION` をセットアップが写してライブラリに持たせる。

リーダーは、タスクを付けて呼ぶ。CI の見張り・Dependabot のマージ・使用上限の見張りは、今のとおり引数なしで呼ぶ。squad-handoff の確認の節も、タスクのある実行はタスクを付けて呼ぶように書く。

`squad-preflight` は、PR #30 で入る。この変更の `squad-preflight` の部分は、PR #30 のマージのあとに積む。

### Multica 以外の CLI

`gh`、`codex` など、JSON を返すほかの CLI の読み取りも、同じ約束に入れる。`gh` の `--json` は、指定した欄の親がないと、欄の名前を出して失敗する。しかし、中の要素の欄は確かめないので、同じように分ける。

| 読み取りの名前 | コマンド | 分け方 |
| --- | --- | --- |
| `gh-pr-checks` | `gh pr view <PR> --json state,headRefOid,statusCheckRollup` | 必須は `state`、`headRefOid`、`statusCheckRollup[].__typename`。`__typename` が `CheckRun` なら `name`、`status`、`workflowName`、（`conclusion`）が条件付き。`StatusContext` なら `context`、`state` が条件付き |
| `gh api` の読み取り | Dependabot のマージが読む PR・コミット・チェック・ブランチの規則など | 読む欄を約束に足す。下に、鍵の有無が動作を変える欄を書く |
| `codex-rate-limits` | `codex app-server` の `account/rateLimits/read` | 必須は `ordinaryUsageAllowed`、`rateLimitsByLimitId`、（`rateLimits.rateLimitReachedType`）。`rateLimitsByLimitId` の各値の（`primary`、`secondary`）は必須で、`null` でなければ `windowDurationMins`、`usedPercent`、`resetsAt` が条件付き |

`codex-rate-limits` は、codex-cli 0.167.0 の実物で確かめた。使っていない枠の `secondary` は、鍵を省かず `null` で出る。上限に達していないときの `rateLimitReachedType` も同じである。そこで省略可能ではなく、null 可の必須にする。`rateLimitsByLimitId` は、`metadata` と同じく中の鍵が枠の名前で決まるので、欄そのものを必須にする。

Dependabot のマージの `gh api` の読み取りには、鍵がないことに意味のある欄が 2 つある。約束から落ちると、確かめが黙って変わる。

- ブランチの規則の `required_status_checks[].integration_id` は、省略可能にする。鍵がなければ、どの App のチェックでも通す。約束から落ちると、App を指定した規則まで、同じ名前の別の App のチェックで通る
- PR のファイルの `patch` は、省略可能にする。GitHub は、バイナリや大きな差分では鍵を省く。鍵がなければ、ダイジェストだけの更新と見なさず、major に倒す

この原本には、Dependabot の PR がない。見本は、Dependabot の PR と必須チェックの規則がある公開リポジトリから取ってよい。取れない形は「見本なし」と書き、欄は GitHub の REST API の仕様で決める。

`StatusContext` の形は、このリポジトリの CI が commit status を使わないので、見本を取れない。約束に「見本なし」と書き、欄は GitHub の GraphQL のスキーマで決める。`claude -p /usage` は JSON の中の文を読むので、約束に入れない。読めないときは今も理由を出して失敗するので、テストのデータを実物の表示から取る。

## 見張りのスクリプトの見直し

`common/monitor/` のすべてのスクリプトを、欄の約束で見直す。見直しの結果は、スクリプトごとに、読む欄、実物で確かめたこと、直したもの、直さない理由を、PR のコメントに表で書く。PR の本文の確認の行から、そのコメントへリンクする。

見直す観点は次の 3 つである。

1. JSON を読む呼び出しが、すべて約束の読み取りの関数を通るか
2. `// 既定値` や `--compact` で、欄の欠けを隠していないか
3. リーダーの実行になるとは限らない実行に、リーダーの実行だけができること（`squad activity` の記録など）を期待していないか

実物の出力と照らして、今わかっている箇所は次のとおりで、見直しで扱う。

| スクリプト | 箇所 | 扱い |
| --- | --- | --- |
| `squad-pr-watch` | `ci-check` が、コメントの `source_task_id` で実行の結果を探す | `issue-comments` を通す。人のコメントには欄がないので、条件付きとして読む |
| `squad-pr-watch` | CI の結果を待つかの判定が、`--full --compact` でコメントを読む | `--compact` をやめ、`issue-comments` を通す |
| `squad-pr-watch` | `status_category // status` で状態を読む | 両方とも必須なので、`//` をやめる |
| `squad-pr-watch` | `ci-check` の CI の失敗の知らせが、リーダーをエージェントでメンションする | 返事の知らせと同じく、役をリーダーとするスクワッドのメンションに変える。スクワッドが決まらなければ、今のエージェントのメンションで知らせる |
| `squad-pr-watch` | `conflicts` と `ci` の wakeup が、リーダーの実行を起こす | 起きた実行は振り分けだけをし、リーダーの実行を要らないので、直さない |
| `squad-review-wait` | 実行の `delivered_comment_ids // []` と、エージェントの `name // empty` | どちらも必須なので、`//` をやめる |
| `squad-review-wait` | 返事を待つ判定が、実行の `trigger_comment_id` を読む | 直接始まった実行には欄がないので、条件付きとして読む |
| `squad-review-wait` | `watch` の wakeup が、リーダーの実行を起こす | 起きた実行は `status` と `proceed` だけを流し、どの実行でも進めるので、直さない |
| `squad-dependabot-merge` | ラベルの `resource_type // "issue"` | 必須なので、`//` をやめる |
| `squad-dependabot-merge`、`squad-pr-link` | PR の紐付けが、metadata の `repository` と `pr_url` を鍵の有無で読む | 約束に省略可能として足し、鍵を補わない。[鍵の有無で決まる動作](#鍵の有無で決まる動作)をテストする |
| `squad-dependabot-merge` | 検索の `project_id` で、プロジェクトのタスクを選ぶ | プロジェクトのないタスクで `null` になるので、null 可にする |
| `squad-dependabot-merge` | 必須チェックの `integration_id` と、ファイルの `patch` | 鍵がないことに意味があるので、省略可能として約束に足す |
| `squad-dependabot-merge` | `gh api` で PR・コミット・チェックを読む | 約束に足し、テストのデータを実物から取る |
| `squad-usage-check`、`squad-usage-lib`、`squad-dispatch-pick` | ラベルの一覧と、Codex の使用量を読む | 約束に足す。Codex の `null` で出る欄は null 可の必須にする。Claude の表示は、テストのデータを実物から取る |

スクワッドを決める処理は、`squad-review-wait` と `squad-pr-watch` で同じものを使う。ライブラリ `squad-cli-lib` に置く。

## 検証用のタスクでの実証

実際の Multica で、レビュー待ちを始めてから返事がそろうまでを動かし、人間の手を借りずに「次に進む」まで進むことを確かめる。結果は PR のコメントに書き、PR の本文の確認の行からリンクする。

### 手順

1. 人間が、動いているタスクがないときに、この変更のブランチを取り出して `bash setup.sh --no-checkout` を流す。見張りと役の指示が、この変更のものに入れ替わる
2. 検証用のタスク を、スクワッドを担当にし、ラベル `検証` を付けて作る。本文で、変更のない小さな対象のレビューを 1 役に頼み、返事がそろったら人間に回して止まるよう依頼する
3. リーダーが回を始め、役が `report` で返し、知らせでリーダーの実行が始まり、`proceed` で次へ進むまでを、人が手を出さずに待つ
4. 次の記録を集めて、PR のコメントに書く

### 集める記録

| 確かめること | 記録 |
| --- | --- |
| 知らせがスクワッドのメンションで始まる | 知らせのコメントの ID と 1 行目 |
| 知らせでリーダーの実行が始まった | `multica issue runs` のうち、`trigger_comment_id` が知らせのコメントの ID の実行の ID |
| その実行がリーダーの実行である | `multica issue timeline` の `squad_leader_evaluated` で、`details.task_id` がその実行の ID のもの |
| 次に進んだ | 記録のコメントの ID と、`proceed` が `返事の待ち: 次に進む` を返したことを書いたその実行の最後のコメント |
| 人間が手を出していない | 回のコメントから次に進むまでの、人が書いたコメントがないこと |
| 正常な省略で止まらない | 検証の間に流れた見張りに、欄の欠けによる失敗がないこと |

リーダーの実行であることは、`squad activity` が受け付けられて timeline に残ったことで示す。`squad activity` はリーダーの実行でなければ受け付けられないので、外から確かめられる事実になる。

検証用のタスク は、確かめが終わったら人間が閉じる。

## 残る危うさ

`proceed` で最も早く記録した実行が、そのあと次の工程の依頼を書く前に止まると、その回は誰も進めない。2 つ目以降の実行は `回ごと済み` で止まり、`status` も記録があるので待たない。止まった実行は Multica の失敗として残るので、人間が気づいて再開する。

この場合に別の実行が代わりに進むには、記録の実行が終わったかを実行の一覧で調べる必要がある。二重に進めない決まりとの兼ね合いがあり、今回の要件にないので、扱わない。

欄の約束は、見本にあった形でしか確かめられない。見本にない形で CLI が欄を省くと、必須の欄の欠けとして止まる。止まるときは欄の名前が出るので、その形を見本に足し、分類を直す。

## 検討した案

### スクワッドの決め方の案

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 回を始めた役をリーダーとするスクワッド（採用） | 回を始めたリーダーに必ず届く。役の指示を変えずに済む | `squad list` の欄に頼る。欄は約束で確かめる |
| タスクの担当のスクワッド | 1 回の読み取りで済む | オートパイロットが作るタスクなど、担当がスクワッドでないことがある |
| 回のコメントにスクワッドの ID を書く | 読み取りが要らない | リーダーの書く行が増え、書き誤ると別のスクワッドを起こす |
| `report` の引数で役が渡す | 読み取りが要らない | すべての役の指示と呼び出しが変わり、渡し誤る箇所が増える |

### 進む実行の決め方の案

`issue runs` の `is_leader_task` を読み、リーダーの実行だけが進む案もある。欄はリーダーの実行にだけ出るので、読めば確かめられる。しかし、知らせで起きた実行がリーダーの実行になるかはプラットフォームが決め、外から保証できない。`squad activity` で確かめる案は、書き込むとその実行がコメントを投稿できなくなった経緯がある（`squad activity no_action` の件）。`proceed` の記録はすでに 1 つだけを選べるので、実行の種類を確かめずに記録だけで決める。

### 欄の分け方の案

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 必須・条件付き・省略可能に分ける（採用） | 正常な省略を受け入れ、欠けは欄の名前で知らせる | 欄ごとに分類と見本が要る |
| 読む欄を一律に必須にする（設計 v1） | 約束が単純 | 人のコメントや直接始まった実行など、正常な出力で止まる |
| 読む側が `// 既定値` で補う（もとの見張り） | 止まらない | あるはずの欄の欠けを見落とす。止まっていた理由 1 の形 |
| 見本で欠けのある欄を、自動で省略可能にする | 分類を書かずに済む | 条件を見つけられず、欠けてはいけない要素の欠けも受け入れる |

### 省略可能な欄の扱いの案

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 鍵を補わない（採用） | 鍵の有無で決まる動作が、実物と同じに働く | 読む側は `has` と `.欄` の違いを意識する |
| 既定値を入れる（設計 v2） | 読む側が鍵の有無を考えずに済む | `has` で決める動作が変わる。初回の紐付けが飛ばされた |
| `null` も未設定とみなすよう紐付けを変える | 約束の整形を変えずに済む | 鍵が `null` のタスクに、外した紐付けを戻す |

既定値は、どの欄でも `null` だったので、`.欄` で読む見張りには効き目がなかった。欄ごとに補う・補わないを選ばせると、同じ取り違えが次の欄で起きるので、すべての欄で補わない。

### 欄を確かめる場所

欄を確かめるのを、テストのデータだけにする案もある。データは CLI のバージョンを上げるまで変わらないので、ホストの CLI だけが上がったときに気づけない。実行のたびのライブラリの確かめと、開始時の確認を足し、実物の CLI で毎回確かめる。

## 利用者向けの文書の変更

`CONTRIBUTING.md` の「テストを書く決まり」に、次を足す。`manual.md` は、リーダーと役の使い方が変わらないので変えない。

- CLI の出力のデータは実物から取り、取り方と、バージョンを上げたときに取り直すこと
- 見張りが読む欄は、先に約束に分類を書き、`// 既定値` や `--compact` で補わないこと
- 見張りのテストは、整形の前と後で同じ動作になることを確かめること
