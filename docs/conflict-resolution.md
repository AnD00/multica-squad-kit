# コンフリクトの解消を速くする検証の決まり

修正の役が PR の `main` とのコンフリクトを解消したとき、手元で流す検証を、関わるテストと静的な確認・生成物の確認に絞る。テスト全体は CI に任せ、落ちたテストは流し直さず、止まったテストは時間の上限で失敗にする。解消からレビューへ、短い時間で進めるようにする。

この文書は、修正の役の指示と検証の決まりの変更、テスト 1 本ごとの時間の上限、並べて流すと落ちる `squad-dispatch-pick-test` の直し方の設計と、その理由を書く。このリポジトリでの関わるテストの選び方と時間の上限は、`CONTRIBUTING.md` の「テストを流す」に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

解消の依頼で時間がかかったのは、文字の上の解消ではなく検証だった。テスト全体は 10 分を超えて、出力のないまま実行の道具の上限で止まった。関わるテストは、意味のコンフリクトで落ち、その修正と流し直しに時間を使った。並べて流すと、変更と関係のない `squad-dispatch-pick-test` が落ちることもある。

そこで、次の 4 つを変える。

1. 修正の役が、解消のあとに手元で流す検証を絞り、見直しは書き換えたときだけにする（[修正の役の決まり](#修正の役の決まり)）
2. 検証のスキルのひな形に、解消のときの検証を記入する節を足す（[検証のスキルの節](#検証のスキルの節)）
3. テストの実行に、1 本ごとの時間の上限を設ける（[テスト 1 本ごとの時間の上限](#テスト-1-本ごとの時間の上限)）
4. `squad-dispatch-pick` が、負荷の高いときに `setpgid` の警告を出さないようにする（[setpgid の警告をなくす](#setpgid-の警告をなくす)）

次は対象にしない。

- 意味のコンフリクトの修正そのものを速くすること。解消の本来の仕事で、検証を絞ってもなくせないため
- `MANIFEST`・`CHANGELOG` の取り込みの手順。今回の時間の原因でなかったため
- テスト全体を短くすること。PR の CI の時間を短くする設計（ファイルの分割と、ジョブを分けて流すこと）が、別に進んでいる
- レビューの指摘や CI の失敗を直すときの検証。今までどおり完了の条件の検証をする
- 版を上げること
- このプロジェクトの検証のスキル `squadkit-verify` を書き換えること。マージのあとに人間が行う（[導入済みのプロジェクト](#導入済みのプロジェクト)）

## 修正の役の決まり

コンフリクトを解消したら、手元では関わるものだけを確かめ、テスト全体は CI に任せる。見直しは、解消のためにコードやテストを書き換えたときだけにする。導入したどのプロジェクトでも同じに動くよう、原本の 2 つの修正の役の指示に書く。

### 手元で流す検証

手元で流すのは、次の 3 つだけにする。どのコマンドで流すかは、検証のスキルの節「コンフリクトを解消したときの検証」に従う。

1. 衝突したファイルと、PR が変えたファイルに関わるテスト
2. 構文・型・lint などの静的な確認
3. 生成物の生成と、生成し直しても差分が出ないことの確認

修正の役の指示は、導入したどのプロジェクトにも配るので、コマンドの名前を書かない。このリポジトリでは、2 が `scripts/check.sh`、3 が `MANIFEST` の生成と差分の確認に当たる。どれに当たるかは、`CONTRIBUTING.md` と `squadkit-verify` の節に書く。

衝突したファイルは、マージで衝突したときに `git diff --name-only --diff-filter=U` で控える。PR が変えたファイルは `git diff --name-only origin/main...HEAD` で読む。

テスト全体は手元で流さず、push のあとの CI で確かめる。引き継ぎに、テスト全体は CI で確かめることを書く。リーダーと人間が、手元で通したものと CI に任せたものを読み分けられるようにするため。

検証のスキルにこの節がないときは、「変更に応じて選ぶ検証」の表から、衝突したファイルと PR が変えたファイルに当たる行のコマンドを流す。テスト全体を流すコマンドは CI に任せる。節がないことを、引き継ぎに書く。節はあるが `[記入: …]` のままのときは、今の未記入の扱いと同じく、推測で流さずに止まる。

### テストが落ちたとき

落ちたテストは流し直さない。時間の上限で止まったテストも、落ちたテストと同じに扱う。流し直して通ると、不安定さが隠れ、通った 1 回を根拠にしてしまうため。

| 落ちたテスト | すること |
| --- | --- |
| 衝突したファイルか、PR が変えたファイルに関わるもの | 直す。意味のコンフリクトとして、見直しの対象にする |
| それ以外 | 直さずに、人間に確認する。報告に、落ちたテストの名前と出力を添える |

関わるかは、[手元で流す検証](#手元で流す検証)の 1 で選んだテストに入るかで決める。関わらないテストの出力は、PR のコメントに置き、タスクのコメントからリンクする。人間が、直すタスクを立てるかをすぐ決められるようにするため。

### 見直し

解消のためにコードやテストを書き換えたとき（意味のコンフリクト）だけ、新しいコンテキストで見直す。文字の上の衝突を取り込んだだけなら、見直さずに返す。取り込んだだけの差分は、両方の側ですでにレビューを通っているため。

| 場合 | 当たるもの |
| --- | --- |
| 書き換えた | 衝突した箇所に、どちらの側にもない行を書いた。マージのあとに、テストを通すためにコードやテストを直した |
| 取り込んだだけ | 衝突した箇所で、片方の側を選んだか、両方の行をそのまま並べた。生成物を生成し直した |

見直し役の呼び方と結果の扱いは、実装の役の「push の前の照合」と同じにする。修正の役の指示には、それぞれの系統の呼び方（Claude は Agent ツールの新しいコンテキストのサブエージェント、Codex は `codex exec` の読み取り専用のサンドボックス）を写す。照らす先と見直す差分だけを変える。

| 照らす先 | 見直す差分 |
| --- | --- |
| PR の `docs/` の差分と PR の本文、取り込んだ `main` の変更（`git diff <マージの基点> origin/main`） | マージで解消した部分（`git show --remerge-diff <マージのコミット>`）と、マージのあとのコミット（`git diff <マージのコミット>..HEAD`） |

見直し役への指示は、両方の変更の意図が残っているかを観点にする。片方の変更が消えた、片方の意図を壊して書き換えた、というずれを挙げさせる。見直しは 1 回にとどめ、失敗したときは省いて「できなかった」と書く。この扱いも「push の前の照合」と同じにする。

### 報告

引き継ぎのコメントに、次の 4 つを必ず書く。解消のあとのコードレビューで、衝突した箇所と書き換えた箇所を重点に見られるようにするため。

1. 衝突したファイル
2. 解消の仕方（ファイルごとに、取り込んだだけか、書き換えたか、その内容）
3. 見直しをしたかどうか。行頭を `見直し:` にそろえ、下の 3 つのいずれかで書く
4. 手元で流した検証の結果と、テスト全体は CI で確かめること

```text
見直し: 新しいコンテキストで、両方の変更の意図に照らした。直したもの: <要約、なければ「なし」>
見直し: しなかった（文字の上の衝突を取り込んだだけ）
見直し: できなかった（<理由>）。直したもの: なし
```

`見直し:` の行は、実装の役と同じ行頭にし、後から検索で数えられるようにする。

### 指示の書き方

2 つの修正の役の指示の「コンフリクトを解消するとき」は、上の決まりを同じ文で書く。違うのは、見直し役の呼び方の段落だけにする。`git merge origin/main` で取り込み、rebase をしない今の決まりと、どちらの意図を残すか判断が要るときに人間に確認する決まりは残す。

「人間に確認するとき」の「自分の変更と関係のないテストが失敗したとき（直さずに報告する）」に、落ちたテストの名前と出力を添えることを足す。レビューの指摘や CI の失敗を直すときも、同じ扱いにそろえる。

## 検証のスキルの節

検証のスキルのひな形 `skeleton/verify-repository.md` に、節「コンフリクトを解消したときの検証（{{repository}}）」を足す。関わるテストの選び方は、言語や構成によってリポジトリごとに違い、原本の指示には書けないため。節は「変更に応じて選ぶ検証」の直後に置く。

```markdown
## コンフリクトを解消したときの検証（{{repository}}）

[記入: 衝突したファイルと PR が変えたファイルから、関わるテストを選ぶ方法とコマンド。手元で流す静的な確認と、生成物の生成と差分の確認のコマンド。テスト全体を任せる CI のチェックの名前。使わないものは対象外とその理由]
```

空欄（`[記入: …]` のまま）の扱いは、ほかの節と同じにする。検証のスキルは、今回の検証に必要な節が未記入なら、推測して実行せずに不足を返す。この節も同じ決まりで扱い、ひな形の決まりの文は変えない。

`tests/project-test.sh` で、展開した検証のスキルにこの節の見出しと `[記入: …]` があることを確かめる。

### 導入済みのプロジェクト

セットアップは、既にある検証のスキルを書き換えないので、新しい節は新しく導入するプロジェクトにだけ届く。導入済みのプロジェクトでは、修正の役は「変更に応じて選ぶ検証」で代える（[手元で流す検証](#手元で流す検証)）。節を足すかは、それぞれのプロジェクトの人が決める。そのことを `CHANGELOG.md` に書く。

このプロジェクトでは、マージのあとに人間が `squadkit-verify` のこのリポジトリの節へ、次を足す。

```markdown
## コンフリクトを解消したときの検証（and00/multica-squad-kit）

`CONTRIBUTING.md` の「コンフリクトを解消したときに流すテスト」の手順で関わるテストを選び、`bash tests/run.sh <選んだファイル>` で流す。続けて `bash scripts/check.sh` を流し、`bash scripts/manifest.sh` のあとに `git diff --exit-code -- MANIFEST` で差分がないことを確かめる。テスト全体と混入の検査は、PR の CI（`check.yml` の各ジョブ）で確かめる。
```

## テスト 1 本ごとの時間の上限

`tests/run.sh` が流すテストのファイルごとに、300 秒の上限を設ける。上限を超えたファイルは、その子のプロセスごと止め、時間切れの失敗にする。手元でも CI でも同じコマンドを流すので、同じ上限が効く。

### 上限の値

上限は 300 秒にする。テストのファイルを分ける設計が、macOS の CI で 1 ファイル 150 秒以下を目標にしているので、その 2 倍の余裕をとる。手元の macOS で 1 ファイルにかかる時間（1〜2.5 分）にも、2 倍ほどの余裕がある。

上限は、エージェントの実行の道具の上限（10 分）と、ファイルを分ける設計で付ける CI のジョブの上限（10 分）より短くする。上の上限で止まると、どのテストで止まったかが出力に出ないため。

| 値 | 根拠 |
| --- | --- |
| 300 秒 | 分けたあとのファイルの目標（macOS の CI で 150 秒）の 2 倍。道具とジョブの上限（600 秒）の半分 |

今の CI の macOS では、300 秒を超えるファイルがある（`squad-dependabot-merge-test` は約 1,260 秒、`project-test`・`setup-runtimes-test` は 330〜350 秒）。要件が前提にした 1 ファイル 1〜2.5 分は、手元の時間で、CI の macOS はそれより長い。そのため、上限はファイルを分ける変更のあとに入れる。先に入れると、正しく動くテストが CI で落ちる。

上限は、環境変数 `SQUAD_KIT_TEST_TIMEOUT`（正の整数の秒）で変えられる。ランナー自身のテストで短い上限を使うためと、遅い機械で一時的に延ばすため。CI では設定しない。正の整数でなければ、`SQUAD_KIT_TEST_JOBS` と同じく、理由を出して 2 で終わる。

### 止め方

`tests/run-one.sh` は、テストのファイルを新しいセッションで起こす。テストが別のプロセスグループで起こした子（`squad-dispatch-pick` の読み取りなど）も、同じセッションに残るので、セッションごと止められる。

1. `python3` の `os.setsid()` のあと、`os.execvp` でテストの `bash` に置き換える。テストのプロセスの ID が、そのままセッションの ID になる
2. 1 秒ごとにテストが終わったかを確かめ、上限を超えたら、`pkill -TERM -s <セッション>` で止める
3. 5 秒待っても残っていれば、`pkill -KILL -s <セッション>` で止める
4. `wait` でテストのプロセスを片付け、結果に時間切れを書く

`pkill -s` は、macOS と Linux の procps のどちらにもある。`python3` は、ホストの依存としてすでに求めている。

上限の中で終わったテストは、今と同じ終了コードと出力で扱う。時間を測る方法と、ログの置き場所は変えない。

### 時間切れの出し方

時間切れのファイルは失敗に数え、テスト全体は 1 で終わる。出力から、どのテストで止まったかが分かるようにする。

| 出力 | 時間切れのとき |
| --- | --- |
| `run-one.sh` の進み具合の行 | `done TIMEOUT tests/x-test.sh 300s` |
| ファイルごとの見出し | `==== FAIL tests/x-test.sh（時間切れ: 300 秒で止めた）` |
| ログのあと | 今と同じく、失敗した場所と直前に通ったケースを出す。どのケースで止まったかを読めるようにするため |
| GitHub Actions の注釈 | `::error` に、テストの名前と「時間切れ: 300 秒で止めた」を出す |
| 最後の行 | 今の `FAIL suite: N 本が失敗: …` に、時間切れのファイルも含める |

### run.sh の起こし方

`tests/run.sh` も、`xargs` を `set -m` で専用のグループに起こしている。負荷の高いときに、同じ `setpgid` の警告が出るおそれがあるので、[setpgid の警告をなくす](#setpgid-の警告をなくす)と同じ起こし方にそろえる。割り込みのときに、グループごと止める今の動きは保つ。

### ランナーのテスト

`tests/test-runner-test.sh` に、次のケースを足す。テスト用のファイルは、`SQUAD_KIT_TEST_TIMEOUT=2` の短い上限で流す。

| ケース | 確かめること |
| --- | --- |
| 時間切れ | 別のプロセスグループで子を起こして眠るファイルが、失敗になる。出力に、ファイルの名前と「時間切れ」が出る。全体の終了コードが 1 になる |
| 子を残さない | 時間切れのあと、テストとその子のプロセスが、1 つも残っていない |
| 上限の中で終わる | 上限の中で終わるファイルの結果と出力の行が、上限を設ける前と同じになる。今ある runner のケースも、変えずに通る |
| 値の誤り | `SQUAD_KIT_TEST_TIMEOUT` が正の整数でなければ、理由を出して 2 で終わる |

## setpgid の警告をなくす

`squad-dispatch-pick` は、使用率の読み取りを、`set -m` ではなく、`python3` で自分のプロセスグループを作ってから `bash` に置き換える形で起こす。グループを作るのを子の 1 か所だけにして、親と子が競う形をなくすため。時間切れのときに、読み取りとその子をグループごと止める今の動きは保つ。

### 原因

bash は、`set -m` で起こしたジョブを別のグループに入れるとき、親と子の両方で `setpgid` を呼ぶ。どちらかが先に済めばよい作りだが、負荷が高いと、子が呼ぶ前に親が子のグループを作り、子が `exec` を進めている間に、子の呼び出しが `EPERM` で失敗する。このとき bash は、子の側で `child setpgid (X to X): Operation not permitted` を標準エラーに出す。読み取りの結果は変わらないが、`squad-dispatch-pick` を呼んだ側の標準エラーに警告が混ざる。

macOS で 8 本を並べて、各 300 回（計 2,400 回）起こすと、`set -m` では 7 回この警告が出た。子の中で `os.setpgrp()` を呼んでから `exec` する形では、同じ条件で 0 回だった。

### 起こし方

読み取りは、次の形で起こす。子は自分のグループを作ってから `bash` に置き換わるので、読み取りのプロセスの ID が、そのままグループの ID になる。

```bash
python3 -c 'import os, sys; os.setpgrp(); os.execvp(sys.argv[1], sys.argv[1:])' \
  bash "$script_dir/squad-usage-read" >"$work_dir/usage.json" 2>"$work_dir/usage.err" &
reader_pid=$!
```

起こした直後で、子がまだ `os.setpgrp()` を呼んでいない間は、グループがない。その間に止めるときのために、グループへの `kill` が失敗したら、読み取りのプロセスに直接 `kill` する。グループを作る前の読み取りは、まだ子を起こしていないので、それで足りる。

読み取りの `squad-usage-read` は、すでに `python3` を使っている。`python3` がないときは、読み取りが失敗した理由で止まり、今と同じ扱いになる。

### 読み取りのテスト

`tests/squad-dispatch-pick-test.sh` は、標準エラーが空であることを確かめる今の決まりを変えない。警告を読み飛ばす変更はしない。時間切れのケース（読み取りとその子を残さない）は今あるので、起こし方を変えたあとも、同じケースで通ることを確かめる。

直したことは、8 本を並べて 1,600 回流し、`setpgid` の警告で 1 回も落ちないことで確かめる。直す前の macOS では、同じ条件で 4 回落ちた。この確かめ方は時間がかかるので、テストには入れず、実装の PR の確認に結果を書く。

## 利用者向けの文書の変更

`CONTRIBUTING.md` の「テストを流す」に、2 つの小節を足す。文書の改行の決まり（1 行に 1 文）に従う。

| 小節 | 書くこと |
| --- | --- |
| コンフリクトを解消したときに流すテスト | 下の選び方、`bash tests/run.sh <選んだファイル>`、`scripts/check.sh` と `MANIFEST` の確認。テスト全体は CI で確かめること |
| テスト 1 本ごとの時間の上限 | 300 秒の上限、時間切れの出力、`SQUAD_KIT_TEST_TIMEOUT`、止まったテストは流し直さずに失敗として扱うこと |

このリポジトリでの関わるテストは、衝突したファイルと PR が変えたファイルのそれぞれについて、次の和にする。

1. 変えたテストのファイル（`tests/*-test.sh`）そのもの
2. ファイルの名前から拡張子を除いた語を含むテストのファイル（`grep -lF -- <語> tests/*-test.sh`）。テストは、確かめるスクリプトや文書を名前で読むので、名前で探せば当たる
3. テストの補助（`tests/*-lib.sh` など）を変えたときは、それを読み込むテストのファイル。2 の探し方で当たる

どれにも当たらないファイルは、関わるテストがないと報告し、CI で確かめる。

`CHANGELOG.md` の「次のバージョン」に、次の 3 つを書く。

- 修正の役が、コンフリクトを解消したとき、手元では関わるテストと静的な確認・生成物の確認だけを流し、テスト全体を CI に任せる。見直しは、解消のためにコードやテストを書き換えたときだけにし、報告に衝突したファイル・解消の仕方・見直しの有無を書く。落ちたテストは流し直さない
- 検証のスキルのひな形に「コンフリクトを解消したときの検証」の節を足した。導入済みのプロジェクトの検証のスキルには届かないので、使うときは人が足す。足すまでは「変更に応じて選ぶ検証」で代える
- テストのファイルごとに 300 秒の上限を設けた。`squad-dispatch-pick` が、負荷の高いときに `setpgid` の警告を標準エラーに出さなくなった

## 残る危うさ

- 関わるテストを名前で選ぶので、名前を使わずに読み込む依存は選び漏れる。漏れは CI のテスト全体で見つかり、修正の役の CI の失敗の直しで扱う
- テストのファイルを分ける変更が入らないと、300 秒の上限で CI の macOS が落ちる。そのときは上限を入れる段を止め、値を人が決め直す
- テストが自分で新しいセッションを作った子は、セッションごとの停止から漏れる。今のテストにはなく、[ランナーのテスト](#ランナーのテスト)の子を残さないケースで、主な形を確かめる
- 「書き換えた」かの判断は、修正の役が行う。判断を誤って見直しを省いても、報告に解消の仕方を書くので、コードレビューで見つけられる

## 検討した案

### setpgid の警告の直し方

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| `python3` で子が自分のグループを作ってから `exec` する | 競う形がなくなり、警告が出ない。グループごと止める動きを保てる。依存が増えない | 起こした直後の短い間だけ、グループがない | 選んだ |
| `set -m` のまま、警告を標準エラーから取り除く | 変更が小さい | 警告を隠すだけで、要件に反する。ほかの警告も取り除くおそれがある | 選ばない |
| `setsid` のコマンドで起こす | 1 行で済む | macOS にない | 選ばない |
| 別のグループにせず、`pkill -P` で子孫をたどって止める | グループを使わない | 親が先に終わった孫を取り逃がす | 選ばない |
| `perl` で同じことをする | `python3` と同じ形にできる | ホストの依存として求めていない | 選ばない |

### 時間の上限の値

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 300 秒。ファイルを分ける変更のあとに入れる | 分けたあとの目標の 2 倍の余裕があり、道具とジョブの上限より先に止まる | ファイルを分ける変更を待つ | 選んだ |
| 150 秒 | 遅くなったファイルに早く気づける | 分けたあとの目標と同じで、揺れで正しいテストが落ちる | 選ばない |
| 1,500 秒。今すぐ入れる | ほかの変更を待たない | 道具とジョブの上限（600 秒）より長く、どのテストで止まったかが出る前に止められる | 選ばない |

### 上限を設ける場所

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| `tests/run-one.sh` でファイルごとに | 手元と CI で同じに効き、止まったファイルの名前を出せる | ランナーの作りが少し増える | 選んだ |
| CI のジョブの上限だけ | 設定 1 行で済む | 手元では効かず、どのテストで止まったかが出ない | 選ばない |
| テストのファイルごとに書く | ファイルに合わせた値にできる | 書き忘れたファイルに効かない | 選ばない |

### 検証のスキルに節を足すか

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| ひな形に節を足し、未記入なら止まる | リポジトリごとの選び方とコマンドを、検証の正本に置ける。未記入の扱いが今と揃う | 導入済みのプロジェクトには届かず、人が足す | 選んだ |
| 節を足さず、「変更に応じて選ぶ検証」を使う | ひな形を変えない | 表にはテスト全体のコマンドが書かれることが多く、推測しないと絞れない | 節がないときの代わりにだけ使う |
| 修正の役の指示に、選び方を直接書く | 1 か所で済む | 言語や構成がリポジトリごとに違い、原本に書けない | 選ばない |

### 見直しをする条件

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| コードやテストを書き換えたときだけ | 取り込んだだけの解消は速く返せる | 書き換えたかを修正の役が判断する | 選んだ |
| いつも見直す | 判断が要らない | 取り込んだだけでも、見直しの時間（上限 10 分）がかかる | 選ばない |
