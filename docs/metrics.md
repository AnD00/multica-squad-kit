# スクワッドの作業の指標を数える

スクワッドの作業の指標を、同じ入力から同じ数で数え直せる手順の設計である。[workflow.md](workflow.md) の計画の候補 1 にあたり、候補 9 の測り直しも同じ手順で行う。

手順は、Multica の記録を読んでスナップショットに残す段と、スナップショットから数える段に分ける。役ごとのトークン数は、Multica が実行ごとに残す使用量から数え、原本に保存の処理を足さない。この点は合意した要件と違うので、[要件の再合意が要る点](#要件の再合意が要る点)で人間の判断を求める。

## 目的と範囲

目的は、ワークフローの改善の効果を、同じ数え方の基準値と比べて判断できるようにすることである。基準値は、計画を作るときに手で数えた値を、この手順で数え直したものにする。

対象は次のとおりである。

- 原本の開発用のスクリプト `scripts/metrics.py` と、そのテスト
- 4 つの指標と、役ごとのトークン数を、タスクごとに数える手順
- 数えた結果と入力のスナップショットを、Multica のタスクに添付する決まり

次は対象にしない。

- 指標の目標の判断と、改善の効果の評価。候補 9 で行う
- コメントの分類。主な指標は総数で測ると計画で決めたため
- 導入先で使用量を集計・表示する機能
- セットアップ、役のひな形、共通スキル、見張りのスクリプトの変更

## 手順の形

手順は、記録を読む `collect` と、数える `count` の 2 つの段からなる。読む段だけが Multica に触れ、数える段はスナップショットだけを読むので、同じスナップショットからは何度でも同じ結果が出る。

```bash
python3 scripts/metrics.py collect --project <プロジェクト ID> --output tmp/metrics/snapshot.json
python3 scripts/metrics.py count tmp/metrics/snapshot.json \
  --cutoff 2026-11-13T00:38:00Z --truncate 2026-11-13T00:38:00Z \
  --human <呼ぶ人間のメンバー ID> --project-key <プロジェクトの印> --member-key <メンバーの印> \
  --output tmp/metrics/result
```

置き場所は、Git が無視する原本の `tmp/` の下にする。スナップショットと結果には、タスクの識別子と、タスクごとの値が入るためである。どちらも公開のリポジトリにコミットしない。

### 記録を読む

`collect` は、`multica` の CLI でプロジェクトの記録を読み、決まった形の JSON に直して書く。読むものと、残す欄は次のとおりである。

| 記録 | 読むコマンド | 残す欄 |
| --- | --- | --- |
| タスク | `multica issue list --project` | ID、識別子、作られた時刻、今の状態 |
| コメント | `multica issue comment list`（すべてのページ） | ID、タスク、書き手の種類と ID、作られた時刻、本文にあるメンバーのメンションの ID |
| 状態の変化 | `multica issue timeline --activity-only` | タスク、変化の前と後の状態、作られた時刻 |
| 実行 | `multica issue runs` | ID、タスク、エージェント、状態、作られた・開始・終了の時刻、使用量の各行 |
| エージェント | `multica agent list` | ID、名前 |

コメントの本文は残さない。数えるのに要るのはメンバーのメンションの ID だけで、本文を添付に広げないためである。メンションは、本文の `mention://member/<ID>` の形を読む。

読み落としは、少なく数える誤りになる。コメントはすべてのページを読み、状態の変化で CLI が切り詰めの警告を出したときは、スナップショットを書かずに止まる。CLI の応答に要る欄がないときも止まる。

スナップショットは、キーの順と配列の並び（作られた時刻、次に ID）を固定して書く。読んだ時刻と CLI のバージョンも記録するが、数える段の結果には影響させない。

### 数える

`count` は、スナップショットと次の入力から、タスクごとの値を数える。入力は、すべて引数で受け、環境や今の時刻を読まない。

| 入力 | 意味 | 基準値での値 |
| --- | --- | --- |
| `--cutoff` | 対象を切る時刻。これより前に作られたものだけを数える | 2026-11-13T00:38:00Z |
| `--truncate` | 実行時間を打ち切る時刻 | 2026-11-13T00:38:00Z |
| `--from` | 対象のタスクの範囲の始め。省略すると始めを切らない | 省略 |
| `--human` | 呼ぶ人間のメンバー ID。複数を渡せる | プロジェクトの値の、呼ぶ人間 |
| `--project-key`、`--member-key` | エージェントの名前から役を読むための印 | セットアップで決めた値 |

数え方は、[workflow.md の記録の読み方](workflow.md#記録の読み方)の表を正本にし、境目を次のように決める。

1. 対象のタスクは、作られた時刻が `--from` 以後で `--cutoff` より前のものとする。状態は問わない
2. コメント・状態の変化・実行は、対象のタスクのもので、作られた時刻が `--cutoff` より前のものだけを数える。`--cutoff` ちょうどのものは数えない
3. 人間のコメントは、書き手の種類がメンバーのコメントの数とする
4. 人間の呼び出しは、書き手の種類がエージェントのコメントのうち、`--human` のどれかのメンションを含むものの数とする。1 件に何度メンションがあっても 1 と数える
5. 実行は、開始の時刻があるものだけを数える。開始の時刻がない実行は、開始する前に取り消されたものとして、回数にも時間にも入れない
6. 実行時間は、開始から「終了の時刻」と `--truncate` の早い方までの秒を足す。終了の時刻がない実行は `--truncate` で終わったとみなし、開始が `--truncate` 以後なら 0 秒とする
7. 差し戻しは、役が `claude-fixer` か `codex-fixer` の、数えた実行の数とする
8. 参考の値として、`in_review` へ移った状態の変化の数も出す

時刻は、秒の小数を含めて比べる。合計は整数の秒で足し、分への直しと 1 タスクあたりの平均は、表示するときにだけ行う。四捨五入は小数第 1 位までとし、浮動小数点を使わずに計算する。

実行の役は、エージェントの名前から読む。セットアップは名前を `<プロジェクトの印>-<役>-<メンバーの印>` にするので、前後の印を外した残りが [common/agents](../common/agents/) の役の名前と一致すれば、その役とする。一致しないエージェントの実行は「その他」にまとめ、エージェントの名前を添える。

### トークン数を数える

役ごとのトークン数は、実行の記録の使用量（`usage`）を足して数える。数える実行は、上の 5 と同じ開始した実行で、時刻の打ち切りはしない。

使用量は、1 つの実行に、モデルごとに 1 行以上ある。入力・キャッシュの作成・キャッシュの読み出し・出力を行ごとに足し、4 つの合計も出す。使用量の行がない実行は 0 にせず「未確認」とし、役ごとにその数を出す。

### 結果の形

結果は、`metrics.json` と `metrics.md` の 2 つのファイルにする。JSON が正本で、Markdown は同じ値を人が読む表にしたものである。

| 部分 | 中身 |
| --- | --- |
| 入力 | 引数の値と、スナップショットの SHA-256、読んだ時刻、CLI のバージョン |
| タスクごと | 識別子、4 つの指標、実行の回数、`in_review` へ移った数、役ごとのトークン数と未確認の数 |
| 合計 | 対象のタスクの数、4 つの指標と参考の値の合計、役ごとのトークン数の合計と未確認の数 |
| 1 タスクあたり | 合計を対象のタスクの数で割った値 |
| 計画の表との差 | 次の節で決める比較 |

同じスナップショットと引数からは、2 つのファイルが 1 バイトも違わない。キーの順、行の並び、数の書き方を固定し、今の時刻や実行した機械の情報を入れないためである。

結果の 2 つのファイルとスナップショットは、数えたタスク（基準値なら候補 1 のタスク）のコメントに添付する。コメントには、使った引数と、スナップショットの SHA-256 を書く。

### 計画の表との差

基準値の結果には、計画の表の値との差と、その理由を添える。比べる値は、[workflow.md の指標の現状と目標](workflow.md#指標の現状と目標)の表と、[使用量の見積り](workflow.md#使用量の見積り)の役ごとの表である。

比べる値は、`count` に `--compare` で渡すファイルに書く。基準値で使うファイルは `scripts/metrics-plan.json` として原本に置く。計画の表の合計だけを持ち、タスクごとの値を持たないためである。差の理由は、数えた人が結果のコメントに書く。

トークン数は、出どころが違うので差が出る見込みである。計画の表は会話の記録から数え、この手順は実行の記録の使用量から数えるためである。差のある役について、差と、その役の未確認の数を並べて書く。

### 候補 9 での測り直し

候補 9 は、同じ 2 つの段を流し直し、`--from` と `--cutoff`、`--truncate` だけを替える。数え方を変えずに範囲だけを動かせるので、基準値と同じ手順の値になる。

20 件を測るときは、改善を入れたあとに作られたタスクから 20 件目までが入るように `--from` と `--cutoff` を決める。決めた時刻は、結果のコメントに書く。

## トークン数の出どころ

役ごとのトークン数は、Multica の実行の記録の使用量から数える。使用量はサーバーに残るので、作業ディレクトリが片付けられた Codex の実行も読めるからである。

計画を作るときは、実行の記録にトークンの欄がないとして、会話の記録から数えた。今の CLI（0.7.0）では、`multica issue runs` の応答の実行ごとに `usage` があり、プロバイダ、モデル、入力・出力・キャッシュの読み出し・キャッシュの作成のトークン数が入る。原本の CLI の見本（`tests/fixtures/cli/issue-runs.json`）にも、この欄がある。

基準値の対象の記録で、次を確かめた。

- 開始した実行 1,156 回のうち 1,130 回に使用量がある。ない実行の多くは、失敗または途中で止まった実行である
- Codex の 3 つの役の実行は、すべてに使用量がある。会話の記録では読めなかった Codex の実装の役の実行も含む
- Claude の最上位の役の出力は、実行の記録の使用量で 326K だった。計画に書いたランタイムの使用量の集計と合い、会話の記録の 191K より多い

このため、実行の記録の使用量は、会話の記録より抜けが少ない。Claude の応答をメッセージと要求の ID で重ねない処理は、ランタイムが使用量を記録するときの処理になり、この手順では行わない。重なっていないことは、実装のときに、会話の記録が残る Claude の実行のいくつかで、実行の記録の使用量と会話の記録を重ねずに足した値を比べて確かめる。

## 置き場所と公開の範囲

原本に置くのは、数える手順と、合成した見本のデータによるテストだけである。タスクの識別子、タスクごとの値、コメントの本文は、原本の差分に入れない。

| もの | 置き場所 |
| --- | --- |
| 数える手順と、計画の表の合計 | `scripts/metrics.py` と `scripts/metrics-plan.json` |
| テストと合成の見本 | `tests/metrics-test.sh` と `tests/fixtures/metrics/` |
| CLI の応答の実物の見本 | `tests/fixtures/cli/`。足す応答は [CLI の実物の見本](../tests/fixtures/cli/README.md)の取り方に従う |
| スナップショットと結果 | 手元の `tmp/metrics/` と、数えたタスクの添付 |

`scripts/` は配布物に入るが、セットアップは `scripts/metrics.py` を読まず、導入先にも配置しない。`scripts/check.sh` と同じ、原本を変える人のための開発用のスクリプトである。

## 互換性と影響を受ける利用者

この設計では、導入済みのプロジェクトの動作は変わらない。変えるのは、原本の開発用のスクリプトとテスト、文書だけで、セットアップが配置・登録するものに触れないためである。

セットアップを流し直しても、エージェント、オートパイロット、スキル、スクワッドの登録は変わらない。ホストの共有のファイル（`gh` の関所、見張りのスクリプト、Codex の設定、シェルの設定）も変わらない。回答ファイルの形も変わらないので、移し替えは要らない。

実行ごとの使用量は、導入先のセットアップによらず、Multica が実行の記録に残している。使用量を記録しないランタイムやデーモンの版の実行は、この手順で「未確認」として数える。

影響を受けるのは、原本を変える人だけである。数える人は、Python 3.11 以上と、プロジェクトの記録を読める `multica` のログインが要る。

### CHANGELOG.md の知らせ

`CHANGELOG.md` は、次にバージョンを上げる PR で、そのバージョンの節に書く。`CHANGELOG.md` の先頭のバージョンと `VERSION` をそろえる発行の決まりがあるため、この設計を実装する PR では書かない。

知らせには、次の 3 つを書く。

1. 原本を変える人向けに、指標とトークン数を数える `scripts/metrics.py` を足したこと。結果と入力は Multica のタスクに添付し、リポジトリには置かないこと
2. 導入した人と導入したプロジェクトの担当向けに、導入先には何も保存されず、新しい保存の場所もないこと。トークン数は、Multica が実行ごとに残す使用量を読むこと
3. セットアップを流し直しても、エージェント、オートパイロット、スキルの登録と、ホストの共有のファイルは変わらないこと

## テスト

テストは `tests/metrics-test.sh` に置き、合成した見本のスナップショットで `count` を確かめる。外部の CLI とサーバーには触れない。

| 確かめること | 見本の作り方 |
| --- | --- |
| 区切りの直前のコメント・実行は数え、ちょうどとその後は数えない | 区切りの 1 秒前、ちょうど、1 秒後に作られた記録 |
| 区切りをまたいだ実行は、区切りまでの秒だけを足す | 区切りの前に始まり、後に終わる実行と、終わっていない実行 |
| 開始する前に取り消された実行は、回数にも時間にも入らない | 開始の時刻がなく、状態が取り消しの実行 |
| メンバーのコメントだけが人間のコメントに、呼ぶ人間のメンションを含むエージェントのコメントだけが呼び出しになる | メンバーとエージェントのコメント、ほかのメンバーへのメンション、1 件に 2 回のメンション |
| 修正の役の開始した実行だけが差し戻しになる | 2 つの修正の役と実装の役の実行、修正の役の開始前の取り消し |
| 役ごとのトークン数が出て、使用量のない実行が未確認と件数で出る | 使用量が 2 行の実行、0 行の実行、名前が規則に合わないエージェント |
| 同じ入力から 2 回流した結果が 1 バイトも違わない | 上の見本で 2 回流し、`cmp` で比べる |
| 区切りと範囲を替えて流せる | `--from` と `--cutoff` を替え、対象のタスクの数と値が変わる |
| 計画の表との差を出せる | `--compare` に合計の見本を渡す |

`collect` は、`tests/cli-stub.py` の CLI のスタブで確かめる。すべてのページを読むこと、切り詰めの警告で止まること、欄の欠けで止まること、本文を残さずメンションの ID だけを残すことを見る。スタブの応答は、実物の見本から作る。状態の変化（`issue timeline`）の実物の見本はまだないので、実装で取る。

## 要件の再合意が要る点

この設計は、合意した要件 9〜14 の、原本に保存の処理を入れる案（質問 2 の案 C）を取らない。要件の目的は、Multica の実行の記録で満たせ、原本を変えると導入先の全員に影響が出るためである。

要件 9〜14 の目的と、この設計での満たし方は次のとおりである。

| 要件 | 目的 | この設計での満たし方 |
| --- | --- | --- |
| 9 | 作業ディレクトリが片付けられる前に、実行ごとの役とトークン数を残す | Multica が実行の記録に使用量を残している。役は実行のエージェントから読む |
| 10 | 実行のタスクに置き、公開のリポジトリに置かない | 実行の記録は、その実行のタスクに付いてサーバーに残る |
| 11 | コメントと通知を増やさず、失敗しても実行を止めない | 原本は何もしないので、コメントも通知も増えず、止める処理もない。使用量のない実行は未確認と数える |
| 12 | 流し直すまでは今のまま動く | 導入先の動作は変わらない |
| 13 | 流し直しで変わる登録を書く | 変わる登録はない |
| 14 | 利用者に知らせる | [CHANGELOG.md の知らせ](#changelogmd-の知らせ)のとおり、変わらないことを知らせる |

受け入れ条件も、次のように読み替えが要る。人間が案 C を保つと決めたときは、[検討した案](#検討した案)の案 C を設計に起こし直す。

- 5 と 7: 会話の記録ではなく実行の記録の使用量から数える。重なりがないことは、[トークン数の出どころ](#トークン数の出どころ)の比べ方で確かめる
- 11 と 12: 原本の保存ではなく、Claude と Codex の両方の実行に使用量が記録されていることと、ない実行が未確認と数えられることで確かめる
- 13: 保存された値として、実行の記録の使用量を入力に使う
- 14: 流し直しで変わる登録がないことを書き、`CHANGELOG.md` で知らせる

## 検討した案

トークン数の出どころとして 3 つの案を比べ、実行の記録の使用量を使う案を推す。案 C は合意した要件の案で、取らない理由と、取るときの形を下に残す。

| 案 | 原本と導入先への影響 | 未確認になる実行 | 判断 |
| --- | --- | --- | --- |
| 実行の記録の使用量を読む（推す） | なし | 使用量を記録しない実行だけ | 要件の目的を満たし、導入先に何も配らない |
| C. 原本に、実行が終わるたびに保存する処理を入れる | ホストの共有の設定が変わり、流し直しが要る。バージョンを上げる知らせが要る | 流し直す前の実行と、保存に失敗した実行 | Multica がすでに残す値を二重に残す。導入先の全員に変更を配る |
| 会話の記録だけから数える | なし | 作業ディレクトリが片付けられた Codex の実行 | 計画のときの数え方。Codex の実装の役の実行の半分ほどが未確認になる |

案 C を取るときは、次の形にする見込みである。どれも実装の前に確かめが要る。

- Claude は、エージェント用の設定のディレクトリ（`CLAUDE_CONFIG_DIR`）の `settings.json` に、セッションの終わりのフックを足す。フックは会話の記録の使用量を、メッセージと要求の ID で重ねずに足す
- Codex は、セッションの終わりのフックがない（未確認）。タスクごとの `CODEX_HOME` が片付けられる前に読むには、`notify` で応答のたびに累計を上書きする形になる。原本の Codex の設定は、人の `notify` と切り離すために `notify` を持たないので、その決まりを変える
- 保存先は、実行のタスクの metadata にする。実行の環境には実行の ID（`MULTICA_TASK_ID`）だけがあり、タスクの ID を CLI から引く方法は未確認である
- 失敗しても実行を止めないよう、フックは時間を区切り、常に 0 で終える。コメントは書かない
- ホストの共有のファイルが変わるので、セットアップの流し直しで保存が始まる。エージェント、オートパイロット、スキルの登録は変わらない見込みである
