# 用語をそろえる

原本の文書、役の指示、共通スキル、ひな形、画面に出す文、コメントとテストで、同じものを同じ語で書く。この文書は、使う語と迷う語の決め方、変えないもの、導入済みの環境との互換性、確認の方法を書く。

語の正本はこの文書にする。役の指示や共通スキルに用語集を写さず、それぞれの文の中で新しい語を使う。持ち主とオーナーの違いは役が読む共通スキル `squad-handoff` に、原本と正本の違いは原本を変える人が読む `CONTRIBUTING.md` に書く（[違いを書く場所](#違いを書く場所)）。

語をそろえる変更は、2 回に分けて入れる。1 回目は、バージョン・フェーズ・タスク・リーダーなどの語をそろえた。2 回目は、確認の意味の語をそろえ、その語を含む固定の行名を変える（[固定の行名](#固定の行名)、[移行の手順](#移行の手順)）。

## 目的と範囲

今は、同じものを指す語が文書ごとに違い、一つの語が別の意味にも使われている。たとえば、Multica の `issue` を、「タスク」と、置き換える語（`U+8AB2 U+984C`）と、英語のままの `issue` の 3 通りで書いている。設計を実装に分けた単位、sub-issue の順番、処理の手順の 1 つを、同じ 1 字（`U+6BB5`）で書いている。読み手と役が取り違えないよう、意味ごとに語を一つに決める。

見て正しいかを判断する意味の語も、「確認」と、`U+78BA U+304B U+3081` で始まる語の 2 通りで書いている。役の指示とスクリプトが読む行の名前にも、後者が入っている。2 回目の変更で、この語を確認にそろえ、文に合わなければ検証か照合にする。

対象は、リポジトリで管理する日本語の文のすべてである。2 回目の変更も、同じ範囲を対象にする。

- 利用者向けの文書（`README.md`、`manual.md`、`CONTRIBUTING.md`、`EXTENSIONS.md`）と `docs/`
- 役の指示と `FORMAT`、スクワッドとオートパイロットの指示、共通スキル、ラベルの説明、セットアップが起票するタスクの題と本文
- ひな形（`skeleton/`）と、このリポジトリの `AGENTS.md` と `.agents/rules/`
- セットアップ・見張り・関所・VM のスクリプトが画面に出す文と、コードのコメント
- テストの名前と、テストが期待する文、テストの場面の入力（`tests/leader-eval/scenes/` など）
- `CHANGELOG.md` の過去の節を含むすべての節

次は対象にしない。

- 公開済みの Release の本文とタグ。動かさない決まり（[タグと Release を出す](../CONTRIBUTING.md#タグと-release-を出す)）を保つ。過去の Release の本文は、書き直した `CHANGELOG.md` の節と食い違ったまま残る
- 外部の CLI・API の名前と、外から受け取る値（[変えないもの](#変えないもの)）
- 英語の識別子とファイル名
- バージョンを上げる PR（`VERSION` の書き換え）
- 導入先で人間が記入したもの（[書き換えないもの](#書き換えないもの)）

## 語の対応

意味ごとに、書く語を一つにする。置き換える前の語は、リポジトリに残さないため、この文書でもコードポイントで書く。`printf '\u7248\n'` のように端末で文字に戻せる。

| 意味 | 書く語 | 置き換える語 |
| --- | --- | --- |
| 配るもののバージョン、道具のバージョン | バージョン | `U+7248` |
| PR の本文を最初に作ったもの（`squad-handoff`、PR の本文） | 最初の本文 | `U+521D U+7248` |
| 最初に出したバージョン（`CHANGELOG.md`） | 最初のバージョン | `U+521D U+7248` |
| 古いバージョンで配った指示 | 古いバージョンの指示 | `U+65E7 U+7248` の指示 |
| 設計を実装に分けた単位 | フェーズ | `U+6BB5` |
| 修正の役が 1 回の依頼で受ける作業 | フェーズ（実装の役と同じ書き方） | 同じ `U+6BB5` の中で |
| sub-issue の順番（`--stage` で付けるもの） | ステージ | `U+6BB5`、`U+6BB5 U+968E` |
| 処理の手順の 1 つ（失敗した手順、進めない手順など） | 手順 | `U+6BB5` |
| Multica の `issue` | タスク | `U+8AB2 U+984C`、文中の `issue` |
| GitHub の `issue` | GitHub の issue | `issue` |
| スクワッドのリーダーの役 | リーダー | 進行の後に役を付けた語、進行の後に「の役」「の担当」を付けた語、役の名前としての進行 |
| AI の使用の上限 | 使用上限、使用率 | AI の後に「の残量」を付けた語は「AI の使用上限」にする |
| 見て正しいかを判断すること | 確認。文に合わなければ検証か照合（[確認・検証・照合の決め方](#確認検証照合の決め方)） | `U+78BA U+304B U+3081` で始まる語 |

次の語は、意味が違うので残す。

| 語 | 意味 |
| --- | --- |
| 段落、普段、入れ子の深さ（1 段まで、一段下げる） | 文の区切り、ふだん、箇条書きと見出しの深さ |
| 工程 | タスクの中の次の仕事 |
| 進行（作業の進行、進行の記録など） | 作業が進むこと。役の名前ではない |
| 利用枠 | その人が提供する AI の契約の枠 |
| 持ち主とオーナー | [違いを書く場所](#違いを書く場所)で分ける |
| 原本と正本 | [違いを書く場所](#違いを書く場所)で分ける |
| `U+78BA U+304B` の後に `U+3081` が続かない語（確かに、確かな） | 間違いないこと。判断する動作ではない |

## 迷う語の決め方

一つの語が複数の意味で使われているものは、文の意味から次のとおり決める。

- `U+6BB5` は、設計を実装に分けた単位ならフェーズ、sub-issue の順番ならステージ、処理の流れの 1 つなら手順にする。段落・普段・入れ子の深さだけ残す。ほかの語の一部として入るもの（ひな形の「E2E の」の後の語など）は、別の語（「方法」など）に言い換える
- `squad-handoff` の「完了した範囲」と「経緯」に付いている `U+6BB5` は、実装のフェーズを指すので、フェーズにする
- 文中で Multica の `issue` を指す `issue` は、タスクにする。`multica issue` のコマンド、CLI のフラグ（`--stage` など）、JSON のキー、`sub-issue` は英語の識別子なので残す
- GitHub の `issue` は「GitHub の issue」と書く。`issue` だけでは Multica のタスクと読み分けられないため
- 役の名前としての進行はリーダーにする。見出しの「開発の」の後の語も同じにする。作業が進む意味の「進行」は残す
- 原本は、この配布するキット（`multica-squad-kit` とそのファイル）だけを指す。決まりや情報の拠り所になる一つの場所は、正本と書く。`squad-handoff` の「原本がある情報」と「原本へのリンク」は、正本にする
- 使用上限と使用率を使う。外から受け取る値は変えない

### 確認・検証・照合の決め方

`U+78BA U+304B U+3081` で始まる語は、確認にするのを基本にする。次の 2 つに当たるときだけ、検証か照合にする。語を選んだら、活用は下の表のとおりにする。

| 書く語 | 使うところ | 例 |
| --- | --- | --- |
| 検証 | 決まった手順で正しさを判定し、通るか止まるかが出るもの。証明、チェックサム、署名、配布物の一覧、入口の `--verify` | 配布物の検証、検証が通りました、展開の前の検証 |
| 照合 | 決まった値と突き合わせて、一致を見るもの。依頼の SHA、記録の文、`MANIFEST` の一覧 | 返ってきたコミットを依頼と照合する |
| 確認 | 上の 2 つに当たらないものすべて。見て判断する、読んで状態を知る、動くことを見る | 受け取ったら最初に確認すること、実機で確認する |

役の指示と `squad-handoff` では、検証の語は検証スキルとテストを流すことを指している。そこでは、手順で判定するものでも、検証スキルと読み違えるおそれがあれば確認にする。

| 置き換える語の形 | 書く形 |
| --- | --- |
| `U+78BA U+304B U+3081 U+308B`、`U+78BA U+304B U+3081 U+305F`、`U+78BA U+304B U+3081 U+3066` | 確認する、確認した、確認して（検証・照合も同じ） |
| 「られない」「られる」を付けた形 | 確認できない、確認できる |
| 「直す」を付けた形 | 確認し直す |
| `U+78BA U+304B U+3081` だけの名詞の形 | 確認（「公開の前の」の後なら検証） |
| `U+78BA U+304B U+3081 U+65B9` | 確認の方法、検証の方法 |

置き換えたあとに「確認を確認する」のように同じ語が重なるときは、片方を「見る」「読み直す」などに言い換える。英語の `verify`・`check` などの識別子は変えない。

## 変えないもの

外から来る値と、名前で照合する登録は変えない。変えると、外の動作と合わなくなるか、導入済みの登録を見つけられなくなるため。

- 外部の CLI と API の名前と値。`multica issue`、`gh issue`、`--stage`、`sub-issue`、Multica の画面の英語の文言（「After PRs merge, move the issue to」など）
- 外から受け取って表示する値。たとえば、Multica の実行の失敗の理由（`squad-review-wait` が表示する「利用上限」など）
- 英語の識別子とファイル名。metadata のキー（`squad_kit_task`、`repository` など）、役のキー、スクリプトとスキルの名前
- 実装のフェーズの大きさの値（`小さな`、`大きな`）。`squad-dispatch-pick` の引数として渡すため
- 見張りが書いて、あとで照合する記録の印。`squad-review-wait` の `返事を待つ役:`、`返事がそろいました` などは、置き換える語を含まないので、そのままにする

役が書き、リーダーと見張りが読む固定の行名のうち 3 つは、置き換える語を含むので変える（[固定の行名](#固定の行名)）。

## 登録済みの名前と互換性

この変更では、Multica に登録する名前は一つも変わらない。名前に置き換える語が入っていないためである。2 回目の変更の語も、登録する名前には入っていない。そのため、導入済みの状態から更新を流しても、名前で照合する登録は同じものを見つけ、重複も取り残しも出ない。変わるのは、同じ登録の説明と指示の中身だけで、更新は既存のものを書き換える。

| 登録 | 名前 | 照合と更新 | この変更で変わるもの |
| --- | --- | --- | --- |
| エージェント | `<p>-<role>-<m>`（英語） | 名前で探し、`multica agent update` で説明と指示を書き換える | 説明と指示 |
| スクワッド | `<P>-<M>`（英大文字） | 名前で探し、指示を書き換える | 指示 |
| 共通スキル・検証スキル | `squad-handoff`、`<p>-verify` | 名前で探し、中身を書き換える | 中身 |
| オートパイロット | 「週 1 回の依存ライブラリの脆弱性チェック …」「Dependabot の PR の週次の確認 …」「使用上限の見張り …」 | 題で探し、説明と指示を書き換える | 説明と指示 |
| ラベル | 開発、運用、検証、指示の改善 | 名前で探し、`multica label update` で説明を書き換える | 説明（`issue` をタスクにする。検証の説明の確認の語） |
| Webhook のトリガー | 「プロジェクトの拡張」「Dependabot の PR」 | 名前で探す | なし |
| セットアップが起票するタスク | `common/setup-issues.json` の 10 種の題 | metadata の `squad_kit_task` と `squad_kit_targets` で探す。印のない古いタスクだけ題で探す | 新しく作るタスクの本文 |
| 使用上限の見張りのタスク | 「[使用上限] …」 | 手元の状態ファイルのタスクの ID で探す | なし |
| Dependabot の PR を人間に回すタスク | 「Dependabot の PR を確認する: …」 | 題の末尾で探す | なし |

エージェントの説明は、`FORMAT` の `description` を写す。「実装の」の後の語がフェーズになるなど、説明の文が変わるが、名前で見つけて書き換えるので、新しいエージェントは作らない。QA の役の `role` の文も、2 回目の変更で確認の語に変わる。

起票済みのタスクの本文は書き換えない。セットアップは、対象を足したときに本文の末尾へ追記するだけで、そのときも同じ追記がすでにあるかを確認する。古いバージョンの追記の途中で止まったあとに、新しいバージョンで流し直すと、言い回しの違う追記が 1 つ増えることがある。読む人が困らないので、この場合は防がない。

### 見張りがあとで照合する記録

`squad-pr-watch` は、リーダーが保留した CI の失敗を引き継ぎで受けたことを、タスクに `/note` の記録で残し、あとでその文と一致するかで、同じ失敗を重ねて知らせないようにしている。この記録の文に、役の名前としての進行が入っている。この文だけは、書き換えると、更新の前に書いた記録を照合できなくなる。

新しい記録は「CI <短い SHA>: 保留した失敗をリーダーが引き継ぎで受けた」にする。照合は、決まった一つの文との一致をやめ、`/note` の次の行が「CI <短い SHA>: 保留した失敗を」で始まり「が引き継ぎで受けた」で終わる記録を受け入れる。古い記録も新しい記録も一致し、置き換える前の語をコードに残さずにすむ。照合の前提（エージェントが書いた記録で、同じ SHA であること）は変えない。

照合しない記録（「CI <短い SHA>: 失敗をリーダーに知らせた」）と、起こす指示の文は、そのまま新しい語にする。登録済みの起こす指示に残る古い語は、役が読む文で、同じ役を指すと分かるので、書き換えない。

見張りのスクリプトは、ホストでセットアップを流し直すまで更新されない（[manual.md の更新](../manual.md#更新と途中で止まったあとの再実行)）。複数のホストで、古いスクリプトと新しいスクリプトが同じタスクを扱うと、古いスクリプトは新しい記録を照合できず、保留した失敗を 1 回重ねて知らせることがある。役が同じ失敗をもう一度受けるだけで、作業は壊れないので、更新の案内でホストごとに流し直すよう書くことで足りるとする。

### 固定の行名

役が決まった形で書き、リーダーと見張りが行の頭で読む行名のうち、次の 3 つを変える。行名の後ろの値（完全な SHA、`なし` と理由、1 件 1 行の結果）と、行を置く場所は変えない。

| 今の行名 | 新しい行名 | 書くもの | 読むもの |
| --- | --- | --- | --- |
| `U+78BA U+304B U+3081 U+308B` の後に `コミット:` | `確認するコミット:` | リーダー。レビュー・E2E・最上位の役への依頼（`leader-review-wait.md`、`leader-principal.md`） | レビューの 4 役、QA、最上位の役。`squad-handoff` の「レビューと E2E の返事を返す」と、役の指示 |
| `U+78BA U+304B U+3081 U+305F` の後に `コミット:` | `確認したコミット:` | レビューの 4 役、QA、最上位の役の結果。`squad-review-wait report` が `/note` で投稿する | リーダーの照合（`leader-review-wait.md` の照合の節、`leader-principal.md`）と、`squad-pr-watch` の `ci-check` |
| `U+78BA U+304B U+3081 U+305F` の後に `こと:` | `確認したこと:` | 引き継ぐすべての役。`squad-handoff` の「引き継ぐとき」の 3 番目の項目 | リーダーと人間。スクリプトは読まない |

古い行名は受け付けない。リーダーの手順、役の指示、`squad-pr-watch` は、新しい行名だけを読む。古い行名を一致の候補に残すと、置き換える前の語がコードと指示に残り、受け付けるのをやめる時機も決めることになるため（[検討した案](#検討した案)）。古い行名の行は、行がないものとして扱う。

| 古い行名が来たとき | 起きること |
| --- | --- |
| リーダーが、結果に `確認したコミット:` の行を見つけられない | 今の決まりの「行がない」に当たり、同じコミットの新しい回でその役だけを頼み直す。2 回続けば人間を呼ぶ |
| 役が、依頼に `確認するコミット:` の行を見つけられない | 今の決まりの「指定がなければ PR の head」を使う。head が依頼と違えば、リーダーの照合で頼み直しになる |
| `squad-pr-watch` が、レビューの報告を引き継ぎと数えない | 報告した役の実行が動いている間は、CI の失敗を作業中として保留する。実行が終われば、ふだんの知らせに進む |

`squad-pr-watch` の判定は、`/note` の次の行が `確認したコミット:` で始まるかに変えるだけにする。照合の前提（その実行を起こした役が書いたコメントで、同じ実行のものであること）と、メンションによる引き継ぎの判定は変えない。

### 移行の手順

固定の行名を書くものと読むものは、更新される時機が違う。そのため、すべてを一度に流し直し、古い行名の依頼と結果を新しい行名で出し直す。

| 置き場所 | 更新される時機 |
| --- | --- |
| 共通スキル `squad-handoff` とリーダーの手順（`references/`） | ワークスペースで共有する。どれか 1 つのプロジェクトでセットアップを流し直した時点で、すべてのプロジェクトに効く |
| 役の指示 | プロジェクトごと。そのプロジェクトで流し直した時点 |
| `squad-pr-watch` | ホストごと。そのホストで流し直した時点 |

移行は、次の 3 つの手順にする。古い行名を受け付けないので、手順 1 で食い違う期間をなくし、手順 2 で残った依頼を出し直し、手順 3 で残るずれを一時的なものとして扱う。

1. 公開したあと、レビューと E2E の返事を待つタスクがないときに、すべてのホストとプロジェクトでセットアップを流し直す。共通スキルとリーダーの手順はワークスペースで共有するので、一部のプロジェクトだけを流すと、流していないプロジェクトの役の指示と食い違う
2. 流し直す前に出したレビューと E2E の依頼は、新しい行名で頼み直す。古い依頼には `確認するコミット:` の行がなく、返事の照合でも頼み直しになるため、先に出し直す
3. 流し直しが遅れたホストでは、レビューの結果の直後の CI の失敗が、報告した役の実行が終わるまで保留されることがある。実行が終われば知らせが届くので、一時的な保留として扱ってよい

手順 3 は、案内に書くことで足りるとする。見張りの判定を変えて取りこぼしを防ぐことはしない。

### 名前で指している節

役の指示、共通スキル、見張りの起こす指示、起票するタスクの本文は、ほかの文書の節を名前やリンクで指している。次の節は、名前に置き換える語が入っているので変える。参照もすべて同じ変更で合わせる。

| 節 | 新しい名前 | 指しているもの |
| --- | --- | --- |
| `designer.md` の実装の後の見出し | 実装のフェーズ | 役の指示の文 |

### 書き換えないもの

プロジェクトの説明は、セットアップが空のときだけ書く。導入先のリポジトリの `AGENTS.md`、作業別のルール、検証スキルは、人間がひな形から記入する。どちらも更新で書き換えないので、古い語が残る。古い語でも同じものを指すと読めるので、セットアップでは直さず、新しい語にそろえたい人が手で直すよう、更新の案内に書く。

2 回目の変更でも同じにする。起票済みのタスクの本文も書き換えない。人間が記入したものに古い行名が残っていても、役は固定の行名を指示と `squad-handoff` から読むので、動作は変わらない。

共通スキルはワークスペースで共有するので、プロジェクトごとに取り出したタグが違うと、共通スキルと役の指示の語が一時的に食い違う。どちらも同じ役とタスクを指すと分かる語なので、動作は変わらない。ただし固定の行名は、食い違うと照合が合わないので、[移行の手順](#移行の手順)で一度に流し直す。

## 違いを書く場所

二つの語の違いは、その語を使い分ける人が読む場所に一度だけ書く。

`squad-handoff` の「呼ぶ人間」に、持ち主とオーナーの違いを書く。オーナーは、ワークスペースの権限の名前（オーナー・管理者・メンバー）である。持ち主は、スクワッドやエージェントなどを作り、そのランタイムと利用枠を提供する人で、`creator_id` や `owner_id` で読む。呼ぶ相手は持ち主で、オーナーとは限らない。

`CONTRIBUTING.md` に、原本と正本の違いを書く。原本は、この配布するキットとそのファイルである。正本は、決まりや情報の拠り所になる一つの場所で、原本の中にも導入先のプロジェクトにもある。

## 更新の案内

`CHANGELOG.md` に新しい節を足し、語をそろえたこと、登録の名前は変わらないこと、手で直してよいもの（[書き換えないもの](#書き換えないもの)）、ホストごとに流し直すこと（[見張りがあとで照合する記録](#見張りがあとで照合する記録)）を書く。置き換える前の語は書かず、意味で示す。

新しい節の見出しは「次のバージョン」にする。番号はバージョンを上げる PR で決め、その PR が見出しを `vX.Y.Z` に直す。見出しを直さずにタグを出そうとすると、`scripts/release.sh` が `VERSION` と先頭の節の違いで止めるので、番号のない節のまま公開されることはない。

過去の節も新しい語に書き直す。過去のバージョンの Release の本文は書き直さないので、Release と `CHANGELOG.md` の節の文が食い違う。中身は同じで、語だけが違う。

2 回目の変更では、「次のバージョン」の節に次を書く。その節がすでにあれば、新しく作らずに足す。置き換える前の語は書かず、「確認の意味の語」「前の行名」のように意味で示す。

1. 確認の意味の語を確認にそろえ、文に合うところは検証か照合にしたこと
2. 固定の行名を `確認するコミット:`、`確認したコミット:`、`確認したこと:` に変え、前の行名は受け付けないこと
3. [移行の手順](#移行の手順)の 1〜3
4. 登録の名前は変わらないことと、手で直してよいもの（[書き換えないもの](#書き換えないもの)）

## テスト

置き換える語が残っていないことを、常に流すテスト `tests/terms-test.sh` で確認する。新しい文を古い語の癖で書き足すと、すぐ戻るため。判定は Python の補助 `tests/check-terms.py` に置き、置き換える語はコードポイントのエスケープで書く。テスト自身が語を含まないようにするため。

対象は、Git で管理するテキストのファイルすべてである。次のどれかがあれば、ファイルと行を出して失敗する。

| 検査 | 失敗にするもの |
| --- | --- |
| `U+7248` | すべて |
| `U+6BB5` | 段落・普段・一段・「数字と空白の後の 1 字と、まで」を除いたもの |
| `U+6BB5 U+968E`、`U+8AB2 U+984C` | すべて |
| 役の名前としての進行 | 進行の後に役、「の役」、「の担当」を付けた語 |
| AI の使用上限 | AI の後に「の残量」を付けた語 |
| 文中の `issue` | バッククォートの中、URL、`GitHub の issue`、`sub-issue`、補助に並べた外の値を除き、日本語の文字と接している `issue`（大文字と小文字を区別しない） |
| `U+78BA U+304B U+3081` | すべて。理由は「確認にする（文に合わなければ検証か照合）」とする。`U+78BA U+304B` の後に `U+3081` が続かない語は止めない |

フェーズ、ステージ、手順の使い分けと、原本と正本、持ち主とオーナーの使い分けは、機械で判定できないので、レビューで確認する。確認・検証・照合の使い分けも同じにする。

既存のテストは、期待する文を新しい語に合わせる。`squad-pr-watch-ci-test.sh` に、古い記録の文がある状態で同じ失敗を重ねて知らせないことと、新しい記録の文でも同じになることを足す。登録の名前は変わらないので、更新で重複と取り残しが出ないことは、既存の流し直しのテストが通ることで確認する。あわせて、登録する名前（エージェント、スクワッド、オートパイロットの題、ラベル、Webhook のトリガー、スキル、起票するタスクの題）を `main` と比べ、変わっていないことを PR で示す。

2 回目の変更では、次を足す。テストと設計文書は、置き換える前の語そのものを書かない。

| テスト | 足すこと |
| --- | --- |
| `tests/terms-test.sh` | 仮の記号で書いた置き換える語を、場所と理由を添えて止めること。確かに・確かな・確認・検証・照合は止めないこと |
| `tests/squad-pr-watch-ci-handoff-test.sh` | `/note` の次の行が `確認したコミット:` で始まる報告を、引き継ぎと数えること。前の行名で始まる報告は数えず、作業中の保留を続けること。前の行名は、jq の文字列の `\uXXXX` のエスケープで書く |
| `tests/agent-templates-test.sh`、`tests/leader-eval-test.sh` と評価の場面 | 期待する行名と見出しを新しい名前にすること。場面の入力のコメントも新しい行名にすること |

登録する名前を `main` と比べた結果は、2 回目の変更でも PR に示す。比べるのは 1 回目と同じ登録の名前で、どれも置き換える語を含まない。

## 検討した案

- 置き換える語を、この文書と `CHANGELOG.md` の新しい節にだけ書く案。読みやすいが、「リポジトリ全体で 0 件」という受け入れ条件と合わず、テストに例外を設けることになるので、コードポイントで書く
- 保留の記録の照合に、古い文を一致の候補として残す案。照合は正しくできるが、置き換える語がコードに残るので、前後の文で照合する
- 語の確認を、実装の最後の 1 回だけの検索にする案。テストを増やさずにすむが、あとから古い語が戻るのを止められないので、常に流すテストにする
- 新しい節に次の番号（`v1.9.0` など）を先に付ける案。番号を決めるのはバージョンを上げる PR なので、見出しは番号を持たない
- 固定の行名で、前の行名も一致の候補に残す案。移行の間の取りこぼしはなくなるが、置き換える語がコードと指示に残り、受け付けるのをやめる時機も決めることになる。要件の合意で、受け付けないと決めたので、移行の手順で食い違う期間をなくす
- 固定の行名だけを変えず、テストの例外にする案。移行は要らないが、「リポジトリ全体で 0 件」と合わないので、行名も変える
- すべてを確認に置き換える案。機械的に置き換えられるが、証明やチェックサムの判定は `--verify` と同じ検証のほうが、決まった値と突き合わせるところは照合のほうが、意味が正確に伝わるので、決め方を分ける
