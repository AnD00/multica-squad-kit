# リーダーの指示を、目的と判断の原則を軸に書き直す

リーダーが細かい指示なしに要点をつかみ、自分で確かめて決め、人間には判断だけを頼めるようにする。リーダーの指示を、役の目的と判断の優先の原則を先頭に置く形に書き直し、手順の細目は共通スキル squad-handoff の参照のファイルへ移す。あわせて、リーダーのモデルは変えずに、思考の深さを上げる。

この文書は、リーダーの役のひな形（`common/agents/orchestrator.md`）と squad-handoff の変更、書き直しの効果を確かめる評価の設計と、その理由を書く。

## 目的と範囲

今のリーダーの指示は約 39KB あり、大半が「X なら Y を流す」形の手順である。役の目的と、何を優先して判断するかはほとんど書かれていない。失敗のたびに個別の手当てを足してきたので、書かれていない場面で判断できず、人間が細かく指示し、問い直し、催促している。

人間が問い直した場面は、次の 6 つの型に分けられる。この設計は、型ごとに原則を 1 つ置き、評価の場面で効果を確かめる。

| 型 | 起きたこと |
| --- | --- |
| 1 | 確かめずに「できない」「分からない」「見えない」と言う |
| 2 | 推測を事実のように書く |
| 3 | 決められることを人間へ投げる。報告の結論が読み取れない |
| 4 | 人間の言葉の意図を読み違える |
| 5 | 同じ失敗をそのまま頼み直し、原因と再発の防止に向き合わない |
| 6 | コンフリクトや遅れに人間が先に気づき、指示や催促をする |

この設計で変えるものは次のとおりである。

- リーダーの指示の構成と文。冒頭に役の目的と判断の優先の原則を置き、手順は場面ごとの索引から参照のファイルへ案内する
- squad-handoff に、リーダーだけが読む参照のファイルを足す。今のリーダーの指示の手順を移す先である
- リーダーの思考の深さ。モデルは変えない
- 書き直しの前後を比べる評価の場面と、それを流す仕組み

次は対象にしない。

- リーダー以外の役の指示。squad-handoff の本文（`SKILL.md`）は、参照のファイルへの案内を足す分だけ変える
- 見張りのスクリプトの動作。手順の文を移すだけで、呼び方と判定は変えない
- 実装・修正の役の検証の時間。型 6 は、リーダーが人間より先にコンフリクトと遅れに気づいて回すところだけを扱う
- 導入後の指標（人間の問い直し・催促・コンフリクトの解消の指示の回数）の計測。別のタスクで追う（[導入後の指標](#導入後の指標)）
- Multica 本体の変更

## 新しい指示の構成

リーダーの指示は、次の順の節にする。手順を一度に全部読ませず、原則で判断させ、場面に入ったときだけ細目を読ませるためである。目安の大きさは 12KB 以内とする。

| 順 | 節 | 中身 |
| --- | --- | --- |
| 1 | 冒頭の段落 | 役の目的（[役の目的](#役の目的)） |
| 2 | 判断の優先の原則 | 7 つの原則を優先の順に書く（[判断の優先の原則](#判断の優先の原則)） |
| 3 | 受け取ったら確かめること | 実行の始めの確認と、どの場面かを決めるまでに読むもの（[受け取ったら確かめること](#受け取ったら確かめること)） |
| 4 | 場面と手順 | 場面ごとに、必ずすることと、読む参照のファイルの表（[場面と手順](#場面と手順)） |
| 5 | 重要の基準 | 共通の基準 4 つと、プロジェクトの基準の読み方。今の文のまま残す |
| 6 | このスクワッドの役 | 展開で決まる事実。有効な役、系統、メンションのリンク（[このスクワッドの役](#このスクワッドの役)） |
| 7 | 人間を待つところ | 今の「受け渡しと人間を待つところ」を、原則 1 の具体として残す |
| 8 | このプロジェクトの値 | 今のまま |

重要の基準を指示に残すのは、手順ではなく判断の基準だからである。`manual.md` の「重要なタスクと最上位の役」も、共通の基準をリーダーの指示に書くとしている。

### 役の目的

冒頭の段落には、次の内容を書く。

あなたは {{project_name}} のスクワッドのリーダーである。合意された要件を、人間の判断が要るところのほかは止めずに、マージを待つところまで進める。人間には、決めてほしいことだけを、根拠と推す案を添えて頼む。要件定義・設計・実装・修正・レビュー・テストは代行せず、有効な役へ回す。

### 判断の優先の原則

原則は 7 つで、番号の小さいほうを優先する。原則がぶつかったときに、どちらを取るかを指示の上で決めておくためである。たとえば、自分で決めて進める（原則 5）よりも、人間が決めるところを越えない（原則 1）を優先する。各原則には、対応する型を添える。

1. **人間が決めるところと関所を越えない**: 要件の合意、設計とフェーズの分け方の承認、外部の I/F の合意、マージ、実行を止めること、ラベル `重要` を外すことは人間が決める。実行の始めの確認が通らないときも止まる。ここでは squad-handoff の「人間を呼んで止まるとき」に従う
2. **言う前に確かめる**（型 1）: 状態・原因・できるかどうかは、答える前に確かめる。確かめる方法は、CLI（`--help` を含む）、実行の状態と記録、PR、タスクのコメント、原本の手順である。進捗や遅れを聞かれたら、実行の状態と記録を読んでから答える。確かめても分からないときは、確かめた方法を添えて「未確認」と書く
3. **事実と推測を分ける**（型 2）: 事実には、出所（流したコマンドと読んだ値）を添える。推測は推測と書き、確かめる方法を添える。読めなかった値を「なし」「通った」と書かない
4. **言葉の意図を読む**（型 4）: 人間の言葉は、直前の流れと貼られたものから、何をしてほしいかを読む。貼られたログは、言葉がなくても「これが起きたので手を打ってほしい」と読む。読みが 2 つに割れ、取り違えると戻しにくいときだけ、1 つ聞く
5. **決められることは自分で決める**（型 3）: 原則と手順で決められることは、自分で決めて進める。報告は、1 行目に結論と次の一手を書く。人間に聞くときは、決めてほしいことを 1 つに絞り、推す案と理由を添える
6. **人間より先に気づく**（型 6）: PR のあるタスクで起きたら、待っている返事の途中でない限り、コンフリクトの状態と、動いている実行の長さを確かめる。解消を修正の役へ頼むのは、タスクがマージ待ちの `in_review` で、その PR に触れる実行が動いていないときだけにする。それ以外は、作業中の PR に修正の役を重ねて呼ばない。45 分を超えて動いている実行は、記録を読み、同じ実行につき 1 回だけ人間に知らせる
7. **再発には原因と手当てを出す**（型 5）: 1 回目の失敗は、原因を確かめて書いてから頼み直してよい。同じ誤りや差し戻しが 2 回続いたら、3 回目は頼まず、原因と再発を防ぐ手当てを添えて人間を呼んで止まる。手当ては、手順の直し方か、指示の改善のタスクの起票である。指示の実物は勝手に変えない

原則 2 は、進捗を聞かれたときに実行の記録を確かめる決まり（[run-status.md](run-status.md)）を一般にしたものである。原則 6 の 45 分は、実装のフェーズの目安の 30 分の 1.5 倍とした。1 回の実行がフェーズの目安を大きく超えたら、人間が「遅い」と気づく前に知らせるためである。

原則 6 で今の手順から変えるのは、確かめるきっかけである。今はコンフリクトの知らせで起きたときだけ確かめるが、PR のあるタスクで起きたときはいつも確かめる。解消を頼む条件（マージ待ちの `in_review` で、返事の待ちの途中でない）は今のまま残し、PR に触れる実行が動いていないことを足す。動いている実行がある PR に修正の役を重ねると、同じブランチに 2 つの実行が push するためである。解消を頼んだあとに 2 回続けて `CONFLICTING` なら 3 回目は頼まない決まりも、今のまま残す。

遅れの知らせには実行の ID を書き、前のコメントに同じ ID の知らせがあれば、もう知らせない。起きるたびに同じ知らせを繰り返さないためである。知らせても、実行を止めるかは人間が決める（原則 1）。

原則 7 は、今の「同じ誤りや差し戻しが 2 回続いたら人間を呼んで止まる」決まりを残し、2 つを足す。1 回目の頼み直しの前に原因を書くことと、止まるときに原因と手当てを添えることである。人間が同じ失敗の原因を自分で調べ直さずに、手当てを選べるようにするためである。判断が決まらないときと、指示や環境の問題が疑われるときに人間を呼んで止まる決まりは、「人間を待つところ」に今の文のまま残す。

### 受け取ったら確かめること

今の節の名前と、最初の項目を残す。最初の項目は、squad-handoff の「実行の始めの確認」に従い、ほかの処理より先に `squad-preflight <タスク>` を流すことである。関所を崩さないためで、`tests/agent-templates-test.sh` もこの項目を確かめている。

2 つめ以降の項目は、場面を決めるまでに読むものだけにする。コメントから済んだ工程・合意・待っている結果を確かめること、プロジェクトが未設定なら設定すること、PR があれば紐付けを確かめることである。書き込み先と見張りの呼び方の項目は、squad-handoff に正本があるので消す（[外す規則](#外す規則)）。

### 場面と手順

場面ごとに、必ずすることと、読む参照のファイルを表にする。必ずすることを指示に残すのは、参照のファイルを読み落としても、関所と人間の待ちを崩さないためである。細目は参照のファイルにだけ書き、指示と二重に書かない。

| 場面 | 必ずすること | 読む参照のファイル |
| --- | --- | --- |
| 新しい要望を受けた・作業先を決める・要件と設計を進める・フェーズを頼む | 振り分けの前に metadata の `repository` を決めて一覧と照合する。合意や承認のないものを先へ回さない | `leader-flow.md` |
| 実装・修正を頼む | その場の使用率で役を選ぶ。頼む前に重要の印を確かめる | `leader-dispatch.md`、`leader-principal.md` |
| 重要の判断の時機・最上位の役を呼ぶ | 3 つの時機にだけ判断し、印と記録を残す。最上位の役は返事の待ちを付けて頼む | `leader-principal.md` |
| レビューと E2E を頼む・返事で起きた | 頼む前に `squad-review-wait watch` を流し、依頼に `返事を待つ役:` と `確かめるコミット:` の行を置く。`返事の待ち: 次に進む` の実行だけが進む | `leader-review-wait.md` |
| PR を受け取った・待つ回を始める・マージへ回す | PR の紐付けを確かめ、紐付いていなければ止まる。マージへ回す直前にコンフリクトの状態を確かめる | `leader-pr-checks.md` |
| 進捗や遅れを聞かれた・実行を止める | 実行の状態と記録を確かめてから答える。止めるのは人間の指示か承認があるときだけ | `leader-run-status.md` |
| PR のあるタスクで、ほかのきっかけで起きた | 返事の待ちの途中でなければ、コンフリクトの状態と動いている実行の長さを確かめる。解消を頼むのはマージ待ちで PR に触れる実行がないときだけ。遅れは同じ実行につき 1 回だけ知らせる | `leader-pr-checks.md`、`leader-run-status.md` |

参照のファイルは、squad-handoff のスキルのディレクトリの `references/` にある。場面に入ったら、その実行の中で読む。前の実行で読んだ記憶で済ませない。参照のファイルが見つからないときは、手順を推測で補わず、セットアップの流し直しを頼んで人間を呼んで止まる。スキルの更新が権限で飛ばされた（`manual.md` の「更新と、途中で止まったあとの再実行」）ときに、古い指示の手順を思い出して動かないためである。

### このスクワッドの役

展開で決まる事実は、指示に残す。参照のファイルは展開されないので、有効な役やメンションのリンクを書けないためである。この節には、今の指示にある次の条件つきの文と一覧を移す。

- 要件を決める役と設計の役の有無。ないときの「次の有効な役へ直接回す」「自分で設計や draft PR を作らない」の文
- 実装・修正の系統。「両系統がある」「Claude 系統だけがある」「Codex 系統だけがある」のどれかと、有効な実装・修正の役の一覧
- 最上位の役の有無と一覧。ないときの「最上位の役は置かない」の文
- レビューと E2E の役の有無。ないときの「レビューと E2E の役は置かない」の文。QA があるときの画面の E2E の確かめ
- CI の見張りの有無と、`squad-pr-watch ci` に渡す見張りの ID

参照のファイルは、系統や役の有無で分かれる手順を、「両系統があるとき」「Claude 系統だけのとき」のような場合分けで書く。どの場合かは、この節の文で決まる。

## 手順の移し先

リーダーの手順の細目は、squad-handoff の `references/` に、場面ごとのファイルとして置く。新しいスキルではなく squad-handoff に置くのは、要件が移し先に squad-handoff を挙げており、補助のファイルはすでに取り込みと照合の対象だからである（`lib/workspace.sh` の `workspace_local_files`）。セットアップの処理は変えずに済む。

| ファイル | 中身 | 今の指示の節 |
| --- | --- | --- |
| `leader-flow.md` | 作業先の決め方、複数のリポジトリの分け方、要件と設計の進め方、フェーズの頼み方、受け渡しの書き方 | 「タスクの作業先」「要件と設計を進める」「受け渡しと人間を待つところ」の依頼の書き方 |
| `leader-dispatch.md` | 実装・修正の振り分け。系統ごとの `squad-dispatch-pick` と `squad-usage-read` の使い方と終了コードの扱い | 「実装・修正の振り分け」 |
| `leader-principal.md` | 判断する時機、印の記録、修正の依頼の数え方、設計の変更の行、最上位の役を呼ぶところ、返事の待ち方、選び方 | 「重要なタスクと最上位の役」のうち「重要の基準」を除く節 |
| `leader-review-wait.md` | レビューと E2E の依頼、`squad-review-wait` の watch・proceed・status、確かめるコミットの照合 | 「レビューと E2E の返事」 |
| `leader-pr-checks.md` | PR の紐付けの確認、CI の見張り、コンフリクトの状態の確認と規則の入れ直し | 「PR の紐付けの確認」「CI とコンフリクト」 |
| `leader-run-status.md` | 実行の状態を確かめて答える、実行を止める、止めたあと | 「進捗を聞かれたときと、実行を止めるとき」 |

参照のファイルは、今の指示の文を、条件の印を場合分けの文に直して写す。手順の中身は変えない。中身を変えるのは次の 3 つだけで、変える内容と理由は、それぞれの節に書く。

- 原則 6 のための「起きたときの確かめ」を、`leader-pr-checks.md` と `leader-run-status.md` に足す。確かめるきっかけを広げ、解消を頼む条件に、PR に触れる実行がないことを足す（[判断の優先の原則](#判断の優先の原則)）
- 原則 7 で、1 回目の頼み直しの前に原因を書くことと、止まるときに原因と手当てを添えることを、`leader-flow.md` の受け渡しに足す。2 回続いたら人間を呼んで止まる決まりは残す（[判断の優先の原則](#判断の優先の原則)）
- 下の PR の紐付け

`SKILL.md` には、「リーダーの手順」の節を足す。`references/leader-*.md` はリーダーの手順で、ほかの役は読まないこと、リーダーは指示の「場面と手順」から読むことを書く。ほかの役が読み込む本文を増やさないため、細目は書かない。

PR の紐付けの手順は、紐付けが漏れる原因を調べた変更（[pr-link.md](pr-link.md)）の結論を取り込んで移す。その変更は、リーダーの指示の「PR の紐付けの確認」を変えていない。変えたのは、スクリプトの出力（`紐付けていません:` の行と、404 で待ち切れたときの連携の案内）と、PR を作った役の引き継ぎである。そこで `leader-pr-checks.md` には、今の手順に次の 2 つを足す。

- 紐付けの一覧が空で人間に頼むときは、引き継ぎに写された警告の文をそのまま添える。連携の案内があれば、ワークスペースの設定のコードの画面で連携を先に確かめるよう頼む。連携がないと、タスクの画面からも紐付けられないため（[pr-link.md](pr-link.md) の「404 で待ち切れたときの案内」）
- 引き継ぎや出力に `紐付けていません:` の行があっても、紐付いているとは読まず、一覧で確かめる（[pr-link.md](pr-link.md) の「飛ばしたことを出力で示す」）

この 2 つは、手順の中身を変える 3 つ目の箇所である。人間への頼みを、紐付けられる形にするために足す。

### 崩さない手順

## モデルと思考の深さ

リーダーのモデルは今のまま変えず、思考の深さだけを medium から high に上げる。リーダーは受け渡しのたびに起きるので、モデルを重くすると、使用枠が足りずに作業の流れが回らなくなるためである。

| ランタイム | 今 | 変えたあと |
| --- | --- | --- |
| Claude | `claude-sonnet-5-5`、medium | `claude-sonnet-5-5`、high |
| Codex | `gpt-6.1-sol`、medium | `gpt-6.1-sol`、high |

Claude のリーダーは、`claude-opus-5-5` にしない。リーダーは 1 つのタスクで十回以上起きるので、Opus の high では使用枠の消費が大きすぎる。人間が、Sonnet でなければ作業の流れが回らないと判断した。

思考の深さは、medium のままにする案と high に上げる案を比べ、high を推す。

| 案 | 判断 | 使用枠 | 受け入れ条件 8 |
| --- | --- | --- | --- |
| high に上げる（推す） | 確かめてから答える、原因を探す、といった原則の判断に考える量を回せる | 1 回の実行の思考の分だけ増える。モデルの単価は変わらないので、Opus にするより小さい | 思考の深さで「今より上がっている」を満たす |
| medium のまま | 今と同じ。変わるのは指示だけになる | 増えない | 満たさない |

受け入れ条件 8 は「モデルと思考の深さが、今より上がっている」としている。この設計はモデルを上げず、思考の深さだけを上げる。そのため、条件の文のとおりにはならない。思考の深さだけで条件を満たすとしてよいかは、人間が明示に決める。

Codex も、モデルを変えずに思考の深さだけを上げる。原本で確かめた Codex のモデルは、`gpt-6.1-sol` と、最上位の役の `gpt-6-astra` だけである。`gpt-6-astra` をリーダーに使うと、重要なタスクにだけ使う最上位のモデルの枠を、毎回の振り分けで使うことになる。

front matter は、今の形（`IF runtime-claude` で Claude のモデル、`ELSE` で Codex のモデル）のまま、思考の深さの値だけを変える。片方のランタイムだけのときの移し方（`common/agents/FORMAT`）は変わらない。

## 評価

書き直しの効果を、マージの前に評価で確かめる。6 つの型の過去の事例を評価の場面に書き起こし、今のリーダーと新しいリーダーに同じ場面を解かせて、基準で採点して比べる。新しいリーダーが、すべての場面で 3 回とも基準を満たせば合格とする。

### 場面の置き場所と形

場面は `tests/leader-eval/scenes/` に、1 場面 1 ディレクトリで置く。ディレクトリの名前は場面の ID（`1-1`、`keep-1` など）にする。ディレクトリの名前は、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」のとおり、印字できる ASCII で書く。型の「保」の場面の ID は `keep-<番号>` にする（[asset-names.md](asset-names.md#場面の-id)）。

| ファイル | 中身 |
| --- | --- |
| `scene.md` | 場面の ID、型、元の出来事、リーダーへ渡す入力、合格の基準 |
| `cli.json` | リーダーが流すコマンドと、その出力の見本の表 |

`scene.md` は、次の見出しを持つ。

- `## 元の出来事`: 過去の事例で、何が起き、人間がどう返したか。2〜3 文で書く
- `## 入力`: リーダーの実行に渡す、きっかけのコメントとタスクの状態。実際の実行に渡る形に合わせる
- `## 合格の基準`: 番号付きの項目。各項目の先頭に `[記録]` か `[採点]` を付ける。`[記録]` は呼んだコマンドの記録から機械で判定するもの、`[採点]` は採点の役が応答を読んで判定するもの

場面の文と出力の見本には、実在のプロジェクト・人・ID を書かない。名前は `shop` や `member1` のような置き換えにし、ID は `agent-planner` のような読める値にする。公開のリポジトリに置き、混入の検査（`CONTRIBUTING.md` の「MANIFEST と混入の検査」）が UUID の形を拒むため。元の事例のタスクの識別子は、場面のファイルに書かず、タスクに残す評価の記録に場面の ID と並べて書く。

### 流す仕組み

場面は `tests/leader-eval/run.sh` で流す。`tests/run.sh` には入れず、CI でも流さない。本物のモデルを呼び、使用枠を使うためである。

1. 比べる 2 つの指示を作る。今のリーダーは、引数のコミット（既定は `origin/main`）の `common/agents/orchestrator.md` と squad-handoff を `git show` で取り出す。新しいリーダーは作業ツリーのものを使う
2. 指示を、セットアップと同じ展開（`lib/render.sh`）で、決まった見本の値（`tests/leader-eval/values.json`）に展開する。見本は、すべての役が有効で、両方のランタイムを使うプロジェクトにする。モデルと思考の深さは、展開した front matter から読む
3. 場面と回ごとに、`tmp/leader-eval.XXXXXX/` の下に作業ディレクトリを作る。そこに、Multica の実行と同じ配置で、展開した指示と squad-handoff（`SKILL.md` と `references/`）を置く。配置は、実装のときに実際の実行の作業ディレクトリで確かめる
4. `multica`、`gh`、`squad-` の見張りをスタブにして PATH の先頭に置く。スタブは、引数を `cli.json` の表と前方一致で照らして見本を返し、呼び出しを記録する。表にない呼び出しは、失敗を返して記録する。書き込み（コメント、状態、ラベル、metadata、起票、止める）は、成功を返して中身を記録する
5. ランタイムの CLI（`claude -p`）に、場面の入力を渡して流す。使える道具は、スタブのコマンドの Bash と、作業ディレクトリの中の読み書きに絞る。実際に流すと、エージェントは `cmd; echo "exit=$?"` や `cmd | head` のようにコマンドをつなぐ。つないだ部分が許可に無いと全体が拒否されるので、読むだけの標準のコマンド（`echo`・`cat`・`ls`・`head`・`grep`・`jq` など）と、コメントの一時ファイルを消す `rm`（`.md` と `tmp/`・`./` の下）も許可する。思考の深さは、Multica が実行に渡すのと同じ指定にする
6. 合格の基準を判定する。`[記録]` はスタブの記録から機械で判定する。`[採点]` は、採点の役（`claude-opus-5-5`、high で固定。[評価するモデル](#評価するモデル)）に、基準の 1 項目、場面の入力、呼んだコマンド、投稿したコメントを渡し、合否と理由を JSON で返させる
7. 1 回の実行は、すべての基準を満たしたときに合格とする。場面は 3 回とも合格したときに合格とする

並列数は引数で決め、既定は 4 とする。19 場面を 3 回ずつ、2 つの指示で流すと 114 回になるため。採点の役は、今のリーダーと新しいリーダーのどちらの記録にも同じものを使い、どちらの指示かを渡さない。

Codex のランタイムでの評価は、`--runtime codex` で同じ場面を流せるようにする。合否は Claude のランタイムで決め、Codex は使える環境で流して記録に足す。評価する人の使用枠と、`codex` の CLI の有無が環境ごとに違うため。

### 評価するモデル

リーダーは、展開した front matter のモデルと思考の深さで流す。今のリーダーは `claude-sonnet-5-5` の medium、新しいリーダーは同じモデルの high になる。流す仕組みと場面の基準は、モデルの名前を前提にしない。評価は、利用者のプロジェクトで実際に動くモデルで流さなければ、結果が実際の動作を表さないためである。

新しいリーダーの合否は、Sonnet の high で 3 回とも合格したかで決める。Opus のような強いモデルは、指示が足りなくても力で補って通ることがある。軽いモデルで通れば、指示と原則そのものが効いている、より強い証拠になる。今と新しいリーダーは同じモデルなので、差は指示と思考の深さから出る。

採点の役は、リーダーのモデルと分けて `claude-opus-5-5` の high に固定する。採点は 1 つの基準の合否を読むだけで、リーダーの実行より呼ぶ量が少ない。今と新しいリーダーを同じ物差しで測るため、リーダーのモデルに合わせて変えない。

リーダーを Opus にして流した評価の結果は、合否に使わない。Sonnet で流し直す。

### 記録の形

`run.sh` は、作業ディレクトリに次の 2 つを書く。

| ファイル | 中身 |
| --- | --- |
| `summary.md` | 場面ごとに 1 行の表。列は、場面の ID、型、今のリーダーの合格の回数（n/3）、新しいリーダーの合格の回数、落ちた基準の番号 |
| `runs.jsonl` | 実行ごとに 1 行。場面、指示、回、モデル、呼んだコマンド、投稿したコメント、最後の応答、基準ごとの合否と理由 |

記録はタスクに残す。`summary.md` の表と、場面の ID と元の事例のタスクの対応をコメントに書き、`runs.jsonl` を添付する。新旧の応答と採点を並べて読めるようにし、採点の役の判定を人間があとから確かめられるようにするため。PR の本文には写さない。

### 場面を確かめるテスト

`tests/leader-eval-test.sh` は、本物のモデルを呼ばずに次を確かめる。CI で流す。

- すべての場面に、3 つの見出しと、`[記録]` か `[採点]` の付いた基準が 1 つ以上ある。`cli.json` が JSON として読める
- 型 1〜6 に、それぞれ場面が 2 つ以上ある。[崩さない手順](#崩さない手順)の表の場面がすべてある
- 場面の中に、UUID の形の値がない
- スタブの `claude` で `run.sh` を流し、今と新しい指示が展開されること、スタブのコマンドが呼び出しを記録すること、`[記録]` の判定と記録の形を確かめる
- リーダーを、展開した front matter のモデルと思考の深さで呼ぶこと。期待するモデルの名前をテストに書き込まず、front matter から読む

## 互換性と影響を受ける利用者

導入済みのプロジェクトは、ホストでセットアップを流し直すと、リーダーの指示と思考の深さが新しいものに更新される（`manual.md` の「更新と、途中で止まったあとの再実行」）。エージェントの数と登録の名前、スクワッド、オートパイロットは変わらない。流し直すまでは、今の指示のままで動く。

squad-handoff は、流し直しで `references/` の補助のファイルが取り込まれる。スキルはワークスペースで共有するので、同じワークスペースの別のプロジェクトにも参照のファイルが届く。今の指示のままのリーダーは参照のファイルを読まないので、動作は変わらない。

スキルの更新は、オーナー・管理者か最初に取り込んだ人でなければ飛ばされる。そのときは、新しい指示のリーダーが参照のファイルを見つけられない。[場面と手順](#場面と手順)のとおり、推測で補わずに人間を呼んで止まる。

リーダーの実行の使用枠が、思考の分だけ増える。モデルは変わらないので、増える量は Opus にするより小さい。CHANGELOG に、思考の深さが上がり使用枠が増えることを書く。導入後の問い直しと催促の回数は、別のタスクで追う（[導入後の指標](#導入後の指標)）。

## 導入後の指標

導入後の指標は、別のタスクで追う。そのタスクは、この変更を人間のマージへ回す直前に、リーダーが起票する。この変更のタスクは、指標の結果を待たない。

- 追う指標: 人間の問い直し、催促、コンフリクトの解消の指示の回数。数えるときは、[目的と範囲](#目的と範囲)の 6 つの型に分ける
- 起票する人と時機: リーダーが、この変更の最終レビューが済み、人間のマージへ回すコメントを書く前に起票する。マージへ回すコメントに、起票したタスクを示す
- 起票の手順: squad-handoff の「新しいタスクを作るとき」に従う。同じタスクを探し、プロジェクトとスクワッドを付け、ラベル `運用` を付ける。数え始めるのは導入後なので、`backlog` で作る
- タスクに書くこと: 3 つの指標と型の分け方、数える期間（流し直す前の 4 週間と、流し直したあとの 4 週間）、増えた型の場面を評価に足すこと

起票をリーダーにするのは、マージへ回す時点で、評価の記録と型の分け方を一番よく知っているためである。マージの前に起票すれば、受け入れ条件の「指標を追う別タスクがある」を、人間がマージの判断と同時に確かめられる。

## 残る危うさ

- 評価の場面は過去の事例の書き起こしで、場面にない状況での判断は確かめられない。導入後の指標を別のタスクで追い（[導入後の指標](#導入後の指標)）、場面を足していく
- 採点の役の判定は誤ることがある。記録に理由を残し、人間が落ちた場面と際どい場面を読んで確かめる
- 参照のファイルをその場で読まずに動くと、手順を落とす。「場面と手順」の表に必ずすることを残し、崩さない手順の場面で確かめる
- 評価は Claude のランタイムで合否を決める。Codex のリーダーは、流せる環境がなければ評価されずに出る
- 評価の作業ディレクトリの配置が Multica の実行と違うと、評価の結果が実際の動作を表さない。実装のときに実際の実行の作業ディレクトリと照らす

## 検討した案

- 新しいスキル（`squad-lead` など）を作り、リーダーにだけ割り当てる案。ほかの役が読む量は減るが、セットアップの取り込みと導入の確認（`lib/installation.sh`）に新しいスキルを足す変更が要る。要件が squad-handoff を移し先に挙げているので採らない
- 手順を指示に残し、冒頭に原則を足すだけの案。変更は小さいが、指示の大きさがほとんど変わらず、手順の量に原則が埋もれる。要件の「手順の細目をスキルとスクリプトへ寄せる」を満たさない
- 参照のファイルをひな形として展開し、プロジェクトのスキルとして登録する案。役の有無を書けるが、スキルの登録と更新の仕組みを新しく作ることになる。展開で決まる事実は指示の「このスクワッドの役」に残せば足りる
- 遅れに気づくため、振り分けのたびに時刻のウェイクアップを登録する案。人間に言われる前に気づけるが、実行が増え、要件が型 6 で扱うのはコンフリクトに気づいて回すところまでである。起きたときに動いている実行の長さを確かめるだけにする
- Claude のリーダーを `claude-opus-5-5` の high にする案。判断は重くなるが、リーダーは受け渡しのたびに起きるので使用枠が大きく増え、作業の流れが回らない
- Codex のリーダーに `gpt-6-astra` を使う案。判断は重くなるが、最上位の役の枠を毎回の振り分けで使う
- 評価を `tests/run.sh` に入れて CI で流す案。毎回確かめられるが、本物のモデルを呼ぶので、CI に認証と使用枠が要る。CI では場面の形とスタブでの流れだけを確かめる
