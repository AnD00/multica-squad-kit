# 進捗を聞かれたときと、実行を止めるときのリーダーの手順

人間がスクワッドの進捗や遅延をリーダーに聞いたとき、リーダーが実行の状態と記録を確かめてから答えるようにする。実行を止める・やり直すときは、人間の指示か承認を受けてから行い、未 push の作業を失うかを人間が判断できるようにする。

この文書は、リーダーの役のひな形（`common/agents/orchestrator.md`）に足す手順の設計と、その理由を書く。現在のリーダーの手順は、squad-handoff の参照ファイル [leader-run-status.md](../common/skills/squad-handoff/references/leader-run-status.md) にある。指示の構成と移した理由は、[leader-principles.md の手順の移し先](leader-principles.md#手順の移し先)を参照する。

## 目的と範囲

今のリーダーの指示には、進捗を聞かれたときの手順も、実行を止める・やり直す手順もない。そのため、リーダーが「実行の中身は見えない」「止める操作はできない」と答え、あとで誤りと訂正したことがある。実際は、Multica の CLI で実行の状態と記録を読め、実行を止められる。

使うコマンドは次のとおりで、どれもリーダーの実行から呼べる。CLI 0.7.0 の `--help` と実物の出力で確かめた。

| コマンド | 使う場面 | 読む欄 |
| --- | --- | --- |
| `multica issue runs <タスク> --active --output json` | 動いている実行を確かめる | `id`、`agent_id`、`status`、`started_at`、`trigger_comment_id` |
| `multica issue runs <タスク> --siblings --output json` | sub-issue の流れで、親と子の動いている実行も確かめる | `task_id`、`issue_identifier`、`agent_id`、`status`、`started_at` |
| `multica issue runs <タスク> --output json` | 動いている実行がないとき、最後の実行の結果を読む | `status`、`completed_at`、`error` |
| `multica issue run-messages <実行の ID> --issue <タスク> --output json` | 実行の直近の記録を読む | `seq`、`type`、`tool`、`input`、`content`、`created_at` |
| `multica issue cancel-task <実行の ID> --issue <タスク>` | 人間の指示か承認を受けて、実行を止める | なし |

次は対象にしない。

- 進まない実行を自動で見つける見張り。今回は、聞かれたときと止めるときの手順だけを直す
- リーダーが自分の判断で実行を止めること。未 push の作業を失う判断を人間に残すため
- 人間が明示して止めるよう指示したときの確認。往復を増やさないため
- リーダー以外の役の指示、共通スキル squad-handoff、見張りのスクリプトの変更と、Multica 側の止める動作の変更

## 置き場所

手順は、リーダーの役のひな形に新しい節「進捗を聞かれたときと、実行を止めるとき」として足す。節は「CI とコンフリクト」と「受け渡しと人間を待つところ」の間に置く。

共通スキルではなくリーダーの指示に置くのは、進捗を聞かれて答える役と、実行を止める役がリーダーだけだからである。役のひな形は、セットアップを流し直すと新しいひな形で合わせるので、導入済みのプロジェクトにも届く（`manual.md` の「更新と、途中で止まったあとの再実行」）。

節は、役の有無で変わる文を持たない。役の対応は「このプロジェクトの値」の ID で引き、そこにはすでに有効な役だけが残るため。新しい条件の印は足さない。

| ファイル | 変えること |
| --- | --- |
| `common/agents/orchestrator.md` | 節「進捗を聞かれたときと、実行を止めるとき」を足す（[実行の状態を確かめて答える](#実行の状態を確かめて答える)、[実行を止める](#実行を止める)、[止めたあと](#止めたあと)） |
| `tests/agent-templates-test.sh` | 節と要の語句が、すべての役の組み合わせで残ることを確かめる（[テスト](#テスト)） |
| `MANIFEST` | 作り直す |

## 実行の状態を確かめて答える

進捗・遅延・止まっているかを聞かれたら、答える前に実行の状態と記録を確かめる。記憶や前のコメントから答えない。実行の状態はほかの実行の間に変わるので、確かめずに答えると古い状態や誤った「見えない」を返すため。

手順は次のとおり。

1. 聞かれたタスクで `multica issue runs <タスク> --active --output json` を流す。タスクに親か子があるときは、`--siblings` も流して親と子の実行も確かめる
2. 一覧から、この返事を書いている自分の実行を除く。自分の実行も `--active` に出るため
3. 残った実行ごとに `multica issue run-messages <実行の ID> --issue <タスク> --output json` を流し、末尾の記録を読む
4. 答えには、実行ごとに次の 5 つを書く

| 項目 | 読む欄 |
| --- | --- |
| 実行の ID | `runs` の `id`（`--siblings` では `task_id`） |
| 役 | `agent_id` を「このプロジェクトの値」の各役の ID と照らした名前 |
| 状態 | `status`（`queued`、`dispatched`、`running` など） |
| 始まった時刻 | `started_at`。まだ始まっていなければ、その旨 |
| 直近にしていたことと、その時刻 | 記録の末尾の `tool` と `input` の要約、または `content`。時刻はその記録の `created_at` |

`agent_id` が「このプロジェクトの値」のどの ID にも当たらないときは、`multica agent get <ID>` の名前を書く。それでも分からなければ ID だけを書き、役は「未確認」と書く。

記録は長いことがあるので、末尾の数件だけを読めばよい。記録が空のときや読めなかったときは、その旨とコマンドを書く。直近にしていたことを推測で埋めない。

`--siblings` は動いている実行を 20 件までしか返さない。打ち切ったときは CLI が標準エラーに出すので、そのときは一覧が全部ではないことを答えに書く。

### 動いている実行がないとき

動いている実行がないときは、その旨と、最後の実行の結果を書く。最後の実行は `multica issue runs <タスク> --output json` の先頭（新しい順）の、自分の実行を除いたものである。

| `status` | 書く結果 |
| --- | --- |
| `completed` | 終わった |
| `failed` | 失敗した。`error` があれば添える |
| `cancelled` | 止められた |
| それ以外 | 値をそのまま書く |

結果に添えて、その実行の役と終わった時刻（`completed_at`）を書く。実行の履歴が一つもなければ、その旨を書く。

### 「見えない」「できない」と答える前に

「見えない」「できない」と答える前に、`multica issue --help` と、使えそうなコマンドの `--help` で、使えるコマンドを確かめる。CLI のバージョンが上がると、できることが増えるため。それでもできないときは、確かめたコマンドを添えて答える。人間が、確かめた範囲と残る手を判断できるようにするため。

### 状態と呼ぶ相手

進捗を答えるだけのときは、タスクの状態を変えず、ほかの役もメンションしない。質問への返事は、タスクの作業を進めたことにならないため。

## 実行を止める

リーダーは、人間の指示か承認があるときだけ `multica issue cancel-task` で実行を止める。自分の判断では止めない。止まって見えるだけの長い実行もあり、止めると未 push の作業を失うことがあるので、その判断を人間に残すため。

### 止めた方がよいと考えたとき

進捗を確かめた結果、止めた方がよいと考えたときは、止めずに人間に提案する。提案には、状況と理由に、次の確認の 4 項目を添える。

1. 止める実行の ID と役
2. タスクのブランチに最後に push されたコミット
3. そのコミットより後の編集・コミットが、実行の記録にあるか
4. 止めると未 push の作業を失うおそれがあること

確認の項目で分からないものは「未確認」と書く。「なし」とは書かない。「なし」と読んだ人間が、失う作業がないと判断して承認するおそれがあるため。

提案では、呼ぶ人間をメンションし、タスクの状態は変えない。提案の間も実行は動いており、タスクはエージェントの番のままだからである。`in_review` にすると、コンフリクトの見張りがマージ待ちと読んで修正の役を呼ぶおそれもある。

### 最後に push されたコミットを読む

最後に push されたコミットは、タスクの metadata の `pr_url` と `branch` から、GitHub の今の値を読む。読み取りだけなので、関所を通る。

| metadata | 読み方 |
| --- | --- |
| `pr_url` がある | `gh pr view <PR の URL> --json headRefOid,headRefName` の `headRefOid` |
| `branch` だけがある | `gh api repos/<repository>/branches/<branch> --jq .commit.sha` |
| どちらもない、または読めない | 「未確認」と書き、理由（metadata にない、読めなかった）を添える |

SHA は 7 文字以上で書く。squad-handoff の「PR の状態を書く」に合わせるため。

### 後の編集・コミットを記録から読む

止める実行の記録を `run-messages` で読み、最後に成功した `git push` より後に、ファイルの編集か `git commit` があるかを確かめる。ファイルの編集は、Claude なら `Edit` や `Write`、Codex なら `apply_patch` などのツールの呼び出しである。記録に `git push` がなければ、その実行のすべての編集とコミットが対象になる。

| 読んだ結果 | 書くこと |
| --- | --- |
| 編集かコミットがある | あり。最初と最後の記録の `seq` と時刻を添える |
| 記録を末尾まで読み、編集もコミットもない | なし |
| 記録を読めなかった、一部しか読めなかった、push の成否が記録から分からない | 未確認 |

記録からの読み取りなので、見落としはありうる。そのため、4 項目目の「失うおそれ」は、3 項目目の結果によらず必ず書く。

### 人間が明示して止めるよう指示したとき

人間が明示して「止めて」と指示したときは、それを承認として扱い、確認の 4 項目を挟まずに止める。往復を増やさないため。

止める実行は、指示の中の実行の ID・役・タスクから決める。候補が一つに決まらないとき（同じタスクで役の違う実行が二つ動いているなど）は、止めずに候補の実行の ID と役を並べて、どれを止めるかを聞く。これは確認の 4 項目とは別で、取り違えて別の実行を止めないためである。

### 止める操作

止める直前に `multica issue runs <タスク> --active` を流し直し、その実行がまだ動いているかを確かめる。提案や指示のあとに、実行が自分で終わっていることがあるため。終わっていれば止めず、最後の結果を人間に書く。

まだ動いていれば、`multica issue cancel-task <実行の ID> --issue <タスク>` で止める。止めたあとに `multica issue runs <タスク> --output json` で、その実行が `cancelled` になったことを確かめる。自分の実行は止めない。

## 止めたあと

止めたら、止めた実行の ID と役、確かめた結果、最後に push されたコミットを人間に書く。そのうえで、やり直す・別の役に振り直す・待つのどれにするかを聞く。止めたあとはエージェントの番の作業がないので、squad-handoff の「人間を呼んで止まるとき」に従って `in_review` にする。

人間の返事には、次のとおり従う。

| 返事 | すること |
| --- | --- |
| やり直す | 止めた役をメンションで呼び、元の依頼の内容を写す。止めた実行の ID と最後に push されたコミットを添え、そこから続けるよう頼む。タスクを `in_progress` にする |
| 別の役に振り直す | 振り直す役をメンションで呼び、やり直すときと同じ内容を添える。タスクを `in_progress` にする |
| 待つ | 何もしない。状態は `in_review` のまま |

元の依頼は、止めた実行の `trigger_comment_id` のコメントから読む。依頼の内容は要約せずに写す。最後に push されたコミットが「未確認」のままなら、そのまま「未確認」と書き、ブランチの最新から確かめて続けるよう頼む。

`multica issue rerun` は使わない。`rerun` はタスクの今の担当で実行し直すので、担当がスクワッドのタスクでは、止めた役ではなくリーダーの実行が起きるおそれがあるため。続きの起点も新しい実行に伝わらない。

レビューや E2E の返事を待つ回の役を止めたときは、やり直しも、今の「レビューと E2E の返事」の手順で頼む。`返事を待つ役:` の行を写しただけでは、待ちの登録と照合がずれるため。

## テスト

ひな形を展開した結果に、新しい節と要の語句が残ることを `tests/agent-templates-test.sh` で確かめる。新しいテストのファイルは足さない。

| 確かめること | 確かめ方 |
| --- | --- |
| すべての役の組み合わせで、節「進捗を聞かれたときと、実行を止めるとき」がある | 今のテストが展開する各組み合わせの `orchestrator` で、見出しの有無を見る |
| 状態の確かめに使うコマンドがある | 節の中に `runs <タスク> --active`、`--siblings`、`run-messages`、`--help` がある |
| 答えに書く項目と、動いている実行がないときの答え方がある | 節の中に、5 つの項目の語と、`終わった`・`失敗した`・`止められた` がある |
| 止めるのは人間の指示か承認のときだけで、自分の判断では止めない | 節の中に `cancel-task` と、自分の判断では止めない旨の語句がある |
| 確認の 4 項目と「未確認」の扱いがある | 4 項目の語と、`未確認`、`「なし」とは書かない` がある |
| 明示の指示では確認を挟まない | 確認を挟まずに止める旨の語句がある |
| やり直しはメンションで呼び、`rerun` を使わない | 止めた実行の ID と最後に push されたコミットを添える旨と、`multica issue rerun` は使わない旨がある |

文の確かめは、見出しと要の語句の有無だけにする。文全体を固定すると、文言の手直しのたびにテストを直すことになるため。実機で、動いている実行の状態と記録を読んで答えること、承認のあとに止めることは、人が確かめる。

## 利用者向けの文書の変更

`manual.md`、`README.md`、`CONTRIBUTING.md` は変えない。人間の操作は、リーダーに聞く・止めるよう頼むだけで、手順は増えないため。

見張りの使用上限の知らせ（`common/monitor/squad-usage-check`）は、人間に `multica issue rerun` での再実行を案内している。これは人間への案内で、リーダーの手順ではないので、今回は変えない。`CHANGELOG.md` と `VERSION` は、次にバージョンを上げる PR で扱う。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 進まない状態が一定時間続けば、リーダーが自分で止めてやり直す | 「進まない」の基準と時間を決める必要がある。未 push の作業を失う判断がエージェントに移る |
| リーダーは止めず、人間が流すコマンドを示すだけにする | 「できない」と言われる困りごとが半分残る |
| 止める前の確認を、実行の ID・役・状態と、失うおそれの注意だけにする | 失う作業があるかを、人間が自分で確かめることになる |
| 人間の明示の「止めて」でも、確認を挟む | 明示の指示でも往復が 1 回増える |
| `multica issue rerun` でやり直す | 担当がスクワッドのタスクでは、止めた役が起きないおそれがある。続きの起点も伝わらない |
| 手順を共通スキル squad-handoff に置く | 進捗に答えて実行を止めるのはリーダーだけで、ほかの役に読ませる理由がない |
| 止める提案のときに `in_review` にする | 実行は動いたままで、エージェントの番が続いている。コンフリクトの見張りがマージ待ちと読むおそれがある |
| 明示の指示で対象が一つに決まらないときも、推測で一つを止める | 別の実行を止めると、その作業を失う。候補を聞くのは 1 往復で済む |
