# gh の関所を PATH の先頭に保つ

エージェントが打つ `gh` が、どのランタイムの通常の実行でも関所を選ぶようにする。Claude のランタイムでは、シェルの起動ファイルのあとに PATH が書き戻されるので、Claude Code がコマンドの直前に読むファイルでも関所を先頭に戻す。

この文書は、その仕組みと理由、セットアップでの確認、テストを書く。使う人への手順は `manual.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

今は、Claude のランタイムの通常の実行で、`gh` が本物の `gh` を選ぶ。そのため、許可していないリポジトリへの書き込みが関所で止まらない。セットアップの確認と原本のテストは、起動ファイルを読んだ直後の PATH だけを見ており、この崩れを見つけられなかった。

この変更で、次のことを保つ。

- セットアップのあと、Claude のランタイムの通常の実行で、エージェントの `gh` が関所を選ぶ。ランタイムが本物の `gh` のディレクトリを PATH の先頭に置き、Claude Code のシェルのスナップショットが PATH を書き戻しても選ぶ
- そのとき、許可していないリポジトリへの `gh` の書き込みは、`gh の関所:` で始まる文で拒否される。許可したリポジトリへの書き込みと読み取りは、今と同じく通る
- 既存の導入先は、同じプロジェクトでセットアップを流し直すと直る
- Codex のランタイムと、`git push` の関所の動きは今と同じにする

次は対象にしない。

- セットアップの中で、エージェントの試しの実行を起こすこと。実行での確かめは、導入後の「スクワッドの動きを試す」で人間が行う
- Multica と Claude Code への報告や変更
- 本物の `gh` を絶対パスで呼ぶことを止めること。今と同じく、関所の外にある
- ホストの設定を手で直すこと

## 崩れる仕組み

起動ファイルは関所を先頭に戻すが、Claude Code はそのあとにスナップショットで PATH を書き戻す。そのため、コマンドを流す時点では本物の `gh` が先になる。

1. Multica のデーモンの PATH は、関所のディレクトリ（`~/.multica-agent/bin`）から始まる
2. Multica は、Claude のランタイムを起こすとき、`claude` の実行ファイルのディレクトリを PATH の先頭に足す。Homebrew で入れたなら `/opt/homebrew/bin` で、本物の `gh` も同じ場所にある
3. Claude Code は、Bash のコマンドごとに `CLAUDE_CODE_SHELL` のシェル（`/bin/zsh`）を新しく起こす。zsh は `ZDOTDIR` の `.zshenv` を読み、関所を PATH の先頭に戻す
4. 続いて、Claude Code が組み立てたコマンドの文字列が流れる。先頭でセッションの初めに作ったシェルのスナップショットを読み、その最後の `export PATH=…` が、2 の PATH に書き戻す
5. エージェントのコマンドが流れ、`gh` は本物を選ぶ

スナップショットは、セッションの初めに Claude Code が使う人の `~/.zshrc` を読んで作る。最後の PATH は、`claude` のプロセスの PATH をそのまま書く。どちらも Claude Code の中の動きで、原本からは変えられない。

## 直し方

Claude のモデルを使う役に、環境変数 `CLAUDE_ENV_FILE` を渡し、プロジェクトの `env.sh` を指す。Claude Code は、このファイルの中身を、スナップショットのあと、エージェントのコマンドの前に流す。

`env.sh` は、`BASH_ENV` で渡している今のファイルをそのまま使う。中身は、許可ファイルの指定と、関所のディレクトリが先頭になければ足す処理だけで、bash と zsh の両方で動く。同じファイルを使えば、起動の時点とコマンドの直前で、関所を戻す処理が 1 つにそろう。

| 順 | 流れるもの | PATH の先頭 |
| --- | --- | --- |
| 1 | シェルの起動（`.zshenv` または `BASH_ENV` の `env.sh`） | 関所 |
| 2 | スナップショットの `export PATH=…` | 本物の `gh` のディレクトリ |
| 3 | `CLAUDE_ENV_FILE` の `env.sh` | 関所 |
| 4 | エージェントのコマンド | 関所 |

Claude Code は、ファイルの中身をセッションで 1 回読み、そのあとのコマンドで使い回す。`env.sh` はセットアップのときにだけ書き替わるので、使い回しで困ることはない。セットアップを流し直したあとは、新しく起きた実行から新しい中身を使う。

`.zshenv` と `env.sh` のひな形は変えない。コメントだけを、起動のときとコマンドの直前の両方で読まれることに合わせて直す（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## エージェントの環境変数

`lib/project.sh` の `project_desired_env` で、モデルの名前が `claude-` で始まる役に、次の 1 つを足す。今の `CLAUDE_CODE_SHELL` などと同じ条件にする。

| 環境変数 | 値 | 渡す役 |
| --- | --- | --- |
| `CLAUDE_ENV_FILE` | `<エージェントの置き場>/template/shell/<プロジェクトの ID>/env.sh`（`BASH_ENV` と同じ値） | モデルが `claude-` で始まる役 |

環境変数をそろえる処理（`custom_env` から原本が持つ値を消してから、望む値を足す）で、消す名前に `CLAUDE_ENV_FILE` を足す。役のモデルを Codex に替えたとき、古い値を残さないため。人間が同じ名前に別の値を入れていたときは、今のほかの名前と同じく、原本の値で上書きする。

使用量の見張り（`usage-monitor`）で Claude の使用量だけを読む役には足さない。その役は Claude Code の実行を起こさず、`CLAUDE_CONFIG_DIR` だけを使うため。

## 既存の導入先への反映

同じプロジェクトでセットアップを流し直すと、環境変数をそろえる処理が差分を見つけ、`CLAUDE_ENV_FILE` を足す。新しい手順は作らない。

`env.sh` の中身は変えないので、ファイルの書き替えは起きない。印のない既存の `env.sh` を使い続けている導入先も、同じファイルを `CLAUDE_ENV_FILE` から読む。その中身が関所を先頭に置かないときは、セットアップの確認ではなく、導入後の試しで見つかる（[前提と限界](#前提と限界)）。

## セットアップの確認

`lib/host.sh` の `host_check_guards` で、関所を選ぶかの確かめを、本物の `gh` が先の PATH で行う。そのうえで、Claude Code と同じ順に流して、関所を通る・拒否されるを確かめる。

本物の `gh` が先の PATH は、セットアップの PATH から、関所のディレクトリの外で最初に見つかる `gh` のディレクトリを、先頭に足して作る。見つからないときは、関所が本物の `gh` を呼べないので、理由を出して止まる。

選んだリポジトリごと、bash と zsh、許可と空の許可の組で、次の 2 つを順に確かめる。

1. 起動の順: 本物の `gh` が先の PATH と、確認用の `ZDOTDIR`・`BASH_ENV` を渡してシェルを起こし、`command -v gh` が関所を指すことを確かめる。Codex のランタイムと、スナップショットの前の Claude の段に当たる
2. Claude の順: 起こしたシェルの中で、PATH を本物の `gh` が先の並びに書き戻し、確認用の `env.sh` を読んでから、今の確認のコマンドを流す。関所を選ぶこと、許可なら GitHub の入力検証（422 または 409）まで届くこと、空の許可なら `gh の関所:` で拒否されることを確かめる

GitHub への要求は、2 でだけ今と同じ回数を送る。1 は手元で `command -v gh` を見るだけなので、通信は増えない。2 の確かめは、役のモデルによらず流す。`env.sh` はどのランタイムでも同じファイルで、通信も増えないため。

1 で関所を選ばないときは、今と同じ「通常の gh が関所を選びません」で止まる。2 で選ばないときは、Claude の実行の順で選ばないことと、ひな形の `env.sh` を確かめることを出して止まる。どちらも、従来の許可と起動ファイルを保つ。

`pre-push` の確かめは、2 の中で今と同じに流す。`git push` の関所は `core.hooksPath` で選ばれ、PATH に頼らないため、動きは変わらない。

## テストと CI

Claude の実行の順を、原本のテストで bash と zsh の両方について再現する。新しいテストのファイルは足さず、今のテストにケースを足す。CI は、今の `tests/run.sh` のジョブのまま流す。

`tests/gh-test.sh` に、Claude の順のケースを足す。今の「本物の `gh` が先でも、起動ファイルで関所が先になる」ケースは、そのまま残す。

- スナップショットに見立てたファイルを、一時の置き場に作る。最後に、本物の `gh`（スタブ）のディレクトリが関所より先の `export PATH=…` を書く
- コマンドの文字列は、Claude Code と同じ形にする。スナップショットを `source` し、`CLAUDE_ENV_FILE` の中身をそのまま並べ、最後にエージェントのコマンドを流す。並べるには ` && ` を使う
- シェルは、`ZDOTDIR` と `BASH_ENV` に描いた起動ファイルを渡して、`/bin/bash` と `/bin/zsh` で起こす

| ケース | 確かめること |
| --- | --- |
| `CLAUDE_ENV_FILE` の中身を並べない | `command -v gh` がスタブを指す。テストが崩れを再現していることの確かめ |
| 中身を並べ、`command -v gh` | 関所を指す |
| 中身を並べ、空の許可で書き込み | `gh の関所:` で始まる文で拒否され、スタブに書き込みが届かない |
| 中身を並べ、選んだリポジトリを許可して書き込み | 関所を通り、スタブに 1 回届く |

`tests/host-test.sh` では、`host_check_guards` の確かめを、関所の外のスタブの `gh`（`tests/guard-backend.sh`）が PATH で関所より先にある状態で流す。スタブは今と同じく 422 を返し、GitHub の入力検証に当たる。次を足す。

- 本物の `gh` が先の PATH でも、許可で 422 まで届き、空の許可で拒否されて、確認が通る
- ひな形の `env.sh` から関所を先頭に置く処理を外した原本で流すと、Claude の順の確かめで止まり、許可ファイルと起動ファイルを書かない
- 関所の外に `gh` がない PATH では、理由を出して止まる

`tests/project-test.sh` と `tests/setup-runtimes-test.sh` では、エージェントの環境変数を確かめる。

- モデルが `claude-` で始まる役に、`CLAUDE_ENV_FILE` が `BASH_ENV` と同じ値で入る
- Codex の役と、使用量の見張りの役には入らない
- Claude の役を Codex に替えて流し直すと、`CLAUDE_ENV_FILE` が消える

Codex のランタイムと `git push` の関所の今のテストは、変えずに通す。テストの中で、本物の GitHub への要求と、`multica` の本物の呼び出しはしない。

- ランタイムが本物の `gh` を先に置いても、非ログインの bash・zsh の起動時に戻す
- Claude のランタイムでは、Claude Code がシェルのスナップショットで PATH を書き戻すので、同じ `env.sh` を `CLAUDE_ENV_FILE` で渡し、コマンドの直前にも戻す
- セットアップは、本物の `gh` が先の PATH で、起動の順と Claude の順の両方を確かめる
- 既存の導入先への反映は、同じプロジェクトでセットアップを流し直す
- 仕組みの理由は、この文書へのリンクで示す

`manual.md` の「スクワッドの動きを試す」に、必ず行う手順を番号付きで足す。

1. 使うランタイムの通常の実行で、エージェントに `which gh` を流させ、関所（`~/.multica-agent/bin/gh`）を指すことを確かめる
2. 同じ実行で、許可していないリポジトリへの `gh` の書き込みが、`gh の関所:` で始まる文で拒否されることを確かめる
3. 1 で関所を指さないときは、ほかの試しに進まず止まり、共有ホストの管理者と呼ぶ人間に知らせる。関所を迂回して試さない

`common/setup-issues.json` の「スクワッドの動きを試す」の本文に、`which gh` が関所を指すことを必ず確かめ、指さなければ止まって知らせる文を足す。手順の本体は、今と同じく `manual.md` へのリンクで示す。

## 前提と限界

この直し方は、Claude Code が `CLAUDE_ENV_FILE` の中身をコマンドの前に流すことに頼る。Claude Code の公開された環境変数で、原本の Claude 向けのほかの設定と同じ扱いにする。

- Claude Code のサンドボックスで、認証情報の環境変数を消す設定を入れると、`CLAUDE_ENV_FILE` を読まない。原本はこの設定を入れない
- Claude Code が、のちの版で読む順を変えたときは、導入後の試しの `which gh` で見つかる。そのため、試しの `which gh` を必ず行う手順にする
- エージェントがコマンドの中で PATH を書き替えたり、本物の `gh` を絶対パスで呼んだりすることは止めない。今と同じく、関所の外にある
- 印のない既存の `env.sh` を使う導入先は、その中身に頼る。セットアップは、ひな形から作った確認用のファイルで確かめるため、印のないファイルの中身は試しで確かめる

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| `gh` をシェルの関数にして、起動ファイルで定める | `command -v gh` が関数を返し、エージェントが流すスクリプトや子のプロセスには届かない |
| Multica の `MULTICA_CLAUDE_PATH` で、`claude` を関所の置き場の包みに向ける | Multica の中の動きに頼る。ランタイムが何を先頭に足しても守る、という要件を満たさない |
| Claude Code の `settings.json` の `env` で PATH を渡す | 値が文字のままで、プロジェクトをまたいで共有の設定になる。スナップショットの書き戻しとの順も保てない |
| SessionStart のフックで、Claude Code が渡す env file に PATH を書く | 共有の設定にフックを足すことになり、動く部品が増える。中身は `env.sh` と同じになる |
| スナップショットの元になる `~/.zshrc` で関所を先頭に置く | 使う人の個人のファイルで、原本が触れない。スナップショットの最後の PATH は、`~/.zshrc` によらず書き戻される |
| `CLAUDE_ENV_FILE` 用に、`env.sh` と別のファイルを作る | 同じ処理を 2 か所に持つ。`BASH_ENV` と同じファイルなら、今の確認とテストをそのまま使える |
| セットアップの中で、エージェントの試しの実行を起こして確かめる | 要件で、確かめは原本のテストと人間の試しに分けると決めた。セットアップが利用枠を使い、時間もかかる |
| Multica と Claude Code に、PATH の扱いを直すよう頼む | 要件の範囲の外。直るまで、関所が効かないままになる |
