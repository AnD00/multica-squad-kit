# セットアップで gh の PATH 復元を確かめる

Claude と Codex の PATH の設定と、実行の始めの確認は、[エージェントの実行で関所と見張りを PATH から選ぶ](agent-path.md)に従う。この文書は、その設定をセットアップで確かめる処理と、関所の許可・拒否を含む回帰テストを補足する。

環境変数やシェル起動ファイルの設定は変えない。本物の `gh` が先にある PATH と、Claude のスナップショットが PATH を書き戻した状態で、既存の設定が関所を先頭に戻すことを確かめる。セットアップでエージェントの試しの実行は起こさず、実際のランタイムは `docs/agent-path.md` の「テストと実機の確かめ」で人間が確認する。

## セットアップの確認

`lib/host.sh` の `host_check_guards` で、関所を選ぶかの確かめを、本物の `gh` が先の PATH で行う。そのうえで、Claude Code と同じ順に流して、関所を通る・拒否されるを確かめる。

本物の `gh` が先の PATH は、セットアップの PATH から、関所のディレクトリの外で最初に見つかる `gh` のディレクトリを、先頭に足して作る。見つからないときは、関所が本物の `gh` を呼べないので、理由を出して止まる。

選んだリポジトリごと、bash と zsh、許可と空の許可の組で、次の 2 つを順に確かめる。

1. 起動の順: 本物の `gh` が先の PATH と、確認用の `ZDOTDIR`・`BASH_ENV` を渡してシェルを起こし、`command -v gh` が関所を指すことを確かめる。Codex のランタイムと、スナップショットの前の Claude の段に当たる
2. Claude の順: 起こしたシェルの中で、PATH を本物の `gh` が先の並びに書き戻し、確認用の `env.sh` を読んでから、今の確認のコマンドを流す。関所を選ぶこと、許可なら GitHub の入力検証（422 または 409）まで届くこと、空の許可なら `gh の関所:` で拒否されることを確かめる

GitHub への要求は、2 でだけ今と同じ回数を送る。1 は手元で `command -v gh` を見るだけなので、通信は増えない。2 の確かめは、役のモデルによらず流す。`env.sh` はどのランタイムでも同じファイルで、通信も増えないため。

1 で関所を選ばないときは、今と同じ「通常の gh が関所を選びません」で止まる。2 で選ばないときは、Claude の実行の順で選ばないことと、ひな形の `env.sh` を確かめることを出して止まる。どちらも、従来の許可と起動ファイルを保つ。

`pre-push` の確かめは、2 の中で今と同じに流す。`git push` の関所は `core.hooksPath` で選ばれ、PATH に頼らないため、動きは変わらない。

## テストと CI

Claude の実行の順を、原本のテストで bash と zsh の両方について再現する。新しいテストのファイルは足さず、今のテストにケースを足す。CI は、今の `tests/run.sh` のジョブのまま流す。

`tests/gh-test.sh` に、Claude の順のケースを足す。今の「本物の `gh` が先でも、起動ファイルで関所が先になる」ケースは、そのまま残す。

- スナップショットに見立てたファイルを、一時の置き場に作る。最後に、本物の `gh`（スタブ）のディレクトリが関所より先の `export PATH=…` を書く
- コマンドの文字列は、Claude Code と同じ形にする。スナップショットを `source` し、`CLAUDE_ENV_FILE` の中身をそのまま並べ、最後にエージェントのコマンドを流す。並べるには ` && ` を使う
- シェルは、`ZDOTDIR` と `BASH_ENV` に描いた起動ファイルを渡して、`/bin/bash` と `/bin/zsh` で起こす

| ケース | 確かめること |
| --- | --- |
| `CLAUDE_ENV_FILE` の中身を並べない | `command -v gh` がスタブを指す。テストが崩れを再現していることの確かめ |
| 中身を並べ、`command -v gh` | 関所を指す |
| 中身を並べ、空の許可で書き込み | `gh の関所:` で始まる文で拒否され、スタブに書き込みが届かない |
| 中身を並べ、選んだリポジトリを許可して書き込み | 関所を通り、スタブに 1 回届く |

`tests/host-test.sh` では、`host_check_guards` の確かめを、関所の外のスタブの `gh`（`tests/guard-backend.sh`）が PATH で関所より先にある状態で流す。スタブは今と同じく 422 を返し、GitHub の入力検証に当たる。次を足す。

- 本物の `gh` が先の PATH でも、許可で 422 まで届き、空の許可で拒否されて、確認が通る
- ひな形の `env.sh` から関所を先頭に置く処理を外した原本で流すと、Claude の順の確かめで止まり、許可ファイルと起動ファイルを書かない
- 関所の外に `gh` がない PATH では、理由を出して止まる

`tests/setup-runtimes-test.sh` では、ランタイムの組み合わせごとに、Claude の役の `CLAUDE_ENV_FILE` が `BASH_ENV` と同じ値で、Codex の役には入らないことを確かめる。環境変数の追加・上書き・モデルの切り替えは、`docs/agent-path.md` のとおり `tests/project-test.sh` で確かめる。

## 前提と限界

セットアップは、ひな形から作った確認用のファイルを使う。印のない既存の `env.sh` を残す導入先では、その中身を実際のランタイムで確かめる必要がある。関所や見張りが使えない実行の止め方と復旧方法は、`docs/agent-path.md` の「実行の始めの確認」に従う。

本物の `gh` を絶対パスで呼ぶことや、コマンドの中で PATH を書き替えることは止めない。`git push` の関所の動きも変えない。
