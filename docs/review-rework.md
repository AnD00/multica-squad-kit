# 差し戻しの往復を止め、安全に触れる設計を security も見直す

修正とレビューの往復が同じ部品で続くとき、リーダーが種類単位の依頼に切り替え、それでも続けば人間を呼んで止まるようにする。印 `重要` のあるタスクでも、修正の依頼が続けば人間に続けるかを聞く。レビューの役は、再確認で前に指摘した部品の周辺を列挙する。安全の仕組みに触れる設計は、実装の前に security-reviewer も見直す。

この文書は、4 つの変更の決まりと、その理由を書く。印と最上位の役の全体の設計は [principal-review.md](principal-review.md) を正本とし、この文書はそこへ足す決まりを書く。リーダーの原則は [leader-principles.md の原則](leader-principles.md#判断の優先の原則)にある。

## 目的と範囲

目的は、同じ部品の抜けを 1 件ずつ見つけて直す往復で、人間の時間と利用枠を使い続けることを防ぐことである。ある重要なタスクでは、修正の依頼が 5 回に達し、security の差し戻しが 4 回続いた。毎回、制御の記録を読む共通の関数の、別の入力の抜けだった。往復のあいだに、人間が止める判断をする機会も来なかった。

原因は 4 つあった。今の「同じ誤りが 2 回続いたら止まる」決まりは、同じ部品の別の抜けに当たらなかった。修正の依頼は、見つかった入力ごとの直しのままだった。印がすでにあるタスクでは、修正の依頼が 4 回目になっても止まらなかった。自由なコメントを信頼の根にする設計を、実装の前に security が読む場がなかった。

変えるのは次の 4 つである。それぞれの節に決まりを書く。

1. 同じ部品への指摘が 2 回続いたら、次の依頼を種類単位にし、3 回目で人間を呼ぶ（[同じ部品に指摘が続くとき](#同じ部品に指摘が続くとき)）
2. 安全の仕組みに触れる設計の見直しに、security-reviewer を加える（[安全の仕組みに触れる設計の見直し](#安全の仕組みに触れる設計の見直し)）
3. 印のあるタスクでも、修正の依頼の 4 回目の前と、そのあと 3 回ごとに人間に聞く（[印のあるタスクで修正の依頼が続くとき](#印のあるタスクで修正の依頼が続くとき)）
4. レビューの役の再確認で、前に指摘した部品の周辺を列挙する（[再確認での列挙](#再確認での列挙)）

次は対象にしない。

- 重要の基準（共通 1〜4）の追加・削除と、文言の変更
- 見張りのスクリプト `squad-review-wait` の変更。すでに複数の役の返事を待てるため
- 修正の役（`claude-fixer`・`codex-fixer`）の指示の変更。種類単位の直しは、依頼の文で頼む
- 再確認の頼み方を変えたら往復が 1 回で済んだかを、同じ入力で比べる実験。効果は、導入後のタスクで `列挙した範囲:` の行から見る

## 用語

この文書と、変える指示で使う語を次のとおり決める。

| 語 | 意味 |
| --- | --- |
| 部品 | 指摘の場所の、ファイルと関数、またはファイルと規則のまとまり。名前は `<ファイル>:<関数か規則の名前>` と書く。指摘に関数や規則の名前がなければ、ファイルの名前だけにする |
| 差し戻し | レビューの ❌、コンフリクト、CI の失敗で、修正の役へ戻すこと |
| 同じ誤り | 修正の役へ回した ❌ の指摘と、部品も、抜けていた入力や場合も同じ指摘が、その直しのあとにまた来ること。コンフリクトは、解消のあとにまた `CONFLICTING` になること。CI の失敗は、直しのあとに同じジョブが同じ原因で失敗すること |
| 同じ部品の指摘 | 前に修正の役へ回した ❌ の指摘と部品が同じで、抜けていた入力や場合が違う指摘 |
| 種類単位の依頼 | 1 件の入力の直しではなく、その部品が受ける入力の種類を列挙して扱いを決め、まとめて直す依頼 |
| 列挙 | 部品が受ける入力の種類と規則を挙げ、それぞれの扱いを確認すること |
| 入力と信頼の表 | 設計が読む入力ごとに、誰が書いた何を、どこで、どの条件で信頼するかを並べた表（[入力と信頼の表](#入力と信頼の表)） |

同じ誤りを先に当てはめる。同じ誤りに当たった指摘は、同じ部品の回数に数えない。コンフリクトと CI の失敗には部品がないので、同じ誤りの決まりだけで扱う。こうすると、1 件の指摘が当たる決まりは 1 つに決まり、2 つの決まりが同じ場面で違う動作を指さない。

指摘は ❌ だけを数える。⚠️ はマージを止めず修正の役へ回さないので、往復を作らないため。

## 同じ誤りが続くとき

今の「同じ誤りや差し戻しが 2 回続いたら、3 回目は頼まず」の文は残し、その文が同じ誤りの差し戻しだけを指すと `leader-flow.md` に書き足す。部品が違う差し戻しが 2 回続いても、この文では止めない。字のとおりに読むと、同じ部品の 2 回目を種類単位で頼む決まりと、同じ場面で違う動作を指すためである。

同じ誤りの回数は、修正の役へ回したあとに同じ誤りが来た数で数える。最初の指摘やコンフリクトは数えない。リーダーは、同じ誤りを頼み直す依頼に次の行を置く。

```text
同じ誤り: <部品の名前 | コンフリクト | CI の <ジョブの名前>> <N> 回目
```

N は、そのタスクのリーダーのコメントにある、同じ対象の `同じ誤り:` の行の数に 1 を足したものにする。N が 1 なら、今の決まりどおり原因を書いて頼み直す。N が 2 になる依頼は出さず、原因と再発を防ぐ手当てを添えて人間を呼ぶ。今の決まりの「1 回目は頼み直し、2 回続いたら 3 回目は頼まない」を、行で数えられるようにしたものである。

場面 5-1 では、解消の依頼（`修正の依頼: 1 回目`）のあとに、また `CONFLICTING` になる。これが同じ誤りの 1 回目なので、`同じ誤り: コンフリクト 1 回目` と `修正の依頼: 2 回目` の行を置いて頼み直す。5-1 の今の基準のとおりに通る。

同じ誤りを頼み直す依頼には、その指摘の `同じ部品:` の行を置かない。同じ部品の回数に数えないためである。

## 同じ部品に指摘が続くとき

同じ部品に指摘が 2 回来たら、リーダーは止めずに次の依頼を種類単位にする。種類単位で頼んだあとも 3 回目が来たら、それ以上頼まずに人間を呼ぶ。決まりは `leader-flow.md` の「同じ誤りや差し戻しが続くとき」に、同じ誤りの決まりと並べて書く。

### 回数の数え方と記録

リーダーは、修正の依頼のコメントに、回す ❌ の指摘の部品ごとに次の行を置く。1 回目から置く。

```text
同じ部品: <部品の名前> <N> 回目
```

N は、そのタスクのリーダーのコメントにある、同じ部品の名前の `同じ部品:` の行の数に 1 を足したものにする。部品の名前は、前の行にあれば、その名前を一字も変えずに写す。名前の揺れで数え直しにならないためである。人間とリーダーは、この行を数えれば、どの部品が何回目かを読める。

数えるのは、タスクの中の行のすべてで、連続した依頼だけではない。あいだに別の部品の依頼が挟まっても数え直さない。数え直すと、部品を交互に指摘される往復が止まらないためである。

### 2 回目の依頼

N が 2 になる部品があれば、リーダーはその修正の依頼に次の行を置き、種類単位で頼む。人間は呼ばない。

```text
頼む範囲: 種類単位（<部品の名前>）
```

依頼の文には、修正の役に次を頼む。修正の役の指示は変えず、依頼の文で頼む。

- その部品が受ける入力の種類と規則を表にし、種類ごとの扱いを決める
- 表の行ごとにテストを置く。テストは表を入力とする形（表に沿ったテスト）にし、表の場所を結果に書く
- 指摘された 2 件の入力も、表の行に含める

直したあとの再確認の依頼には、その部品を指摘したレビューの役に向けて次の行を置く。レビューの役は、この部品の周辺を 1 回で列挙する（[再確認での列挙](#再確認での列挙)）。

```text
列挙を頼む部品: <部品の名前>
```

### 3 回目で止まる

N が 3 以上になる部品があれば、リーダーは修正を頼まず、人間を呼んで `in_review` にする。呼ぶコメントには次の行を置き、あわせて次を書く。

```text
同じ部品の確認: <部品の名前> <N> 回目の前
```

- その部品への指摘。それぞれの結果へのリンクと 1 行の要点
- 2 回目に種類単位で頼んだ範囲と、修正の役が書いた表の場所
- 決めてほしいこと。続けて 1 回頼むか、設計を見直すか、やめるか。推す案と理由を添える

出してよい条件は、同じ部品で同じ N の `同じ部品の確認:` の行のあとに、人間の続ける返事があることである。そのとき、`同じ部品: <部品の名前> <N> 回目` の行で 1 回だけ頼む。その部品に次の指摘が来たら、N + 1 の確認の行を置いて、また止まる。

### 部品が違う指摘

部品が違う指摘が続くときは、今までどおり指摘ごとの依頼にする。どの部品も `同じ部品: <部品の名前> 1 回目` の行になる。

## 印のあるタスクで修正の依頼が続くとき

印 `重要` があるタスクでは、修正の依頼が 4 回目になる前に止め、続けるかを人間に聞く。続けたあとは、7 回目・10 回目と 3 回ごとの依頼の前に同じく聞く。印のないタスクの今の動作（4 回目の前に共通 4 で印を付ける）は変えない。

今の「すでにラベルがあるタスクでは判断を飛ばす」は、印を付けるかの判断を飛ばすだけにする。修正の依頼の数え方は、印の有無によらず数える。印がすでにあるタスクで、4 回目の前に止まる決まりが働かなかったためである。

止まる条件は、次の 3 つがそろうことである。止まるとき、リーダーは次の行を置き、人間を呼んで `in_review` にする。

1. ラベル `重要` がいまある
2. 次の `修正の依頼: <N> 回目` の N が 4 以上で、N − 1 が 3 で割り切れる
3. N − 1 個目の `修正の依頼:` の行より後に、リーダーが共通 4 で付けた `重要の印:` の行がない

```text
修正の続行の確認: <N> 回目の前
```

呼ぶコメントには、直前の 3 回の修正の依頼の要点（何の指摘で、どの部品か）を、依頼のコメントへのリンクと 1 行ずつで添える。決めてほしいことは、このまま続けるか、設計を見直すか、やめるかである。

出してよい条件は、同じ N の `修正の続行の確認:` の行のあとに、人間の続ける返事があることである。そのとき、`修正の依頼: <N> 回目` の依頼を出す。

3 つめの条件は、共通 4 で印を付けた直後の 4 回目を外すためのものである。印のないタスクは、4 回目の前に共通 4 で印を付け、設計と PR の見直しのあとに、止めた 4 回目を再開する。再開の時点では印があり N が 4 だが、その N の前に付けた印なので、確認せずに出す。そのタスクは 7 回目の前に、この確認で初めて止まる。

人間がラベルを外したタスクは、ラベルがないので、この確認では止まらない。タスクに `重要の印:` の行があるので、共通 4 で付け直すこともしない（`leader-principal.md` の「印の記録」の今の決まり）。

## 修正の依頼の前に確認する順

修正の役へ回す前に、リーダーは次の 1〜3 をすべて確認する。当たるものが 1 つでもあれば、頼まずに人間を呼び、当たったものを 1 つのコメントにまとめて書く。1 回の実行で書くコメントは 1 つという決まりを保つためである。1〜3 のどれにも当たらなければ、4 と 5 を順に見る。

1. 同じ誤りの N が 2 になる: 原因と手当てを添える（[同じ誤りが続くとき](#同じ誤りが続くとき)）
2. 同じ部品の N が 3 以上で、その N の確認を人間が通していない: `同じ部品の確認:` の行を置く
3. 印のあるタスクの続行の確認に当たり、その N の確認を人間が通していない: `修正の続行の確認:` の行を置く

4. ラベルがなく、タスクに `重要の印:` の行がなく、修正の依頼の N が 4: 共通 4 で印を付け、設計と PR の見直しを頼む（今の決まり）
5. どれにも当たらない: 頼む。N が 2 の部品は種類単位にする

2 と 3 が同じ実行で当たったときは、1 つのコメントで両方を聞く。人間の続ける返事は、そのコメントに置いたすべての確認の行を通す。人間を 2 回続けて呼ばないためである。1 に当たったときの人間の返事は、今の決まりどおり、手当てを選ぶか、続けて 1 回頼むかである。

人間を呼ぶ確認（1〜3）を、印を付ける 4 より先に見る。印のないタスクで 4 回目と同じ部品の 3 回目が重なったら、先に人間を呼ぶ。人間が続けると返した次の実行で、4 に当たって印を付ける。同じ部品の往復は、回数より早く止められ、止めたときに頼む範囲もはっきりするためである。

この順は `leader-flow.md` に置き、`leader-dispatch.md` の「印を確認する」文と `leader-principal.md` の「修正の依頼の数え方」から、この順へ案内する。

## 再確認での列挙

レビューの役と最上位の役は、再確認で、前の直しの確認に加え、前に ❌ で指摘した部品の周辺を列挙する。周辺とは、同じ規則と、同じ種類の入力である。初回のレビューと、前に指摘がない役の再確認の読み方は変えない。

レビューの 4 役（`code-reviewer`・`ux-reviewer`・`performance-reviewer`・`security-reviewer`）の指示の「受け取ったら最初に確認すること」に、次を置く。

- 同じ PR に自分の前の結果があれば、その指摘が直っているかを確認する
- 前の結果で ❌ を出した部品と、依頼の `列挙を頼む部品:` の行の部品は、同じ規則と同じ種類の入力を列挙して確認する

結果には、列挙した部品ごとに次の行を置く。PR の結果では先頭の 1 行と `確認したコミット:` のあとに置き、タスクに返す要約にも写す。

```text
列挙した範囲: <部品の名前>（<規則・入力の種類>）
```

最上位の役（`claude-principal`・`codex-principal`）は、最終レビューの再確認で同じことをする。今の「再確認は前の最終レビューからの差分だけを見る」は、次の一つの決まりにする。

- 読む差分は、依頼の `見る範囲:` の行のとおりにする
- 前の最終レビューで ❌ を出した部品は、差分の外でも、同じ規則と同じ種類の入力を列挙する。前の最終レビューは、どちらの最上位の役の結果でもよい

最上位の役は、どちらの系統が頼まれるかを前もって決めない。前の最終レビューを書いたのが別の系統でも、同じ役として周辺を見る必要があるためである。設計の見直しと、設計と PR の見直しの読み方は変えない。

列挙を ❌ の部品に限るのは、利用枠の増え方を、往復を生む指摘の分に抑えるためである。⚠️ は修正の役へ回らず、再確認で直しを見る対象にならない。

## 安全の仕組みに触れる設計の見直し

基準の共通 2（認証・権限・秘密の情報・関所など、安全の仕組みに触れる）に当たるタスクでは、設計の見直しを、最上位の役と security-reviewer の両方に頼む。security-reviewer を置かないスクワッドでは、最上位の役に入力と信頼の表の確認も頼む。

### 対象のタスク

次のどれかに当たるタスクを対象にする。どれにも当たらない印のタスクと、印のないタスクでは、security に設計を頼まない。

| 場合 | 対象と決める根拠 |
| --- | --- |
| リーダーが印を付けた | `重要の印:` の行の基準に `共通 2` がある |
| 人間が付けた印 | 最上位の役に設計の見直しか設計と PR の見直しを頼むときに、リーダーが共通 2 に当たると判断した |
| 設計の承認のときに新しく印を付けた | 付けたときの `重要の印:` の行の基準に `共通 2` がある |

### 印の記録の行

`重要の印:` の行は、当てはまる基準をすべて書く形にする。共通 1 と共通 2 の両方に当たるタスクで、共通 2 が記録から落ちないようにするためである。

```text
重要の印: 付けた。基準: <基準>（<基準の短い名前>）[、<基準>（<基準の短い名前>）…]。理由: <このタスクが当てはまる理由を 1 文>
```

人間が付けた印には基準の記録がない。リーダーは、そのタスクで初めて最上位の役に設計の見直しか設計と PR の見直しを頼むとき、共通 2 に当たるかを判断し、依頼のコメントに次の行を置く。行がすでにあれば、判断し直さない。

```text
共通 2 の判断: <当たる | 当たらない>。理由: <1 文>
```

前のバージョンで書いた、基準を 1 つだけ書いた行は、そのまま読む。その行に `共通 2` がなければ対象にしない。

### 入力と信頼の表

設計の役は、設計が安全の仕組みに触れるとき、または記録の行に `共通 2` があるときに、設計の文書に入力と信頼の表を置く。人間が付けた印の判断は設計が出たあとなので、記録の行を待たず、設計の中身で決める。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 例: タスクのコメントの `/note` の行（リーダー以外も書ける） | 返事がそろったかの判定 | 作者がそのタスクで頼んだ役で、依頼より後の時刻 | 読まずに飛ばし、記録に残す |

設計を見る役は、設計が認証・権限・秘密の情報・関所に触れるのに表がなければ、❌ にする。security-reviewer の有無によらず、最上位の役も見る。印を付けたあとに、設計が安全の仕組みに触れたと分かった場合も拾うためである。表の中身は、security-reviewer に頼んだときは security-reviewer が、置かないスクワッドでは最上位の役が確認する。

中身の確認では、表の行ごとに次を見る。最上位の役の指示にも同じ項目を書く。security を置かない形には、`security-reviewer.md` が展開されないためである。

- 入力の欄に、書き手が誰か（リーダーだけか、ほかの役や人間も書けるか）がある
- 読むところの欄に、その入力で決める判定や動作がある
- 信頼する条件に、書き手の確認（作者の ID や役）がある。書き手を選べない入力を、条件なしに信頼しない
- 合わないときの欄が、読まずに飛ばすか止まる動作で、合わない入力をそのまま使わない

### 頼み方と返事の待ち方

security-reviewer がいるスクワッドでは、リーダーは 1 つの依頼で 2 つの役に頼む。security-reviewer がいるかは、リーダーの指示の「このスクワッドの役」から読む。

- `squad-review-wait watch <タスク> <きっかけのコメント> <最上位の役の ID> <security-reviewer の ID>` を流す
- 依頼のコメントに、`見直しの種類: <設計の見直し | 設計と PR の見直し>`、2 つの役を並べた `返事を待つ役:`、`確認するコミット:` の行を置く。設計の承認のときやあとに印が付いたタスクでは、今の決まりどおり種類を `設計と PR の見直し` にする
- 返事は 2 つとも、今の `squad-review-wait proceed` で待つ。そろってから結果を扱う

security-reviewer がいないスクワッドでは、今のとおり最上位の役だけに頼み、依頼に次の行を足す。代わりの実行は足さない。

```text
入力と信頼の表の確認: 頼む
```

`leader-principal.md` の「最上位の役は 1 体だけを頼む」は、「最上位の役は 1 体だけを選ぶ」に直す。security-reviewer を同じ依頼に並べることを許し、最上位の役の選び方は変えないためである。

### 結果の扱い

両方の返事がそろったら、リーダーは見直しの種類ごとに扱う。どちらの種類でも、最上位の役には、今のとおり直した設計を見せ直さない。

**設計の見直し**: 次の順に扱い、最初に当たったもので決める。

| 結果 | リーダーがすること |
| --- | --- |
| 2 つの役の指摘が逆を求める | 設計の役に直しを頼まず、両方の指摘を添えて人間を呼び、どちらを採るかを決めてもらう。`in_review` にする |
| security に ❌ がある | 両方の結果へのリンクを添えて、設計の役に直しを頼む。依頼に `直したあとの返し先: スクワッド` の行を置く |
| ほかの ❌ か ⚠️ がある | 両方の結果へのリンクを添えて、設計の役に直しを頼む。設計の役は直したあと、今のとおり人間に承認を頼む |
| どちらも ✅ | 設計の役のコメントと両方の結果を示して、人間に承認を頼み、`in_review` にする |

**設計と PR の見直し**: 今の `leader-principal.md` の決まりを、2 つの役の結果に当てはめる。security-reviewer も、最上位の役と同じく指摘ごとに `設計` か `コード` を添える。security-reviewer の指示に、この種類の依頼でだけ添えることを書く。

| 結果 | リーダーがすること |
| --- | --- |
| 2 つの役の `設計` の指摘が逆を求める | 振り分けを止めたまま、両方の指摘を添えて人間を呼び、`in_review` にする |
| `設計` の指摘がある | 設計の役に直しを頼み、人間にもう一度承認してもらってから、止めた振り分けを再開する。security の `設計` の ❌ なら、依頼に `直したあとの返し先: スクワッド` の行を置き、見せ直しのあとに人間の承認を頼む |
| `コード` の指摘だけがある | 止めた修正の依頼に加えて、修正の役へ回す。実装のフェーズの前なら、該当するフェーズの依頼に添える |
| どちらも ✅ | 人間の承認を待たず、止めた振り分けを再開する |

逆を求めるとは、片方の指摘に従うと、もう片方の指摘を満たせないことである。片方だけに指摘があるときと、両方の指摘を同時に満たせるときは、人間を呼ばずに合わせて頼む。人間がどちらを採るかを決めたら、リーダーはその決定を添えて設計の役に直しを頼む。この直しは見せ直さず、設計の役が人間に承認を頼む。人間がすでに中身を決めているためである。

### 見せ直し

`直したあとの返し先: スクワッド` の依頼を受けた設計の役は、直したあと人間ではなくスクワッドへ返す。リーダーは、security-reviewer だけに直した設計を見せ直す。依頼の形は次のとおりにする。

- `squad-review-wait watch <タスク> <きっかけのコメント> <security-reviewer の ID>` を流す
- 依頼のコメントに、元の依頼と同じ `見直しの種類:` の行、`見せ直し: 1 回目` の行、security-reviewer だけの `返事を待つ役:` の行、直したコミットの `確認するコミット:` の行を置く

見せ直しの結果に ❌ がなければ、人間に承認を頼んで `in_review` にする。見せ直しでも ❌ なら、それ以上直しを頼まず、両方の結果を添えて人間を呼び、`in_review` にする。

見せ直しを security の ❌ に限るのは、利用枠を、安全の抜けを直した確認にだけ使うためである。⚠️ だけのときは、人間の承認で直しの妥当さを確認する。

### 役の指示の変更

役の指示は次のように変える。条件で出し分ける文は、`common/agents/FORMAT` の IF と ELSE で書く。

| 役 | 変えること |
| --- | --- |
| `security-reviewer` | 依頼が `見直しの種類: 設計の見直し` か `設計と PR の見直し` なら、設計の文書の差分を読み、入力と信頼の表を中心に見る。表がない、または信頼の条件が足りなければ ❌ にする。`設計と PR の見直し` では、指摘ごとに `設計` か `コード` を添える。見る観点に、入力と信頼の表を足す |
| `claude-principal`、`codex-principal` | 共通の部分に、設計が安全の仕組みに触れるのに入力と信頼の表がなければ ❌ にすることを書く。security-reviewer を置かないときだけ（`<!-- IF security-reviewer -->` の ELSE）、`入力と信頼の表の確認: 頼む` の行がある依頼で、表の中身を上の項目で確認することを書く |
| `designer` | 「ラベル `重要` のあるタスク」に、入力と信頼の表を置く条件と表の列を書く。`直したあとの返し先: スクワッド` の依頼では、直したあとスクワッドへ返すことを書く |

## 互換性と影響を受ける利用者

この変更は、役のひな形の内容と、手順書の動作を変える。影響を受けるのは、導入したプロジェクトの担当と、原本を導入・更新する人である。

セットアップを流し直すと、リーダー、設計の役、レビューの 4 役、最上位の役の指示と squad-handoff が入れ替わる。置いていない役の指示は配られない。エージェントとオートパイロットの登録は変わらない。増える役も、回答ファイルの項目もないためである。

変わる動作は次の 5 つである。

1. 同じ部品への指摘が 2 回続くと、種類単位の修正とテストの表を頼む。3 回目で人間が呼ばれる
2. 印のあるタスクで、修正の依頼の 4 回目の前と、そのあと 3 回ごとに、続けるかを聞かれる
3. レビューの役の再確認が、前に ❌ を出した部品の周辺まで読む。その回の実行は長くなる
4. 共通 2 の印のタスクで、設計の見直しに security-reviewer の実行が 1 回増える。security の ❌ を直したときは、もう 1 回増える
5. `重要の印:` の行に、基準が複数並ぶことがある

流し直しの前から動いているタスクでは、`同じ部品:` と `同じ誤り:` の行がない修正の依頼がある。新しいリーダーは、行のない依頼を数えず、次の依頼から数え始める。修正の依頼の回数は今の行で数えるので、印のあるタスクは、流し直しの直後でも 4 回目の前の確認が働く。

### CHANGELOG の知らせ

`CHANGELOG.md` の「次のバージョン」に、次の内容を段落で書く。先頭の段落を、人間が呼ばれる場面が増える知らせにする。

- 印 `重要` のあるタスクでも、修正の依頼の 4 回目の前と、そのあと 3 回ごとに、続けるかを聞かれる。同じ部品への指摘が 3 回目になったときも呼ばれる
- 同じ部品への指摘が 2 回続くと、リーダーは種類単位の修正と、規則の表に沿ったテストを頼む
- レビューの役と最上位の役は、再確認で前に ❌ を出した部品の周辺を列挙し、`列挙した範囲:` の行を書く
- 安全の仕組みに触れるタスク（基準の共通 2）では、設計の見直しを security-reviewer も行う。置かないスクワッドでは、最上位の役が入力と信頼の表を確認する
- セットアップを流し直すと、指示とスキルが入れ替わる。エージェントとオートパイロットの登録は変わらない。動いているタスクがないときに流し直す

## テスト

自動テストで、次を確認する。

- 展開したリーダーの手順に、差し戻し・同じ誤り・同じ部品の定義、確認する順、`同じ誤り:`・`同じ部品:`・`同じ部品の確認:`・`頼む範囲:`・`列挙を頼む部品:`・`修正の続行の確認:`・`共通 2 の判断:`・`入力と信頼の表の確認:` の行の決まりがある。今の語句（`修正の依頼: <N> 回目`、`同じ誤りや差し戻しが 2 回続いたら` など）も残る
- 展開したレビューの 4 役と最上位の役の指示に、再確認の列挙と `列挙した範囲:` の行がある
- security-reviewer を置く形と置かない形で、最上位の役の指示を描く。どちらの形にも表がないときの ❌ の文がある。置かない形にだけ `入力と信頼の表の確認:` の文と確認の項目があり、置く形にはない

- 文書の用語と改行の検査が通る

自動テストは、場面の形と一覧だけを確認し、リーダーの動作は確認しない。動作は、次の評価の場面で確認する。

評価は本物のモデルを呼び、使用上限を使い、全場面で数時間かかる。そのため、実装の役は評価を流さず、自動テストだけを流す。実装の役は、評価の場面を足したことを報告し、評価の受け入れ条件を満たしたとは報告しない。

リーダーが部品を見分ける判断と、指摘が逆を求めるかの判断は、評価の場面の `[採点]` の基準で確認する。

## 残る危うさ

部品の名前は、指摘の書き方によって揺れることがある。名前が揺れると、同じ部品が別の部品として数えられ、止まるのが遅れる。前の行の名前を写す決まりで揺れを減らし、関数の名前がない指摘はファイル単位で数えて、遅れより早めに止まる側に寄せる。

種類単位の依頼と列挙で、1 回の修正と再確認は長くなる。往復が 1 回で済むタスクでは、その分だけ利用枠が増える。

共通 2 の判断は、リーダーが付けた印では、付けたときの記録で決まる。印を付けたあとに設計が安全の仕組みに触れたと分かっても、記録に共通 2 がなければ security は設計を見ない。この場合は、最上位の役が表のないことを ❌ にできるが、表の中身は見ない。実装のあとのレビューでは、今のとおり security が見る。

security-reviewer を置かないスクワッドでは、最上位の役の表の指摘を直した設計を、見せ直す役がない。直しの妥当さは、人間の承認だけで確認する。

2 つの役の指摘が逆を求めるかは、リーダーの読みで決まる。読み違えて合わせて頼むと、設計の役が両立しない直しに迷い、人間に聞くことになる。その場合も、往復が 1 回増えるだけで止まる。

## 検討した案

- 同じ部品の 2 回目で止めて人間を呼ぶ案は選ばない。種類単位で頼めば往復が止まる見込みが高く、人間を呼ぶのは種類単位でも続いたときで足りるため
- 連続した依頼だけを数える案は選ばない。別の部品が挟まると数え直しになり、交互の往復が止まらないため
- ⚠️ の部品も列挙する案は選ばない。修正の役へ回らない指摘で、再確認を長くするだけのため
- 修正の役の指示に種類単位の直し方を書く案は選ばない。種類単位にするのはリーダーが決める場面だけで、依頼の文で頼めば足りるため
- 印のあるタスクで、続けたあとも毎回聞く案は選ばない。人間が続けると決めたあとに毎回呼ぶと、判断の手間が増えるため
- security を置かないスクワッドで、別の役に security の代わりの実行をさせる案は選ばない。最上位の役が設計の見直しと同じ回で表を見れば、実行を増やさずに済むため
- 指摘が食い違えば必ず人間を呼ぶ案は選ばない。多くの食い違いは両方を満たせ、人間を呼ぶのは逆を求めるときで足りるため
- 直した設計を、最上位の役にも見せ直す案は選ばない。今の決まりのとおり、最上位の役の指摘の直しは人間の承認で確認するため
- 印の記録を基準 1 つのままにし、共通 2 だけを別の行にする案は選ばない。記録の行が 2 つに分かれ、人間とリーダーの読む場所が増えるため
