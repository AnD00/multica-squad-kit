# 端末の画面の設計

セットアップ（`setup.sh`）と公開のコマンド（`scripts/release.sh`）が端末に出す画面の、共通の決まりと、セットアップの画面を書く。公開の画面は [タグと Release を出す仕組み](release.md#確認) に書き、この文書の共通の決まりを使う。使う人への説明は `manual.md` の「表示の色と印」と、セットアップの画面の各節に書く。

## 目的と範囲

画面の構造と状態を、見出しやラベルの文字ではなく、配置・余白・字下げ・配色・記号・進行の表示で伝える。npm、brew、gem のような CLI の表示を見慣れた人が、説明の文字を読まずに、今どこにいて、通ったか失敗したかを見分けられるようにするためである。

文字で出すのは、値（名前、バージョン、SHA、URL、件数、かかった時間など）と、手順の動作そのもの（例: タグを push）と、確認の問いだけにする。「成功」「一致」「作成」「新規」「既存」のような状態を表す結果の語と、「すること:」「リポジトリ:」のような構造を説明する文字は出さない。止まるときの `エラー:` の行と、その文は今のまま変えない。

変えるのは見せ方だけである。セットアップの質問の流れ、答えの確かめ、保存する答え、作るもの・直すもの、確認の答え方、終了コードは変えない。公開のコマンドの流れと約束も変えない。

## 記号と色

記号ごとに意味と色を一つに決め、両方の画面で同じに使う。色は `lib/ui.sh` の今の 8 色のまま足さない。

| 記号・部分 | 意味 | 色 |
| --- | --- | --- |
| `✔` | 通った、作った、今あるものを確かめた | 緑（28） |
| `✖` | 失敗した | 太字の赤（196） |
| スピナー（`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`）、ゲージの進んだ部分 `━` | 動いている | 青（32） |
| `?`、`›` | 今の問い、入力の行、次にすること | 青（32） |
| `●` | 質問の進みの、答えた分と今の質問 | 青（32） |
| `○` と手順の名前 | まだの手順 | 灰（244） |
| `○`（質問の進み） | まだの質問 | 灰（244） |
| `│` | Release の本文の範囲を示す左の罫線 | 灰（244） |
| ゲージの残りの部分 `─` | まだの分 | 灰（244） |
| 添える値 | 補足の値（パス、件数と時間、名前の規則、理由） | 灰（244） |
| `+` | 新しく作る、新しく起票した | 緑（28） |
| `~` | 今あるものを直す | 既定の色 |
| `·` | 今あるものをそのまま使う、飛ばした | 灰（244） |
| `!` | 確かめが要る、変えずに残す、記録がない | 太字の橙（166） |
| `-` | 外す、一時停止する | 灰（244） |
| `…` | 端末でない出力で、待っている手順の経過の行 | 灰（244） |
| `→` | 公開すると変わる下書きの URL の、変わったあとの URL | 灰（244） |
| 完了の印 `✔` と、続く名前やバージョン | 全体が終わった | 太字の青緑（30） |
| 選択肢の番号 | 選べる番号 | 太字の紫（98） |

色が出ない環境（`NO_COLOR`、端末でない出力、`TERM` が空か `dumb`、256 色未満）では、色を付けず、同じ記号と配置だけで状態が分かるようにする。この判定は `lib/ui.sh` の `ui_init` の今の判定を出力先ごとに使い、変えない。

行の書き換え（スピナー、ゲージ、質問を縮めること、一覧の印を変えること）は、出力先が端末で、色が出るときだけ行う。`NO_COLOR` を付けた人は動く表示も望まないとみなし、端末でない出力と同じに、書き換えずに行を順に出す。書き換えに使う制御文字は、カーソルを上へ動かす `ESC[nA`、行を消す `ESC[2K`、画面の下まで消す `ESC[J`、行の頭へ戻す `\r` に限る。カーソルの位置の保存と復元は、画面が流れると位置がずれるので使わない。

## 表示の部品（lib/ui.sh）

両方の画面は、`lib/ui.sh` の部品だけで記号・色・書き換えを出す。呼び出す側は記号の文字と色の番号を持たず、意味の名前で呼ぶ。bash 3.2 で動かし、今の `ui_init`、`ui_paint`、`ui_line`、`ui_error`、`ui_warning` は残す。結果の語を色に写す `ui_result` は、公開のコマンドとセットアップ（`lib/project.sh`、`lib/installation.sh`、`lib/webhooks.sh`）の呼び出す側をすべて移したあとで外す。途中で外すと、移していない画面が動かなくなるため。

### 色の種類

`ui_kinds` に `active`（青、太字なし）と `strong`（太字、色なし）を足す。`active` はスピナー、ゲージの進んだ部分、`●`、`›` に使う。今の `question` は太字の青なので、問いの `?` と題に使い分ける。`strong` は、色の意味を持たせずに目を引く語に使う。ほかの 8 種類の色と太字は変えない。

| 種類 | 太字 | 色 | 使うところ |
| --- | --- | --- | --- |
| `question` | 太字 | 32 | 問いの `?` と題 |
| `active` | なし | 32 | スピナー、ゲージの進んだ部分、`●`、`›` |
| `strong` | 太字 | なし | 公開の見出しのバージョン、完了の表示の種類の名前と、次に流すコマンド |
| `description` | なし | なし | 本文、`~` の行 |
| `choice` | 太字 | 98 | 選択肢の番号 |
| `default` | なし | 244 | 灰の記号と値 |
| `success` | なし | 28 | `✔`、`+` |
| `warning` | 太字 | 166 | `!` |
| `error` | 太字 | 196 | `✖` |
| `done` | 太字 | 30 | 完了の印と名前 |

### 書き換えの判定

`ui_init` は、出力先ごとの色の判定に加えて、書き換えてよいかを `ui_live_out` と `ui_live_err` に置く。出力先が端末で色が出るときだけ `yes` にする。入力を読む画面（質問と確認）は、標準入力も端末であることを加える。テストは、疑似端末と環境変数で両方の場合を流す。

### 記号の行

| 関数 | 出すもの |
| --- | --- |
| `ui_mark <out\|err> <印> <本文> [値]` | 印と本文と灰の値を 1 行に出す。印は `ok`、`fail`、`add`、`change`、`keep`、`warn`、`drop`、`todo` の名前で渡し、上の表の記号と色にする |
| `ui_pad <幅> <本文>` | 表示の幅で数えて、本文の後ろを空白で埋める。全角の文字を 2 として数える |
| `ui_width <本文>` | 本文の表示の幅を返す。bash だけで、UTF-8 のバイトから文字ごとの符号位置を組み立て、東アジアの全角の範囲を 2、ほかを 1 とする |
| `ui_size <out\|err>` | その出力先の端末の高さと幅を読み、`ui_lines` と `ui_columns` に置く。読み方は[端末の大きさの読み方](#端末の大きさの読み方)のとおりにする |
| `ui_rows <本文>` | 本文が端末で占める行の数を返す。`ui_width` を、最後に `ui_size` で読んだ幅で割って切り上げる。まだ読んでいなければ、`ui_size err` で読む |

幅は外の道具を使わずに数える。公開のコマンドは `jq` を要る道具にしておらず（値は `gh --jq` で読む）、幅のために道具を足すと、今まで公開できた環境で止まるため。数え方は次のとおりにする。

- 関数の中だけ `LC_ALL=C` にし、本文を 1 バイトずつ読む。`printf '%d' "'<バイト>"` で値を読み、先頭のバイトから 1〜4 バイトの文字を組み立てる。bash 3.2 の `printf -v` で、子のプロセスを起こさずに数える
- 幅 2 とする範囲は、U+1100–115F、U+2E80–A4CF、U+AC00–D7A3、U+F900–FAFF、U+FE30–FE4F、U+FF00–FF60、U+FFE0–FFE6 と、4 バイトの文字とする。`✔`、`●`、`│`、`━`、スピナーの点字のような記号は幅 1 になる
- UTF-8 として読めないバイトは、幅 1 として数える。止まらずに出すため

### 端末の大きさの読み方

端末の大きさは、書き換える出力先の端末から `stty size` で読む。macOS の `tput` は、出力をパイプへつなぐと、実際の大きさではなく端末の定義の 80 桁・24 行を返し、変数に受けるコマンド置換もこれに当たるため。この読み方では、低い端末を 24 行とみなし、大きさが変わっても同じ値を読み続ける。

- 出力先の fd を標準入力に渡して `stty size` を流す（`out` は `<&1`、`err` は `<&2`）。`stty` の出力は変数に受けてよい。読むのは標準入力の端末なので、コマンド置換の中でも実際の大きさが返る
- `stty` が失敗したとき、または行か桁が正の整数でないときは、`tput lines` と `tput cols`、次に `LINES` と `COLUMNS`、次に 24 行と 80 桁へ進む。行と桁は、それぞれ正の整数が得られたところで決める
- `ui_size` は、値を変数に置き、標準出力には出さない。コマンド置換の中では標準出力がパイプになり、`out` の端末を読めなくなるため。書き換える部品は、`ui_size` を今のシェルで呼ぶ
- チェックリストと質問の場面、`ui_rows` は、この読み方を共用する。文字の幅は、上のとおり bash だけで数え、`stty` は大きさを読むためだけに使う

### チェックリスト

手順の一覧を出し、同じ一覧の印をその場で変えていく部品である。1 つの出力先（`out` か `err`）に出し、一覧のあいだにほかの行を混ぜない。手順の行の下に添える行（URL、入れ子の確かめ、`!` と `-` の行）は `ui_step_line` で足し、手順の行と一緒に書き換える。一覧のあいだに出る警告は、`ui_warning` で直接出さず、`ui_step_line warn` で、その手順の下の `!` の行にする。

| 関数 | 動き |
| --- | --- |
| `ui_steps_begin <out\|err> <字下げ> <名前…>` | 手順の名前を覚える。書き換えるときは、すべての手順を `○` と灰の名前で並べる。書き換えないときは何も出さない |
| `ui_steps_show` | 書き換えるかによらず、今の一覧を出す。公開の画面で、確認の問いの前に一覧を出すときに使う |
| `ui_step_start <番号>` | その手順を動いている印にする。書き換えるときは、スピナーを 0.1 秒ごとに回す |
| `ui_step_progress <済んだ数> <全体の数> [名前] [nocount]` | 動いている手順の行に、ゲージと `済んだ数/全体の数` と、灰の名前を出す。4 つ目に `nocount` を渡すと、`済んだ数/全体の数` を出さず、ゲージと名前は残す。件数を読めても画面に出したくないとき（公開の画面の、ワークフローのステップの割合）に使う。次の手順を始めると、件数は元に戻る |
| `ui_step_wait <経過の秒>` | 動いている手順の行に、経過の時間を出す。書き換えないときは、決まった間隔でだけ 1 行を足す |
| `ui_step_done <値>` | その手順を `✔` にし、灰の値を添える。書き換えないときは、この行を 1 行出す |
| `ui_step_fail [名前]` | その手順を `✖` にし、扱っていた名前を灰で添える。書き換えないときも、この行を出す |
| `ui_step_line <印\|-> <本文> [値]` | 今の手順の行の下に、手順より 2 桁深く字下げした行を足す。印は `ui_mark` と同じ名前で、`-` を渡すと印を付けない。書き換えないときは、その手順の行のあとに出す |

書き換えるときは、書き換える範囲の行の数を数えておき、カーソルをその数だけ上へ動かして、範囲の行を出し直す。範囲は、まだ終わっていない最初の手順の行から、一覧の下に出した行までとする（[画面に収まらないとき](#画面に収まらないとき)）。行の数を数え違えても前の画面を消しすぎないよう、上へ動かすのは自分が出した行の数までにする。スピナーは、手順を動かすあいだだけ裏で回し、`ui_step_done` か `ui_step_fail` か、終わりの片付けで止める。止めたあとは、カーソルを一覧の下に置く。

スピナーは、起動前に親が置いた稼働中の印を消して止め、子の終了を待ってから次へ進む。子に停止のシグナルを送らず、子では親の後片付けの trap を外し、一覧の片付けも一覧を始めたプロセスだけが行う。

サブシェルに表示を渡す呼び出し側は、子を起こす前に自分が起動したスピナーを止めて終了を待つ。子では親の子プロセスを待てず、同じ稼働中の印を作り直すと古いスピナーが動き続けるため。

ゲージは幅 18 の `━`（進んだ分）と `─`（残り）で描く。件数の分かる手順は済んだ数の割合で、件数の分からない待ちは、呼ぶ側が割合を渡す。

時間は `48s`、`1m12s` の形で書く。60 秒未満は秒だけ、それ以上は分と秒にする。

### 画面に収まらないとき

書き換えは、画面に見えている行の中だけで行う。カーソルは画面の上に流れた行へは戻れないので、書き換える範囲が画面の高さを超えると、消し残しや、出し直しによる行の積み重ねが起きるため。

- 端末の大きさは、書き換える出力先について `ui_size` で読む（[端末の大きさの読み方](#端末の大きさの読み方)）。書き換えるたびに読み直す
- チェックリストの手順は上から順に終わるので、終わった手順の行と続きの行は、終わったときに切らずに出し、それ以上書き換えずに画面に残す。書き換える範囲は、まだ終わっていない最初の手順の行から下だけになる
- 書き換える範囲の行（動いている手順、まだの手順、一覧の下の行）は、端末の幅から 1 を引いた幅で切り、切ったところに灰の `…` を付ける。1 行がいつも画面の 1 行になり、折り返しで行の数がずれないようにするため。`✖` で止まったときの描き直しは切らずに出す
- それでも書き換える範囲が、端末の高さから 1 を引いた行の数を超えるときは、そこで書き換えをやめる。今の一覧を切らずに 1 回出し直し、それより後は、書き換えないときと同じに行を足していく
- 書き換えのあいだに端末の大きさが変わったときも、同じに書き換えをやめる。大きさが変わると、端末が前の行を折り返し直し、数えた行の数が合わなくなるため。前の描画が画面に残ることはあるが、自分が出した行より上は消さない

スピナーの裏のプロセスも、回すたびに同じ出力先について `ui_size` で大きさを読み、変わっていれば回すのをやめて、表のプロセスに書き換えをやめさせる。

## 質問の場面

答えた質問を `✔ 題  答え` の 1 行に縮め、今の質問だけを開いて見せる。答えた内容が上に一覧で残り、今の質問は位置と `?` で分かる。

```text
✔ ワークスペース        acme
✔ プロジェクト          Demo Project  新しく作る
✔ プロジェクトの区別    demo

? リポジトリ  ●●●●○○○○○
  このプロジェクトのエージェントが作業し、書き込める場所です。選んだものだけに push と PR ができ、複数選べます。
  1 3、または 1,3
    1  acme/web
    2  acme/api
    3  acme/docs
› 1 3
```

- 開いた質問は、`?` と太字の題、2 つの空白、進みの `●○` の順に出す。`●` は答えた質問と今の質問の数、`○` は残りの数で、全体は `question_order` の 9 問とする
- 説明と例は、2 つの空白で字下げした灰の行にする。例は `例:` を付けず、例の値だけを出す
- 選択肢は 4 つの空白で字下げし、太字の紫の番号、2 つの空白、本文の順に出す。番号で選ぶ入力のしかたと、0 の選択肢は変えない
- 入力の行は `›` と空白にする。既定値があれば、入力の前に灰で出す。Enter で既定値を使うことは変えない。既定値のない質問は、`›` だけを出す
- 常に入る役と外せる役の説明、選んだ値の注意（今の `question_notice`）は、説明の下に、同じ字下げで出す。注意は `!` の行にする
- 入力を受け付けなかったときは、入力の行の下に `✖` と理由の行を出し、同じ質問の入力の行をもう一度出す。今の `エラー:` は付けない

答えると、開いた質問の行（題から入力の行まで）を消し、`✔`、題、答えの 1 行に置き換える。題は 9 問の中で最も長い題の幅にそろえ、答えのあとに灰の補足（`新しく作る`、`今あるものを使う` など、今 `plan_action` が出す文）を添える。答えが複数のときは、2 つの空白で区切って 1 行に並べる。飛ばす質問（今の `question_skip`）は、`·` と題と灰の理由の 1 行にする。

縮める行の数は、開いた質問を出すときに、`ui_size err` で大きさを読んでから `ui_rows` で数えておく。入力の行は、`›` と打たれた答えの幅を、そのときの端末の幅で割って、折り返した行の数で数える。入力を受け付けずにもう一度聞くときは、理由の行と入力の行も数えに入れ、答えたときにまとめて消す。

開いた質問の行の数が、端末の高さから 1 を引いた数を超えるとき（選択肢が多い、端末が低い、狭くて説明が折り返すなど）と、答えるまでに端末の大きさが変わったときは、その質問を縮めない。書き換えないときと同じに、入力の行のあとへ答えの `✔` の行を 1 行足す。次の質問からは、また縮める。質問の行は切らずに出すので、[画面に収まらないとき](#画面に収まらないとき)の切り方は使わない。

書き換えないときは縮めず、開いた質問を順に出す。入力の行のあとに、答えの `✔` の行を 1 行足す。説明や記号の形は、書き換えるときと同じにする。

| 今の出力 | 変えたあと |
| --- | --- |
| `質問 (3/9) リポジトリ` | `? リポジトリ  ●●●○○○○○○` |
| 説明の行 | 灰の説明の行（字下げ 2） |
| `例: demo、shop` | 灰の `demo、shop`（字下げ 2） |
| `1: acme/web` | 紫の `1`、`acme/web`（字下げ 4） |
| `既定値: 1 3（Enter で使います）` と `入力 [1 3]:` | `›` と空白と灰の `1 3` |
| `既定値: なし。例と説明を見て入力してください。` | `›` と空白だけ |
| `質問 (n/N) 題: 理由` | `· 題  理由` |
| `エラー: …`（入力の誤り） | `✖ …` |

## 答えの一覧

答えは質問の場面の `✔` の一覧に残るので、答えの一覧では繰り返さない。これから作るもの・直すものだけを、ものの種類ごとにまとめ、名前ごとに頭の記号で示す。

```text
  エージェント
    + demo-orchestrator-member1
    + demo-planner-member1
    ~ demo-claude-implementer-member1
  スクワッド
    + DEMO-MEMBER1
  スキル
    · demo-verify
  リポジトリ
    + acme/web
    · acme/docs
  オートパイロット
    + 週 1 回の依存ライブラリの脆弱性チェック demo acme/web
    + 使用上限の見張り demo-member1
    ! Dependabot の PR の週次の確認 demo acme/docs  別の担当
  役
    - designer  demo-designer-member1

  +14  ~3  ·2  !1  -1
? 保存して作りますか  yes/no
› no
```

種類の名前は、2 つの空白で字下げした太字にする。ものの種類を示す語として残し、ラベルの `:` は付けない。名前の行は 4 つの空白で字下げし、記号、空白、名前、灰の補足の順にする。種類の中に行がないときは、種類の名前も出さない。

| 種類 | 名前と記号の決め方（今の `confirmation_plan` の行） |
| --- | --- |
| エージェント | 役ごとの完成名。今あるものがなければ `+`、あれば `~` |
| スクワッド | スクワッドの名前。`plan_action` が新しく作るなら `+`、今あるものを使うなら `~` |
| スキル | プロジェクトだけのスキルの名前。新しく作るなら `+`、今あるものを使う（内容は保持）なら `·` |
| リポジトリ | 選んだリポジトリ。新しくプロジェクトへ紐付けるなら `+`、既存の紐付けを使うなら `·`。紐付け専用のリポジトリは、灰の補足 `紐付けだけ` を添える |
| オートパイロット | オートパイロットの題。`plan_autopilot_action` が新しく作るなら `+`、今あるものを直すなら `~`、今あるものを保持（別の担当またはプロジェクト）なら `!` と灰の `別の担当` |
| 人間 | スクワッドに入れる人間の名前。まだスクワッドにいなければ `+`、いれば `·` |
| 役 | 外す役。`-`、役の名前、灰の、一緒に外れるもの（今の `role_choice_text`） |

サーバー、ワークスペース、プロジェクト、使うランタイム、Dependabot の PR の Webhook は、質問の場面の `✔` の行に答えがあるので、答えの一覧には出さない。外れた拡張の役（エージェントは残す）は、`役` の種類に `-` と灰の `エージェントは残す` で出す。

最後に空行を置き、記号ごとの件数を、2 つの空白で字下げした 1 行に出す。件数が 0 の記号は出さない。件数の記号は、名前の行と同じ色にする。

問いは `? 保存して作りますか` と灰の `yes/no`、入力の行は `›` と空白と灰の既定値 `no` にする。`yes` で続け、`no` か Enter で中止し、ほかの答えはもう一度聞くことと、中止したときの文と終了コードは変えない。もう一度聞くときは、質問の場面と同じく `✖` の行を出す。

答えの一覧は、書き換えるかによらず、同じ行を順に出す。書き換えるのは、問いの入力を受け付けなかったときの `✖` の行と入力の行だけである。

## 作成の進み

`yes` のあと、流す手順をすべて `○` で並べ、同じ一覧の印を、スピナー、`✔` の順に変えていく。1 件ごとの行と、`ホストを準備しています。` のような文は出さない。

```text
? 保存して作りますか  yes/no
› yes

  ✔ ホストを準備                ~/.squad-kit/agents/bin/gh  ~/.squad-kit/agents/git-hooks/pre-push
  ✔ 共通のラベルとスキル
  ✔ プロジェクトとリポジトリ    Demo Project  acme/web  acme/docs
  ✔ エージェントの ID            12  4s
  ✔ スクワッド                  DEMO-MEMBER1
  ✔ 指示とスキル                12  2s
  ⠹ エージェントを設定          ━━━━━━━──────────── 5/12  demo-designer-member1
  ○ エージェントを公開
  ○ スクワッドのメンバー
  ○ オートパイロット
  ○ Webhook
  ○ 導入の確認
  ○ タスクの起票
```

一覧は標準エラーに出し、2 つの空白で字下げする。手順の名前は、最も長い名前の幅にそろえ、値はそのあとに灰で添える。手順は次の 13 とし、流すかによらず、いつも同じ並びで出す。

| 番号 | 手順 | 今の処理 | 動いている間 | 終わったときの値 |
| --- | --- | --- | --- | --- |
| 1 | ホストを準備 | `prepare_host` | スピナー | 関所のパス（gh、git push、使うなら Codex の設定） |
| 2 | 共通のラベルとスキル | `prepare_workspace` | スピナー | なし。更新を飛ばしたスキルは `!` の行 |
| 3 | プロジェクトとリポジトリ | `prepare_project` の、プロジェクトの用意、`prepare_project_host`、`project_resources` | スピナーと、確かめているリポジトリ | プロジェクトの名前と、許すリポジトリ。許すリポジトリから外したものは `-` の行 |
| 4 | エージェントの ID | 役の定義の確かめ、既存の設定の確かめ、ID の準備 | ゲージ、`n/N`、名前 | 件数と時間 |
| 5 | スクワッド | スクワッドの用意 | スピナー | スクワッドの名前 |
| 6 | 指示とスキル | 指示の展開と確かめ、`project_skills` | ゲージ、`n/N`、名前 | 件数と時間 |
| 7 | エージェントを設定 | エージェントの設定 | ゲージ、`n/N`、名前 | 件数と時間 |
| 8 | エージェントを公開 | 公開の設定 | ゲージ、`n/N`、名前 | 件数と時間 |
| 9 | スクワッドのメンバー | `complete_project` の、スクワッドの指示とメンバー | スピナー | メンバーの数 |
| 10 | オートパイロット | `sync_project_autopilots` | ゲージ、`n/N`、題 | 件数と時間。保持したものは `!`、一時停止したものは `-` の行 |
| 11 | Webhook | `prepare_project_webhooks` | スピナーと、リポジトリ | リポジトリの数。使わない答えなら値なし |
| 12 | 導入の確認 | `verify_project_installation` | スピナー | 確かめた項目の数 |
| 13 | タスクの起票 | `prepare_project_issues` | スピナー | 起票した件数を `+n` で |

手順 3 の関所の確かめ（今の `許可の確認: …: 成功` の行）と、手順 10 の保持と一時停止の行は、1 件ごとに積まず、上の値と `!`・`-` の行にまとめる。答えの一覧で示した `!` と `-` を、作ったあとにも同じ記号で残すためである。

失敗したときは、動いていた手順を `✖` にし、扱っていた名前（エージェント、題、リポジトリ）を灰で添える。そのあと、今と同じ `エラー:` の行を出し、今と同じ終了コードで止まる。`setup.sh` の `die` は、チェックリストが動いていれば `ui_step_fail` を呼んでから、今の `ui_error` を呼ぶ。チェックリストの前に止まるときは、今のまま `ui_error` だけを出す。

書き換えないときは、`○` の一覧を出さず、終わった手順の行を `✔ 手順  値` の形で順に出す。ゲージと 1 件ごとの名前は出さない。失敗したときは `✖ 手順  名前` の行を出してから、`エラー:` の行を出す。

## 完了の表示

公開の終わりの表示と同じ形で、すべての項目を印で並べる。見出しは付けず、空行と字下げで分ける。完了の表示は、今と同じく標準出力に出す。

```text
✔ Demo Project  demo-workspace  +9 エージェント  +1 スクワッド  +3 オートパイロット

  ✔ claude-runtime
  ✔ codex-runtime
  ! squad-kit-skills  スキルのバージョンが原本と違う

  and00/app      ✔ トリガー  ✔ 登録  ✔ 配信 200
  and00/infra    ✔ トリガー  · 登録  ! 配信
  ! and00/old  Webhook を使わない答えですが、前の実行で作った Webhook のトリガーが残っています。外すよう起票しました。

  + DEMO-1  and00/app の Dependabot の Webhook のフィルターを設定する
  · DEMO-3  プロジェクトの説明と検証スキルを記入する
  ✖ 導入の確認で要確認になった項目を直す  HTTP 500

  › 表示したタスクを対象のプロジェクトで開き、担当と本文に沿って作業してください。
  › ひな形の記入は skeleton/ の案内を参照してください。
  › エージェント用のログインが切れた場合は、次を実行してから bash setup.sh を流し直してください。
      CLAUDE_CONFIG_DIR=~/.squad/claude claude
      CODEX_HOME=~/.squad/codex codex login
```

| 塊 | 今の関数 | 形 |
| --- | --- | --- |
| 1 行目 | `project_completion` | 太字の青緑の `✔` とプロジェクトの名前。灰で、ワークスペースの名前（なければ ID）と、今回作った件数を種類ごとに `+n 種類` で添える。0 の種類は出さない |
| 導入の確認 | `project_installation_completion` | 項目ごとに、問題がなければ `✔` と名前、要確認なら `!` と名前と灰の理由 |
| Webhook | `project_webhook_completion` | リポジトリごとに 1 行。リポジトリの名前をそろえ、トリガー・登録・配信を印と語で並べる。作ったものと既存のものは `✔`、飛ばした登録は `·`、記録のない配信は `!` だけで値を付けず、失敗は `✖`。配信の HTTP コードは灰で添える |
| Webhook の残り | `project_webhook_completion` | 今の `警告:` の行を、`!`、リポジトリ、今の文の行にする |
| 起票したタスク | `project_issue_completion` | 新しく起票したものは `+`、既存のものは `·` と灰の行で、識別子と件名。起票できなかったものは `✖`、件名、灰の理由 |
| 次にすること | `project_completion` | 今の案内の文を、それぞれ `›` と空白を付けた行にする。入り直すコマンドは、6 つの空白で字下げした太字の行にする |

Webhook の行の `トリガー`、`登録`、`配信` は、印の対象を示す名前として残す。配信の記録がないことは、HTTP コードを付けない `! 配信` で示し、`記録なし` の語は出さない。HTTP コードのない失敗は、`✖` と語だけにする。

塊に行がないとき（Webhook を使わない、起票したタスクがないなど）は、その塊と前の空行を出さない。起票が失敗しても完了の表示を出し、終了コードを 0 以外にすることは変えない。

書き換えるかによらず、完了の表示は同じ行を順に出す。色が出ないときは、同じ記号と配置で出す。

| 今の出力 | 変えたあと |
| --- | --- |
| `プロジェクトの設定が終わりました: 名前（ワークスペース）` | `✔ 名前  ワークスペース  …` |
| `今回作った件数: エージェント 9 件、…` | 1 行目の灰の `+9 エージェント  …` |
| `導入の確認:` と `名前: 一致` / `要確認` | 見出しなし。`✔ 名前` / `! 名前  理由` |
| `Webhook の登録:` と `作成`・`既存`・`飛ばした`・`成功（HTTP n）`・`失敗（HTTP n）`・`記録なし` | 見出しなし。`✔`・`·`・`✖`・`!` と灰の HTTP コード |
| `起票したタスク:` と `（新規）`・`（既存）` | 見出しなし。`+`・`·` |
| `起票できなかったタスク:` と `題: 理由` | 見出しなし。`✖ 題  理由` |
| `次にすること:` | 見出しなし。`›` と空白の行 |

## 変えないもの

- 質問の順、答えの確かめ、保存する答え、選択肢の番号の入力のしかた、Enter で既定値を使うこと
- 確認の答え方（`yes` で続け、`no` か Enter で中止）と、中止したときの文と終了コード
- 作るもの・直すもの、エージェント・スクワッド・オートパイロットの登録、起票するタスクとその本文
- 止まるときの `エラー:` の行と文、終了コード
- チェックリストの前に出る警告（ホストの道具の確かめなど）の `警告:` の行
- 標準出力と標準エラーの使い分け。質問、答えの一覧、作成の進みは標準エラー、完了の表示は標準出力に出す

## テスト

セットアップのテストは、今の答えを流し込むテストのまま、期待する画面の文字を新しい形に直す。答えと、作るもの・直すもの・起票するタスクの照合は変えずに通すことで、見せ方だけを変えたことを確かめる。

| 確かめること | テスト |
| --- | --- |
| 記号と色の割り当て、`active` と `strong` の色、色が出ない環境 | `tests/ui-test.sh` |
| 表示の幅（全角、記号、UTF-8 として読めないバイト）を、`jq` を PATH から外して数えること | `tests/ui-test.sh` |
| 端末の大きさを出力先の端末から読むこと。`tput` が 80 桁・24 行を返す偽物でも、疑似端末の 40 桁・10 行を読み、大きさを変えたあとは変えた値を読むこと。`stty` が失敗したときに `tput`、`LINES` と `COLUMNS`、既定値の順に進むこと | `tests/ui-test.sh` と、疑似端末の補助（`tests/ui-pty.py` の大きさを変える指定） |
| 画面に収まらないとき。低い端末（10 行）と狭い端末（40 桁）での切り方、終わった行を残すこと、書き換えをやめること、途中で大きさを変えたときにやめること | `tests/ui-test.sh` と、疑似端末の補助（`tests/ui-pty.py` の大きさを変える指定） |
| 書き換えの判定（端末、色、`NO_COLOR`）と、チェックリストの書き換え、スピナーの片付け | `tests/ui-test.sh` と、疑似端末の補助（`tests/ui-pty.py`） |
| 質問を縮めること、`●○` の進み、出さない文字（`質問 (`、`例:`、`既定値:`、`入力`）、入力の誤りの `✖` | `tests/questions-ui-test.sh` |
| 書き換えないときに縮めず順に出すこと | `tests/questions-ui-test.sh` |
| 高さを超える質問と、途中で大きさが変わった質問を縮めないこと、折り返した入力の行を消し残さないこと | `tests/questions-ui-test.sh` と、疑似端末の補助 |
| 答えの一覧の種類と記号と件数、出さない見出しとラベル、`yes`/`no`/Enter の動きと終了コード | `tests/setup-test.sh`、`tests/role-choices` の系、`tests/runtime-selection` の系 |
| 作成の進みの手順の並び、値、1 件ごとの行と文が出ないこと、失敗の `✖` と名前 | `tests/project-*` の系、`tests/host-test.sh`、`tests/error-marks-test.sh` |
| 完了の表示の形、出さない見出しと結果の語（`記録なし` を含む）、`!` と `✖`、起票の失敗の終了コード | `tests/completion-colors-test.sh`、`tests/project-issues-test.sh`、`tests/webhooks-test.sh` |
| 同じ答えで、保存する答え・登録・起票が変わらないこと | 今のセットアップのテストの照合をそのまま通す |
| `manual.md` の記述と出力の一致 | `tests/manual-test.sh` |

画面の文字の照合では、色の制御文字を外した文字で比べ、色は `ui-test.sh` で別に確かめる。書き換える画面は、疑似端末で流し、最後に端末に残る行を照合する。残る行は、画像の描き方と同じ端末の読み取り（[公開の設計の描き方](release.md#描き方)）で求める。テストと画像で、同じ画面の読み方を使うため。

## 検討した案

| 案 | 採らなかった理由・採った理由 |
| --- | --- |
| 答えた質問をそのまま残す（gem、brew の対話型） | 9 問に答えると画面が長くなり、答えた内容が上へ流れる。人間が、答えを 1 行に縮める案を選んだ |
| 矢印のキーで選ぶ（inquirer 型） | 入力のしかたそのものが変わり、手順書と答えを流し込むテストの作り直しが要る。bash 3.2 で矢印のキーを読むのは端末ごとに動きが違う |
| 答えの一覧を種類ごとの件数だけに縮める | どのエージェントが新しくでき、どれが直されるかが名前で分からない。変える前の最後の確認なので、人間が名前ごとの記号の案を選んだ |
| 作成の進みを手順ごとに 1 行ずつ積む（npm 型） | 残りの手順が見えず、公開の画面と見せ方が分かれる。人間がチェックリスト型を選んだ |
| 完了の表示で、問題のある項目だけを出し、ほかは件数にまとめる | 作ったものの名前と既存のタスクの識別子が残らず、あとで見返せない。人間がすべての項目を印で並べる案を選んだ |
| 縮める行の数を、カーソルの位置の保存と復元で扱う | 画面が下まで流れると保存した位置がずれ、前の行を消し残すか消しすぎる。出した行の数を幅から数えて、上へ動かす |
| 表示の幅を数えるのに python3 を使う | セットアップと公開のコマンドの要る道具に python3 はない |
| 表示の幅を数えるのに `jq` の `explode` を使う | 公開のコマンドは `jq` を要る道具にしていない。足すと、今まで公開できた環境で止まる。bash だけで数えられる |
| 端末の大きさを `tput` だけで読む | macOS の `tput` は、出力がパイプのときに端末の定義の 80 桁・24 行を返す。変数に受けると、低い端末でも 24 行とみなし、大きさが変わっても気づけない |
| 画面に収まらないときも、出した行の数だけ上へ動かして書き換える | 画面の上に流れた行へはカーソルが戻れず、消し残しと行の積み重ねが起きる |
| 別の画面（代替のスクリーン）に切り替えて描く | 終わると画面が消え、答えた内容と結果が端末に残らない。ログとして見返せない |
| 画面に収まらないときに、見えている部分だけを窓のように書き換え続ける | 終わった行を残す仕組みに加えて、窓の位置を動かす仕組みが要る。終わった行を残せば、多くの場合は範囲が収まり、収まらないときは書き換えをやめれば足りる |
| `NO_COLOR` でも行を書き換える | 色を止める人は動く表示も望まないことが多く、受け入れ条件でも書き換えないことを求めている。端末でない出力と同じに扱う |
