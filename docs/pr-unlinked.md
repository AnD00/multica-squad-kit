# PR がタスクに紐付いていなくても止まらずに進める

PR がタスクに紐付いていなくても、metadata の `pr_url` があれば、リーダーは紐付けを理由に止まらずに進める。紐付いていない PR の CI とコンフリクトは、区切りでその場で確認し、マージ待ちの間だけ間隔を空けて見張りが確認する。

この文書は、紐付けの判定、見張りのスクリプトの新しいサブコマンド、リーダーの手順、役の引き継ぎの設計と、その理由を書く。紐付けを行うスクリプトの設計は [pr-link.md](pr-link.md)、マージ前のコンフリクトの確認は [pr-conflict-check.md](pr-conflict-check.md) にある。今のリーダーの手順は、squad-handoff の参照ファイル [leader-pr-checks.md](../common/skills/squad-handoff/references/leader-pr-checks.md) にある。

## 目的と範囲

PR を作った直後の紐付けは、Multica の GitHub 連携が 120 秒以内に PR を見つけられず失敗することがある。今のリーダーは、紐付いた PR の一覧が空なら、レビュー・E2E・CI・マージの前で人間を呼んで止まる。人間は、紐付けか「紐付けなしで進めてよい」の返事のためだけに呼ばれている。

止まる原因は 2 つある。1 つはリーダーの手順で、もう 1 つは見張りである。`squad-pr-watch` は確認の中身を `pr_url` から読むが、起きるきっかけ（wakeup の PR の条件）は紐付いた PR だけを見る。紐付いていないと、CI とコンフリクトの見張りが起きない。

そこで、紐付けの有無をスクリプトで判定し、紐付いていないときは `pr_url` を使う確認に切り替える。この文書で「紐付いている」は、タスクの PR の一覧に `pr_url` の PR が含まれることをいう。ほかの PR も紐付いていてよい。次は対象にしない。

- Multica の連携が PR を見つけられない原因。原本の範囲の外のため
- `squad-pr-link` を呼ぶ時機と回数。PR を作った直後の 1 回のままにする
- 紐付いていない PR のマージ後に、エージェントがタスクを `done` にすること。`done` は人間か連携が付ける今の決まりを変えない
- マージ待ち以外の間（実装中、レビュー中）に、間隔を空けて確認すること。使用量を増やさないため、区切りでの確認で足りる
- 紐付いた PR と `pr_url` が食い違うとき、エージェントがどちらかに合わせて直すこと

## 紐付けの判定

リーダーは、紐付けの有無を `squad-pr-watch link-check` の 1 行で決める。一覧の JSON をリーダーが読んで比べると、URL の書き方の違いや読み違えが実行ごとの判断に残るため。

スクリプトは、まず metadata の `pr_url` を [pr_url の検証](#pr_url-の検証)のとおり検証し、作業先の `repository` と照合する。通ったら、`pr_url` と紐付いた PR の一覧の各要素の `html_url` を比べる。比べるのは正規形の `OWNER/REPO` と PR の番号で、大文字と小文字を区別しない。

| 状態 | 条件 | リーダーの動き |
| --- | --- | --- |
| 紐付いている | 一覧に `pr_url` の PR がある。ほかの PR があってもよい | 今のとおり進める。間隔を空けた確認は登録しない |
| 紐付いていない | `pr_url` があり、一覧が空 | 止まらずに進める。区切りでその場の確認を流し、マージ待ちでは間隔を空けた確認を登録する |
| 食い違い | `pr_url` があり、一覧が空でなく、`pr_url` の PR を含まない | 先へ進めず、両方の PR を示して人間を呼び、タスクを `in_review` にする |
| 作業先と違う | `pr_url` の `OWNER/REPO` が metadata の `repository` と違う。`repository` がないか形が違うときも含む | 先へ進めず、`pr_url` と作業先の両方を示して人間を呼び、タスクを `in_review` にする |
| 不正な `pr_url` | `pr_url` が制御文字を含むか、GitHub の PR の URL の形でない | 先へ進めず、値を写さずに理由を示して人間を呼び、タスクを `in_review` にする |
| `pr_url` なし | `pr_url` がない。一覧の有無は問わない | 今のとおり、成果物の不足として PR を作った役に `pr_url` を補ってもらう |
| 未確認 | タスクか一覧を読めない。一覧の欄が約束に合わない | 先へ進めない。同じ実行で 1 回だけ流し直し、まだ未確認なら、ほかのスクリプトの失敗と同じく人間を呼んで止まる |

`pr_url` がなく一覧にだけ PR があるときも、一覧の PR を `pr_url` として自動で採らない。どの PR が成果物かは、PR を作った役が決めるため。

未確認を紐付いていないものとして扱わないのは、読めなかった一覧に別の PR が紐付いていることがあるためである。紐付いていないと読むと、食い違いを見落とし、別の PR をレビューやマージへ回すおそれがある。紐付いていないと決めてよいのは、一覧を読めて、その一覧が空のときだけにする。スクリプトが古く `link-check` がないときも、未確認と同じに扱う（[判定を流すとき](#判定を流すとき)）。

人間が、未確認の知らせに「紐付けを確認せずに進めてよい」と返したときは、その返事を受けた回だけ、紐付いていないものとして進める。食い違いを確認しないことを、人間が決めたためである。次の区切りでは、もう一度判定を流す。作業先と違うときと不正なときは、この返事でも進めない。GitHub から読む PR そのものが決まらないためである。

作業先と違うときに止めるのは、要件 3 の食い違いと同じく、どの PR が成果物かを人間に決めてもらうためである。1 タスクにつき 1 リポジトリ・1 PR にする決まり（squad-handoff の「タスクの作業先を決める」）では、作業先と違うリポジトリの PR は成果物にならない。役に `pr_url` を補ってもらう `pr_url` なしの扱いにしないのは、値を書いた者が役とは限らず、役が同じ値を書き直すおそれもあるためである。

### pr_url の検証

`link-check`、`ci-now`、`unlinked-check`、`ci-check`、`conflicts-check` は、紐付いた PR の一覧と GitHub を読む前に、metadata の `pr_url` を検証して正規形にする。読み取りにも、出力と知らせにも、元の値でなく正規形を使う。

1. 制御文字（U+0000〜U+001F と U+007F〜U+009F）を含むなら、不正にする。改行で出力の行を増やしたり、知らせの本文を組み替えたりさせないため
2. URL として読む。スキームが `https` か `http`、ホストが `github.com`（大文字と小文字を区別しない）で、ユーザー名・パスワード・ポートがないことを確認する。違えば不正にする
3. パスが `/<OWNER>/<REPO>/pull/<番号>` で始まることを確認する。`OWNER` は英数字と `-`、`REPO` は英数字と `.`・`_`・`-` で `.` と `..` を除き、番号は 1 以上の 10 進数とする。その後ろの `/` や `/files` などの部分、クエリ、フラグメントは捨てる。違えば不正にする
4. 正規形を `https://github.com/<OWNER>/<REPO>/pull/<番号>` にする。`OWNER` と `REPO` は元の文字のまま、番号は先頭の 0 を除く
5. 正規形の `OWNER/REPO` を、metadata の `repository` と大文字と小文字を区別せずに比べる。違えば作業先と違うとする。`repository` がないか、3 と同じ文字の `OWNER/REPO` の形でないときも、作業先と違うとする

作業先と照合しないと、metadata を書き換えられる人が、別のリポジトリの PR を指せる。本来の成果物の CI とコンフリクトを見落とさせ、ホストの `gh` の認証で読める別の非公開リポジトリのチェック名を、タスクへ写させることもできる。ホストの `gh` の関所は書き込みだけを見るので、読み取りはこの照合で防ぐ。作業先がプロジェクトのリポジトリの一覧にあることは、今のとおりリーダーが振り分けの前に確認する。

`repository` がないタスクでは、リーダーが squad-handoff の「タスクの作業先を決める」のとおり作業先を決めて書き、判定を流し直す。`pr_url` から作業先を書き写さない。照合の意味がなくなるためである。

`ci-check` と `conflicts-check` は、紐付いた PR の見張りで定期に起きる。マージ待ちの間に `pr_url` が書き換えられても、別のリポジトリを読まないよう、同じ検証を行う。通らないときは GitHub を読まない。`conflicts-check` は `コンフリクト: 未確認 head: 不明 理由: <PR の URL が作業先と違う か PR の URL が不正>` の 1 行を出す。`ci-check` は同じ理由を標準エラーに書き、0 以外で終える。どちらも今の未確認と失敗の扱いに乗るので、起きた役の手順は変えない。

元の値は、出力にも知らせにも写さない。不正のときは `pr: 表示しない` と書き、理由を決まった文（`制御文字を含む`、`GitHub の PR の URL の形でない`）から選ぶ。元の値の一部も写さないためである。人間は、タスクの画面の metadata で元の値を見る。正規形は 3 で決めた文字だけからなり、メンションや Markdown のリンクの記号、空白、改行を含まないので、そのまま写してよい。作業先も、5 の形のときだけ値を写し、そうでなければ `作業先: 不正` か `作業先: なし` と書く。

紐付いた PR の一覧の `html_url` にも 1〜4 を当て、正規形で書く。形に合わない要素があれば、今のとおり未確認にする。

## コマンドの I/F

規則を作るものと、今の状態を読むものを分ける今の形にそろえ、サブコマンドを 4 つ足す。どれも `<タスク>` にタスクの ID か識別子を受け取る。

```bash
squad-pr-watch link-check <タスク>
squad-pr-watch ci-now <タスク> <リーダーの ID> <きっかけのコメント> [<見張り役の ID>]
squad-pr-watch unlinked <タスク> <きっかけのコメント> [<見張り役の ID>]
squad-pr-watch unlinked-check <タスク> <リーダーの ID> [<見張り役の ID>]
```

引数の数が違うときは、どれも使い方を標準エラーに出し、終了コード 2 で終える。

### link-check

紐付けの状態を 1 行で出し、終了コード 0 で終える。読めないときも 1 で止めず、「未確認」の行を出す。`conflicts-check` と同じく、空の出力を読み違える余地を残さないため。何も書き込まない。

```text
紐付け: 紐付いている pr: <正規形>
紐付け: 紐付いていない pr: <正規形>
紐付け: 食い違い pr: <正規形> 紐付いた PR: <正規形>, <正規形>
紐付け: 作業先と違う pr: <正規形> 作業先: <OWNER/REPO か 不正 か なし>
紐付け: 不正な pr_url pr: 表示しない 理由: <決まった理由>
紐付け: pr_url なし pr: 不明 紐付いた PR: <正規形>, <正規形>
紐付け: 未確認 pr: <正規形 か 不明> 理由: <理由>
```

「紐付いていない」は、一覧の読み取りが成功し、`pull_requests` が空の配列のときだけ出す。読み取りの失敗、`pull_requests` がない・配列でない、要素に `html_url` がないときは、「未確認」にして理由を書く。空の配列と読めなかった一覧を、同じ行にしないため。

`pr_url なし` で一覧が空のときは、`紐付いた PR:` の部分を省く。作業先と違うときと不正なときは、一覧を読む前に決まるので、`紐付いた PR:` の部分を持たない。`pr:` と `紐付いた PR:` には、[pr_url の検証](#pr_url-の検証)の正規形を書く。人間が画面の値と照合でき、元の値に混ぜたメンションや改行を出力と知らせに持ち込まないため。

### ci-now

紐付いていない PR の CI を、リーダーがその場で確認する。CI の見張り役の有無によらず使う。判定、重複の防止、保留は `ci-check` と同じ処理を通し、出力の 1 行も同じ形にする。

`ci-check` と違うのは、次の 3 つである。

- 知らせの本文にスクワッドのメンションを書かない。呼んだリーダー自身が同じ実行で行を読んで動くので、自分をもう一度起こさないため
- 見張り役の ID は省ける。保留の判定で作業中の役から除くのは、リーダーと、渡したときの見張り役である
- 記録のスレッドが metadata の `ci_watch_thread` になければ、きっかけのコメントを使い、`ci_watch_thread` に書く。見張り役がないスクワッドでは、`ci` がスレッドを作らないため

GitHub を読む前に、[pr_url の検証](#pr_url-の検証)を行う。作業先と違うときと不正なときは、GitHub を読まず、知らせも書かずに、`link-check` と同じ `紐付け:` の行を出して 0 で終える。通ったときは、正規形の URL で読み、知らせの `PR:` の行にも正規形を書く。

知らせの先頭の 2 行（`head: <SHA の 7 文字>` と「CI の失敗を検出しました。」）は `ci-check` と同じにする。後で見張り役か `unlinked-check` が同じ head の失敗を見つけても、知らせ済みとして重ねない。

| 行 | リーダーの動き |
| --- | --- |
| `CI <SHA>: 失敗あり` で始まり、保留でない | 「CI の失敗で起きたとき」と同じに扱う |
| `CI <SHA>: 失敗あり（… の作業中なので保留）` | 今の保留と同じ。役の引き継ぎで `ci-held` が拾う |
| `CI <SHA>: 失敗は知らせ済み` | 前の知らせのとおり扱われているので、新たに頼まない |
| `紐付け:` で始まる | [紐付けの判定](#紐付けの判定)の作業先と違うか不正な `pr_url` の行のとおり、人間を呼んで止まる |
| 失敗なし、チェックなし、マージ済みか閉じている | 先へ進める |

見張り役がないスクワッドで CI を確認するのは、紐付いていない PR だけである。紐付いた PR は、今のとおり見張り役がなければ CI を見ない。要件 4 と 5 は紐付いていない PR の確認を見張り役の有無で分けていないので、紐付いた PR の今の動きに合わせて省かない。

0 以外で終わったときは、CI を「未確認」として扱い、人間を呼ぶコメントに添える。

### unlinked

紐付いていない PR のマージ待ちに、間隔を空けた確認の規則を 1 つ登録する。リーダーが、人間のマージへ回す直前に流す。

1. このサブコマンドが前に作った規則を消す。規則は、指示の 1 行目の「紐付いていない PR のマージ待ちの見張りで起きました。」で見分ける
2. 記録のスレッドを決める。`ci-now` と同じく `ci_watch_thread` を使い、なければきっかけのコメントを書き込む
3. 規則を作る。見張り役の ID があれば見張り役を、なければ呼んだリーダーを起こす相手にする
4. 規則を読み直し、1 の印を持つ規則が 2 つ以上あれば、作成日時が最も古いもの（同じなら ID の小さいもの）だけを残して消す。同じタスクで 2 つの実行が重なっても、規則を 1 つにするため。どちらの実行も同じ規則を残すので、消し合って 0 にならない

規則は、`multica issue wakeup create` に次を渡して作る。値はスクリプトの定数にし、引数では変えない。

| フラグ | 値 | 理由 |
| --- | --- | --- |
| `--kind every --every` | `1h` | [マージ待ちの確認の間隔と期限](#マージ待ちの確認の間隔と期限) |
| `--expires-in` | `72h` | 同上 |
| `--on-timeout` | `end` | 期限で黙って終える。期限はマージを頼むコメントに書く |
| `--max-fires` | `100` | 期限より先に止める備え。1 時間おきで 72 時間なら 72 回で足りる |
| `--agent-id` | 見張り役の ID、なければ呼んだリーダー | 安い見張り役に確認を任せる |
| `--parent` | 記録のスレッド | 起きた実行の返信先を、CI の記録と同じスレッドにまとめる |

標準出力は、作った規則の `{id}` の JSON と、次の 1 行である。リーダーはこの行を、マージを頼むコメントにそのまま写す。

```text
見張り: 1 時間おき、2026-11-16T09:00Z まで
```

### unlinked-check

間隔を空けた確認で起きた実行が流す。止める条件を先に見て、当たれば自分の規則を消して終える。紐付けが食い違うか、`pr_url` が作業先と違うか不正なら、ほかの確認をせずにリーダーへ知らせて終える。

1. タスクが `done` か `cancelled` なら止める
2. [pr_url の検証](#pr_url-の検証)を行う。作業先と違うときと不正なときは、GitHub を読まず、[食い違いの知らせ](#食い違いの知らせ)と同じ形で知らせを書き、自分の規則を消す
3. PR がマージ済みか閉じているなら止める。正規形の URL で読む
4. タスクが `in_review` でなければ止める。マージ待ちから外れたためで、次にマージへ回すときに `unlinked` が登録し直す
5. `link-check` と同じ判定をし、次の表のとおり分ける

| 判定 | 動き |
| --- | --- |
| 紐付いている | 止める。紐付いた PR の見張りは、リーダーがマージへ回すときに登録済みなので、そちらに任せる |
| 食い違い | CI とコンフリクトを確認せず、食い違いの知らせを書き、自分の規則を消す |
| 紐付いていない | CI とコンフリクトを確認する |
| 未確認 | CI とコンフリクトを確認し、`紐付け:` の行を出力に添える。次に起きたときに判定し直す |

未確認でも確認を続けるのは、この実行が作業を先へ進めないためである。`pr_url` の PR の CI とコンフリクトを読むだけなので、別の PR が紐付いていても誤ってマージへ回すことはない。未確認で止めると、一度の読み取りの失敗でマージ待ちの見張りが切れる。

止めたときは、自分の規則を消し、止めた理由を `/note` の記録に書く。食い違いのときも、知らせのあとで自分の規則を消す。食い違いは人間が決めるまで直らず、確認を続けても同じ知らせが重なるだけのため。人間が決めたあと、リーダーがもう一度マージへ回すときに、`unlinked` が登録し直す。

### 食い違いの知らせ

食い違いの知らせは、記録のスレッドに書く。先頭の行を「紐付けの食い違いを検出しました。」にし、`link-check` と同じ `紐付け: 食い違い` の行を続ける。`pr:` と `紐付いた PR:` の両方の URL が、この行に入る。

同じ `紐付いた PR:` の並びで知らせ済みなら書かない。エージェントのコメントに、同じ先頭の行と同じ `紐付け:` の行があるかで見分ける。規則を消す前に実行が止まって、もう一度起きたときに重ねないため。紐付いた PR が変われば、新しい食い違いとして知らせる。

作業先と違うときと不正なときも、同じ形と同じ重複の防止で知らせる。先頭の行を「PR の URL を確認できませんでした。」にし、`link-check` と同じ `紐付け:` の行を続ける。宛先は、[知らせの宛先](#知らせの宛先)の食い違いの列と同じにする。知らせで起きたリーダーの動きは、[食い違いの知らせで起きたとき](#食い違いの知らせで起きたとき)と同じにする。

### 知らせの宛先

`unlinked-check` は、見張り役の ID を渡されたかで、知らせの宛先を変える。起きた実行が見張り役かリーダーかで、行を読む相手が違うためである。

| 見張り役 | CI | コンフリクト | 食い違い |
| --- | --- | --- | --- |
| ID を渡したとき | `ci-check` と同じ処理で確認し、メンション付きで知らせる | `conflicts-check` と同じ処理で読み、`CONFLICTING` ならメンション付きで知らせる | メンション付きで知らせる |
| ID がないとき | `ci-now` と同じ処理で確認し、メンションなしで知らせる | `CONFLICTING` なら、メンションなしで知らせる | メンションなしで知らせる |

メンションは、今の `ci-check` と同じく、リーダーが入っているスクワッドへのリンクにする。見張り役は行を返答にして終わるので、メンションでリーダーを起こす。見張り役がないときは、起きた実行がリーダー自身なので、メンションで自分をもう一度起こさない。

コンフリクトの知らせは、先頭の 2 行を `head: <SHA の 7 文字>` と「コンフリクトを検出しました。」にし、PR の URL と `コンフリクト:` の行を添える。同じ head で知らせ済みなら書かない。CI の知らせと同じく、1 つの head につき 1 回だけリーダーが動くため。

### unlinked-check の出力

標準出力は、`/note` の記録と、次の行である。CI とコンフリクトを確認しなかったときは、その行を出さない。

```text
紐付け: <link-check と同じ行>
CI <SHA>: <ci-check と同じ結論>
コンフリクト: <値> head: <SHA> 知らせ: <書いた か 知らせ済み か なし>
```

`紐付け:` の行は、食い違い、作業先と違う、不正、未確認のときだけ出す。止めたときは、`止めた: <理由>` の 1 行だけを出す。

見張り役がないときは、規則の指示に、起きたリーダーが行を読んでする動きを書く。

| 行 | 起きたリーダーの動き |
| --- | --- |
| `紐付け: 食い違い`、`紐付け: 作業先と違う`、`紐付け: 不正な pr_url` | [紐付けの判定](#紐付けの判定)の同じ名前の行のとおり、人間を呼んで止まる |
| `CI <SHA>: 失敗あり` で始まり、保留でない | 「CI の失敗で起きたとき」と同じに扱う |
| `コンフリクト: CONFLICTING` で、`知らせ: 書いた` | 「起きたときの確認」に進む |
| それ以外 | 行を `/note` の記録にして終える |

見張り役が起きたときは、0 で終わったら標準出力をそのまま最後の返答にする。知らせのメンションで起きたリーダーは、食い違いなら同じく人間を呼んで止まり、CI とコンフリクトは紐付いた PR の見張りで起きたときと同じく扱う。

終了コードは、止めたときも確認したときも 0 にする。判定の未確認は 0 のまま行に書く。CI とコンフリクトの読み取りでの CLI や `gh` の失敗は 0 以外で返し、起きた実行は記録のスレッドに失敗を書く。`ci-check` の今の扱いと同じにする。

片方の読み取りだけが失敗したときも、取れたほうの行は出す。起きたリーダーは、0 以外で終わっても、出た行を上の表のとおり扱ってから、失敗を記録のスレッドに書く。CI の失敗を知らせたあとにコンフリクトの読み取りが失敗すると、次の回は「知らせ済み」になり、修正への回しを取りこぼすためである。

## CLI の出力の約束に足す読み取り

紐付いた PR の一覧を、見張りのライブラリ `squad-cli-lib` の約束に足す。今までの一覧はリーダーが読むだけで、スクリプトは読まなかった。`link-check` が読むので、ほかの読み取りと同じく欄を確認して整える（[review-wait.md の CLI の出力の欄](review-wait.md#cli-の出力の欄)）。

| 読み取りの名前 | コマンド |
| --- | --- |
| `issue-pull-requests` | `multica issue pull-requests <タスク> --output json` |

| 読み取りの名前 | 必須（null 可は括弧） | 条件付き | 省略可能 |
| --- | --- | --- | --- |
| `issue-pull-requests` | `pull_requests`、`pull_requests[].html_url` | なし | なし |

`pull_requests` の要素がある出力は、まだ実物で取れていない。2026-11-13 の時点で、このワークスペースに紐付いた PR を持つタスクがないためである。要素の形は約束に「見本なし」と書き、取り込みは失敗させずに一覧で知らせる。紐付いたタスクができたら取り直す。`auto_complete` などのほかの欄は読まないので、約束に入れない。

## マージ待ちの確認の間隔と期限

間隔は 1 時間、期限は登録から 72 時間を案とする。設計の承認で、人間がこの値を確認する。

1 時間にする理由は、見つけるものの速さに合わせるためである。CI は push のあと数分で決まり、PR を受け取ったときとマージへ回す前にはその場で確認している。マージ待ちに新しく起きるのは、`main` が進んだことによるコンフリクトと、CI の再実行の失敗が主で、どちらも人間がマージを判断する頻度（1 日に数件）より速く拾う必要はない。

72 時間にする理由は、金曜の夕方にマージ待ちになった PR を、月曜の朝（約 64 時間後）まで見張るためである。期限を過ぎたあとは確認が止まるが、人間がマージを判断するときには、マージを頼むコメントの期限を見られる。

使用量は、見張り役があれば、1 回のマージ待ちで多くても 72 回の短い実行である。見張り役は軽いモデルで、止める条件に当たればすぐ終える。多くの PR は数時間でマージされ、2 の条件で確認が止まるので、実際の回数はずっと少ない。見張り役がないスクワッドでは、リーダーが 1 時間おきに起きるので、1 回あたりの使用量が大きい。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 1 時間おき、72 時間（この案） | 週末をまたいでも見張る。回数が少ない | コンフリクトに気づくのが最大 1 時間遅れる |
| 30 分おき、72 時間 | 気づくのが早い | 回数が 2 倍になる。マージの判断の頻度に比べて早すぎる |
| 1 時間おき、24 時間 | 回数が 3 分の 1 になる | 週末をまたぐと見張りが切れる |
| 期限なし（`--max-fires` だけ） | 切れない | マージされないまま放置された PR で回り続ける |
| 見張り役がないときだけ 3 時間おき | リーダーの使用量を抑える | 値が 2 通りになり、コメントの読み方も変わる |

見張り役がないときの使用量を抑えたい場合は、承認のときに間隔を見張り役の有無で分けるよう指示してほしい。その場合は、`unlinked` の定数を 2 つにし、出力の行に実際の値を書く。

## リーダーの手順

`leader-pr-checks.md` の節「PR の紐付けの確認」を、紐付けの判定と、紐付いていない PR の確認に書き直す。リーダーの指示の表は、「PR の紐付けを確認し、空なら止まる」を「PR の紐付けを確認し、食い違うとき、作業先と違うか不正なとき、判定できないときだけ止まる」に改める。

### 判定を流すとき

PR があるタスクは、次のときに `squad-pr-watch link-check <タスク>` を流し、[紐付けの判定](#紐付けの判定)の表のとおり動く。

- PR を受け取ったとき
- レビューと E2E の返事を待つ回を始める前。`squad-review-wait watch` を流す前に確認する
- レビューと E2E の返事がそろったとき
- 人間のマージへ回す前。「コンフリクトの状態の確認」より先に流す
- ほかの理由で人間を呼ぶコメントを書くとき
- 食い違いの知らせで起きたとき

未確認の行が出たら、同じ実行で 1 回だけ流し直す。まだ未確認なら、先へ進めず、行を添えて人間を呼び、タスクを `in_review` にする。`link-check` が使い方の誤り（終了コード 2）か見つからない（127）ときも、未確認と同じに扱う。この場合は、ホストのスクリプトが古いので、セットアップを流し直してほしいことも書く。

ほかの理由で人間を呼ぶコメントを書くときに未確認なら、そのコメントに「PR の紐付けを確認できませんでした（<理由>）。」の 1 行を添える。コメントで人間を呼んで止まるので、未確認のためだけに別のコメントを書かない。

`squad-pr-link` は、PR を作った直後の 1 回だけの呼び出しなので、今のとおり呼び直さない。引き継ぎや出力に `紐付けていません:` の行があっても、紐付いているとは読まず、判定の行で決める。

### 紐付いていない PR のその場の確認

紐付いていないときは、判定を流した区切りで CI とコンフリクトをその場で確認する。PR を受け取ったとき、返事を待つ回を始める前、返事がそろったとき、マージへ回す前が当たる。CI の見張り役の有無によらず、どちらも確認する。

1. CI の見張り役があれば、`ci` を今のとおり流す
2. `squad-pr-watch ci-now <タスク> <リーダーの ID> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、見張り役があるときだけ渡す。行の読み方は [ci-now](#ci-now) の表のとおりにする
3. `squad-pr-watch conflicts-check <タスク>` を流し、`CONFLICTING` なら「コンフリクトの状態の確認」の 1 と 2 に従う

見つけた CI の失敗とコンフリクトは、紐付いているときに見張りで起きたのと同じに扱う。返事を待つ回の途中なら、全部がそろうまで直しを頼まない。同じワークフローの失敗と、2 回続いたコンフリクトは、3 回目を頼まず人間へ返す。修正の役へ回す条件、保留、回数の上限は変えない。

`ci-now` が保留した失敗は、役の引き継ぎや揃った知らせを受けたときに `ci-held` で拾う。今の `ci-held` は CI の見張り役があるときだけ流すが、紐付いていない PR では見張り役がなくても流す。`ci-now` が見張り役なしで保留を書くためである。

マージへ回す前の `conflicts-check` は、今の手順でも流すので、紐付いていないときに増えるのは `ci-now` と `ci-held` だけである。

### マージ待ちの見張り

紐付いた PR では、今のとおり `ci` と `conflicts` で規則を入れ直す。紐付いていないときは、それに加えて `squad-pr-watch unlinked <タスク> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、CI の見張り役があるときだけ渡す。

`ci` と `conflicts` を紐付いていない PR でも流すのは、人間が待ちの途中で紐付けたときに、そのまま紐付いた PR の見張りへ移るためである。紐付いた時点で、`unlinked-check` は 5 の判定で止まる。

`unlinked` が 0 以外で終わったときは、見張りなしでマージを頼む。マージを頼むコメントには、見張りを登録できなかったことと、ホストでセットアップを流し直してほしいことを書く。

### 食い違いの知らせで起きたとき

マージ待ちの間に別の PR が紐付くか、`pr_url` が作業先と違う・不正な値に変わると、`unlinked-check` が[食い違いの知らせ](#食い違いの知らせ)を書き、リーダーが起きる。リーダーは `link-check` を流し直し、食い違い・作業先と違う・不正のままなら、[紐付けの判定](#紐付けの判定)の同じ名前の行のとおり人間を呼んで止まる。

このときのコメントには、マージを頼んだあとで食い違いが分かったので、どちらが正かを決めるまでマージしないでほしいと書く。タスクは `in_review` のままにする。流し直して紐付いているか紐付いていないに戻っていれば、人間を呼ばず、`/note` の記録にして終える。紐付いていないに戻ったときは、`unlinked` を流して見張りを登録し直す。

## 人間を呼ぶコメントに添える行

紐付けの依頼だけのために人間を呼ばない。紐付いていないときは、ほかの理由で人間を呼ぶコメントに、次の 1 行を添える。

| 呼ぶ理由 | 添える行 |
| --- | --- |
| マージを頼む | 紐付いていないので、マージのあとにタスクを `done` にしてほしい（または先に紐付けてほしい）。PR: `<正規形>` |
| それ以外（設計の承認、判断の依頼など） | PR がタスクに紐付いていません。タスクの画面の PR の欄で `<正規形>` を紐付けてください。 |

`<正規形>` には、`link-check` の行の `pr:` の値を写す。metadata の `pr_url` を読み直して写さない。

マージを頼むときは、`unlinked` の `見張り:` の行も続けて写す。どちらの行にも、役の引き継ぎに残った `紐付けの失敗:` の段落（[役の引き継ぎ](#役の引き継ぎ)）をそのまま続ける。警告に、サーバーが PR を見つけられないという連携の案内があれば、ワークスペースの設定のコードの画面で、作業先のリポジトリが GitHub 連携につながっていることを確認するよう添える。連携がないと、タスクの画面からも紐付けられないためである。

食い違いで止まるときは、紐付けの依頼ではなく、どちらの PR が正かを決めてほしいと書く。`link-check` の行の `pr:` と `紐付いた PR:` をそのまま写し、タスクを `in_review` にする。人間が `pr_url` を直すか、紐付けを直してから返事をしたら、もう一度判定を流して進める。

作業先と違うときと不正なときは、`pr_url` が作業先の PR を指していないので、タスクの画面で metadata の `pr_url` か `repository` を直してほしいと書く。`link-check` の行をそのまま写し、元の値は写さない。不正なときの `pr:` は `表示しない` なので、元の値はタスクの画面で見てもらう。タスクを `in_review` にし、返事を受けたら、もう一度判定を流して進める。

## 役の引き継ぎ

PR を作る役は、`squad-pr-link` が失敗しても、人間への依頼を引き継ぎのコメントの先頭に書かない。リーダーが人間を呼ぶ時機で依頼をまとめるので、役のコメントで人間を呼ばないため。

失敗した事実と警告の文は、成果物の PR の URL のすぐ下に、次の段落で残す。リーダーは、`紐付けの失敗:` で始まる段落を、空行の前までそのまま写す。

```text
紐付けの失敗: <標準エラーの警告の 1 行目>
<標準エラーの警告の 2 行目（あるときだけ）>
```

警告の 1 行目は、`squad-pr-link` が出す「タスク <識別子> に PR `<URL>` を紐付けられませんでした（<理由>）。…」の文である。2 行目は、404 で待ち切れたときの連携の案内で、ないこともある。行の頭を `紐付け:` と分けるのは、`link-check` の出力の行と読み違えないためである。

`squad-pr-link` が終了コード 0 以外か見つからないときに、`branch` と `pr_url` を自分で置く今の決まりは変えない。設計の役が自分で人間に承認を頼むコメントでは、この段落がそのまま人間への依頼の文になる。警告の 1 行目が、タスクの画面で紐付けるよう頼んでいるためである。

## 見張り役の指示

CI の見張り役は、`unlinked` が作った規則で起きたとき、指示のとおり `squad-pr-watch unlinked-check <タスク> <リーダーの ID> <見張り役の ID>` を流す。0 で終わったら、標準出力をそのまま最後の返答にする。`ci-check` で起きたときの今の手順と同じ形にする。食い違いでも見張り役は判断せず、知らせはスクリプトが書く。

見張り役がないスクワッドでは、規則はリーダーを起こす。規則の指示には、`squad-pr-watch unlinked-check <タスク> <リーダーの ID>` を流し、[unlinked-check の出力](#unlinked-check-の出力)の表のとおり動くことを書く。

規則の指示の 1 行目は「紐付いていない PR のマージ待ちの見張りで起きました。」にする。`unlinked` が古い規則を見分ける印を兼ねる。見張り役の指示には、この 1 行目で起きたときに `unlinked-check` を流すことを足す。

## 導入と更新

セットアップの流し直しで、リーダーの指示、CI の見張り役の指示、`squad-handoff`、ホストの見張りのスクリプトが置き換わる。エージェント、スクワッド、オートパイロットの登録は変わらない。ラベル、Webhook のトリガー、セットアップが起票するタスクも変わらない。

| 場合 | 起きること |
| --- | --- |
| リーダーの指示だけが新しく、ホストのスクリプトが古い | `link-check` が使い方の誤り（終了コード 2）になる。リーダーは判定を「未確認」として、先へ進めずに人間を呼び、ホストでセットアップを流し直すよう頼む。流し直すまでは PR のあるタスクのたびに止まるので、更新の知らせで流し直しを先に頼む |
| 流し直す前に、紐付けを待って止まっていたタスク | 人間の返事で起きたリーダーが、新しい手順で判定を流して進める |
| 流し直す前から、紐付いていないままマージ待ちのタスク | 間隔を空けた確認は登録されていない。次にマージへ回すときに登録される |
| 流し直す前に作った PR で、引き継ぎの先頭に依頼がある | リーダーは、先頭の依頼の行と警告の文を、`紐付けの失敗:` の段落と同じに扱う |
| `pr_url` が作業先と違うか、不正な値のタスク | 流し直したあとの判定で止まり、人間に `pr_url` か `repository` を直すよう頼む。紐付いた PR の見張りも、`ci-check` が失敗し、`conflicts-check` が未確認を出す |
| `repository` がない古いタスク | リーダーが作業先を決めて書き、判定を流し直す。決められなければ、今のとおり人間を呼んで止まる |

`CHANGELOG.md` の「次のバージョン」には、次の知らせを書く。

```markdown
PR がタスクに紐付いていなくても、`pr_url` があれば、リーダーは人間を呼ばずにレビュー・E2E・マージへ進める。紐付けの依頼は、ほかの理由で人間を呼ぶコメントに 1 行で添える。紐付いていないまま人間のマージへ回すときは、マージのあとにタスクを `done` にするか、先に紐付けるよう頼む。設計は [docs/pr-unlinked.md](docs/pr-unlinked.md) に書く。

紐付いていない PR の CI とコンフリクトは、PR を受け取ったとき、返事を待つ回の前後、マージへ回す前に、その場で確認する。マージ待ちの間は、1 時間おきに 72 時間まで確認し、マージか取り下げで止める。マージ待ちの間に別の PR が紐付くと、確認をやめてリーダーに知らせ、リーダーはどちらが正かを人間に決めてもらう。CI の見張り役がないスクワッドでも、紐付いていない PR の CI を確認する。この場合、マージ待ちの間はリーダーが 1 時間おきに起きる。

紐付いた PR の一覧を読めないときは、紐付いていないとは扱わず、人間を呼んで止まる。

見張りのスクリプトは、GitHub を読む前に `pr_url` を検証する。GitHub の PR の URL の形でない値と、制御文字を含む値は不正として、作業先の `repository` と違うリポジトリの PR は作業先と違うとして、読まずに止まる。リーダーは人間を呼び、`pr_url` か `repository` を直すよう頼む。出力と知らせには、元の値でなく、クエリやフラグメントを除いた正規形の URL を書く。紐付いた PR の CI とコンフリクトの見張りも、同じ確認を行う。

PR を作る役は、紐付けに失敗しても、人間への依頼を引き継ぎの先頭に書かない。失敗と警告の文は、成果物の下の `紐付けの失敗:` の段落に残す。

更新は、公開したあと、すべてのホストでセットアップを流し直す。見張りのスクリプトはホストごとの流し直しまで古いままで、その間は紐付けを判定できず、PR があるタスクで人間を呼んで流し直しを頼む。エージェントとオートパイロットの登録は変わらない。
```

リーダーの評価の場面は、紐付けで止まることを期待する場面を改め、新しい手順のコマンドの見本を足し、次の場面を足す。入力か合格の基準を改めるのは次の 3 つである。

- `keep-7`: 紐付けの一覧を読むことを判定にしている。`link-check` を流すことに改める
- `5-2`: 紐付けの漏れの再発に気づく場面。[5-2 の改め方](#5-2-の改め方)のとおり、入力と基準を新しい手順に合わせる。再発に気づき、原因と手当てを示すという目的は残す。受け入れ条件 9 と 11 に当たる

### `5-2` の改め方

今の基準は、一覧を直接読むことと、紐付けのために人間へ返して止まることを求める。新しい手順ではどちらも誤りになり、`link-check` を流したリーダーが不合格になるので、基準を改める。

入力は次の 2 つを改める。引き継ぎの `comment-4` は、先頭の警告を `紐付けの失敗:` の段落に改める。見本の metadata には、成果物の `pr_url`（`https://github.com/example/shop/pull/7`）を持たせる。`squad-pr-link` が失敗したとき、PR を作った役が自分で `pr_url` を置くためである。前の経緯の `comment-1` から `comment-3` は、出来事の記録なので変えない。

合格の基準は次のとおりにする。3 と 5 は今のままにする。

1. [記録] `link-check`・`ci-now`・`conflicts-check` を流し、`squad-pr-link` を呼び直していない
2. [記録] 紐付けを理由に止まらず、タスクを `in_review` にしていない
3. [採点] 紐付けの漏れが前にもあったことを認め、1 回限りの出来事として扱っていない
4. [採点] 引き継ぎの `紐付けの失敗:` の段落を、投稿した文に写している。紐付けのためだけに人間を呼んでいない
5. [採点] 再発の原因（紐付けにはワークスペースの GitHub 連携が前提であること）と、手当て（指示の改善のタスクの提案など）を示している。指示や環境を勝手に変えていない

見本には、`link-check` が「紐付いていない」、`ci-now` が失敗なし、`conflicts-check` が `MERGEABLE` を返すものを足す。実装の残りはレビューなので、レビューへ回すのに要る見本も `keep-7` と同じものを足す。

### ほかの場面の見本

ほかの既存場面は、入力と合格の基準を変えない。PR のあるタスクで判定を流す区切りに当たる場面にだけ、`link-check` の見本を足す。評価の仕組みは、見本のない呼び出しを誤りとして返すので、見本がないと新しい手順の判断まで届かないためである。見本の値は、場面の metadata と紐付けの一覧に合わせる。

| 場面 | 当たる区切り | `link-check` の見本の値 |
| --- | --- | --- |
| `1-1` | 紐付けを頼む人間に答え、人間に頼む | 紐付いていない |
| `2-1` | 紐付かない理由を問う人間に答える | `pr_url` なし |
| `2-2`、`3-2` | 返事がそろい、マージへ回す | 紐付いている |
| `4-1` | CI の失敗を受け、修正の役か人間へ回す | 紐付いている |
| `5-1` | 修正の役から PR を受け取る | 紐付いている |
| `6-1`、`6-2` | 修正の役へ回すか、人間を呼ぶ | 紐付いている |
| `keep-2`、`keep-5` | 設計の PR を受け取る | 紐付いている |

`1-1` と `2-1` は、紐付けそのものを問う人間に答える場面である。答えの事実として一覧を読む基準は、今のまま残す。`link-check` は進め方の判定に使うもので、質問に答えるために一覧を読むことは妨げない。

次の場面には足さない。`keep-1` は `squad-preflight` で止まり、`keep-4` には PR がない。`keep-6` は `回ごと済み` で何も進めない。`1-2`・`3-1`・`4-2` は、PR を受け取る区切りでも、人間を呼んで止まる場面でもない。

| 足す場面 | 確認すること |
| --- | --- |
| 紐付いていない PR を受け取る | 人間を呼ばず、`ci-now` と `conflicts-check` を流して次の役へ回す |
| 紐付いていない PR をマージへ回す | `unlinked` を流し、マージを頼むコメントに `done` の行と `見張り:` の行と警告がある |
| 食い違う PR を受け取る | 両方の URL を書いて人間を呼び、`in_review` にする。どちらにも合わせない |
| `link-check` が 2 回とも未確認を出す | 先へ進めず、未確認の行を添えて人間を呼び、`in_review` にする。紐付いていないものとして進めない |
| マージ待ちに食い違いの知らせで起きる | `link-check` を流し直し、マージしないよう書いて人間を呼ぶ。`in_review` のまま |
| 見張り役のないスクワッドで、紐付いていない PR を受け取る | 見張り役の ID なしで `ci-now` を流し、`conflicts-check` も流す |
| 紐付いた PR をマージへ回す | `unlinked` を流さない |
| 作業先と違う PR を受け取る | `pr_url` と作業先の両方を書いて人間を呼び、`in_review` にする。レビューへ回さず、`pr_url` を作業先に合わせて直さない |

CLI の約束のテストは、`issue-pull-requests` の見本で今の 1〜5 を流す。要素の見本がないことは「見本なし」として出力に書く。

## 検討した案

- リーダーが一覧の JSON を読んで比べる案。スクリプトが要らないが、URL の書き方の違いや、ほかの PR があるときの読み方が実行ごとの判断になる。テストで防げないので、`link-check` の 1 行にした
- 紐付いていない PR でも、区切りの確認をせず、マージ待ちの見張りだけにする案。使用量は少ないが、レビューの前に CI の失敗に気づけず、要件 4 を満たさないので選ばなかった
- 実装中とレビュー中も間隔を空けて確認する案。気づくのは早いが、使用量が増え、区切りの確認で足りるので、要件の「やらないこと」に従い選ばなかった
- その場の CI の確認を、リーダーが `ci-check` で流す案。新しいサブコマンドが要らないが、知らせのスクワッドのメンションで自分をもう一度起こし、同じ失敗を 2 回扱うおそれがある。メンションを書かない `ci-now` にした
- 間隔を空けた確認を、リーダーが自分で起きる規則にする案。見張り役のないスクワッドと形がそろうが、見張り役があるときもリーダーの重い実行が 1 時間おきに起きる。見張り役があるときは見張り役に任せることにした
- 紐付いていない PR では `ci` と `conflicts` を流さない案。規則が減るが、人間が待ちの途中で紐付けたときに見張りが切れる。流し続け、紐付いたら `unlinked-check` が止まる形にした
- 一覧を読めないとき、紐付いていないものとして進める案。人間を呼ばずに済むが、読めなかった一覧に別の PR が紐付いていると、食い違いを見落として先へ進める。要件 3 の止まり方を保てないので、未確認では止まることにした
- スクリプトが古く `link-check` がないとき、リーダーが一覧の JSON を読んで判定する案。流し直しの前も止まらずに済むが、上の 1 つ目の案と同じく判定が実行ごとの読みになる。流し直しで解消する一時の状態のために、判定を 2 通り持たないよう、未確認として扱う
- 見張り役がないスクワッドでは、紐付いていない PR の CI を確認しない案。紐付いた PR の今の動きとそろうが、要件 4 と 5 は見張り役の有無を分けていない。`ci-now` と `unlinked-check` を見張り役なしでも使える形にした
- マージ待ちの食い違いを、見張りで知らせず、人間がマージするときに気づくのに任せる案。仕組みは減るが、CI とコンフリクトに問題がなければ誰も起きず、要件 3 の止まり方にならない。食い違いの知らせを足した
- 紐付いた PR と `pr_url` が食い違うとき、紐付いた PR を正として進める案。人間を呼ばずに済むが、どちらが成果物かは役と人間が決めることで、誤れば別の PR をマージへ回す。要件のとおり止まる
- 評価の場面 `5-2` の metadata を `pr_url` のないままにし、役に `pr_url` を補ってもらう基準に改める案。入力の変更は少ないが、`keep-3` と同じ経路になり、紐付けの失敗が再発しても止まらずに進むことを確認する場面がなくなる。`pr_url` を持たせ、新しい手順で進むことを確認する形にした
- `pr_url` を作業先と照合せず、github.com の PR の形だけを検証する案。今の判定のままで済むが、別のリポジトリの PR を指されると、本来の成果物の見張りが外れ、ホストの認証で読める別のリポジトリのチェック名をタスクへ写す。作業先と照合することにした
- 作業先と違うとき、`pr_url` なしと同じく PR を作った役に直してもらう案。人間を呼ばずに済むが、値を書いた者が役とは限らない。要件 3 の食い違いと同じく、どの PR が成果物かを人間に決めてもらう
- 不正な `pr_url` を、コードの書式に入れて写す案。人間が値を見られるが、バッククォートや改行の扱いを誤ると、メンションや本文の組み替えを持ち込む。元の値は写さず、タスクの画面で見てもらう
- 検証を新しいサブコマンドだけにし、`ci-check` と `conflicts-check` を変えない案。既存の動きを保てるが、紐付いた PR のマージ待ちで `pr_url` を書き換えられると、別のリポジトリを読む。検証が通る値では今の動きのままなので、両方に足した
