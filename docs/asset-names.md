# 配布物の名前を ASCII に限り、PR とタグの前に検証する

原本のファイルとディレクトリの名前を、印字できる ASCII に限る。PR の CI とタグを付ける前のコマンドで、発行と同じ道で配布物を作って検証し、名前の誤りをマージとタグの前に止める。

この文書は、名前の決まりと、それを確認する場所の全体、v1.11.1 の出し方を書く。配布物を作るスクリプトと発行のコマンドの変更は `docs/release.md`、入口の一覧の検証は `docs/install.md`、CI のジョブは `docs/ci.md` に書く。

## 目的と範囲

v1.11.0 は、タグと下書きの Release はできたが、発行のワークフローが配布物を作れずに止まった。原因は、リーダーの評価の場面のディレクトリ `tests/leader-eval/scenes/保-1`〜`保-7` である。

`scripts/build-assets.sh` は配布物の一覧を `LC_ALL=C` で読む。GNU tar は、この設定で ASCII 以外の名前を `\344\277\235` のような 8 進の形で出す。そのバックスラッシュを、[展開の前の検証](install.md#展開の前の検証)が読み違えのおそれがある名前として拒んだ。入口の `install.sh` も同じ検証を持つので、配布物ができても使う人の側で止まる。

配布物は、タグを付けたあとの発行のワークフローで初めて作っていた。PR の CI も `scripts/release.sh` も配布物を作らないため、名前の誤りがタグまで届いた。発行済みのタグは動かさない決まりなので、v1.11.0 は配布物のないまま残り、修正は v1.11.1 で配る。

この変更で、次の 3 つを行う。

1. 名前の決まりを決め、`CONTRIBUTING.md` に書く（[名前の決まり](#名前の決まり)）
2. 発行と同じスクリプトで配布物を作る検証を、PR の CI とタグの前に流す（[確認する場所](#確認する場所)）
3. 場面の ID を ASCII に替え、v1.11.1 を出す（[場面の ID](#場面の-id)、[v1.11.1 の出し方](#v1111-の出し方)）

次は対象にしない。

- PR の CI で、`VERSION` と `CHANGELOG.md` を検証すること
- 発行のワークフローの、証明と載せる手順を前もって検証すること
- v1.11.0 のタグと下書きの Release を、消すことや付け替えること。下書きの扱いは人が決める
- 一覧の検証を緩めること。ASCII 以外の名前を、配布物で通すことはしない

## 名前の決まり

原本の Git で追跡するファイルとディレクトリの名前は、印字できる ASCII（`0x20` の空白から `0x7E` の `~` まで）だけで書く。その中でも、バックスラッシュ（`\`）は使わない。

- 漢字やかななど、ASCII 以外の文字は、ファイルの中身には書いてよい。名前にだけ使わない
- 空白は許す。入口の一覧の検証が、今も空白を拒まないため。決まりと一覧の検証の答えを同じにする
- バックスラッシュを除くのは、入口の一覧の検証がすでに拒むため。名前の決まりと、使う人の側の検証を、同じ範囲にそろえる
- 決まりは、パスの全体に当てる。ディレクトリの名前も、ファイルの名前と同じに扱う

この決まりは、配布物の一覧を `LC_ALL=C` で読む限り、GNU tar と bsdtar のどちらでも名前を読み違えないためのものである。一覧の検証を緩めて ASCII 以外の名前を通すと、tar の実装と言語の設定ごとに出る形が変わり、展開の前の検証で同じ名前と見なせなくなる。

## 確認する場所

名前の決まりと配布物の検証を、次の 3 か所で同じスクリプトで流す。どこも、発行のワークフローと同じ `scripts/build-assets.sh` で配布物を作り、入口の `install.sh` の一覧の検証を当てる。

| 場所 | いつ | 検証する中身 | 止まったとき | 設計 |
| --- | --- | --- | --- | --- |
| PR の CI の `assets` のジョブ | PR への push と、`main` への push | PR の head のコミット（`main` ではそのコミット） | ジョブが失敗し、名前と理由を出す。マージの前に気づく | [ci.md](ci.md#配布物の検証) |
| `scripts/release.sh` の検証の 9 | タグを付ける前、確認を求める前。これから配布物を作らせる状態のときだけ | タグを付けるコミット | タグ、push、下書きを作らずに 1 で終わる | [release.md](release.md#確認すること) |
| 発行のワークフロー | タグを付けたあと | タグのコミット | 今のとおり、配布物を作らずに失敗する | [release.md](release.md#配布物を作る) |

`scripts/build-assets.sh` には、タグがなくても、コミットを渡して同じ検証を流す形を足す（[release.md の配布物を作る](release.md#配布物を作る)）。PR の CI と `scripts/release.sh` はこの形を使う。名前の検証は、配布物を作る前に、コミットの木の名前を `git ls-tree` で読んで行う。tar の一覧に出る形ではなく、Git に入っている名前のバイトで見分けるため、どの名前がなぜ止まったかを、そのまま出せる。

配布物の一覧の検証は、`install.sh` に一本化する。今の `scripts/build-assets.sh` は、`install.sh` の `check_listing` と同じ処理を写して持っている。写しをやめ、`install.sh` に足す一覧だけを検証する形（[install.md の入口のスクリプト](install.md#入口のスクリプト)）を呼ぶ。作る側と使う側の答えが、同じ処理から出るようにするため。

### 止まったときに出すもの

名前で止まったときは、次の 3 つを、標準エラー出力に `エラー:` の印で出す。

1. 名前。パスの全体を出す。制御文字は `\ooo` の 8 進の形に置き換え、ほかの文字はそのまま出す。端末を乱さずに、漢字などは読める形で見せるため
2. 理由。「印字できる ASCII ではない文字がある」「バックスラッシュがある」のどちらか
3. 直し方。`CONTRIBUTING.md` の「ファイルとディレクトリの名前」の決まりに沿って、名前を ASCII に替えること

当てはまる名前が 2 つ以上あるときは、最初の 1 つで止めず、すべてを出してから止まる。1 つずつ直して流し直す手間を省くため。上限は 20 件とし、超えたら残りの件数を出す。

## 場面の ID

`tests/leader-eval/scenes/保-1`〜`保-7` を、`keep-1`〜`keep-7` に替える。番号は 1 対 1 に保つ。ディレクトリの名前を場面の ID にする決まりは変えないので、各 `scene.md` の「場面の ID」も `keep-<番号>` にする。

| 今の ID | 新しい ID | 型 |
| --- | --- | --- |
| `保-1`〜`保-7` | `keep-1`〜`keep-7` | `保` のまま |

- 型の名前の「保」は、ファイルの中身なので変えない。評価の結果の表の型の列にも、今のとおり「保」と出る
- `keep` は、型の「保」が指す、書き直しのあとも崩さない手順を表す語にする
- 場面の並びは、ID の文字の順で決まる。`keep-` も、数字で始まる ID のあとに並ぶので、結果の表の順は変わらない
- 新しい ID を、`docs/leader-principles.md`、各 `scene.md`、`tests/leader-eval-test.sh`、`MANIFEST` に入れる。`docs/leader-principles.md` は、この設計とともに替えてある。`tests/leader-eval/leader_eval.py` は ID の形を決めていないので変えない

## テスト

配布物の検証の各部のテストは、それぞれの設計に書く。この文書では、受け入れの条件とテストの対応だけを書く。

| 検証すること | テスト |
| --- | --- |
| 追跡するファイルの名前が、すべて印字できる ASCII | CI の `assets` のジョブが、PR と `main` の木に名前の検証を流す |
| 場面の ID が `keep-<番号>` で、ディレクトリの名前と一致する | `tests/leader-eval-test.sh` |
| ASCII 以外の名前で、名前と理由を出して止まる。除けば通る | `tests/build-assets-test.sh` の[コミットの形のケース](release.md#テストと-ci) |
| 作る側が拒む名前は入口も拒み、作る側が通す名前は入口も通す | `tests/build-assets-test.sh` の同じ答えのケース |
| ASCII 以外の名前のコミットで、タグ、push、下書きを作らずに止まる | `tests/release-test.sh` の[配布物を作れないケース](release.md#テストと-ci) |
| CI のジョブの定義 | `tests/release-workflow-test.sh` に足す [CI のジョブの決まり](ci.md#配布物の検証) |

PR の CI のジョブが本物の PR で止まることは、この変更の PR の中で確認する。CI のジョブを足したコミットを、場面の ID を替える前に push し、`assets` のジョブが `保-1` などの名前と理由を出して失敗することを見る。場面の ID を替えたコミットで、同じジョブが通ることを見る。

`.github/workflows/check.yml` の `concurrency` は、PR への新しい push で動いている実行を取り消す。そのため、場面の ID を替える実装の担当は、push の前に、CI のジョブを足したコミットの `assets` の結果を `gh run list` で 1 回読む。失敗で終わっていれば、その実行の URL と、出た名前と理由を PR のコメントに残してから push する。まだ終わっていないか、失敗していないときは push せず、読んだ結果を引き継ぎに書いて止まる。

## 利用者向けの文書の変更

原本を変える人への決まりは `CONTRIBUTING.md` に書き、この文書の理由は写さない。

`CONTRIBUTING.md` の「文書の改行」のあとに、節「ファイルとディレクトリの名前」を足す。止まったときの文は、この節を名前で示す。節には次を書く。

- 原本に置くファイルとディレクトリの名前は、印字できる ASCII（空白から `~` まで）だけで書き、バックスラッシュは使わないこと
- 漢字やかなは、ファイルの中身には書いてよいが、名前には使わないこと
- ASCII 以外の名前があると、配布物を作れず、バージョンを出せないこと
- PR の CI の `assets` のジョブと、`scripts/release.sh` が検証すること。手元では `bash scripts/build-assets.sh --commit HEAD tmp/assets` で同じ検証を流せること
- 止まったら、出た名前を ASCII に替えて、参照する文書とテストと `MANIFEST` を合わせること

`CONTRIBUTING.md` の「タグと Release を出す」に、タグを付ける前に配布物を作って検証し、名前の決まりに合わないと何も作らずに止まることを 1 文足す。タグがすでにあるときに止まったら、そのタグは使わず、直したコミットを新しいバージョンで出すことも足す。

`manual.md` と `README.md` は変えない。使う人の手順と、入口の検証の結果は変わらないため。`install.sh` に足す形は、`--help` の使い方に載せるが、使う人の手順には書かない。

## v1.11.1 の出し方

修正とバージョンを上げる変更を、1 つの PR にまとめる。v1.11.0 は配布物なしで止まっており、修正を入れたら同じ PR で v1.11.1 として出すため。

| 積む順 | 中身 |
| --- | --- |
| 修正 | この文書の変更のすべて。場面の ID、`install.sh`、`scripts/build-assets.sh`、`scripts/release.sh`、CI、テスト、`CONTRIBUTING.md`、`MANIFEST` |
| バージョンを上げる変更（最後） | `VERSION` を `v1.11.1` にし、`CHANGELOG.md` の先頭に `## v1.11.1` の節を足し、`MANIFEST` を作り直す |

バージョンを上げる変更は、修正をすべて積んだあとに最後のコミットとして積む。`CHANGELOG.md` の節に、積んだ修正の中身をそのまま書けるようにするため。修正だけを積んだ途中で `scripts/release.sh` を流しても、`VERSION` は `v1.11.0` のままで、`v1.11.0` のタグと下書きがあるので、検証の 9 で止まり、何も作らない。

### v1.11.1 の節

`## v1.11.1` の節には、次の段落を、利用者への影響が大きい順に書く。`## v1.11.0` の節は、タグの中身と同じに残し、書き換えない。

1. v1.11.0 は配布物なしで出せなかったこと。原因は、原本に ASCII 以外の名前のディレクトリがあり、配布物を作る検証で止まったこと。v1.11.0 の Release は公開していないこと
2. v1.11.1 は、v1.11.0 の変更をすべて含むこと。v1.11.0 の Release は公開しないので、Release の画面から読めるよう、`v1.11.1` のタグの `CHANGELOG.md` の `## v1.11.0` の節へ、絶対の URL（`https://github.com/AnD00/multica-squad-kit/blob/v1.11.1/CHANGELOG.md#v1110`）でリンクする
3. 原本を変える人への変更。ファイルとディレクトリの名前を印字できる ASCII に限り、PR の CI と `scripts/release.sh` が、発行と同じ手順で配布物を作って検証すること
4. 導入済みのプロジェクトへの影響。v1.10.0 から上げる人のために、v1.11.0 の影響をこの節で 1〜2 文に書き直す。セットアップを流し直すと、リーダーの指示と思考の深さ、実装・修正・QA の役の指示、squad-handoff、スクワッドの指示が置き換わり、エージェントとオートパイロットの登録は変わらないこと。v1.11.1 で足す影響はないこと。リーダーの評価の場面の ID は配布物の中のテストだけで、導入したプロジェクトには写らないこと

`scripts/release.sh` は、`v1.11.1` のタグを付けるコミットで `VERSION` と先頭の節を照合し、節が空でないことを確認して、検証の 9 を流す。

### 人が行うこと

タグと Release の操作は、今のとおり人が行う。

1. この PR のマージの前に、`CONTRIBUTING.md` の「バージョンを出す前に VM で確認する」を行い、結果を PR に書く。v1.11.0 で行った結果を使うか、行い直すかは、人が決める
2. マージのあと、`main` で `bash scripts/release.sh` を流し、確認に答える
3. v1.11.0 の下書きの Release を残すか、GitHub の画面で消すかを決める。v1.11.1 の発行は、v1.11.0 の下書きに触れずに進む

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| v1.11.0 のタグを付け直す | 発行済みのタグは動かさないと決めている。リポジトリの設定の ruleset も付け替えを拒む |
| 一覧の検証を緩め、ASCII 以外の名前を通す | tar の実装と言語の設定で出る形が変わり、展開の前に同じ名前と見なせない。要件で緩めないと決めた |
| 名前の検証を、`tests/` のテスト 1 本だけで行う | テストを流さずにタグを付けると、発行まで届く。発行と同じスクリプトでなければ、検証の漏れが残る |
| 作る側と入口に一覧の検証を 2 つ持ち、答えをテストで照合する | 写しが今回の食い違いの温床になる。一つの処理にすれば、テストは呼び出しの道を確認するだけで済む |
| PR の CI で、マージのコミット（`refs/pull/<番号>/merge`）を検証する | 要件で、PR の head の木を検証すると決めた。PR の作者が直すのは head の名前である |
| 名前の決まりを、英数字と `-`・`_`・`.`・`/` に絞る | 今の名前を変えずに済む範囲で、入口の検証と同じ範囲にそろえた。絞るかは別の要件で決める |
| `scripts/release.sh` が、タグを付けるコミットの `scripts/build-assets.sh` を取り出して流す | 取り出しのために作業ツリーかワークツリーを変える。今の `main` の検証は、タグの中身の検証より緩くならない |
| 修正の PR とバージョンを上げる PR を分ける（今までの上げ方） | v1.11.0 は配布物なしで止まっており、修正だけをマージしても出せない。1 つの PR にまとめ、マージのあとすぐ v1.11.1 を出す |
