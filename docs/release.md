# タグと Release を 1 つのコマンドで出す

バージョンを上げる PR をマージしたあとの、タグの発行と Release の作成を、原本の 1 つのコマンドにまとめる。人間が `main` で流し、公開の前にコマンドが確認を求める。配布物は、コマンドが下書きの Release を作ったあと、発行のワークフローが作って証明を付ける。コマンドは配布物を確かめてから Release を公開する。

この文書は、そのコマンドと発行のワークフローの設計と、その理由を書く。配布物の形と、使う人の側での確かめ方は `docs/install.md` に書く。原本を変える人への手順は `CONTRIBUTING.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

今は、マージのあとに、人間が `CONTRIBUTING.md` の長いシェルを 2 つ貼って流している。手間がかかり、流し忘れが起きやすい。Release を作り忘れると、Watch で「Releases」を選んだ人に新しいバージョンの通知が届かない。

コマンドは、今の 2 つのシェルと同じ確かめをしてから、注釈付きのタグの作成と push、下書きの Release の作成、配布物の作成の依頼、配布物の確かめ、Release の公開を続けて行う。自動にするのは、配布物を作って証明を付ける部分だけにする。次は対象にしない。

- バージョンを上げる PR（`VERSION`、`CHANGELOG.md`、`MANIFEST` の書き換え）の自動化。PR のレビューと CI を通す決まりを変えないため、今のまま手で作る
- マージをきっかけに、CI がタグと Release を作ること。公開は、人間がコマンドを流して決める。発行のワークフローは、コマンドが作った下書きに配布物を載せるだけで、タグと Release を作らず、公開もしない
- 利用側のリポジトリの、使うバージョンの記録を変えること。原本は利用側のリポジトリに触れない
- 変更の記録の本文を作ること。何を書くかは、バージョンを上げる PR で人間かエージェントが決める
- 発行済みのタグを動かすこと、消すこと。修正は新しいタグで配る。リポジトリの設定でも拒む（[リポジトリの設定](#リポジトリの設定)）
- 下書きの Release と、その配布物を消すこと。確かめで止まったときに、何が起きたかを人が見られるように残す。片付けは人が GitHub の画面で行う

## 置くもの

原本の `scripts/` に、コマンドを 1 つ置く。`scripts/check.sh` と `scripts/manifest.sh` と同じく、原本を変える人が使う道具なので、同じ場所にする。配布物を作るスクリプトも `scripts/` に置き、発行のワークフローから呼ぶ。

| ファイル | 役目 |
| --- | --- |
| `scripts/release.sh` | 確かめ、確認、タグの作成と push、下書きの Release の作成、配布物の作成の依頼と確かめ、公開をする |
| `scripts/build-assets.sh` | タグかコミットの中身から、配布物と `SHA256SUMS` を作る（[配布物を作る](#配布物を作る)）。PR の CI と、このコマンドの確かめの 9 でも使う |
| `.github/workflows/release-assets.yml` | 発行のワークフロー。配布物を作り、証明を付け、下書きの Release に載せる（[発行のワークフロー](#発行のワークフロー)） |
| `tests/release-test.sh`、`tests/release-check-test.sh`、`tests/release-failure-test.sh` | コマンドの動きを、一時の Git のリポジトリとスタブの `gh` で確かめる。ケースの分け方は[テストのファイルの分け方](#テストのファイルの分け方) |
| `tests/release-test-lib.sh` | 公開の 4 つのテストと画面の画像の仕組みが共有する準備。テストの照合と一時領域の用意は `tests/release-assertions.sh` が受け持つ。`-test.sh` で終えず、単独では流さない |
| `tests/build-assets-test.sh` | 配布物を作るスクリプトを、一時の Git のリポジトリで確かめる |
| `tests/release-workflow-test.sh` | 発行のワークフローの定義の決まり（きっかけ、権限、固定したバージョン）を確かめる |

`tests/release-tags-test.sh` は消す。`CONTRIBUTING.md` から取り出したシェルを流すテストで、そのシェルがなくなるため。`scripts/check.sh` は、`scripts/` の `*.sh` の `bash -n` をすでに流すので、変えない。

エラーと警告は、`lib/ui.sh` の `ui_init` と `ui_error`・`ui_warning` で出す。セットアップと同じ `エラー:`・`警告:` の印と色にそろえるため。確かめの一覧、手順の一覧、終わりの表示の記号と色と、行の書き換えも、`lib/ui.sh` の部品で出す（[色と印](#色と印)）。部品の形は [端末の画面の設計](screens.md#表示の部品libuish) に書く。

画面を画像にして、変える前と後を見比べる仕組みのファイルは、[画面を画像で見比べる](#画面を画像で見比べる)に書く。

## コマンドの形

原本のリポジトリのルートで、引数なしで流す。

```bash
bash scripts/release.sh
```

- 引数は `--help`（`-h`）だけを受ける。ほかの引数は、使い方を出して 2 で終わる
- 確認を飛ばす指定（`--yes` など）は持たない。公開は、毎回人間が中身を見て決めるため
- 出すバージョンは `VERSION` から読む。バージョンを引数で受けると、`VERSION` と違うバージョンを出す誤りの入り口になるため

終わり方は、次の 3 つにする。

| 終わり方 | 終了コード |
| --- | --- |
| タグと Release を作った、Release だけを作った、すでに両方ある | 0 |
| 確かめで止まった、確認で承認されなかった、途中で失敗した | 1 |
| 引数の誤り | 2 |

## 流れ

確かめをすべて終えてから確認を求め、承認されてから初めてタグと Release を作る。確かめで止まるときと、承認されないときは、何も変えない。承認は 1 回にし、そのあとは、配布物の確かめが通ったときだけ公開まで進む。

1. 確かめる（[確かめること](#確かめること)）。1 つでも当てはまれば、理由を出して止まる
2. タグと Release の今の状態を読み、することを決める（[タグと Release の状態](#タグと-release-の状態)）。すでに公開済みのときも、タグが指すコミットで 6〜8 を確かめ、通れば、そう出して 0 で終わる
3. これから配布物を作らせる状態のときは、タグを付けるコミットの中身で配布物を作り、確かめる（[確かめること](#確かめること)の 9）。止まれば、何も作らずに 1 で終わる
4. 公開する中身を出し、確認を求める（[確認](#確認)）
5. 承認されたら、することに応じて、タグの作成と push、下書きの Release の作成、配布物の作成の依頼、配布物の確かめ、公開を行う（[公開](#公開)）

## 確かめること

次の順に確かめる。今の `CONTRIBUTING.md` の 2 つのシェルが確かめていることに、手で確かめていたこと（未コミットの変更、Release の本文が空でないこと）と、バージョンの形を足したもの。

| 順 | 止まるとき | 出す理由の例 |
| --- | --- | --- |
| 1 | `git` か `gh` がない。`gh` が 2.102.0 より古い。原本のリポジトリのルートで流していない | `gh` がない、必要なバージョン |
| 2 | `origin` の URL から GitHub のリポジトリ（`OWNER/REPO`）を読めない | `origin` が GitHub のリポジトリでない |
| 3 | 今のブランチが `main` でない | `main` に切り替えて、`git pull --ff-only` してから流す |
| 4 | 追跡しているファイルに、未コミットの変更がある | 変更をコミットするか戻してから流す |
| 5 | `origin` の `main` を取ってきて比べ、手元の `main` と一致しない | 未公開のコミットがあるか、`origin/main` に遅れている |
| 6 | `VERSION` が `vX.Y.Z`（`X`・`Y`・`Z` は 0 以上の整数）の形でない | `VERSION` の中身と、期待する形 |
| 7 | `CHANGELOG.md` の先頭のバージョン（最初の `##` で始まる見出し）が `VERSION` と違う | 両方のバージョン |
| 8 | `CHANGELOG.md` のそのバージョンの節が、空白と改行だけ | そのバージョンの節が空 |
| 9 | タグを付けるコミットの中身から、配布物を作れないか、作った配布物が確かめを通らない | 止まった名前とその理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」 |

9 の開始は案内し、配布物を作るコマンドの出力は保存しておく。成功したときは表示せず、失敗したときはコマンドと受けた出力を標準エラーへ出してから、止まる理由を示す。

- 5 では、`git fetch --no-tags origin main` で `origin/main` だけを更新する。ブランチ、タグ、作業ツリーは変えない。古い `origin/main` と比べても、`main` が最新かは分からないため
- 4 は、追跡していないファイルを見ない。タグはコミットに付くので、追跡していないファイルは公開する中身に入らないため。`tmp/` などで止まらないようにする
- 6〜8 は、作業ツリーではなく、タグを付けるコミット（[タグと Release の状態](#タグと-release-の状態)）の `VERSION` と `CHANGELOG.md` を `git show` で読む。公開する中身と、確かめた中身を同じにするため
- 1 の `gh` のバージョンは、`docs/install.md` の[必要な `gh` のバージョン](install.md#必要な-gh-のバージョン)と同じにする。公開の前に、使う人と同じ確かめを流すため
- 9 は、[状態](#タグと-release-の状態)を読んでタグを付けるコミットが決まったあと、確認を求める前に行う。`bash scripts/build-assets.sh --commit <タグを付けるコミット> <一時の置き場>` を流し、発行のワークフローと同じ確かめを、タグを作る前に流す。一時の置き場は、通っても止まっても消す。止まったときは、`scripts/build-assets.sh` の出した名前と理由をそのまま見せ、そのあとに 9 で止まったことを出す
- 9 で流すのは、今の作業ツリーの `scripts/build-assets.sh` と `install.sh` である。4 と 5 で、作業ツリーは `origin/main` の先頭と同じになっている。タグがすでにあるときも、取り出しのために作業ツリーを変えない。中身は、タグを付けるコミットから `git archive` で取る
- 9 でタグがすでにあるときに止まったら、そのタグでは出せないことと、直したコミットを新しいバージョンで出すことを添える。発行済みのタグは動かさないため
- 9 を流すのは、これから発行のワークフローに配布物を作らせる 3 つの状態だけとする。タグも Release もない、タグがあって Release がない、配布物のない下書きがある、の 3 つである
- 配布物の 4 つがそろった下書きでは、9 を流さず、[公開の前の確かめ](#公開の前の確かめ)に任せる。その配布物は、タグの中身で作って確かめ終えている。タグのあとに `main` の確かめが厳しくなっても、出せる配布物の公開を止めないため
- 公開済みのときも、9 を行わない。公開済みの配布物は変えられず、止めても防げるものがないため。配布物が足りないか余分な下書きなど、止まる状態は、9 の前に止まる
- 3 と 5 で止まったときは、自分で `git switch` や `git pull` をしない。公開の前に手元の状態を黙って変えないため。止まった理由に、流すコマンドを添える

そのバージョンの節は、`## <バージョン>` の見出しの次の行から、次の `##` で始まる見出しの前の行までとする。前後の空行を除いたものを、Release の本文にする。

`OWNER/REPO` は、`git config --get remote.origin.url` の値から読む。`https://github.com/OWNER/REPO(.git)`、`git@github.com:OWNER/REPO(.git)`、`ssh://git@github.com/OWNER/REPO(.git)` の 3 つの形を受ける。`git remote get-url` を使わないのは、`url.<base>.insteadOf` で書き換えた先を返し、テストで GitHub の名前を保てないため（[テストと CI](#テストと-ci)）。

## タグと Release の状態

そのバージョンのタグと Release が、手元、`origin`、GitHub のどこにあるかと、Release が下書きか公開済みかを読み、次の表ですることを決める。すでにあるタグは、作り直さず、動かさない。

| 手元のタグ | `origin` のタグ | Release | すること |
| --- | --- | --- | --- |
| ない | ない | ない | 確認のあと、タグを作って push し、下書きを作り、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | ない | 確認のあと、下書きを作り、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物なし | 確認のあと、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物の 4 つがそろう | 確認のあと、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物が足りないか余分 | 止まる。下書きの配布物を GitHub の画面で消してから流し直すことを出す |
| ある | ある（同じタグ） | 公開済み | 公開の操作はせず、タグが指すコミットで 6〜8 を確かめ、通れば、すでに出してあることと Release の URL を出して 0 で終わる |
| ある | ない | どれでも | 止まる。手元のタグがまだ公開されていないことと、`git tag -d <バージョン>` で消してから流し直すことを出す |
| ない | ある | どれでも | 止まる。`git fetch origin tag <バージョン>` で取ってきてから流し直すことを出す |
| ある | ある（違うタグ） | どれでも | 止まる。手元と `origin` のタグが違うことを出す |
| ない | ない | ある | 止まる。タグのない Release があることを出す |

- 手元のタグは、`git rev-parse --verify --quiet refs/tags/<バージョン>` で読む。`origin` のタグは、`git ls-remote origin refs/tags/<バージョン>` で読む。`git fetch --tags` を使わないのは、`origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠すため
- 「同じタグ」は、手元のタグのオブジェクトの SHA と、`ls-remote` が返す SHA が一致することとする
- 手元にタグがあっても、注釈付きでない（`git cat-file -t` が `tag` でない）ときは、止まる。今の手順は注釈付きのタグだけを作るので、手で付けた別のタグのおそれがあるため
- Release は、`gh api --paginate repos/OWNER/REPO/releases` の一覧から、`tag_name` が `<バージョン>` のものを探して読む。`releases/tags/<バージョン>` は下書きを返さないため。一覧に 2 つ以上あるときは、止まる。一覧を読めない（認証、ネットワーク）ときも、理由を出して止まる
- 配布物の 4 つは、`docs/install.md` の[配布物](install.md#配布物)の名前とする。下書きに、この 4 つのほかの配布物があるときも「余分」とする
- 配布物が足りないか余分な下書きを、コマンドは直さない。ワークフローの途中の失敗か、誰かの差し替えかを、人が見て決めるため
- 1 つ前のバージョンまでの、配布物のない公開済みの Release も、「公開済み」として扱う

タグを付けるコミットは、タグがないときは手元の `main` の先頭（`origin/main` と一致したもの）とする。タグがあるときは、そのタグが指すコミットとし、[確かめること](#確かめること)の 6〜8 もそのコミットで確かめる。タグを付けたあとに `main` に別のコミットが入っていても、Release の本文と配布物はタグの中身から作るため。

## 確認

確かめの一覧、Release の本文、出すものの見出し、流す手順の一覧の順に出し、そのあとで問いを出して、標準入力から答えを読む。問いに答えるときに、確かめた結果と、出すもの・流す手順が画面に残るようにするため。問いは標準エラー出力に、ほかは標準出力に出す。

画面の構造と状態は、見出しやラベルの文字ではなく、字下げ・空行・記号・色で示す（[端末の画面の設計](screens.md#目的と範囲)）。文字で出すのは、値、手順の動作、問いだけにする。

```text
  ✔ 道具              git gh tar shasum diff cmp  gh 2.110.0  2.102.0 以上
  ✔ 場所              example/kit  main
  ✔ 未コミットの変更  なし
  ✔ origin/main       0123456789ab
  ✔ バージョン        VERSION v1.6.0  CHANGELOG.md v1.6.0
  ✔ タグと Release    手元 なし  origin なし  Release なし

  │ ### Added
  │
  │ - （そのバージョンの節の全文）

  v1.6.0  example/kit
  0123456789ab  バージョンを v1.6.0 にする

  ○ タグを作って push する
  ○ 下書きの Release を作る
  ○ 発行のワークフローに配布物を作らせ、終わるまで待つ
  ○ 配布物を確かめる
  ○ Release を公開する

公開しますか [y/N]:
```

- `y` か `Y` だけを承認とする。ほかの答え、空の答え、入力の終わりは、`公開を取りやめました。` と出して、何も変えずに 1 で終わる。`vm/lima.sh` の `delete` の確認とそろえる
- 標準入力が端末でない（`[[ -t 0 ]]` が偽の）ときは、問いを出さずに、確認を求められないことを出して 1 で終わる。パイプで `y` を流し込んで確認を飛ばせないようにするため。エージェントの実行も端末を持たないので、エージェントが公開することもない
- 端末の判定は、[状態](#タグと-release-の状態)を読んで、することが決まったあとに行う。9 を流す状態では、9 が通ったあとに行う。すでに公開済みのときは、6〜8 の確かめのあとなら、端末でなくても 0 で終わる
- 確かめの一覧、本文、見出し、手順の一覧は、端末の判定を通ったあとに、まとめて出す。止まるとき、公開済みのとき、端末でないときの出力は、今の 1 行のままにする
- 確認の前の画面は、出力が端末でも書き換えない。行を順に出すので、端末でない出力にも同じ行が残る

### 確かめの一覧

[確かめること](#確かめること)と[タグと Release の状態](#タグと-release-の状態)の結果を、6 つの項目に分けて、1 項目 1 行で出す。行は、2 字の字下げ、緑の `✔`、項目の名前、灰の読んだ値の順にする。項目の名前は、6 つの中で最も長い名前の幅にそろえ、`:` を付けない。通ったことは記号と色で示し、結果の語は出さない。

| 項目 | 束ねる確かめ | 灰の値 |
| --- | --- | --- |
| 道具 | 1 の道具と `gh` のバージョン | 道具の名前、今の `gh` のバージョン、必要なバージョン |
| 場所 | 1 のルート、2 の `OWNER/REPO`、3 のブランチ | `OWNER/REPO` と、ブランチの名前 |
| 未コミットの変更 | 4 | `なし` |
| origin/main | 5 | 取ってきた `origin/main` の先頭 12 文字の SHA |
| バージョン | 6〜8 | `VERSION` のバージョンと、`CHANGELOG.md` の先頭のバージョン |
| タグと Release | [状態](#タグと-release-の状態)の表 | 手元のタグ（ある・ない）、`origin` のタグ（ある・ない・同じ）、Release（ない・下書き・配布物の数） |

- 確かめは今の順に流し、結果の行は一覧の順にためておいて、端末の判定のあとで出す。止まるときに、それまでに通った行を出すと、止まるときの出力が変わるため
- 一覧に出るのは、すべて通ったときだけなので、記号は `✔` だけを使う。止まるときは、今の `エラー:` の行だけを出す
- 6〜8 は、[タグを付けるコミット](#タグと-release-の状態)の中身で確かめたので、バージョンの行の値もそのコミットから読んだ値にする

### Release の本文

本文は、抜粋にせず全文を出す。本文の各行の頭に、2 字の字下げと灰の `│` と空白 1 字を付け、範囲を左の罫線で示す。空の行は、字下げと `│` だけにする。行の頭の字下げと `│` と空白を除くと、本文と同じ文になる。

区切りの文字の行は出さない。本文の行の頭が `│` になるので、行をそのままタスクやチャットに貼っても、`#` や `-` や `>` で始まる行として読まれず、見出しや横線や引用に化けない。本文の行の色は既定の色のままにし、罫線だけを灰にする。

### 出すものの見出しと、流す手順

本文のあと、問いの直前に、出すものの見出しと、流す手順の一覧を出す。本文が長くても、答えるときに見出しと手順が画面に残るようにするため。

- 見出しの 1 行目は、太字のバージョンと、灰の `OWNER/REPO` にする。2 行目は、灰のタグを付けるコミットの先頭 12 文字の SHA と、既定の色の件名にする。ラベルは付けない
- タグは、今までどおり完全な SHA を明示して付ける（[公開](#公開)）
- 流す手順は、番号付きの文ではなく、チェックリストの一覧として出す（[端末の画面の設計](screens.md#チェックリスト)）。手順は[公開](#公開)の手順の表の 5 つで、[状態](#タグと-release-の状態)から決まる手順だけを、灰の `○` と灰の名前で並べる
- 承認のあとは、この一覧の印を、その場で書き換えていく（[手順の表示](#手順の表示)）。並びと名前は同じにする

| [状態](#タグと-release-の状態)の「すること」 | 並べる手順 | 数 |
| --- | --- | --- |
| タグを作るところから | 1〜5 | 5 |
| 下書きを作るところから | 2〜5 | 4 |
| 配布物を作らせるところから | 3〜5 | 3 |
| 確かめるところから | 4〜5 | 2 |

手順の一覧は、出力が端末でなくても出す（`ui_steps_show`）。問いの前に、流す手順を人が見て決めるため。

## 公開

承認されたら、することに応じて次の手順を順に行う。どの手順で失敗しても、その先は行わずに 1 で終わる。

| 手順 | 名前 | 行うこと |
| --- | --- | --- |
| 1 | タグを作って push する | `git tag -a <バージョン> -m <バージョン> <タグを付けるコミット>` でタグを作り、`git push origin refs/tags/<バージョン>` で push する。`HEAD` ではなく、確認で出したコミットを明示する。`--force` は付けない。`origin` に同じ名前のタグがあれば、Git が拒むので、動かすことはない |
| 2 | 下書きの Release を作る | `gh release create <バージョン> --repo OWNER/REPO --draft --verify-tag --title <バージョン> --notes-file <本文のファイル>`。本文は一時のファイルで渡し、空白と改行をそのまま保つ |
| 3 | 発行のワークフローに配布物を作らせ、終わるまで待つ | `gh workflow run release-assets.yml --repo OWNER/REPO --ref <バージョン>` で発行のワークフローを起こし、その実行を `gh run list` で見つけて、`gh run watch --exit-status` で終わるまで待つ |
| 4 | 配布物を確かめる | [公開の前の確かめ](#公開の前の確かめ) |
| 5 | Release を公開する | `gh release edit <バージョン> --repo OWNER/REPO --draft=false` |

3 の実行は、起こした時刻のあとに作られた、`workflow_dispatch` の実行で、`headBranch` が `<バージョン>` のものとする。起こしてから一覧に出るまで間があるので、決まった回数だけ間を空けて読み直す。見つからないときは止まる。

途中で失敗したときは、次のようにする。止まるときの案内の文は変えない。失敗した手順の `✖`、[隠す出力](#隠す出力)の中身、下書きの URL の続きの行（[手順の表示](#手順の表示)）だけを足す。

| 失敗した手順 | すること |
| --- | --- |
| 1 の push | この実行で作った手元のタグを `git tag -d` で消し、push に失敗したことを出す。流し直せば、はじめからやり直せる |
| 2 の下書きの作成 | タグは残す。下書きの作成に失敗したことと、同じコマンドを流し直せばタグのあとから続けることを出す |
| 3 のワークフロー | 下書きは残す。実行の URL を出す。配布物がないなら、流し直すと配布物を作らせ直す。途中まで載っているなら、[状態](#タグと-release-の状態)の「足りないか余分」で止まる |
| 4 の確かめ | 公開しない。下書きと配布物は残し、何が合わなかったかを出す。配布物の差し替えのおそれがあるので、人が見るまで流し直さないことも出す |
| 5 の公開 | 下書きは残す。流し直すと、配布物を確かめ直して公開する |

push の失敗で手元のタグを消すのは、まだ公開していないタグを手元に残すと、次の実行が「手元だけにある」で止まるため。push が実は `origin` に届いていたときは、次の実行が「`origin` だけにある」で止まり、取ってくるコマンドを出す。

終えたら、[終わりの表示](#終わりの表示)を出す。Watch の通知は、GitHub が Release の公開をきっかけに送る。下書きの間は送られない。コマンドは通知を送らない。

### 手順の表示

承認のあと、確認の前に出した手順の一覧の印を、その場で、スピナー、`✔` の順に変えていく。今の手順と残りの手順が、いつも見える。部品は `lib/ui.sh` のチェックリスト（[端末の画面の設計](screens.md#チェックリスト)）を使う。

```text
  ✔ タグを作って push する                              v1.6.0  0123456789ab
  ✔ 下書きの Release を作る
      https://github.com/OWNER/REPO/releases/tag/untagged-0123456789ab
      → https://github.com/OWNER/REPO/releases/tag/v1.6.0
  ⠼ 発行のワークフローに配布物を作らせ、終わるまで待つ  ━━━━━━━━━━──────── 48s
      https://github.com/OWNER/REPO/actions/runs/4242
  ○ 配布物を確かめる
  ○ Release を公開する

公開しますか [y/N]: y
```

一覧は標準出力に、問いは標準エラー出力に出ている。書き換えるのは、標準出力と標準エラー出力の両方が端末で色が出るときだけにする。書き換えるときは、書き換える範囲の先頭まで上へ戻って、範囲の手順の行と、その下の空行と、答えた問いの行を出し直す。答えた問いの行を一覧の下に残し、承認したことが画面から消えないようにするため。終わった手順の行を残すこと、行を端末の幅で切ること、画面に収まらないときや端末の大きさが変わったときに書き換えをやめることは、[画面に収まらないとき](screens.md#画面に収まらないとき)のとおりにする。

| 手順 | `✔` に添える値 | 続きの行 |
| --- | --- | --- |
| 1 | 灰のバージョンと、タグを付けたコミットの先頭 12 文字の SHA | なし |
| 2 | なし | 灰の下書きの URL と、`→` と既定の色のタグの名前の URL の 2 行 |
| 3 | 起こしたときから見張りが終わるまでの時間 | 灰の実行の URL。見つけた時点で出す |
| 4 | なし | 4 つの確かめの行（[公開の前の確かめ](#公開の前の確かめ)） |
| 5 | なし | なし |

- 下書きの URL は、灰の色で、`→` を付けたタグの名前の URL の上に出す。灰の URL が今だけのもので、矢印の先が公開のあとの URL であることを、配置と色で示す。説明の文は足さない
- 止まるときの案内に下書きの URL を出すとき（[状態](#タグと-release-の状態)の「足りないか余分」と、タグのない Release が下書きのとき）も、案内の URL の次の行に、同じ `→` とタグの名前の URL を出す。案内の文は変えない
- 時間は、[端末の画面の設計](screens.md#チェックリスト)の形（`48s`、`1m12s`）にする
- 続きの行は、手順の行の下に、6 字の字下げで出す
- 確かめるところから続けるときは、この実行でワークフローを起こさないので、3 の手順を一覧に出さない

失敗したときは、動いていた手順を太字の赤の `✖` にし、灰の値に扱っていたもの（実行の URL など）を添える。書き換えはそこで止め、カーソルを一覧の下に置く。そのあと、[隠す出力](#隠す出力)の中身を出し、今の止まるときの案内を出す。残りの手順は `○` のまま残す。

出力が端末でないか色が出ないときは、一覧を書き換えない。手順が終わるたびに、`✔` か `✖` の手順の行と、その続きの行を順に出す。確認の前の `○` の一覧と合わせて、どこまで進んだかを行の並びで追える。

### 隠す出力

タグの push、ワークフローの起動、ワークフローの見張りは、標準出力と標準エラー出力を一時の置き場のファイルに受け、画面に出さない。代わりに、[手順の表示](#手順の表示)の印と値で示す。英語の案内や進み具合の行が、コマンドの行に混ざらないようにするため。

| コマンド | 隠す出力の例 | 代わりに示すもの |
| --- | --- | --- |
| `git push origin refs/tags/<バージョン>` | `Enumerating objects`、`Writing objects`、`To <URL>`、`[new tag]` | 1 の手順の `✔` と、バージョンと SHA |
| `gh workflow run` | `Created workflow_dispatch event`、実行の URL、`To see the created workflow run` | 3 の手順の続きの行の、実行の URL（`gh run list` で見つけたもの） |
| `gh run watch --exit-status` | 実行の名前、`JOBS`、ジョブとステップの一覧、`completed with` | 3 の手順のスピナー、ゲージ、経過の時間と、かかった時間 |

- コマンドが失敗したときは、失敗した手順を `✖` にしたあと、灰の `$` と流したコマンドの 1 行を出し、受けたファイルの中身を、そのまま標準エラー出力に出す。そのあとに、今の止まるときの案内を出す。コマンドの行で、スクリプトの行と外のコマンドの出力の境目を示す。区切りの文字の行は出さない
- 止まる条件と終了コードは、コマンドの終了コードで決める今のままにする。出力の行き先を変えるだけである
- `gh release create` と `gh release edit` は、今も標準出力を受けて URL を読んでいる。標準エラー出力は、失敗したときに出るものなので、今のまま画面に出す。書き換えているときは、`✖` を出してから画面に出るよう、標準エラー出力もファイルに受けて、失敗したときに同じ形で出す

### ワークフローを待つ間の経過

`gh run watch --exit-status` を、出力をファイルに受けて裏で流し（端末には書かせない）、終わるまで、3 の手順の行にスピナー、ゲージ、経過の時間を出す。終わったら、その終了コードで成否を決める。端末へ描くのは、待つループを持つ親のプロセスだけにする。

- 待つループが 0.1 秒ごとに `ui_step_tick` を呼んでスピナーを 1 コマ回し、経過の時間は 1 秒ごとに書き換える。スピナーを回す裏のプロセスは置かない
- ゲージは、実行のジョブのステップのうち、終わったステップの割合で描く。`gh run view <実行の ID> --repo OWNER/REPO --json jobs` を 5 秒ごとに読む。読めないときや、ステップがまだないときは、ゲージを前の割合のまま残し、止まらない。成否は `gh run watch` の終了コードだけで決める
- 読む間隔は、テストで短くするために、環境変数 `RELEASE_PROGRESS_INTERVAL`（秒）で変えられるようにする。`RELEASE_RUN_FIND_INTERVAL` と同じ扱いにする
- ゲージを読むのは、書き換えるときだけにする。書き換えないときは、行に描けないので、`gh` を余分に呼ばない
- 書き換えないときは、決まった間隔で、灰の `…`、手順の名前、経過の時間の 1 行を出す。間隔は 30 秒にし、ワークフローが 1 分ほどで終わる間に 1〜2 行だけ出す。行を積み重ねすぎず、ファイルやパイプに残した出力でも止まっていないことが分かるようにするため
- 書き換えないときの間隔は、環境変数 `RELEASE_WATCH_TICK_INTERVAL`（秒）で変えられるようにする
- 裏で流す見張り（`gh run watch`）は、終わる前にコマンドが止まったとき（Ctrl-C、エラー）に、`cleanup` の中で止める。端末を持たない裏の処理は Ctrl-C を受けず、残り続けるため

### 公開の前の確かめ

下書きの配布物を、使う人と同じ確かめと、タグの中身との照らし合わせで確かめる。公開したあとは差し替えられないので、公開の前に止めるため。

1. 下書きの 4 つの配布物を、一覧で読んだ配布物の ID から `gh api -H 'Accept: application/octet-stream' repos/OWNER/REPO/releases/assets/<ID>` で、新しい一時の置き場へ取ってくる。下書きの配布物は、タグの名前からは取れないため
2. タグの `install.sh`（`git show <バージョン>:install.sh`）で、`bash <その写し> --verify <バージョン> <置き場>` を流す。証明、チェックサム、一覧の確かめを、使う人の入口と同じ道で行うため
3. 配布物の `install.sh` の証明を確かめ、`SHA256SUMS` の行と照合し、タグの `install.sh` とバイトごとに一致することを確かめる
4. 配布物を展開したものと、`git archive <バージョン>` を展開したものを、`diff -r` で比べる。ワークフローがタグと違う中身を固めていないことを確かめるため
5. 証明の束（`.sigstore.json`）で、`gh attestation verify <配布物> --bundle <束>` を、`docs/install.md` の[確かめ方](install.md#確かめ方)の 4 つの指定で流す

2〜5 は、通るたびに、4 の手順の続きの行に、[確かめの一覧](#確かめの一覧)と同じ形の 1 行を出す。行は、6 字の字下げ、緑の `✔`、項目の名前、灰の値の順にする。1 の取得は、行を出さない。取得に失敗したときは、今の止まるときの案内を出す。

```text
  ✔ 配布物を確かめる
      ✔ タグの install.sh    証明  チェックサム  tar.gz の中の一覧
      ✔ 配布物の install.sh  証明  SHA256SUMS の行  タグの install.sh
      ✔ 配布物の中身        git archive v1.6.0
      ✔ 証明                配布物  SHA256SUMS
```

| 確かめ | 項目 | 灰の値 |
| --- | --- | --- |
| 2 | タグの install.sh | 証明、チェックサム、tar.gz の中の一覧 |
| 3 | 配布物の install.sh | 証明、SHA256SUMS の行、照らし合わせたタグの install.sh |
| 4 | 配布物の中身 | 照らし合わせた `git archive <バージョン>` |
| 5 | 証明 | 配布物と SHA256SUMS |

確かめが通らなかったときは、その確かめの行を太字の赤の `✖` にし、4 の手順も `✖` にする。

2 の `install.sh` の出力は、標準出力と標準エラー出力をファイルに受け、画面に出さない。`install.sh` の文は導入する人に向けたもので、「展開も実行もしていません」のように、公開のコマンドの流れでは誤解を招く行があるため。`install.sh` の出力は変えない。失敗したときは、[隠す出力](#隠す出力)と同じ形で中身を出してから、今の止まるときの案内を出す。3 と 5 の証明の失敗と、4 の差分は、今のまま止まるときの案内の前に出す。

### 終わりの表示

公開したら、手順の一覧の下に、空行と、完了の印の付いた終わりの表示を出す。どの手順から続けたときも、同じ形にする。項目名のラベルは並べず、値の形と配置で見分ける。

```text
✔ v1.6.0  https://github.com/OWNER/REPO/releases/tag/v1.6.0
  0123456789abcdef0123456789abcdef01234567

  multica-squad-kit-v1.6.0.tar.gz
  install.sh
  SHA256SUMS
  multica-squad-kit-v1.6.0.sigstore.json

  https://github.com/OWNER/REPO/actions/runs/4242
```

| 行 | 中身 | 色 |
| --- | --- | --- |
| 1 行目 | 完了の印 `✔` とバージョン、Release の URL | 印とバージョンは太字の青緑、URL は既定の色 |
| 2 行目 | タグを付けたコミットの完全な SHA | 灰 |
| 配布物 | 4 つの配布物の名前を 1 行ずつ | 既定の色 |
| 最後 | 発行のワークフローの実行の URL | 灰 |

- コミットは、タグを付けたコミットの完全な SHA にする。見出しの 12 文字ではなく、あとで照らし合わせられる値を残すため
- Release の URL は、`gh release edit` が返した URL にする。返さなかったときは、今と同じくタグの名前の URL にする
- 配布物の sha256 は出さない。同じ値が Release の `SHA256SUMS` にあるため
- 確かめるところから続けたときは、この実行でワークフローを起こしていない。そのときは、`gh run list` で、`workflow_dispatch` の実行のうち、`headBranch` が `<バージョン>` で成功したものの最も新しい URL を読んで出す。読めない、または見つからないときは、最後の行を、橙の `!` と `発行のワークフローの実行が見つかりません。GitHub の Actions の画面で確かめてください。` にする。公開は済んでいるので、ここでは止まらず 0 で終わる

## 色と印

記号と色は、[端末の画面の設計](screens.md#記号と色)の決まりを使い、セットアップの画面とそろえる。色は `lib/ui.sh` の部品だけで付け、`scripts/release.sh` は記号の文字と色の番号を持たない。使う人への説明は、`manual.md` の「表示の色と印」に書く。

| 表示 | 記号と色 |
| --- | --- |
| 確かめの一覧、確かめの行、終わった手順 | 緑の `✔` と、灰の値 |
| まだの手順 | 灰の `○` と灰の名前 |
| 動いている手順 | 青のスピナーと、青と灰のゲージ |
| 失敗した手順と確かめ | 太字の赤の `✖` |
| Release の本文の罫線 | 灰の `│` |
| 見出しのバージョン | 太字 |
| 下書きの URL | 灰の URL と、`→` の付いたタグの名前の URL |
| 終わりの表示 | 太字の青緑の `✔` とバージョン |
| 実行の URL が見つからない | 太字の橙の `!` |
| 止まるとき | 今の `エラー:` の行（`ui_error`） |

色を付けるかと、行を書き換えるかは、`lib/ui.sh` の判定のとおりにする（[端末の画面の設計](screens.md#書き換えの判定)）。`NO_COLOR`、端末でない出力、`TERM` が空か `dumb`、256 色未満のときは、色の制御文字と行の書き換えを出さない。そのときも、`✔`・`✖`・`○`・`│`・`→` の記号と字下げで、状態と範囲が分かる。

## 発行のワークフロー

`.github/workflows/release-assets.yml` は、`scripts/release.sh` が起こしたときだけ動き、下書きの Release に配布物を載せる。タグと Release は作らず、公開もしない。

- きっかけは `workflow_dispatch` だけにする。タグの push をきっかけにすると、下書きができる前に動き、下書きを待つか作る仕事が要るため
- 最初に、`github.ref` が `refs/tags/vX.Y.Z` の形であることと、そのタグの下書きの Release が配布物なしであることを確かめる。当てはまらなければ、何も作らずに失敗する
- 動かす場所は、GitHub の用意した `ubuntu-24.04` にする。使う人は `--deny-self-hosted-runners` で確かめる
- 権限は、ワークフローの全体を `{}` にし、ジョブだけに `contents: write`（下書きへの載せ）、`id-token: write` と `attestations: write`（証明）を与える。証明のアクションの README が、固定したバージョンでほかの権限を求めるときは、その権限だけを足す
- 使うアクションは、コミットの SHA で固定し、バージョンを注記する。タグの付け替えで中身が変わらないようにするため
- `actions/checkout` は、`persist-credentials: false` でタグを取り出す。タグの指すコミットと、取り出した `HEAD` が同じことを確かめる
- 証明は、GitHub の `actions/attest-build-provenance` で、配布物、`install.sh`、`SHA256SUMS` の 3 つに付ける。出力の証明の束を、`multica-squad-kit-<バージョン>.sigstore.json` の名前で写す
- 4 つを `gh release upload <バージョン>` で下書きに載せる。`--clobber` は付けない。同じ名前のものがあれば、上書きせずに失敗する

書き込みの権限を持つ人は、このワークフローを手で起こせる。それでも、下書きでない Release と、配布物の載った下書きには載せないので、公開済みの Release は変わらない。

### 配布物を作る

`scripts/build-assets.sh` は、タグかコミットの中身から、配布物、`install.sh`、`SHA256SUMS` を出力先に作る。ワークフローの中に処理を書かず、スクリプトにして、手元のテストで確かめられるようにする。

```bash
bash scripts/build-assets.sh <バージョン> <出力先>
bash scripts/build-assets.sh --commit <コミット> <出力先>
```

- タグの形は、発行のワークフローが使う。取り出したタグの中身から作る
- コミットの形は、PR の CI と `scripts/release.sh` の確かめの 9 が使う。タグがなくても、渡したコミットの中身で、タグの形と同じ確かめを流す。`<コミット>` は `HEAD` やブランチの名前でもよく、`git rev-parse --verify <コミット>^{commit}` で SHA に決めてから使う
- コミットの形のバージョンは、そのコミットの `VERSION` を `git show <SHA>:VERSION` で読む。`vX.Y.Z` の形でなければ止まる

どちらの形も、次の順に行う。下の「対象」は、タグの形ではタグ、コミットの形では決めた SHA である。

1. タグの形では、`HEAD` が `<バージョン>` のタグの指すコミットで、`VERSION` が `<バージョン>` と一致することを確かめる。コミットの形では行わない
2. 対象の木の名前を、`git ls-tree -r -t -z --name-only <対象>` で読み、`docs/asset-names.md` の[名前の決まり](asset-names.md#名前の決まり)に合わないものがあれば止まる。見分けは `LC_ALL=C` で、名前のバイトに `[:print:]` でない文字かバックスラッシュがあるかで行う。出すものは[止まったときに出すもの](asset-names.md#止まったときに出すもの)のとおり
3. `git archive --format=tar.gz --prefix=multica-squad-kit-<バージョン>/ <対象>` で、配布物を作る
4. 配布物を、作業ツリーの `install.sh` の `--check-listing`（`docs/install.md` の[入口のスクリプト](install.md#入口のスクリプト)）で確かめる。止まったら、`install.sh` の出した理由に、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」と `docs/install.md` の[展開の前の確かめ](install.md#展開の前の確かめ)を添えて止まる
5. 新しい一時の置き場に展開し、`MANIFEST` の一覧と中のファイルが一致し、`shasum -a 256 -c MANIFEST` が通ることを確かめる。配布物で流すセットアップが、`MANIFEST` の確かめで止まらないようにするため
6. ルートの `install.sh` を写し、2 つの SHA-256 を `SHA256SUMS` に書く。コミットの形でも同じに作る。作るものを形で変えず、確かめる道を発行と同じにするため

2 の名前の確かめを 4 の前に置くのは、tar の一覧ではなく Git の名前のバイトで見分け、どの名前がなぜ止まったかを、言語の設定によらずにそのまま出すため。4 は、2 をすり抜けたもの（リンク、特殊なファイル、上へ出るパスなど）を、使う人と同じ処理で止める。今の `scripts/build-assets.sh` にある一覧の確かめの写しは消し、`install.sh` に一本化する。

4 で呼ぶ `install.sh` は、作業ツリーのもの（`scripts/build-assets.sh` と同じ取り出しの、ルートの `install.sh`）とする。発行のワークフローとタグの形では、作業ツリーはタグの中身である。PR の CI では PR の head、`scripts/release.sh` では `origin/main` の先頭である。

`.gitattributes` の `export-ignore` は使わない。配布物の中身と `MANIFEST` を、タグの中身と同じにするため。

## リポジトリの設定

公開したあとの Release の配布物とタグを差し替えられないように、人がリポジトリの設定を変える。コマンドとワークフローは、設定を変えない。README の 1 行のコマンドは、最新の Release の `install.sh` を確かめずに流すので、公開後の差し替えはこの設定だけで防ぐ（`docs/install.md` の[防げることと残るリスク](install.md#防げることと残るリスク)）。

| 設定 | 値 | 防ぐもの |
| --- | --- | --- |
| Settings の Releases の「Enable release immutability」 | 有効 | 公開済みの Release の配布物の差し替えと、そのタグの付け替えと削除 |
| タグの ruleset（Target tags に `v*`） | 「Restrict updates」と「Restrict deletions」を有効にし、「Restrict creations」は付けない。bypass の一覧は空にする | 下書きの間と、この設定の前に公開したタグの付け替えと削除 |

- 不変の Release は、有効にしたあとに公開した Release にだけ効く。そのため、この設定は、この変更を入れた最初のバージョンを出す前に行う
- ruleset は、作ることを止めない。`scripts/release.sh` がタグを push できるようにするため
- 設定のあと、最初のバージョンを出したときに、公開済みの Release への `gh release upload --clobber` と、タグの `git push --force` が拒まれることを確かめる。手順は `CONTRIBUTING.md` に書く

リポジトリの管理者は、これらの設定を外せる。そのため、発行の権限の乗っ取りは防げず、`docs/install.md` の[防げることと残るリスク](install.md#防げることと残るリスク)に書く。

## テストと CI

今の `tests/release-test.sh` を新しい流れに合わせて広げ、`tests/build-assets-test.sh` と `tests/release-workflow-test.sh` を足して、今の CI の `scripts` の両 OS で流す。本物の GitHub には push せず、Release もワークフローの実行も作らない。発行のワークフローそのものは、手元では動かせないので、定義の決まりを読んで確かめ、最初のバージョンを出すときに人が確かめる。

- `origin` は、一時の置き場に作った bare のリポジトリにする。手元の作業コピーの `remote.origin.url` は `https://github.com/example/kit.git` のままにし、`url.<bare のパス>.insteadOf` で、Git の取得と push を bare に向ける。コマンドは本物と同じ道で `OWNER/REPO` を読み、push は bare に届く
- `gh` は、`PATH` の先頭に置いたスタブにする。受けた引数と、`--notes-file` の中身を記録する。`--version` のバージョン、`api` の Release の一覧（ない、下書き、公開済み、配布物の数、読めない）、`release create`、`workflow run`、`run list`、`run watch`、`release edit` の成否と、配布物の取得で返すファイル、`attestation verify` の成否を、ケースごとに切り替える
- スタブの `gh` と、一時のリポジトリを作る関数は、`tests/release-test-lib.sh` に移し、[画面を画像で見比べる](#画面を画像で見比べる)の仕組みと共有する。隠す対象のコマンド（`gh workflow run`、`gh run watch`、タグの push）のスタブは、本物と同じ文面を出す（[スタブ](#スタブ)）。隠したことを、テストで確かめられるようにするため
- 配布物は、テストの中で `scripts/build-assets.sh` をタグに流して作り、スタブが返す。中身を差し替えた配布物も、同じ道で作る
- 確認の答えは、標準入力を疑似端末につないで送る。`tests/ui-pty.py` に、標準入力を疑似端末につなぎ、ファイルの中身を送る指定を足す。今の `--stdin` はパイプにつなぐので、端末の判定を通らないため
- Git の名前とメールは、`CONTRIBUTING.md` の「テストを書く決まり」のとおり、環境変数か `-c` で渡す

確かめるケースは次のとおり。

| ケース | 確かめること |
| --- | --- |
| 承認する | `origin` に注釈付きのタグができ、`main` の先頭を指す。`release create --draft` が 1 回呼ばれ、本文がそのバージョンの節と一致する。`workflow run`、確かめ、`release edit --draft=false` の順に呼ばれる。0 で終わる |
| 承認しない（`n`、空の答え、入力の終わり） | 手元と `origin` にタグがなく、`gh` の書き込みが呼ばれない。1 で終わる |
| 標準入力が端末でない | 問いを出さず、タグも Release もできない。1 で終わる |
| [確かめること](#確かめること)の 1 の `gh` のバージョンと、3〜8 | それぞれ理由を出して止まり、`git fetch` のほかは何も変えず、`gh` の書き込みを呼ばない。バージョンが古いときは、必要なバージョンを出す |
| タグがあって Release がない | 承認すると、タグのオブジェクトの SHA が変わらず、下書きの作成から続ける。タグのあとに `main` に別のコミットがあっても、本文と配布物はタグの中身から作る |
| 配布物のない下書きがある | 承認すると、`release create` を呼ばず、`workflow run` から続ける |

| 配布物が足りないか余分な下書き | 理由と、画面で消すことを出して止まり、何も変えない |
| 公開済み | 問いを出さず、何も変えずに 0 で終わる |
| タグを付けるコミットに、ASCII 以外の名前がある（タグがないとき、タグがあって Release がないとき、タグと配布物のない下書きがあるとき） | 問いを出さず、手元と `origin` にタグを作らず、push も `gh` の書き込みもせずに、1 で終わる。出力に、名前、理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」がある。タグがあるときは、新しいバージョンで出すことも出す |

| push が失敗する | 手元のタグが消え、`release create` が呼ばれない。1 で終わる |
| `release create` が失敗する | タグが残り、流し直すと下書きの作成から続ける |

| 確かめが失敗する（証明が通らない、チェックサムが合わない、`install.sh` がタグと違う、中身が `git archive` と違う） | 何が合わなかったかを出し、`release edit` も削除も呼ばない。1 で終わる |

| 引数の誤りと `--help` | 2 で終わる、0 で使い方を出す |
| 確認の前の画面 | 6 つの確かめの行が、`✔` と項目の名前と値で、本文より前に出る。本文の各行が、字下げと `│` と空白で始まり、それを除くと本文と同じ文になる。問いの直前に、バージョンと `OWNER/REPO`、12 文字の SHA と件名、`○` の手順の一覧が出る。すべての状態で、手順の数と並びが決めたものになる |

### テストのファイルの分け方

上の表のケースを、画面のケースを含めて 4 つのテストのファイルに分ける。1 本の所要時間を短くし、手元の並列でも 1 本の時間の上限（`docs/ci.md` の[時間の予算](ci.md#時間の予算)）に近づかないようにするため。準備は `tests/release-test-lib.sh`、照合と一時領域の用意は `tests/release-assertions.sh` にまとめる。

| ファイル | 持つケース |
| --- | --- |
| `tests/release-test.sh` | 承認する、承認しない、標準入力が端末でない、タグがあって Release がない、配布物のない下書き・そろった下書き・足りないか余分な下書き、公開済み |
| `tests/release-check-test.sh` | 確かめで止まるケース。[確かめること](#確かめること)の 1 の `gh` のバージョン（新しいバージョンが通ることを含む）とルートでないところに置いたコピー、2〜9（配布物のそろった下書きと公開済みで 9 を省くことを含む） |
| `tests/release-failure-test.sh` | 手元だけ・`origin` だけ・違うタグ・注釈付きでないタグ・タグのない Release・同じタグの Release が 2 つ、一覧を読めない、6〜8 をタグのコミットで確かめること、各手順の失敗と流し直し、中断と片付け |
| `tests/release-display-test.sh` | 公開の前の確かめの失敗、引数の誤りと `--help`、経過とゲージ、色と `NO_COLOR`、完了の表示 |

- 各ケースは、どれか 1 つのファイルにだけ置く。4 つを合わせると、上の表のケースをすべて流す
- 分けるときは、ケースの手順と確かめる内容を変えない。変えるのは、置き場所と、冒頭の説明、節の説明、最後の `PASS` の行の文だけにする
- 最後の `PASS` の行は、そのファイルが確かめたケースに合わせる。`tests/release-test.sh` の行から確かめで止まるケースを除き、`tests/release-check-test.sh` には自分の行を置く
- `tests/release-check-test.sh` の名前は、`docs/ci.md` の[長いファイルを分ける](ci.md#長いファイルを分ける)の決まりで、元の名前にまとまりの名前を足した形にする。まとまりは、この文書の[確かめること](#確かめること)にあたる
- 各ファイルの冒頭の説明には、そのファイルが持つケースと、残りのケースがどのファイルにあるかを書く。`tests/release-test-lib.sh` の冒頭の、読み込むファイルの一覧も合わせる
- 4 つのファイルは、`tests/test-weights` に重みを持つ（[分けたときの重み](#分けたときの重み)）

#### 分けたときの重み

`tests/release-check-test.sh` を足すときは、分ける前の `tests/release-test.sh` の重み（macOS の CI の実測）を、手元で流した 2 つの所要時間の比で分けて、2 つの重みにする。macOS の CI の実測を待たずに、分けたあとの値に近い目安を置くため。

1. 分けたあとの `tests/release-test.sh` と `tests/release-check-test.sh` を、`SQUAD_KIT_TEST_JOBS=1 bash tests/run.sh tests/release-test.sh tests/release-check-test.sh` で 1 本ずつ流す。並列の負荷で、比がずれないようにするため
2. 2 つの `==== PASS` の行の秒数を a（`release-test.sh`）と b（`release-check-test.sh`）とする
3. 分ける前の重みを W とし、`release-test.sh` に W × a ÷ (a + b)、`release-check-test.sh` に W × b ÷ (a + b) を、それぞれ切り上げて書く

ケースの数の比では分けない。確かめで止まるケースは、配布物を作らずに止まるので、1 つのケースが承認のケースよりずっと短いため。分けた 2 つの重みはどちらも W 以下で、W は 150 秒以下なので、[重みの上限](ci.md#時間の予算)を超えない。

この重みは目安で、採取元の行（`tests/test-weights` の `# 更新したテストの採取元:` など）は足さない。macOS の CI の実測が出たら、`CONTRIBUTING.md` の「テストを書く決まり」のとおり、2 倍以上ずれたときに実測を写して直す。

`tests/build-assets-test.sh` は、一時の Git のリポジトリにタグを付けて、`scripts/build-assets.sh` を流す。配布物の一番上が 1 つのディレクトリであること、中身が `git archive` と同じこと、`SHA256SUMS` が 2 行で `shasum -a 256 -c` が通ることを確かめる。`VERSION` がタグと違う、`HEAD` がタグと違う、`MANIFEST` が合わない、リンクを含むときに止まることも確かめる。

同じテストに、コミットの形のケースを足す。

| ケース | 確かめること |
| --- | --- |
| タグのないコミット | `--commit HEAD` で、タグの形と同じ 3 つのファイルができ、配布物の中身が `git archive` と同じ。`HEAD` と違うコミットを渡しても、そのコミットの中身で作る |
| 名前に漢字、制御文字（タブ）、バックスラッシュがある | 配布物を作らずに 1 で終わり、名前、理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」を出す。漢字の名前は、`\ooo` の形ではなくそのまま出る。ディレクトリの名前だけにあるときも止まる |
| 当てはまる名前が 2 つ以上ある | すべての名前を出してから止まる |
| 名前に空白と、`~` などの記号がある | 通る |
| 同じ答え | 上の名前ごとに、`git archive` で作った配布物を `install.sh --check-listing` にも渡し、`scripts/build-assets.sh` が拒むものは入口も拒み、通すものは入口も通すことを確かめる。macOS（bsdtar）と ubuntu（GNU tar）の両方で流す |
| `VERSION` が形に合わないコミット | 止まる |

同じ答えのケースは、`scripts/build-assets.sh` の 2 の名前の確かめと、入口の一覧の確かめの範囲がそろっていることを確かめる。4 の一覧の確かめは入口の処理を呼ぶので、2 の範囲を入口より広げたり狭めたりすると、このケースが落ちる。

`tests/release-workflow-test.sh` は、`.github/workflows/release-assets.yml` を読み、次を確かめる。きっかけが `workflow_dispatch` だけであること、全体の権限が `{}` でジョブの権限が決めたものだけであること、`uses:` がすべて 40 桁の SHA であること、`runs-on` が `ubuntu-24.04` であること、`persist-credentials: false` と、`--clobber` を使わないことである。

`tests/release-screens-test.sh` は、画面を画像にする仕組みの、出力を取るところまでを流す（[CI で流す範囲](#ci-で流す範囲)）。

## 画面を画像で見比べる

出力を変える PR では、変える前と後の画面を、同じ場面・同じ入力で流して PNG に描き、並べて見比べる。テストの文字列の一致に加えて、人が見た目で確かめるため。画像を作る仕組みはリポジトリに置き、画像はリポジトリに置かずに PR のコメントに添える。画像は出力を変えるたびに古くなり、古くなっても気づきにくいため。

### 置くもの（画像）

| ファイル | 役目 |
| --- | --- |
| `tests/release-screens.sh` | 場面ごとにスタブの状態を作り、渡された `scripts/release.sh` を疑似端末で流して出力を取り、PNG に描く |
| `tests/ansi-to-png.py` | 色の制御文字を含む出力を、端末と同じ桁の折り返しで PNG に描く |
| `tests/release-screens-requirements.txt` | `tests/ansi-to-png.py` が使う Pillow のバージョンを `==` で固定する |
| `tests/release-screens-test.sh` | 画像の仕組みが壊れていないことを、CI で確かめる（[CI で流す範囲](#ci-で流す範囲)） |

スタブと一時のリポジトリは、[置くもの（画像）](#置くもの画像)の `tests/release-test-lib.sh` をテストと共有する。

`tests/ui-pty.py` には、標準入力・標準出力・標準エラー出力を 1 つの疑似端末につなぐ指定を足す。本物の端末と同じく、2 つの出力が出た順に混ざり、答えの `y` が問いのあとに表示されるようにするため。決まった文字列（問い）が出たのを待ってから答えを送り、端末の大きさ（100 桁、40 行）と `TERM=xterm-256color` を与える。

画像とテストのために、`tests/ui-pty.py` に次の 2 つを足す。

- 答えを送る前と後の出力を 2 つのファイルに分けるときも、2 つを続けて読めば 1 つの端末の出力になるようにする。後の出力は、前の出力が作った画面の上でカーソルを動かすため
- 決まった文字列が出たら、端末の大きさを変えて `SIGWINCH` を送る指定を足す。途中で大きさが変わったときの動きを、テストで確かめるため

### スタブ

スタブは、テストと同じものを使う。前と後で、スタブの状態と Release の本文を同じにする。本物の Release は出さない。

- 隠す対象の出力は、v1.10.0 の公開のログと同じ文面で出す。前の画像に、外のコマンドの出力が混ざる様子が写るようにするため。バージョン、リポジトリ、実行の ID は、テストの値（`v1.6.0`、`example/kit`、`4242`）に置き換える
- `git` のスタブは、`git push origin refs/tags/*` のときだけ、本物の `git` で bare に push し、成功すれば v1.10.0 のログの進み具合と `To`・`[new tag]` の行を出す。失敗すれば本物の出力をそのまま出す。ほかの引数は、本物の `git` にそのまま渡す
- `gh workflow run` のスタブは、`Created workflow_dispatch event` と実行の URL、`To see` の 2 行を出す。`gh run watch` のスタブは、実行の名前、`JOBS`、ジョブとステップの一覧、`completed with` の行を出す。失敗させるときは、失敗の印の一覧を出す
- `gh run watch` のスタブは、環境変数で決めた秒数だけ待ってから終わる。経過の行を画像とテストに写すため
- 画像の Release の本文は、作業ツリーの `CHANGELOG.md` の `v1.10.0` の節を使う。本文が長いと手順の一覧と問いが流れるという、元の困りごとを写すため

### 場面

場面は次の 5 つにし、前と後で同じ場面・同じ入力を使う。答えは、どの場面も `y` にする。

| 場面 | スタブの状態 | 写すもの |
| --- | --- | --- |
| 1 | タグがない。すべて成功する | 確認の前の画面と、承認のあとから終わりまで |
| 2 | 下書きがあり、配布物がない。すべて成功する | 途中から続けるときの、3 つだけの手順の一覧 |
| 3 | タグがない。`gh run watch` が失敗する | 隠した出力と、止まるときの案内 |
| 4 | タグがない。`gh attestation verify` が失敗し、タグの `install.sh` の確かめが通らない | 隠した出力と、止まるときの案内 |
| 5 | 場面 1 に `NO_COLOR=1` を付ける | 色と書き換えがなくても、記号と配置で状態が分かること |

場面ごとに、2 枚の画像を作る。

- `<場面>-confirm.png`: 問いが出た時点の、端末の最後の 40 行。答えるときに見える画面を写すため
- `<場面>-after.png`: 答えのあとから終わりまでの出力で書き換えたあとの、書き換えた一覧の先頭から最後までの画面に残る行（書き換えない場面 5 は問いの行から）

### 描き方

`tests/ansi-to-png.py` は、取った出力を 100 桁、40 行の端末として読み、画面に残る行を描く。新しい画面は行をその場で書き換えるので、出力の行をそのまま並べると、書き換える前と後の行が両方残り、端末に見える画面にならないため。

- 端末の読み取りは、標準のライブラリだけで書く。画面の 40 行と、上に流れた行を持ち、カーソルの行と桁を動かす
- 改行で次の行へ、`\r` で行の頭へ動かす。`ESC[nA` で n 行上へ動かし、画面の一番上で止める。上に流れた行へは戻らない。`ESC[2K` で今の行を消し、`ESC[J` でカーソルから画面の下までを消す
- 色の制御文字のうち、`0`（戻す）、`1`（太字）、`38;5;<番号>`（256 色の文字色）、`39`、`22` を、文字ごとの色として持つ。ほかの制御文字は描かずに捨てる
- `--text` を付けると、PNG を描かず、画面に残る行を色の制御文字のない文字で出す。Pillow が要らないので、テストが最後に端末に残る行を照合するのに使う
- 確認の画像は、答えを送る前の出力を読んだ画面の、最後の 40 行を描く。後の画像は、前と後の出力を続けて読んだ画面の、答えのあとにカーソルが届いた一番上の行（書き換えた一覧の先頭。書き換えないときは問いの行）から最後までを描く
- 256 色の番号は、xterm の標準の値で色にする。端末に出る色のまま写すため
- 全角の文字（Unicode の East Asian Width が W か F）は 2 桁、ほかは 1 桁として数え、100 桁で折り返す。全角の文字は 2 桁を占め、書き換えで半分だけ消えたときは、残った半分を空白にする
- 背景は暗い色にし、文字の大きさは 20 px にする
- 半角の文字は等幅のフォント、全角の文字は日本語のフォントで、桁の位置に 1 文字ずつ描く。macOS では Menlo とヒラギノ角ゴシック、Ubuntu では DejaVu Sans Mono と Noto Sans CJK（`fonts-noto-cjk`）を探し、`--font` と `--wide-font` で替えられるようにする

Pillow は標準のライブラリにないので、`tmp/` の venv に、`tests/release-screens-requirements.txt` で入れる。原本を使う人には要らない道具なので、導入の前提には足さない。

### 作り方

前と後は、同じ仕組みに、`scripts/release.sh` のファイルだけを替えて流す。`tests/release-screens.sh <release.sh のパス> <出力先>` の形にする。`lib/ui.sh`、`install.sh` などのほかのファイルは、作業ツリーのものを使う。

```bash
python3 -m venv tmp/screens-venv
tmp/screens-venv/bin/pip install -r tests/release-screens-requirements.txt
git fetch origin main
git show origin/main:scripts/release.sh >tmp/release-before.sh
RELEASE_SCREENS_PYTHON=tmp/screens-venv/bin/python bash tests/release-screens.sh tmp/release-before.sh tmp/screens/before
RELEASE_SCREENS_PYTHON=tmp/screens-venv/bin/python bash tests/release-screens.sh scripts/release.sh tmp/screens/after
```

- `RELEASE_SCREENS_PYTHON` は、描くときの Python のパスである。指定がなければ `python3` を使い、Pillow がなければ、入れ方を出して止まる
- `--capture-only` を付けると、出力を取るところまでで終わり、PNG を描かない。CI と、描く道具のない手元で使う
- 前の `scripts/release.sh` は、変える前の `main` のファイルを使う。PR に、使った `main` のコミットを書く

PR には、場面ごとの前と後の画像の組、上の作り方、前に使ったコミットを、作った人が載せる。人に頼む前に、載せられるかを実際に試す。人は、載った画像を見て良し悪しを判断するだけにする。

1. 上のコマンドで、10 枚の画像を `tmp/screens/` に作る
2. 作り方と前に使ったコミットを書いた本文を `tmp/` に置き、`gh pr comment <PR> --body-file <本文> --attach '<画像>#<説明>'` で、10 枚を 1 つのコメントに載せる。`--attach` は `gh` 2.99.0 からあり、このコマンドの前提の 2.102.0 で使える
3. `gh pr view <PR> --json comments` で、載せたコメントに画像の URL があり、手元のパスが残っていないことを確かめる
4. 2 か 3 が通らなければ、画像を Multica のタスクのコメントに `--attachment` で添え、試したコマンド、終了コード、出力を書いたテキストのファイルも添える。載せられないと書くのは、試した結果を添えるときだけにする
5. 載せたあとで、人に、載せたコメントか添えたタスクのコメントを示して判断を頼む

### CI で流す範囲

CI では、毎回、場面を流して出力を取るところまでを流し、PNG に描くところは流さない。

- `tests/release-screens-test.sh` が、作業ツリーの `scripts/release.sh` に `--capture-only` で 5 つの場面を流し、場面ごとの終了コード（1・2・5 は 0、3・4 は 1）と、問いの行が取れたこと、後の画像の文字に完了した手順と失敗の印が残ることを確かめる。時間切れや問いが出ないときは、`tests/ui-pty.py` が 125 を返し、`tests/release-screens.sh` が止まる。出力を変えたときに、場面やスタブが壊れたことに気づけるようにするため
- 描くところを流さないのは、Pillow と日本語のフォントを毎回入れる時間が、`docs/ci.md` の予算を削るため。CI で描いた画像は誰も見ず、見た目の良し悪しは人が PR で判断する
- `tests/ansi-to-png.py` の構文は、`scripts/check.sh` が `tests/*.py` を読む今の確かめで見る
- `tests/release-screens-test.sh` は `tests/test-weights` に足す。5 つの場面で 15 秒ほどの見込みで、`scripts` の 1 つの分け方の 300 秒の上限に収まる

## 利用者向けの文書の変更

原本を変える人への手順は `CONTRIBUTING.md` に書き、この文書の設計の理由は写さない。

`CONTRIBUTING.md` の「タグを発行する」と、その下の「Release を作る」を、1 つの節「タグと Release を出す」に置き換える。貼って流すシェルは残さない。節には次を書く。

- 人間が、バージョンを上げる PR のマージのあとに流すこと
- 流すコマンド（`git switch main`、`git pull --ff-only origin main`、`bash scripts/release.sh`）
- 公開の前に、バージョン、コミット、Release の本文が出て、確認を求められること。端末から流すこと
- 公開の前に、配布物を作るワークフローの終わりを待ち、配布物を確かめてから公開すること。`gh` は 2.102.0 以上が要ること
- 止まったときは、出た理由に従って直してから流し直すこと。下書きの作成、ワークフロー、公開のどこで失敗したときも、同じコマンドを流し直すと続きから進むこと
- 配布物の確かめで止まったときは、流し直さず、下書きの配布物を見て、差し替えのおそれを調べること
- 発行済みのタグは動かさず、修正は新しいタグで配ること
- [リポジトリの設定](#リポジトリの設定)の 2 つを、この変更を入れた最初のバージョンを出す前に行うことと、行ったあとに確かめる手順

`manual.md` の「原本を変える人の手順」のリンクを、新しい節（`CONTRIBUTING.md#タグと-release-を出す`）に替える。`docs/vm.md` の「利用者向けの文書の変更」で、節の名前を「タグと Release を出す」に替え、`tests/release-tags-test.sh` に触れた文を消す。

画面を変える変更では、次を書き換える。画面の例と記号の決まりは写さず、この文書と [端末の画面の設計](screens.md) へ案内する。

- `CONTRIBUTING.md` の「タグと Release を出す」に、確認の前に確かめの一覧、本文、手順の一覧が出ることと、承認したあと手順の一覧の印が進み、終わりの表示が出ることを書く。[確認](#確認)と[公開](#公開)へ案内する
- `CONTRIBUTING.md` に、出力を変える PR で画面の画像を作り、PR に載せる手順の節を足す。[作り方](#作り方)のコマンドと、載せられるかを試してから人に判断を頼むことを書く
- `manual.md` の「表示の色と印」を、記号ごとの意味と色の表にし、セットアップと、タグと Release を出すコマンド（`scripts/release.sh`）の両方に当てはまる形にする。色が出ない条件の文は残す
- `manual.md` のセットアップの説明に、質問への答え方（答えたあとに 1 行に畳まれること）、最後の確認の答えの一覧の印、作成中の手順の一覧、完了の表示を足す。どれも [端末の画面の設計](screens.md) の決まりを、使う人の言葉で書く
- `manual.md` を変えたら、`grep -rn 'manual.md' .` で、節の名前やリンクを使うところを確かめる

`VERSION` と `CHANGELOG.md` は、この変更では変えない。次にバージョンを上げる PR で、変更の記録に入れるかを決める。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 確認を飛ばす `--yes` を付ける | 要件で付けないと決めた。パイプや自動の実行から公開できてしまう |
| 確認で、`y` ではなくバージョンの名前を打たせる | 出すバージョンは確認の画面に出ている。原本のほかの確認（`vm/lima.sh` の `delete`）と形がそろわない |
| コマンドの中で `git switch main` と `git pull --ff-only` をする | 確かめの前に手元の状態を変える。引いたコミットを人が見ないまま公開に進む |
| `git fetch --tags` で `origin` のタグを取ってから比べる | `origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠す |
| `gh release view` で Release の有無を読む | ないことと、認証やネットワークで読めないことを、終了コードで分けられない |
| `gh release create --target` で、GitHub の側でタグを作る | 注釈付きでないタグができ、今の手順のタグと形が変わる |
| リポジトリの名前を `AnD00/multica-squad-kit` に固定する | フォークで流せず、テストで本物のリポジトリの名前を使うことになる |
| 本文を `--notes` の引数で渡す | 長い本文で引数の上限と、引用の扱いに気を使う。ファイルなら中身をそのまま渡せる |
| push の失敗のあとも手元のタグを残す | 次の実行が「手元だけにある」で止まり、人が消す手間が増える |
| Release の作成を GitHub Actions に任せる（タグの push をきっかけにする） | 公開は人間がコマンドを流して決めると決めた |
| 配布物を手元で作り、手元から載せる | 証明は GitHub Actions の中でしか付けられない。使う人が、決まったワークフローで作られたことを確かめられない |
| ワークフローのきっかけを、タグの push か Release の `published` にする | タグの push では下書きがまだない。下書きは `release` の出来事を起こさず、公開のあとでは差し替えられない |
| ワークフローが下書きを公開する | 公開を人間のコマンドの外に出すことになる。コマンドが配布物を確かめる前に公開される |
| ワークフローの承認に Environment の reviewers を使う | 公開の確認と合わせて 2 回の承認になる。コマンドが流れを待てず、人が画面を行き来する |
| 公開の前に、もう 1 回確認を求める | 確かめが通らなければ公開しないので、人が判断する材料が増えない。要件の確認は 1 回にそろえる |
| 確かめで止まったとき、下書きや配布物を消す | 差し替えのおそれを人が調べる材料が消える |
| 確かめで止まるケースのファイルを `tests/release-preflight-test.sh` や `tests/release-stop-test.sh` にする | この文書の[確かめること](#確かめること)と名前が対応しない。止まるケースは `tests/release-failure-test.sh` にもあり、`stop` では分けた境が読めない |
| 分けたときの重みを、分ける前の値のまま 2 つに置く | 分けたあとの値に合わせる要件に合わない。シャードの分け方で、2 つの合計を実際の倍に見積もる |
| 分けたときの重みを、ケースの数の比で分ける | 確かめで止まるケースは承認のケースよりずっと短く、数の比では `tests/release-check-test.sh` を大きく見積もる |
| 分けたときの重みを、PR の macOS の CI の実測を待って書く | 実装の引き継ぎが CI を待つことになる。実測で直す決まりがすでにあるので、目安を置いてあとで直せる |
| `gh release verify` で確かめる | 不変の Release になったあとの確かめで、公開の前の下書きには使えない。使う人と同じ確かめを公開の前に流すため、入口の `--verify` を使う |
| 本文を手順の一覧のあとに出す | 本文が長いと、手順の一覧と問いが画面の上に流れる。困りごとの元に戻る |
| `gh run watch` をやめ、`gh run view` を一定の間隔で読む | 見張りの終わり方と終了コードの扱いを作り直すことになる。`gh run watch` を裏で流せば、今の成否の決め方のまま経過を出せる |
| 画像の描き方で、出力の行をそのまま並べる | 書き換える画面では、書き換える前と後の行が両方残り、端末に見える画面にならない |
| 本物の端末のスクリーンショットで見比べる | 端末やフォント、ウィンドウの大きさで見た目が変わり、前と後を同じ条件にそろえられない。手で撮るので、流し直せない |
| SVG に描いてから PNG に変える | 変える道具がもう 1 つ要る。Pillow で直接 PNG に描けば、道具は 1 つで済む |
| ImageMagick や aha などの外の道具で描く | 道具のバージョンと、OS ごとの入れ方を決める必要が増える。色の制御文字と全角の幅の扱いを、手元のスクリプトで決められない |
| CI で毎回 PNG を描く | Pillow と日本語のフォントを毎回入れる時間が、CI の予算を削る。CI で描いた画像は誰も見ない。文面はテストで確かめている |
| 画像の仕組みを CI で流さない | 出力を変えたときに、場面やスタブが壊れても気づかず、次に画像を作る人が直すことになる |
| 画像をリポジトリや一時のブランチに置く | 出力を変えるたびに古くなる。一時のブランチは、消し忘れと、書き込みの範囲が増える |
| 確かめの結果を、確かめるたびに 1 行ずつ出す | 端末でないときや公開済みのとき、確かめの行が残り、今の 1 行の出力が変わる。端末の判定のあとにまとめて出す |
| 結果の語とラベルの文で画面を作る（「成功」「リポジトリ:」など） | 行ごとに語を読まないと状態が分からず、ほかの CLI の画面と離れる。印と配置で状態が分かるチェックリストにする |
| 本文を「ここから」「ここまで」や全角の括弧の行で囲む | 囲みの行が本文と同じ重さで読まれ、画面の行が増える。左の `│` なら、本文の範囲が行を足さずに分かる |
| 本文の区切りを `----` の行にする | 変更の記録の本文に、Markdown の区切りの線や表の行として現れうる |
| 隠した出力を区切りの行で囲んで出す | 区切りの語が増える。灰の `$` のコマンドの行を見出しにすれば、どの出力かが分かる |
| 端末でない出力でも行を書き換える | ファイルやパイプに残した出力で、行が重なって読めない。端末でないときは、行を足すだけにする |
| ワークフローのゲージを、経過の時間と前の実行の長さで見積もる | 前の実行がないと出せず、遅いときに 100% で止まって見える。済んだステップの割合なら、実際の進みと合う |
| 下書きの URL に「公開すると変わる」などの説明の文を付ける | 説明の語が増える。灰の URL の次に `→` とタグの名前の URL を並べれば、仮の URL だと分かる |
| `gh` で画像を PR に載せられないとして、人に載せてもらう | `gh pr comment --attach` で載せられる。試さずに人に頼むと、人の手間が増え、判断だけを頼む形にならない |
