# タグと Release を 1 つのコマンドで出す

版を上げる PR をマージしたあとの、タグの発行と Release の作成を、原本の 1 つのコマンドにまとめる。人間が `main` で流し、公開の前にコマンドが確認を求める。

この文書は、そのコマンドの設計と、その理由を書く。原本を変える人への手順は `CONTRIBUTING.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

今は、マージのあとに、人間が `CONTRIBUTING.md` の長いシェルを 2 つ貼って流している。手間がかかり、流し忘れが起きやすい。Release を作り忘れると、Watch で「Releases」を選んだ人に新しい版の通知が届かない。

コマンドは、今の 2 つのシェルと同じ確かめをしてから、注釈付きのタグの作成と push、Release の作成を続けて行う。次は対象にしない。

- 版を上げる PR（`VERSION`、`CHANGELOG.md`、`MANIFEST` の書き換え）の自動化。PR のレビューと CI を通す決まりを変えないため、今のまま手で作る
- マージをきっかけに、CI がタグと Release を作ること。公開は、人間がコマンドを流して決める
- 利用側のリポジトリの、使う版の記録を変えること。原本は利用側のリポジトリに触れない
- 変更の記録の本文を作ること。何を書くかは、版を上げる PR で人間かエージェントが決める
- 発行済みのタグを動かすこと、消すこと。修正は新しいタグで配る
- 下書きの Release の扱い。`gh` の API で、タグから Release を引くときに下書きは見えないため、下書きは人が GitHub の画面で片付ける

## 置くもの

原本の `scripts/` に、コマンドを 1 つ置く。`scripts/check.sh` と `scripts/manifest.sh` と同じく、原本を変える人が使う道具なので、同じ場所にする。

| ファイル | 役目 |
| --- | --- |
| `scripts/release.sh` | 確かめ、確認、タグの作成と push、Release の作成をする |
| `tests/release-test.sh` | コマンドの動きを、一時の Git のリポジトリとスタブの `gh` で確かめる |

`tests/release-tags-test.sh` は消す。`CONTRIBUTING.md` から取り出したシェルを流すテストで、そのシェルがなくなるため。`scripts/check.sh` は、`scripts/` の `*.sh` の `bash -n` をすでに流すので、変えない。

エラーと警告は、`lib/ui.sh` の `ui_init` と `ui_error`・`ui_warning` で出す。セットアップと同じ `エラー:`・`警告:` の印と色にそろえるため。

## コマンドの形

原本のリポジトリのルートで、引数なしで流す。

```bash
bash scripts/release.sh
```

- 引数は `--help`（`-h`）だけを受ける。ほかの引数は、使い方を出して 2 で終わる
- 確認を飛ばす指定（`--yes` など）は持たない。公開は、毎回人間が中身を見て決めるため
- 出す版は `VERSION` から読む。版を引数で受けると、`VERSION` と違う版を出す誤りの入り口になるため

終わり方は、次の 3 つにする。

| 終わり方 | 終了コード |
| --- | --- |
| タグと Release を作った、Release だけを作った、すでに両方ある | 0 |
| 確かめで止まった、確認で承認されなかった、途中で失敗した | 1 |
| 引数の誤り | 2 |

## 流れ

確かめをすべて終えてから確認を求め、承認されてから初めてタグと Release を作る。確かめで止まるときと、承認されないときは、何も変えない。

1. 確かめる（[確かめること](#確かめること)）。1 つでも当てはまれば、理由を出して止まる
2. タグと Release の今の状態を読み、することを決める（[タグと Release の状態](#タグと-release-の状態)）。すでに両方あれば、そう出して 0 で終わる
3. 公開する中身を出し、確認を求める（[確認](#確認)）
4. 承認されたら、することに応じて、タグの作成と push、Release の作成を行う（[公開](#公開)）

## 確かめること

次の順に確かめる。今の `CONTRIBUTING.md` の 2 つのシェルが確かめていることに、手で確かめていたこと（未コミットの変更、Release の本文が空でないこと）と、版の形を足したもの。

| 順 | 止まるとき | 出す理由の例 |
| --- | --- | --- |
| 1 | `git` か `gh` がない。原本のリポジトリのルートで流していない | `gh` がない |
| 2 | `origin` の URL から GitHub のリポジトリ（`OWNER/REPO`）を読めない | `origin` が GitHub のリポジトリでない |
| 3 | 今のブランチが `main` でない | `main` に切り替えて、`git pull --ff-only` してから流す |
| 4 | 追跡しているファイルに、未コミットの変更がある | 変更をコミットするか戻してから流す |
| 5 | `origin` の `main` を取ってきて比べ、手元の `main` と一致しない | 未公開のコミットがあるか、`origin/main` に遅れている |
| 6 | `VERSION` が `vX.Y.Z`（`X`・`Y`・`Z` は 0 以上の整数）の形でない | `VERSION` の中身と、期待する形 |
| 7 | `CHANGELOG.md` の先頭の版（最初の `##` で始まる見出し）が `VERSION` と違う | 両方の版 |
| 8 | `CHANGELOG.md` のその版の節が、空白と改行だけ | その版の節が空 |

- 5 では、`git fetch --no-tags origin main` で `origin/main` だけを更新する。ブランチ、タグ、作業ツリーは変えない。古い `origin/main` と比べても、`main` が最新かは分からないため
- 4 は、追跡していないファイルを見ない。タグはコミットに付くので、追跡していないファイルは公開する中身に入らないため。`tmp/` などで止まらないようにする
- 6〜8 は、作業ツリーではなく、タグを付けるコミット（[タグと Release の状態](#タグと-release-の状態)）の `VERSION` と `CHANGELOG.md` を `git show` で読む。公開する中身と、確かめた中身を同じにするため
- 3 と 5 で止まったときは、自分で `git switch` や `git pull` をしない。公開の前に手元の状態を黙って変えないため。止まった理由に、流すコマンドを添える

その版の節は、`## <版>` の見出しの次の行から、次の `##` で始まる見出しの前の行までとする。前後の空行を除いたものを、Release の本文にする。

`OWNER/REPO` は、`git config --get remote.origin.url` の値から読む。`https://github.com/OWNER/REPO(.git)`、`git@github.com:OWNER/REPO(.git)`、`ssh://git@github.com/OWNER/REPO(.git)` の 3 つの形を受ける。`git remote get-url` を使わないのは、`url.<base>.insteadOf` で書き換えた先を返し、テストで GitHub の名前を保てないため（[テストと CI](#テストと-ci)）。

## タグと Release の状態

その版のタグと Release が、手元、`origin`、GitHub のどこにあるかを読み、次の表ですることを決める。すでにあるタグは、作り直さず、動かさない。

| 手元のタグ | `origin` のタグ | Release | すること |
| --- | --- | --- | --- |
| ない | ない | ない | 確認のあと、タグを作って push し、Release を作る |
| ある | ある（同じタグ） | ない | 確認のあと、Release だけを作る |
| ある | ある（同じタグ） | ある | 何もせず、すでに出してあることと Release の URL を出して 0 で終わる |
| ある | ない | どれでも | 止まる。手元のタグがまだ公開されていないことと、`git tag -d <版>` で消してから流し直すことを出す |
| ない | ある | どれでも | 止まる。`git fetch origin tag <版>` で取ってきてから流し直すことを出す |
| ある | ある（違うタグ） | どれでも | 止まる。手元と `origin` のタグが違うことを出す |
| ない | ない | ある | 止まる。タグのない Release があることを出す |

- 手元のタグは、`git rev-parse --verify --quiet refs/tags/<版>` で読む。`origin` のタグは、`git ls-remote origin refs/tags/<版>` で読む。`git fetch --tags` を使わないのは、`origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠すため
- 「同じタグ」は、手元のタグのオブジェクトの SHA と、`ls-remote` が返す SHA が一致することとする
- 手元にタグがあっても、注釈付きでない（`git cat-file -t` が `tag` でない）ときは、止まる。今の手順は注釈付きのタグだけを作るので、手で付けた別のタグのおそれがあるため
- Release は、`gh api repos/OWNER/REPO/releases/tags/<版>` で読む。成功すればあり、`HTTP 404` で失敗すればなしとする。それ以外の失敗（認証、ネットワーク）は、理由を出して止まる。`gh release view` を使わないのは、ないことと、読めないことを終了コードで分けられないため

タグを付けるコミットは、タグがないときは手元の `main` の先頭（`origin/main` と一致したもの）とする。タグがあるときは、そのタグが指すコミットとし、[確かめること](#確かめること)の 6〜8 もそのコミットで確かめる。タグを付けたあとに `main` に別のコミットが入っていても、Release の本文はタグの中身から作るため。

## 確認

公開する中身を標準出力に出し、標準エラー出力に問いを出して、標準入力から答えを読む。

```text
リポジトリ: OWNER/REPO
出す版: v1.6.0
タグを付けるコミット: 0123456789abcdef0123456789abcdef01234567 版を v1.6.0 にする
すること: 注釈付きのタグを作って origin に push し、Release を作る
Release の本文:
----------------------------------------
（その版の節）
----------------------------------------
公開しますか [y/N]:
```

- Release だけを作るときは、「すること」を「すでにあるタグのまま、Release だけを作る」にする
- `y` か `Y` だけを承認とする。ほかの答え、空の答え、入力の終わりは、`公開を取りやめました。` と出して、何も変えずに 1 で終わる。`vm/lima.sh` の `delete` の確認とそろえる
- 標準入力が端末でない（`[[ -t 0 ]]` が偽の）ときは、問いを出さずに、確認を求められないことを出して 1 で終わる。パイプで `y` を流し込んで確認を飛ばせないようにするため。エージェントの実行も端末を持たないので、エージェントが公開することもない
- 端末の判定は、[状態](#タグと-release-の状態)を読んで、することが決まったあとに行う。すでに両方あるときは、端末でなくても 0 で終わる

## 公開

承認されたら、することに応じて次を順に行う。どの段で失敗しても、その先は行わずに 1 で終わる。

1. タグを作る: `git tag -a <版> -m <版> <タグを付けるコミット>`。`HEAD` ではなく、確認で出したコミットを明示する
2. タグを push する: `git push origin refs/tags/<版>`。`--force` は付けない。`origin` に同じ名前のタグがあれば、Git が拒むので、動かすことはない
3. Release を作る: `gh release create <版> --repo OWNER/REPO --verify-tag --title <版> --notes-file <本文のファイル>`。本文は一時のファイルで渡し、空白と改行をそのまま保つ

途中で失敗したときは、次のようにする。

| 失敗した段 | すること |
| --- | --- |
| 2 の push | この実行で作った手元のタグを `git tag -d` で消し、push に失敗したことを出す。流し直せば、はじめからやり直せる |
| 3 の Release の作成 | タグは残す。Release の作成に失敗したことと、同じコマンドを流し直せば Release だけを作ることを出す |

push の失敗で手元のタグを消すのは、まだ公開していないタグを手元に残すと、次の実行が「手元だけにある」で止まるため。push が実は `origin` に届いていたときは、次の実行が「`origin` だけにある」で止まり、取ってくるコマンドを出す。

終えたら、作った Release の URL を出す。Watch の通知は、GitHub が Release の公開をきっかけに送る。コマンドは通知を送らない。

## テストと CI

`tests/release-test.sh` を足し、今の CI の `scripts` の両 OS で流す。本物の GitHub には push せず、Release も作らない。

- `origin` は、一時の置き場に作った bare のリポジトリにする。手元の作業コピーの `remote.origin.url` は `https://github.com/example/kit.git` のままにし、`url.<bare のパス>.insteadOf` で、Git の取得と push を bare に向ける。コマンドは本物と同じ道で `OWNER/REPO` を読み、push は bare に届く
- `gh` は、`PATH` の先頭に置いたスタブにする。受けた引数と、`--notes-file` の中身を記録する。`api` で Release があるか、ないか、ほかの失敗かと、`release create` の成否を、ケースごとに切り替える
- 確認の答えは、標準入力を疑似端末につないで送る。`tests/ui-pty.py` に、標準入力を疑似端末につなぎ、ファイルの中身を送る指定を足す。今の `--stdin` はパイプにつなぐので、端末の判定を通らないため
- Git の名前とメールは、`CONTRIBUTING.md` の「テストを書く決まり」のとおり、環境変数か `-c` で渡す

確かめるケースは次のとおり。

| ケース | 確かめること |
| --- | --- |
| 承認する | `origin` に注釈付きのタグができ、`main` の先頭を指す。`release create` が 1 回呼ばれ、本文がその版の節と一致する。0 で終わる |
| 承認しない（`n`、空の答え、入力の終わり） | 手元と `origin` にタグがなく、`release create` が呼ばれない。1 で終わる |
| 標準入力が端末でない | 問いを出さず、タグも Release もできない。1 で終わる |
| [確かめること](#確かめること)の 3〜8 | それぞれ理由を出して止まり、`git fetch` のほかは何も変えず、`gh` の `release create` を呼ばない |
| タグがあって Release がない | 承認すると、タグのオブジェクトの SHA が変わらず、`release create` が呼ばれる。タグのあとに `main` に別のコミットがあっても、本文はタグの中身から作る |
| タグも Release もある | 問いを出さず、何も変えずに 0 で終わる |
| 手元だけ、`origin` だけ、違うタグ、注釈付きでないタグ、タグのない Release | それぞれ理由を出して止まり、タグを変えない |
| `gh api` が 404 のほかで失敗する | 理由を出して止まる |
| push が失敗する | 手元のタグが消え、`release create` が呼ばれない。1 で終わる |
| `release create` が失敗する | タグが残り、流し直すと Release だけを作る |
| 引数の誤りと `--help` | 2 で終わる、0 で使い方を出す |

## 利用者向けの文書の変更

原本を変える人への手順は `CONTRIBUTING.md` に書き、この文書の設計の理由は写さない。

`CONTRIBUTING.md` の「タグを発行する」と、その下の「Release を作る」を、1 つの節「タグと Release を出す」に置き換える。貼って流すシェルは残さない。節には次を書く。

- 人間が、版を上げる PR のマージのあとに流すこと
- 流すコマンド（`git switch main`、`git pull --ff-only origin main`、`bash scripts/release.sh`）
- 公開の前に、版、コミット、Release の本文が出て、確認を求められること。端末から流すこと
- 止まったときは、出た理由に従って直してから流し直すこと。Release の作成だけが失敗したときも、同じコマンドを流し直すこと
- 発行済みのタグは動かさず、修正は新しいタグで配ること

`manual.md` の「原本を変える人の手順」のリンクを、新しい節（`CONTRIBUTING.md#タグと-release-を出す`）に替える。`docs/vm.md` の「利用者向けの文書の変更」で、節の名前を「タグと Release を出す」に替え、`tests/release-tags-test.sh` に触れた文を消す。

`VERSION` と `CHANGELOG.md` は、この変更では変えない。次に版を上げる PR で、変更の記録に入れるかを決める。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 確認を飛ばす `--yes` を付ける | 要件で付けないと決めた。パイプや自動の実行から公開できてしまう |
| 確認で、`y` ではなく版の名前を打たせる | 出す版は確認の画面に出ている。原本のほかの確認（`vm/lima.sh` の `delete`）と形がそろわない |
| コマンドの中で `git switch main` と `git pull --ff-only` をする | 確かめの前に手元の状態を変える。引いたコミットを人が見ないまま公開に進む |
| `git fetch --tags` で `origin` のタグを取ってから比べる | `origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠す |
| `gh release view` で Release の有無を読む | ないことと、認証やネットワークで読めないことを、終了コードで分けられない |
| `gh release create --target` で、GitHub の側でタグを作る | 注釈付きでないタグができ、今の手順のタグと形が変わる |
| リポジトリの名前を `AnD00/multica-squad-kit` に固定する | フォークで流せず、テストで本物のリポジトリの名前を使うことになる |
| 本文を `--notes` の引数で渡す | 長い本文で引数の上限と、引用の扱いに気を使う。ファイルなら中身をそのまま渡せる |
| push の失敗のあとも手元のタグを残す | 次の実行が「手元だけにある」で止まり、人が消す手間が増える |
| Release の作成を GitHub Actions に任せる（タグの push をきっかけにする） | 公開は人間がコマンドを流して決めると決めた。CI に書き込みの権限を持たせることになる |
