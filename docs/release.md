# タグと Release を 1 つのコマンドで出す

バージョンを上げる PR をマージしたあとの、タグの発行と Release の作成を、原本の 1 つのコマンドにまとめる。人間が `main` で流し、公開の前にコマンドが確認を求める。配布物は、コマンドが下書きの Release を作ったあと、発行のワークフローが作って証明を付ける。コマンドは配布物を確かめてから Release を公開する。

この文書は、そのコマンドと発行のワークフローの設計と、その理由を書く。配布物の形と、使う人の側での確かめ方は `docs/install.md` に書く。原本を変える人への手順は `CONTRIBUTING.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

今は、マージのあとに、人間が `CONTRIBUTING.md` の長いシェルを 2 つ貼って流している。手間がかかり、流し忘れが起きやすい。Release を作り忘れると、Watch で「Releases」を選んだ人に新しいバージョンの通知が届かない。

コマンドは、今の 2 つのシェルと同じ確かめをしてから、注釈付きのタグの作成と push、下書きの Release の作成、配布物の作成の依頼、配布物の確かめ、Release の公開を続けて行う。自動にするのは、配布物を作って証明を付ける部分だけにする。次は対象にしない。

- バージョンを上げる PR（`VERSION`、`CHANGELOG.md`、`MANIFEST` の書き換え）の自動化。PR のレビューと CI を通す決まりを変えないため、今のまま手で作る
- マージをきっかけに、CI がタグと Release を作ること。公開は、人間がコマンドを流して決める。発行のワークフローは、コマンドが作った下書きに配布物を載せるだけで、タグと Release を作らず、公開もしない
- 利用側のリポジトリの、使うバージョンの記録を変えること。原本は利用側のリポジトリに触れない
- 変更の記録の本文を作ること。何を書くかは、バージョンを上げる PR で人間かエージェントが決める
- 発行済みのタグを動かすこと、消すこと。修正は新しいタグで配る。リポジトリの設定でも拒む（[リポジトリの設定](#リポジトリの設定)）
- 下書きの Release と、その配布物を消すこと。確かめで止まったときに、何が起きたかを人が見られるように残す。片付けは人が GitHub の画面で行う

## 置くもの

原本の `scripts/` に、コマンドを 1 つ置く。`scripts/check.sh` と `scripts/manifest.sh` と同じく、原本を変える人が使う道具なので、同じ場所にする。配布物を作るスクリプトも `scripts/` に置き、発行のワークフローから呼ぶ。

| ファイル | 役目 |
| --- | --- |
| `scripts/release.sh` | 確かめ、確認、タグの作成と push、下書きの Release の作成、配布物の作成の依頼と確かめ、公開をする |
| `scripts/build-assets.sh` | タグかコミットの中身から、配布物と `SHA256SUMS` を作る（[配布物を作る](#配布物を作る)）。PR の CI と、このコマンドの確かめの 9 でも使う |
| `.github/workflows/release-assets.yml` | 発行のワークフロー。配布物を作り、証明を付け、下書きの Release に載せる（[発行のワークフロー](#発行のワークフロー)） |
| `tests/release-test.sh` | コマンドの動きを、一時の Git のリポジトリとスタブの `gh` で確かめる |
| `tests/build-assets-test.sh` | 配布物を作るスクリプトを、一時の Git のリポジトリで確かめる |
| `tests/release-workflow-test.sh` | 発行のワークフローの定義の決まり（きっかけ、権限、固定したバージョン）を確かめる |

`tests/release-tags-test.sh` は消す。`CONTRIBUTING.md` から取り出したシェルを流すテストで、そのシェルがなくなるため。`scripts/check.sh` は、`scripts/` の `*.sh` の `bash -n` をすでに流すので、変えない。

エラーと警告は、`lib/ui.sh` の `ui_init` と `ui_error`・`ui_warning` で出す。セットアップと同じ `エラー:`・`警告:` の印と色にそろえるため。

## コマンドの形

原本のリポジトリのルートで、引数なしで流す。

```bash
bash scripts/release.sh
```

- 引数は `--help`（`-h`）だけを受ける。ほかの引数は、使い方を出して 2 で終わる
- 確認を飛ばす指定（`--yes` など）は持たない。公開は、毎回人間が中身を見て決めるため
- 出すバージョンは `VERSION` から読む。バージョンを引数で受けると、`VERSION` と違うバージョンを出す誤りの入り口になるため

終わり方は、次の 3 つにする。

| 終わり方 | 終了コード |
| --- | --- |
| タグと Release を作った、Release だけを作った、すでに両方ある | 0 |
| 確かめで止まった、確認で承認されなかった、途中で失敗した | 1 |
| 引数の誤り | 2 |

## 流れ

確かめをすべて終えてから確認を求め、承認されてから初めてタグと Release を作る。確かめで止まるときと、承認されないときは、何も変えない。承認は 1 回にし、そのあとは、配布物の確かめが通ったときだけ公開まで進む。

1. 確かめる（[確かめること](#確かめること)）。1 つでも当てはまれば、理由を出して止まる
2. タグと Release の今の状態を読み、することを決める（[タグと Release の状態](#タグと-release-の状態)）。すでに公開済みのときも、タグが指すコミットで 6〜8 を確かめ、通れば、そう出して 0 で終わる
3. タグを付けるコミットの中身で配布物を作り、確かめる（[確かめること](#確かめること)の 9）。止まれば、何も作らずに 1 で終わる
4. 公開する中身を出し、確認を求める（[確認](#確認)）
5. 承認されたら、することに応じて、タグの作成と push、下書きの Release の作成、配布物の作成の依頼、配布物の確かめ、公開を行う（[公開](#公開)）

## 確かめること

次の順に確かめる。今の `CONTRIBUTING.md` の 2 つのシェルが確かめていることに、手で確かめていたこと（未コミットの変更、Release の本文が空でないこと）と、バージョンの形を足したもの。

| 順 | 止まるとき | 出す理由の例 |
| --- | --- | --- |
| 1 | `git` か `gh` がない。`gh` が 2.102.0 より古い。原本のリポジトリのルートで流していない | `gh` がない、必要なバージョン |
| 2 | `origin` の URL から GitHub のリポジトリ（`OWNER/REPO`）を読めない | `origin` が GitHub のリポジトリでない |
| 3 | 今のブランチが `main` でない | `main` に切り替えて、`git pull --ff-only` してから流す |
| 4 | 追跡しているファイルに、未コミットの変更がある | 変更をコミットするか戻してから流す |
| 5 | `origin` の `main` を取ってきて比べ、手元の `main` と一致しない | 未公開のコミットがあるか、`origin/main` に遅れている |
| 6 | `VERSION` が `vX.Y.Z`（`X`・`Y`・`Z` は 0 以上の整数）の形でない | `VERSION` の中身と、期待する形 |
| 7 | `CHANGELOG.md` の先頭のバージョン（最初の `##` で始まる見出し）が `VERSION` と違う | 両方のバージョン |
| 8 | `CHANGELOG.md` のそのバージョンの節が、空白と改行だけ | そのバージョンの節が空 |
| 9 | タグを付けるコミットの中身から、配布物を作れないか、作った配布物が確かめを通らない | 止まった名前とその理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」 |

- 5 では、`git fetch --no-tags origin main` で `origin/main` だけを更新する。ブランチ、タグ、作業ツリーは変えない。古い `origin/main` と比べても、`main` が最新かは分からないため
- 4 は、追跡していないファイルを見ない。タグはコミットに付くので、追跡していないファイルは公開する中身に入らないため。`tmp/` などで止まらないようにする
- 6〜8 は、作業ツリーではなく、タグを付けるコミット（[タグと Release の状態](#タグと-release-の状態)）の `VERSION` と `CHANGELOG.md` を `git show` で読む。公開する中身と、確かめた中身を同じにするため
- 1 の `gh` のバージョンは、`docs/install.md` の[必要な `gh` のバージョン](install.md#必要な-gh-のバージョン)と同じにする。公開の前に、使う人と同じ確かめを流すため
- 9 は、[状態](#タグと-release-の状態)を読んでタグを付けるコミットが決まったあと、確認を求める前に行う。`bash scripts/build-assets.sh --commit <タグを付けるコミット> <一時の置き場>` を流し、発行のワークフローと同じ確かめを、タグを作る前に流す。一時の置き場は、通っても止まっても消す。止まったときは、`scripts/build-assets.sh` の出した名前と理由をそのまま見せ、そのあとに 9 で止まったことを出す
- 9 で流すのは、今の作業ツリーの `scripts/build-assets.sh` と `install.sh` である。4 と 5 で、作業ツリーは `origin/main` の先頭と同じになっている。タグがすでにあるときも、取り出しのために作業ツリーを変えない。中身は、タグを付けるコミットから `git archive` で取る
- 9 でタグがすでにあるときに止まったら、そのタグでは出せないことと、直したコミットを新しいバージョンで出すことを添える。発行済みのタグは動かさないため
- 9 は、すでに公開済みのときは行わない。公開済みの配布物は変えられず、止めても防げるものがないため
- 3 と 5 で止まったときは、自分で `git switch` や `git pull` をしない。公開の前に手元の状態を黙って変えないため。止まった理由に、流すコマンドを添える

そのバージョンの節は、`## <バージョン>` の見出しの次の行から、次の `##` で始まる見出しの前の行までとする。前後の空行を除いたものを、Release の本文にする。

`OWNER/REPO` は、`git config --get remote.origin.url` の値から読む。`https://github.com/OWNER/REPO(.git)`、`git@github.com:OWNER/REPO(.git)`、`ssh://git@github.com/OWNER/REPO(.git)` の 3 つの形を受ける。`git remote get-url` を使わないのは、`url.<base>.insteadOf` で書き換えた先を返し、テストで GitHub の名前を保てないため（[テストと CI](#テストと-ci)）。

## タグと Release の状態

そのバージョンのタグと Release が、手元、`origin`、GitHub のどこにあるかと、Release が下書きか公開済みかを読み、次の表ですることを決める。すでにあるタグは、作り直さず、動かさない。

| 手元のタグ | `origin` のタグ | Release | すること |
| --- | --- | --- | --- |
| ない | ない | ない | 確認のあと、タグを作って push し、下書きを作り、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | ない | 確認のあと、下書きを作り、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物なし | 確認のあと、配布物を作らせ、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物の 4 つがそろう | 確認のあと、確かめて公開する |
| ある | ある（同じタグ） | 下書き、配布物が足りないか余分 | 止まる。下書きの配布物を GitHub の画面で消してから流し直すことを出す |
| ある | ある（同じタグ） | 公開済み | 公開の操作はせず、タグが指すコミットで 6〜8 を確かめ、通れば、すでに出してあることと Release の URL を出して 0 で終わる |
| ある | ない | どれでも | 止まる。手元のタグがまだ公開されていないことと、`git tag -d <バージョン>` で消してから流し直すことを出す |
| ない | ある | どれでも | 止まる。`git fetch origin tag <バージョン>` で取ってきてから流し直すことを出す |
| ある | ある（違うタグ） | どれでも | 止まる。手元と `origin` のタグが違うことを出す |
| ない | ない | ある | 止まる。タグのない Release があることを出す |

- 手元のタグは、`git rev-parse --verify --quiet refs/tags/<バージョン>` で読む。`origin` のタグは、`git ls-remote origin refs/tags/<バージョン>` で読む。`git fetch --tags` を使わないのは、`origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠すため
- 「同じタグ」は、手元のタグのオブジェクトの SHA と、`ls-remote` が返す SHA が一致することとする
- 手元にタグがあっても、注釈付きでない（`git cat-file -t` が `tag` でない）ときは、止まる。今の手順は注釈付きのタグだけを作るので、手で付けた別のタグのおそれがあるため
- Release は、`gh api --paginate repos/OWNER/REPO/releases` の一覧から、`tag_name` が `<バージョン>` のものを探して読む。`releases/tags/<バージョン>` は下書きを返さないため。一覧に 2 つ以上あるときは、止まる。一覧を読めない（認証、ネットワーク）ときも、理由を出して止まる
- 配布物の 4 つは、`docs/install.md` の[配布物](install.md#配布物)の名前とする。下書きに、この 4 つのほかの配布物があるときも「余分」とする
- 配布物が足りないか余分な下書きを、コマンドは直さない。ワークフローの途中の失敗か、誰かの差し替えかを、人が見て決めるため
- 1 つ前のバージョンまでの、配布物のない公開済みの Release も、「公開済み」として扱う

タグを付けるコミットは、タグがないときは手元の `main` の先頭（`origin/main` と一致したもの）とする。タグがあるときは、そのタグが指すコミットとし、[確かめること](#確かめること)の 6〜8 もそのコミットで確かめる。タグを付けたあとに `main` に別のコミットが入っていても、Release の本文と配布物はタグの中身から作るため。

## 確認

公開する中身を標準出力に出し、標準エラー出力に問いを出して、標準入力から答えを読む。

```text
リポジトリ: OWNER/REPO
出すバージョン: v1.6.0
タグを付けるコミット: 0123456789abcdef0123456789abcdef01234567 バージョンを v1.6.0 にする
すること: 注釈付きのタグを作って origin に push し、下書きの Release を作り、配布物を作らせて確かめ、公開する
Release の本文:
----------------------------------------
（そのバージョンの節）
----------------------------------------
公開しますか [y/N]:
```

- タグがすでにあるときは、「すること」の文を、[状態](#タグと-release-の状態)の表の「すること」に合わせて、行う部分だけにする
- `y` か `Y` だけを承認とする。ほかの答え、空の答え、入力の終わりは、`公開を取りやめました。` と出して、何も変えずに 1 で終わる。`vm/lima.sh` の `delete` の確認とそろえる
- 標準入力が端末でない（`[[ -t 0 ]]` が偽の）ときは、問いを出さずに、確認を求められないことを出して 1 で終わる。パイプで `y` を流し込んで確認を飛ばせないようにするため。エージェントの実行も端末を持たないので、エージェントが公開することもない
- 端末の判定は、[状態](#タグと-release-の状態)を読んで、することが決まり、[確かめること](#確かめること)の 9 が通ったあとに行う。すでに公開済みのときは、6〜8 の確かめのあとなら、端末でなくても 0 で終わる

## 公開

承認されたら、することに応じて次を順に行う。どの手順で失敗しても、その先は行わずに 1 で終わる。

1. タグを作る: `git tag -a <バージョン> -m <バージョン> <タグを付けるコミット>`。`HEAD` ではなく、確認で出したコミットを明示する
2. タグを push する: `git push origin refs/tags/<バージョン>`。`--force` は付けない。`origin` に同じ名前のタグがあれば、Git が拒むので、動かすことはない
3. 下書きの Release を作る: `gh release create <バージョン> --repo OWNER/REPO --draft --verify-tag --title <バージョン> --notes-file <本文のファイル>`。本文は一時のファイルで渡し、空白と改行をそのまま保つ
4. 配布物を作らせる: `gh workflow run release-assets.yml --repo OWNER/REPO --ref <バージョン>` で発行のワークフローを起こし、その実行を `gh run list` で見つけて、`gh run watch --exit-status` で終わるまで待つ
5. 配布物を確かめる（[公開の前の確かめ](#公開の前の確かめ)）
6. 公開する: `gh release edit <バージョン> --repo OWNER/REPO --draft=false`

4 の実行は、起こした時刻のあとに作られた、`workflow_dispatch` の実行で、`headBranch` が `<バージョン>` のものとする。起こしてから一覧に出るまで間があるので、決まった回数だけ間を空けて読み直す。見つからないときは止まる。

途中で失敗したときは、次のようにする。

| 失敗した手順 | すること |
| --- | --- |
| 2 の push | この実行で作った手元のタグを `git tag -d` で消し、push に失敗したことを出す。流し直せば、はじめからやり直せる |
| 3 の下書きの作成 | タグは残す。下書きの作成に失敗したことと、同じコマンドを流し直せばタグのあとから続けることを出す |
| 4 のワークフロー | 下書きは残す。実行の URL を出す。配布物がないなら、流し直すと配布物を作らせ直す。途中まで載っているなら、[状態](#タグと-release-の状態)の「足りないか余分」で止まる |
| 5 の確かめ | 公開しない。下書きと配布物は残し、何が合わなかったかを出す。配布物の差し替えのおそれがあるので、人が見るまで流し直さないことも出す |
| 6 の公開 | 下書きは残す。流し直すと、配布物を確かめ直して公開する |

push の失敗で手元のタグを消すのは、まだ公開していないタグを手元に残すと、次の実行が「手元だけにある」で止まるため。push が実は `origin` に届いていたときは、次の実行が「`origin` だけにある」で止まり、取ってくるコマンドを出す。

終えたら、公開した Release の URL を出す。Watch の通知は、GitHub が Release の公開をきっかけに送る。下書きの間は送られない。コマンドは通知を送らない。

### 公開の前の確かめ

下書きの配布物を、使う人と同じ確かめと、タグの中身との照らし合わせで確かめる。公開したあとは差し替えられないので、公開の前に止めるため。

1. 下書きの 4 つの配布物を、一覧で読んだ配布物の ID から `gh api -H 'Accept: application/octet-stream' repos/OWNER/REPO/releases/assets/<ID>` で、新しい一時の置き場へ取ってくる。下書きの配布物は、タグの名前からは取れないため
2. タグの `install.sh`（`git show <バージョン>:install.sh`）で、`bash <その写し> --verify <バージョン> <置き場>` を流す。証明、チェックサム、一覧の確かめを、使う人の入口と同じ道で行うため
3. 配布物の `install.sh` の証明を確かめ、`SHA256SUMS` の行と照合し、タグの `install.sh` とバイトごとに一致することを確かめる
4. 配布物を展開したものと、`git archive <バージョン>` を展開したものを、`diff -r` で比べる。ワークフローがタグと違う中身を固めていないことを確かめるため
5. 証明の束（`.sigstore.json`）で、`gh attestation verify <配布物> --bundle <束>` を、`docs/install.md` の[確かめ方](install.md#確かめ方)の 4 つの指定で流す

## 発行のワークフロー

`.github/workflows/release-assets.yml` は、`scripts/release.sh` が起こしたときだけ動き、下書きの Release に配布物を載せる。タグと Release は作らず、公開もしない。

- きっかけは `workflow_dispatch` だけにする。タグの push をきっかけにすると、下書きができる前に動き、下書きを待つか作る仕事が要るため
- 最初に、`github.ref` が `refs/tags/vX.Y.Z` の形であることと、そのタグの下書きの Release が配布物なしであることを確かめる。当てはまらなければ、何も作らずに失敗する
- 動かす場所は、GitHub の用意した `ubuntu-24.04` にする。使う人は `--deny-self-hosted-runners` で確かめる
- 権限は、ワークフローの全体を `{}` にし、ジョブだけに `contents: write`（下書きへの載せ）、`id-token: write` と `attestations: write`（証明）を与える。証明のアクションの README が、固定したバージョンでほかの権限を求めるときは、その権限だけを足す
- 使うアクションは、コミットの SHA で固定し、バージョンを注記する。タグの付け替えで中身が変わらないようにするため
- `actions/checkout` は、`persist-credentials: false` でタグを取り出す。タグの指すコミットと、取り出した `HEAD` が同じことを確かめる
- 証明は、GitHub の `actions/attest-build-provenance` で、配布物、`install.sh`、`SHA256SUMS` の 3 つに付ける。出力の証明の束を、`multica-squad-kit-<バージョン>.sigstore.json` の名前で写す
- 4 つを `gh release upload <バージョン>` で下書きに載せる。`--clobber` は付けない。同じ名前のものがあれば、上書きせずに失敗する

書き込みの権限を持つ人は、このワークフローを手で起こせる。それでも、下書きでない Release と、配布物の載った下書きには載せないので、公開済みの Release は変わらない。

### 配布物を作る

`scripts/build-assets.sh` は、タグかコミットの中身から、配布物、`install.sh`、`SHA256SUMS` を出力先に作る。ワークフローの中に処理を書かず、スクリプトにして、手元のテストで確かめられるようにする。

```bash
bash scripts/build-assets.sh <バージョン> <出力先>
bash scripts/build-assets.sh --commit <コミット> <出力先>
```

- タグの形は、発行のワークフローが使う。取り出したタグの中身から作る
- コミットの形は、PR の CI と `scripts/release.sh` の確かめの 9 が使う。タグがなくても、渡したコミットの中身で、タグの形と同じ確かめを流す。`<コミット>` は `HEAD` やブランチの名前でもよく、`git rev-parse --verify <コミット>^{commit}` で SHA に決めてから使う
- コミットの形のバージョンは、そのコミットの `VERSION` を `git show <SHA>:VERSION` で読む。`vX.Y.Z` の形でなければ止まる

どちらの形も、次の順に行う。下の「対象」は、タグの形ではタグ、コミットの形では決めた SHA である。

1. タグの形では、`HEAD` が `<バージョン>` のタグの指すコミットで、`VERSION` が `<バージョン>` と一致することを確かめる。コミットの形では行わない
2. 対象の木の名前を、`git ls-tree -r -t -z --name-only <対象>` で読み、`docs/asset-names.md` の[名前の決まり](asset-names.md#名前の決まり)に合わないものがあれば止まる。見分けは `LC_ALL=C` で、名前のバイトに `[:print:]` でない文字かバックスラッシュがあるかで行う。出すものは[止まったときに出すもの](asset-names.md#止まったときに出すもの)のとおり
3. `git archive --format=tar.gz --prefix=multica-squad-kit-<バージョン>/ <対象>` で、配布物を作る
4. 配布物を、作業ツリーの `install.sh` の `--check-listing`（`docs/install.md` の[入口のスクリプト](install.md#入口のスクリプト)）で確かめる。止まったら、`install.sh` の出した理由に、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」と `docs/install.md` の[展開の前の確かめ](install.md#展開の前の確かめ)を添えて止まる
5. 新しい一時の置き場に展開し、`MANIFEST` の一覧と中のファイルが一致し、`shasum -a 256 -c MANIFEST` が通ることを確かめる。配布物で流すセットアップが、`MANIFEST` の確かめで止まらないようにするため
6. ルートの `install.sh` を写し、2 つの SHA-256 を `SHA256SUMS` に書く。コミットの形でも同じに作る。作るものを形で変えず、確かめる道を発行と同じにするため

2 の名前の確かめを 4 の前に置くのは、tar の一覧ではなく Git の名前のバイトで見分け、どの名前がなぜ止まったかを、言語の設定によらずにそのまま出すため。4 は、2 をすり抜けたもの（リンク、特殊なファイル、上へ出るパスなど）を、使う人と同じ処理で止める。今の `scripts/build-assets.sh` にある一覧の確かめの写しは消し、`install.sh` に一本化する。

4 で呼ぶ `install.sh` は、作業ツリーのもの（`scripts/build-assets.sh` と同じ取り出しの、ルートの `install.sh`）とする。発行のワークフローとタグの形では、作業ツリーはタグの中身である。PR の CI では PR の head、`scripts/release.sh` では `origin/main` の先頭である。

`.gitattributes` の `export-ignore` は使わない。配布物の中身と `MANIFEST` を、タグの中身と同じにするため。

## リポジトリの設定

公開したあとの Release の配布物とタグを差し替えられないように、人がリポジトリの設定を変える。コマンドとワークフローは、設定を変えない。README の 1 行のコマンドは、最新の Release の `install.sh` を確かめずに流すので、公開後の差し替えはこの設定だけで防ぐ（`docs/install.md` の[防げることと残るリスク](install.md#防げることと残るリスク)）。

| 設定 | 値 | 防ぐもの |
| --- | --- | --- |
| Settings の Releases の「Enable release immutability」 | 有効 | 公開済みの Release の配布物の差し替えと、そのタグの付け替えと削除 |
| タグの ruleset（Target tags に `v*`） | 「Restrict updates」と「Restrict deletions」を有効にし、「Restrict creations」は付けない。bypass の一覧は空にする | 下書きの間と、この設定の前に公開したタグの付け替えと削除 |

- 不変の Release は、有効にしたあとに公開した Release にだけ効く。そのため、この設定は、この変更を入れた最初のバージョンを出す前に行う
- ruleset は、作ることを止めない。`scripts/release.sh` がタグを push できるようにするため
- 設定のあと、最初のバージョンを出したときに、公開済みの Release への `gh release upload --clobber` と、タグの `git push --force` が拒まれることを確かめる。手順は `CONTRIBUTING.md` に書く

リポジトリの管理者は、これらの設定を外せる。そのため、発行の権限の乗っ取りは防げず、`docs/install.md` の[防げることと残るリスク](install.md#防げることと残るリスク)に書く。

## テストと CI

今の `tests/release-test.sh` を新しい流れに合わせて広げ、`tests/build-assets-test.sh` と `tests/release-workflow-test.sh` を足して、今の CI の `scripts` の両 OS で流す。本物の GitHub には push せず、Release もワークフローの実行も作らない。発行のワークフローそのものは、手元では動かせないので、定義の決まりを読んで確かめ、最初のバージョンを出すときに人が確かめる。

- `origin` は、一時の置き場に作った bare のリポジトリにする。手元の作業コピーの `remote.origin.url` は `https://github.com/example/kit.git` のままにし、`url.<bare のパス>.insteadOf` で、Git の取得と push を bare に向ける。コマンドは本物と同じ道で `OWNER/REPO` を読み、push は bare に届く
- `gh` は、`PATH` の先頭に置いたスタブにする。受けた引数と、`--notes-file` の中身を記録する。`--version` のバージョン、`api` の Release の一覧（ない、下書き、公開済み、配布物の数、読めない）、`release create`、`workflow run`、`run list`、`run watch`、`release edit` の成否と、配布物の取得で返すファイル、`attestation verify` の成否を、ケースごとに切り替える
- 配布物は、テストの中で `scripts/build-assets.sh` をタグに流して作り、スタブが返す。中身を差し替えた配布物も、同じ道で作る
- 確認の答えは、標準入力を疑似端末につないで送る。`tests/ui-pty.py` に、標準入力を疑似端末につなぎ、ファイルの中身を送る指定を足す。今の `--stdin` はパイプにつなぐので、端末の判定を通らないため
- Git の名前とメールは、`CONTRIBUTING.md` の「テストを書く決まり」のとおり、環境変数か `-c` で渡す

確かめるケースは次のとおり。

| ケース | 確かめること |
| --- | --- |
| 承認する | `origin` に注釈付きのタグができ、`main` の先頭を指す。`release create --draft` が 1 回呼ばれ、本文がそのバージョンの節と一致する。`workflow run`、確かめ、`release edit --draft=false` の順に呼ばれる。0 で終わる |
| 承認しない（`n`、空の答え、入力の終わり） | 手元と `origin` にタグがなく、`gh` の書き込みが呼ばれない。1 で終わる |
| 標準入力が端末でない | 問いを出さず、タグも Release もできない。1 で終わる |
| [確かめること](#確かめること)の 1 の `gh` のバージョンと、3〜8 | それぞれ理由を出して止まり、`git fetch` のほかは何も変えず、`gh` の書き込みを呼ばない。バージョンが古いときは、必要なバージョンを出す |
| タグがあって Release がない | 承認すると、タグのオブジェクトの SHA が変わらず、下書きの作成から続ける。タグのあとに `main` に別のコミットがあっても、本文と配布物はタグの中身から作る |
| 配布物のない下書きがある | 承認すると、`release create` を呼ばず、`workflow run` から続ける |
| 配布物のそろった下書きがある | 承認すると、`workflow run` を呼ばず、確かめから続ける |
| 配布物が足りないか余分な下書き | 理由と、画面で消すことを出して止まり、何も変えない |
| 公開済み | 問いを出さず、何も変えずに 0 で終わる |
| タグを付けるコミットに、ASCII 以外の名前がある（タグがないときと、タグと配布物のない下書きがあるとき） | 問いを出さず、手元と `origin` にタグを作らず、push も `gh` の書き込みもせずに、1 で終わる。出力に、名前、理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」がある。タグがあるときは、新しいバージョンで出すことも出す |
| タグを付けるコミットが確かめの 9 を通る | 今までのケースの流れ（タグ、下書き、ワークフロー、確かめ、公開）が変わらない |
| 手元だけ、`origin` だけ、違うタグ、注釈付きでないタグ、タグのない Release、同じタグの Release が 2 つ | それぞれ理由を出して止まり、タグを変えない |
| Release の一覧を読めない | 理由を出して止まる |
| push が失敗する | 手元のタグが消え、`release create` が呼ばれない。1 で終わる |
| `release create` が失敗する | タグが残り、流し直すと下書きの作成から続ける |
| ワークフローの実行が見つからないか失敗する | 実行の URL か、見つからないことを出し、`release edit` を呼ばない。1 で終わる |
| 確かめが失敗する（証明が通らない、チェックサムが合わない、`install.sh` がタグと違う、中身が `git archive` と違う） | 何が合わなかったかを出し、`release edit` も削除も呼ばない。1 で終わる |
| `release edit` が失敗する | 下書きが残り、流し直すと確かめから続ける |
| 引数の誤りと `--help` | 2 で終わる、0 で使い方を出す |

`tests/build-assets-test.sh` は、一時の Git のリポジトリにタグを付けて、`scripts/build-assets.sh` を流す。配布物の一番上が 1 つのディレクトリであること、中身が `git archive` と同じこと、`SHA256SUMS` が 2 行で `shasum -a 256 -c` が通ることを確かめる。`VERSION` がタグと違う、`HEAD` がタグと違う、`MANIFEST` が合わない、リンクを含むときに止まることも確かめる。

同じテストに、コミットの形のケースを足す。

| ケース | 確かめること |
| --- | --- |
| タグのないコミット | `--commit HEAD` で、タグの形と同じ 3 つのファイルができ、配布物の中身が `git archive` と同じ。`HEAD` と違うコミットを渡しても、そのコミットの中身で作る |
| 名前に漢字、制御文字（タブ）、バックスラッシュがある | 配布物を作らずに 1 で終わり、名前、理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」を出す。漢字の名前は、`\ooo` の形ではなくそのまま出る。ディレクトリの名前だけにあるときも止まる |
| 当てはまる名前が 2 つ以上ある | すべての名前を出してから止まる |
| 名前に空白と、`~` などの記号がある | 通る |
| 同じ答え | 上の名前ごとに、`git archive` で作った配布物を `install.sh --check-listing` にも渡し、`scripts/build-assets.sh` が拒むものは入口も拒み、通すものは入口も通すことを確かめる。macOS（bsdtar）と ubuntu（GNU tar）の両方で流す |
| `VERSION` が形に合わないコミット | 止まる |

同じ答えのケースは、`scripts/build-assets.sh` の 2 の名前の確かめと、入口の一覧の確かめの範囲がそろっていることを確かめる。4 の一覧の確かめは入口の処理を呼ぶので、2 の範囲を入口より広げたり狭めたりすると、このケースが落ちる。

`tests/release-workflow-test.sh` は、`.github/workflows/release-assets.yml` を読み、次を確かめる。きっかけが `workflow_dispatch` だけであること、全体の権限が `{}` でジョブの権限が決めたものだけであること、`uses:` がすべて 40 桁の SHA であること、`runs-on` が `ubuntu-24.04` であること、`persist-credentials: false` と、`--clobber` を使わないことである。

## 利用者向けの文書の変更

原本を変える人への手順は `CONTRIBUTING.md` に書き、この文書の設計の理由は写さない。

`CONTRIBUTING.md` の「タグを発行する」と、その下の「Release を作る」を、1 つの節「タグと Release を出す」に置き換える。貼って流すシェルは残さない。節には次を書く。

- 人間が、バージョンを上げる PR のマージのあとに流すこと
- 流すコマンド（`git switch main`、`git pull --ff-only origin main`、`bash scripts/release.sh`）
- 公開の前に、バージョン、コミット、Release の本文が出て、確認を求められること。端末から流すこと
- 公開の前に、配布物を作るワークフローの終わりを待ち、配布物を確かめてから公開すること。`gh` は 2.102.0 以上が要ること
- 止まったときは、出た理由に従って直してから流し直すこと。下書きの作成、ワークフロー、公開のどこで失敗したときも、同じコマンドを流し直すと続きから進むこと
- 配布物の確かめで止まったときは、流し直さず、下書きの配布物を見て、差し替えのおそれを調べること
- 発行済みのタグは動かさず、修正は新しいタグで配ること
- [リポジトリの設定](#リポジトリの設定)の 2 つを、この変更を入れた最初のバージョンを出す前に行うことと、行ったあとに確かめる手順

`manual.md` の「原本を変える人の手順」のリンクを、新しい節（`CONTRIBUTING.md#タグと-release-を出す`）に替える。`docs/vm.md` の「利用者向けの文書の変更」で、節の名前を「タグと Release を出す」に替え、`tests/release-tags-test.sh` に触れた文を消す。

`VERSION` と `CHANGELOG.md` は、この変更では変えない。次にバージョンを上げる PR で、変更の記録に入れるかを決める。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 確認を飛ばす `--yes` を付ける | 要件で付けないと決めた。パイプや自動の実行から公開できてしまう |
| 確認で、`y` ではなくバージョンの名前を打たせる | 出すバージョンは確認の画面に出ている。原本のほかの確認（`vm/lima.sh` の `delete`）と形がそろわない |
| コマンドの中で `git switch main` と `git pull --ff-only` をする | 確かめの前に手元の状態を変える。引いたコミットを人が見ないまま公開に進む |
| `git fetch --tags` で `origin` のタグを取ってから比べる | `origin` だけにあるタグを手元に持ち込み、状態が合わないことを隠す |
| `gh release view` で Release の有無を読む | ないことと、認証やネットワークで読めないことを、終了コードで分けられない |
| `gh release create --target` で、GitHub の側でタグを作る | 注釈付きでないタグができ、今の手順のタグと形が変わる |
| リポジトリの名前を `AnD00/multica-squad-kit` に固定する | フォークで流せず、テストで本物のリポジトリの名前を使うことになる |
| 本文を `--notes` の引数で渡す | 長い本文で引数の上限と、引用の扱いに気を使う。ファイルなら中身をそのまま渡せる |
| push の失敗のあとも手元のタグを残す | 次の実行が「手元だけにある」で止まり、人が消す手間が増える |
| Release の作成を GitHub Actions に任せる（タグの push をきっかけにする） | 公開は人間がコマンドを流して決めると決めた |
| 配布物を手元で作り、手元から載せる | 証明は GitHub Actions の中でしか付けられない。使う人が、決まったワークフローで作られたことを確かめられない |
| ワークフローのきっかけを、タグの push か Release の `published` にする | タグの push では下書きがまだない。下書きは `release` の出来事を起こさず、公開のあとでは差し替えられない |
| ワークフローが下書きを公開する | 公開を人間のコマンドの外に出すことになる。コマンドが配布物を確かめる前に公開される |
| ワークフローの承認に Environment の reviewers を使う | 公開の確認と合わせて 2 回の承認になる。コマンドが流れを待てず、人が画面を行き来する |
| 公開の前に、もう 1 回確認を求める | 確かめが通らなければ公開しないので、人が判断する材料が増えない。要件の確認は 1 回にそろえる |
| 確かめで止まったとき、下書きや配布物を消す | 差し替えのおそれを人が調べる材料が消える |
| `gh release verify` で確かめる | 不変の Release になったあとの確かめで、公開の前の下書きには使えない。使う人と同じ確かめを公開の前に流すため、入口の `--verify` を使う |
