# 画像を載せる方法と、できないと頼む前に残すこと

役が画像を PR とタスクのコメントに自分で載せられるようにする。PR には `gh` の `--attach`、タスクには `multica issue comment add --attachment` を使う。あわせて、「できない」として人間に操作を頼む前に、試した方法とコマンドの出力を残させる。

この文書は、共通スキル squad-handoff と役の指示に足す手順の設計と、その理由を書く。関所は変えず、許可と拒否をテストで確かめる（[関所](#関所)）。

## 目的と範囲

ある役が「`gh` に画像を添付する口がない」と書き、画像を PR に載せる作業を人間に回した。試した方法と結果の記録はなく、人間の指摘で誤りと分かった。`gh` には 2.99.0 から `--attach` があり、`--help` を読めば分かることだった。導入したプロジェクトで PR を確かめる人間は、役が止まるたびに手で画像を載せ、止まった理由が正しいかも調べ直すことになる。

そこで、心がけの文ではなく、使うコマンドと失敗したときの扱いを指示に書く。画像の載せ方を決め、頼む前に残すものを決める。

次は対象にしない。

- `--attach` を包むスクリプトを原本に足すこと。`gh` の公式の使い方で足り、配るものとテストを増やさないため
- 画像を別のブランチ・Release・外部の置き場に置き、URL を本文に書く方法
- 関所（`gh` と `git push`）の許可の範囲を変えること。書き込めるリポジトリの安全の前提を変えるため
- 原本が求める `gh` の最低のバージョン（2.102.0）を変えること。`--attach` の入った 2.99.0 より新しいため
- 動画の添付の扱い。`--attach` は動画も受けるが、決まりは画像について書く

## 載せる方法

PR に載せるときは、`gh` の `--attach` を使う。タスクに載せるときは、`multica issue comment add --attachment` を使う。根拠は GitHub の公式の文書「[GitHub CLI でファイルを添付する](https://docs.github.com/ja/github-cli/github-cli/attaching-files-with-github-cli)」と、`gh` 2.103.3 のヘルプである。

| 載せる先 | コマンド | 確かめたこと |
| --- | --- | --- |
| PR のコメント | `gh pr comment <PR> --body-file <本文> --attach '<画像>#<説明>'` | `gh pr comment --help` の FLAGS に `--attach file` がある |
| PR の本文 | `gh pr create` か `gh pr edit` に同じ `--attach` | 両方の `--help` に同じフラグがある |
| タスクのコメント | `multica issue comment add <タスク> --content-file <本文> --attachment <画像>` | `--attachment` は何度も指定でき、画像はコメントの中に表示される |

画像は、作業ディレクトリの `tmp/` に置く。`multica` は作業ディレクトリの外のファイルを既定で読まず、squad-handoff も一時ファイルを `tmp/` に置くと決めているため。

`gh` の `--attach` の動きは、ヘルプに次のとおり書かれている。役の指示には、このうち使い方に関わる前の 3 つを書く。

1. 本文に `![説明](./shot.png)` のような参照があり、同じファイルを `--attach` で渡すと、参照がアップロード先の URL に置き換わる
2. `--body-file` の本文の中のパスは、本文のファイルのディレクトリから探し、なければ作業ディレクトリから探す
3. 本文に参照のない画像は、コメントの末尾に足される。説明は `#` の後ろに書き、なければファイルの名前を使う
4. 1 回のコマンドで 50 個まで載せられる。リポジトリへの push の権限が要る

PR に載せたあとは、終了コードだけでなく、コメントの本文で参照が置き換わったことを確かめる。`gh pr view <PR> --json comments` で最後のコメントを読み、本文に手元のパス（`./shot.png` など）が残っていないことを見る。0 で終わっても参照が残っていれば、画面に画像が出ないため。

## 関所

関所は変えない。エージェントが `--attach` を使っても、関所は止めない。

関所は、フラグの型を本物の `gh` のヘルプから読む（`common/guard/gh` の `parse_args`）。`--attach file` は、フラグの名前と型の間の空白が 1 つなので、値を取るフラグとして読む。書き込み先の判定は、今の `gh pr comment` と同じく位置引数の URL、`--repo`、今のディレクトリのリポジトリで行い、一覧にないリポジトリなら止める。アップロードは本物の `gh` の中で行われ、関所の外の `gh` を呼ばない。

`--attach` のない古い `gh`（2.98 以前）では、ヘルプにフラグがないので、関所が「`--attach` のフラグの型が分からないので止めた」で止める。原本は `gh` 2.102.0 以上を求めるが、確かめるのは入口のスクリプト（`install.sh`）だけである。clone から流したホストでは古い `gh` が残ることがあるので、この拒否は[失敗したとき](#失敗したとき)の関所の場合として扱う。

## 失敗したとき

`gh` で PR に載せられなかったときは、同じ画像をタスクのコメントに `--attachment` で載せる。人間には、載せられなかった理由と、試したコマンドの出力を示す。PR に載せるまで作業を止めることはしない。

| 理由 | 見分け方の例 | 人間に頼むこと |
| --- | --- | --- |
| 認証 | `gh auth status` が未ログインを示す。401 で返る | ホストの `gh` のログイン |
| 権限 | 403 や 404 で返る。push の権限がない | リポジトリの権限、または PR への手での添付 |
| 関所 | 標準エラーが `gh の関所:` で始まる | 関所を避けない。古い `gh` なら `gh` の更新 |
| ファイルの形 | 対応していない形式や大きさのエラー | なし。役が PNG に変えて載せ直す |

試したコマンドと出力は、`tmp/` のテキストのファイルに書き、タスクのコメントに `--attachment` で添える。タスクのコメントの本文には、試したコマンドの名前、終了コード、上の表の理由を書く。squad-handoff の「タスクのコメントを書く」が、本文にパスを書かないと決めており、出力にはパスが混ざるため。

関所に止められたときは、squad-handoff の「書き込んでよいリポジトリ」のとおり、関所を避ける呼び方をしない。本物の `gh` を絶対パスで呼ぶことや、`gh api` でアップロードを組み立てることも、避ける呼び方に入れる。

## 頼む前に残すこと

画像に限らず、「できない」「口がない」として人間に操作を頼む前に、試した方法とコマンドの出力をコメントに残す。調べずに書いた「できない」は、人間が調べ直すことになるため。

試す順は、次のとおりにする。

1. 使う CLI の `--help` で、その操作のコマンドとフラグを探す。画像を PR に載せるなら `gh pr comment --help` の `--attach` を見る
2. 見つかった方法を実際に流す
3. 失敗したら、コマンド、終了コード、標準エラーを含む出力を残す。残し方は[失敗したとき](#失敗したとき)と同じにする
4. 人間に頼むコメントには、探したヘルプ、流したコマンド、理由を書く

`--help` に方法がなかったときも、その結果を残す。人間が、探した範囲を確かめられるようにするため。

## 置き場所

手順の本体は、共通スキル squad-handoff に 2 つの節として書く。実装・修正・QA の役の指示には、決まりの 1 文と `--attach` の使い方を書き、手順は squad-handoff の節へ案内する。

| `common/agents/claude-implementer.md`、`codex-implementer.md`、`claude-fixer.md`、`codex-fixer.md`、`qa.md` | 「人間に確認するとき」に 1 項目を足す（[役の指示に足す文](#役の指示に足す文)） |

共通スキルに本体を置くのは、スキルを使うすべての役に一度で効き、セットアップで導入済みのプロジェクトに届くため。役の指示にも書くのは、画像を扱う役が指示を読むだけで `--attach` にたどり着けるようにするため。同じ手順を複数の場所に写さないよう、役の指示には決まりの文と 1 行の使い方だけを置く。

レビューの 4 役と設計・要件・リーダーの指示は変えない。squad-handoff の節で同じ動きになるため。UX のレビュー役のスクショも、squad-handoff の「画像を載せる」で `--attach` を使う。

### squad-handoff に足す節

2 つの節を、「タスクのコメントを書く」と「引き継ぐとき」の間に、この順で置く。「記入が足りずに止まるとき」と「人間を呼んで止まるとき」の間には置かない。今のテストが、その 2 つの見出しの間を切り出して読むため。

節「画像を載せる」には、次を書く。

- 見出しのすぐ下に、PR には `gh` の `--attach`、タスクには `multica issue comment add --attachment` を使うと書く。画像を別の置き場に置いて URL を書く方法は使わないと添える
- 画像を `tmp/` に置くこと
- PR のコメントのコマンドの例を 1 つ、コードブロックで書く。`gh pr comment <PR> --body-file tmp/result.md --attach 'tmp/shot.png#<説明>'` の形にする
- [載せる方法](#載せる方法)の 1〜3（参照の置き換え、パスの探し方、参照のない画像と説明）を書く。`gh pr create` と `gh pr edit` にも同じフラグがあることを添える
- 載せたあとに、コメントの本文に手元のパスが残っていないことを確かめること
- PR に載せられなかったときは、タスクのコメントに `--attachment` で載せ、「人間に操作を頼む前に」に従うこと

節「人間に操作を頼む前に」には、次を書く。

- 見出しのすぐ下に、要件の決まりの文を書く。「できない」「口がない」として人間に操作を頼む前に、試した方法とコマンドの出力をコメントに残す
- [頼む前に残すこと](#頼む前に残すこと)の 1〜4 を、番号付きで書く
- [失敗したとき](#失敗したとき)の表と、出力をファイルにして `--attachment` で添えること。本文にはコマンドの名前・終了コード・理由を書くこと
- 関所に止められたときは避けないこと。本物の `gh` の絶対パスと `gh api` でのアップロードも、避ける呼び方に入ること

「PR にレビューやテストの結果を書く」の「スクリーンショットは、今のままにする」の文に、載せ方は「画像を載せる」に従うと添える。今の文の意味（結果の表とスクショを残す）は変えない。

### 役の指示に足す文

実装（Claude・Codex）、修正（Claude・Codex）、QA の 5 つの指示の「人間に確認するとき」に、次の 1 項目を足す。5 つとも同じ文にする。

```text
- 「できない」「口がない」として人間に操作を頼む前に、試した方法とコマンドの出力をコメントに残す。画像は、PR には `gh pr comment <PR> --body-file <本文> --attach <PNG>` で、タスクには `multica issue comment add --attachment` で載せる。手順と、載せられなかったときの扱いは、スキル squad-handoff の「画像を載せる」と「人間に操作を頼む前に」に従う
```

QA の「結果の出し方」のうち、画面に触れる PR で表とスクショを PR のコメントに書く項目に、「スクショはスキル squad-handoff の「画像を載せる」のとおり `--attach` で載せる」を足す。撮る画面と保存の仕方は、今のとおりスキル verify に従う。

## 導入と更新

セットアップの手順は変えない。セットアップは、役の指示を名前で探して書き換え、共通スキルをタグの URL から同じ ID のまま更新する（[用語の設計](terms.md)の登録の表）。導入済みのプロジェクトは、このバージョンでセットアップを流し直すと、5 つの役の指示と squad-handoff が新しい文に置き換わる。エージェントとオートパイロットの登録の数は変わらない。

`VERSION` と `CHANGELOG.md` は、次にバージョンを上げる PR で扱う。流し直すまでは、今の指示のまま動く。

## 利用者向けの文書の変更

`manual.md` の「受け取る人の準備」の道具の表で、`gh` の用途の欄に「PR への画像の添付（`--attach`）」を足す。必要なバージョンの 2.102.0 は変えない。PR に画像を載せるにはリポジトリへの push の権限が要ることを、表の後ろに 1 文で足す。`manual.md` は 1 文 1 行の決まり（`CONTRIBUTING.md` の「文書の改行」）に従う。

`README.md`、`EXTENSIONS.md`、`CONTRIBUTING.md` は変えない。

## テスト

関所の許可と拒否は `tests/gh-test.sh` で、指示とスキルの文は `tests/agent-templates-test.sh` で確かめる。新しいテストのファイルは足さない。

`tests/gh-test.sh` のスタブの `gh` は、`pr comment` のヘルプに `--attach file` と `-F, --body-file file` の行を足す。古い `gh` をまねるときは、テストの一時のディレクトリの印のファイルで、`--attach` の行を出さないようにする。

| ケース | 期待する結果 |
| --- | --- |
| `pr comment 367 --body-file body.md --attach './shot.png#説明'` | 許可され、元の引数のまま本物の `gh` に渡る |
| `pr comment https://github.com/example/template/pull/367 --attach shot.png`、`--attach=shot.png` の形 | 許可される |
| `pr comment https://github.com/other/repo/pull/1 --attach shot.png` | `other/repo への gh pr comment は止めた` で拒否される |
| `pr comment 367 --repo other/repo --attach shot.png` | 同じく拒否される |
| `pr comment 367 --attach`（値なし） | `値がない` で拒否される |
| 古い `gh` のヘルプで `--attach` を渡す | `フラグの型が分からない` で拒否され、書き込みは呼ばれない |

`tests/agent-templates-test.sh` には、次を足す。文全体は固定せず、見出しと要の語句の有無だけを見る。文言の手直しのたびにテストを直さないため。

- squad-handoff に、見出し「画像を載せる」と「人間に操作を頼む前に」がある。前の節に `gh pr comment`、`--attach`、`multica issue comment add`、`--attachment` がある
- 展開した 5 つの役の指示に、`試した方法とコマンドの出力をコメントに残す`、`--attach`、`squad-handoff の「画像を載せる」` がある

導入済みのプロジェクトに届く仕組みは、今の `tests/project-create-test.sh`（役の指示を ID を変えずに合わせる）と `tests/workspace-test.sh`（タグが変われば共通スキルを同じ ID で更新する）が確かめている。新しいテストは足さない。

## 実機で確かめる

本物の GitHub へのアップロードは、スタブでは確かめられない。実装のあとに、エージェントの実行から、関所を通して次を流す。対象の PR は、この設計の PR にする。

1. `tmp/` に PNG を作る。追加の道具を入れないよう、`python3` の標準ライブラリで小さな画像を書く
2. 本文のファイルに `![確認の画像](./attach-check.png)` を書き、`gh pr comment <PR> --body-file <本文> --attach <PNG>` を流す。終了コードが 0 であることを確かめる
3. `gh pr view <PR> --json comments` で、そのコメントの本文の参照が、アップロード先の URL に置き換わったことを確かめる
4. コメントの HTML（`gh api` の `body_html`）に `<img` があり、画像の URL が画像として返ることを確かめる
5. 同じ PNG を、`multica issue comment add --attachment` でタスクのコメントに添付する。このコメントに、PR のコメントの URL と画像の URL を書く

タスクのコメントが画像の URL のパスで拒否されたときは、squad-handoff の「タスクのコメントを書く」のとおり本文から外す。画像の URL はテキストのファイルに書き、同じコメントに添付する。画面で画像が見えることは、人間がマージの前に PR の画面で確かめる。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| `--attach` と、失敗したときの Multica の添付への切り替えを包むスクリプトを足す | 配るスクリプトとテストが増え、`gh` と同じことをする部分が重なる。今回の誤りは方法がないことではなく、調べずに書いたことだった |
| 画像を同じリポジトリの専用のブランチに置き、URL を書く | リポジトリに画像の履歴がたまり、片づける決まりが要る。`--attach` で足りる |
| Multica の添付の URL を PR に書く | Multica へのログインが要る URL は、GitHub の画面に出ない |
| 関所に `--attach` 専用の許可を足す | 今の関所はヘルプからフラグの型を読むので、足さなくても通る。許可の範囲も変えない |
| 手順を 5 つの役の指示に全部書く | 同じ手順を 5 か所に写すことになり、直すときにずれる。共通スキルなら 1 か所で全員に届く |
| 共通スキルだけに書く | 要件が役の指示に決まりの文を求めている。画像を扱う役が、指示だけで `--attach` にたどり着けなくなる |
| 原本の `gh` の最低のバージョンを上げる | 2.102.0 は `--attach` の入った 2.99.0 より新しく、上げる理由がない |
