# PR の CI を 7 分以内に終える

PR の Checks のすべてのジョブを、ジョブの開始から 7 分以内に終える。テストのケースは、同じ動作を別のテストで確認しているときに限り、減らしてよい。減らしたりまとめたりしたケースは、対応表で示す。macOS と ubuntu の両方で、残したテストをすべて流す。

この文書は、遅さの原因と、ワークフロー・テストの流し方・テストと見張りの呼び出しの変更の設計と、その理由を書く。ランナーの揺れで時間切れになったあとの見直しは、[揺れに耐える余裕を取る](#揺れに耐える余裕を取る)に書く。テストの流し方の使い方は `CONTRIBUTING.md` の「テストを流す」に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

原本を変える人とレビュー・QA の役は、Checks の結果を待ってから次に進む。PR 34 のマージ後は macOS のジョブが 23 分かかり、すべての PR と main で同じ遅さになる。次の 5 つを目的にする。

1. PR の Checks のすべてのジョブが、開始から 7 分以内に終わる。ランナーの空きを待つ時間は含めない
2. 同じ PR に新しい push があったら、その PR の古い実行を取り消す。main への push の実行は取り消さない
3. `scripts` のジョブに 10 分の上限を付け、止まったテストと大きく遅くなったテストを失敗として見せる
4. 結果を変えない手順をワークフローから除く
5. 手元の `bash tests/run.sh` は、今までどおりすべてのテストを流す

次は対象にしない。

- PR で macOS を流すのをやめること。macOS の bash 3.2 で起きる不具合を、マージの前に止めておくため
- 文書だけの変更で CI を省くこと。文書の行・語・内容の検査もテストに含まれるため
- main への push の実行をやめること。マージ後の状態を確認する唯一の実行であるため
- 有料の大きいランナーに替えること。費用が増えるため
- 手元での実行時間に目標を置くこと。手元の機械の性能はそろわないため

## 今の時間と原因

ジョブの長さは、毎回 macOS の `Tests` の手順が決める。ほかの手順は、両方の OS で合わせて 20 秒ほどである。2026-11-11 の実行の記録（`tests/run.sh` の `==== PASS` の行の秒数）は次のとおり。

| 実行 | ジョブ | Tests の手順 | テストの秒数の合計 | 並列数 | 最も遅いファイル |
| --- | --- | --- | --- | --- | --- |
| PR 34 の直前の main | macOS | 12 分 31 秒 | 2,052 秒 | 3 | `project-test` 429 秒 |
| 同上 | ubuntu | 5 分 19 秒 | 1,056 秒 | 4 | `setup-runtimes-test` 206 秒 |
| PR 34 の最後の実行 | macOS | 23 分 4 秒 | 3,944 秒 | 3 | `squad-dependabot-merge-test` 1,344 秒 |
| 同上 | ubuntu | 9 分 7 秒 | 1,598 秒 | 4 | `squad-dependabot-merge-test` 547 秒 |

`tests/run.sh` はファイル単位で並列に流す。そのため、手順の長さは「秒数の合計 ÷ 並列数」と「最も遅いファイル」の大きいほうより短くならない。PR 34 の前の macOS でも、合計 2,052 秒を 3 並列で流すと 684 秒（11 分 24 秒）かかる。テストを速くするだけでは、1 つのジョブで 7 分に届かない。

ほかに、次の無駄がある。

- 同じ PR へ続けて push すると、古い実行も最後まで流れる。ランナーを取り合い、ほかの PR の待ちも延びる
- ジョブに時間の上限がない。テストが止まると、GitHub の既定の 6 時間まで待つ
- macOS の `brew install jq python` は、毎回「already installed and up-to-date」で何も入れていない（macOS 26 のイメージ）

ubuntu の `apt-get install` は、イメージにない `zsh`・`zsh-common`・`libdigest-sha-perl` の 3 つを入れている。テストに要るので残す。

`apt-get update` が DNS の失敗（`Temporary failure resolving 'azure.archive.ubuntu.com'`）で落ちると、ミラーごとに再試行して約 6 分を使い切ってから終わる。この間、テストは始まらない。

この取得は `scripts/ci-install.sh` が行う。  
ランナーにあるものは取得せず、足りないものだけを、署名を検証したキャッシュ、ミラーの順に取り、ミラーは再試行する。  
キャッシュは、署名が正しいだけでは使わない。ランナーのリリースの情報であることと、`.deb` がランナー自身の APT の候補より古くないことも確認する。  
シャードごとのジョブが同じキャッシュのキーを使うので、同時に保存しようとした 1 つ以外は保存を飛ばす（失敗にはならない）。

## PR 34 で延びた原因

PR 34 は、見張りが CLI の出力を約束で確認して整える仕組み（[CLI の出力の欄](review-wait.md#cli-の出力の欄)）と、そのテストを入れた。延びたのは、CLI を 1 回読むたびに起こすプロセスが増えたためである。テストのケースの数ではない。

`squad-dependabot-merge-test` を手元で流し、`python3` と `jq` の起動を数えた。最初の 180 秒で、CLI の読み取り（`squad_cli_read`）が約 350 回あり、`python3` を 1,532 回、`jq` を 3,134 回起こした。1 回の読み取りで起こすものは次のとおり。

| 起こすもの | 1 回の読み取りでの数 | 置き場所 |
| --- | --- | --- |
| スタブの呼び出しの記録（`cli-test-trace.py`） | 2（読み取りと `--version`） | テスト |
| 見本を重ねて返す（`gh-fixture.py`・`multica-fixture.py`） | 1 | テスト |
| スタブの呼び出しの記録（`jq -cn --args`） | 1〜2 | テスト |
| 約束の読み込み（`squad_cli_contracts \| jq`）と、コマンドの取り出し | 4（`jq` 4 回） | 見張りのライブラリ |
| CLI のバージョンの読み取り（`gh --version` などのスタブ） | 1。スタブの記録の 1 回を含む | 見張りのライブラリ |
| 確認して整える（`python3 -c`） | 1 | 見張りのライブラリ |
| 条件付きの欄の条件（`jq -e`） | 条件 × 要素の数 | 見張りのライブラリと `cli-fixture-lib.py` |

さらに、見張りのテストは、整形の前と後の 2 通りでファイル全体を流す（[約束のテスト](review-wait.md#約束のテスト)）。同じ読み取りを 2 回流すので、上の数も 2 倍になる。macOS のランナーはプロセスの起動が ubuntu より重く、延びが大きく出た（ubuntu は 1.5 倍、macOS は 1.9 倍）。この 2 回流しは、のちにやめた（[整形の前と後の 2 回流しをやめる](#整形の前と後の-2-回流しをやめる)）。

## 時間の予算

7 分の中に、ジョブの準備と後片付け（約 20 秒）と、ランナーの速さのばらつきの余裕を取る。macOS のランナーは、同じテストでも実行ごとに速さが 1 割ほど変わる。そこで、`Tests` の手順の目安を 300 秒以下にする。

| 項目 | 目安 |
| --- | --- |
| `Tests` の手順 | 300 秒以下 |
| 1 つのテストのファイル | macOS の CI で 150 秒以下を上限にする。分けたときに、並列の 3 本へ詰められるようにするため |
| 準備・構文と整合の検査・後片付け | 30 秒以下 |
| 残りの余裕 | 90 秒ほど。ばらつきで 7 分を超えないため |

目安を守るため、次の 3 つを合わせて行う。

1. テストを複数のジョブへ分けて流す（[テストを分けて流す](#テストを分けて流す)）。合計の秒数を、ジョブの数で割れるようにする
2. 呼び出しを減らし、合計の秒数を減らす（[呼び出しを減らす](#呼び出しを減らす)）
3. 150 秒を超えるファイルを、ケースのまとまりで分ける（[長いファイルを分ける](#長いファイルを分ける)）

150 秒の上限は、`tests/test-weights` の重みを `tests/test-runner-test.sh` が検査する。150 秒は許可し、超えたらファイルの名前と理由を出して失敗する。目安を超えるファイルが増えるのを防ぐため、重みは macOS の CI の実測値を写し、手で小さくしない。

止まったテストの検出には、手元でも CI でも 1 ファイルの経過時間で 450 秒の上限を使う。150 秒の 3 倍の余裕をとり、並列実行やほかのエージェントの負荷による遅れを時間切れにしないため。出力のない時間や CPU 時間では数えない。`SQUAD_KIT_TEST_TIMEOUT` で変えられることと、時間切れを失敗として扱って流し直さない決まりは保つ。CI のジョブの上限（10 分）は変えない。停止の仕組みは [テスト 1 本ごとの時間の上限](conflict-resolution.md#テスト-1-本ごとの時間の上限)を参照する。

## ワークフローの変更

`.github/workflows/check.yml` を次のように変える。ジョブの名前は変わるが、main の必須のチェックはすべてのジョブをまとめる `checks-passed` だけなので（[main の保護](supply-chain.md#main-の保護)）、マージの条件は変わらない。

| 変更 | 内容 | 満たす目的 |
| --- | --- | --- |
| 実行の取り消し | `concurrency` の `group` を、PR なら PR の番号、push ならコミットの SHA にする。`cancel-in-progress` は PR のときだけ真にする | 2 |
| 時間の上限 | `scripts` と `content` の各ジョブに `timeout-minutes: 10` を付ける | 3 |
| 分けて流す | `scripts` の matrix を OS とシャードの組にする。macOS は 5 つ、ubuntu は 2 つにする（[シャードの数](#シャードの数)） | 1 |
| 構文と整合の検査 | 各 OS の 1 つ目のシャードでだけ流す | 4 |
| macOS の道具 | `brew install jq python` の手順を除く | 4 |

取り消しのグループは、push では実行ごとに違う値にする。同じ値にすると、`cancel-in-progress` が偽でも、待っている実行は新しい実行に取り消される。main へ続けて 3 回 push すると、2 回目が流れなくなる。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.event_name == 'pull_request' && format('pr-{0}', github.event.pull_request.number) || github.sha }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

`content` のジョブは 5 秒ほどで終わるが、同じ理由で上限を付ける。`scripts` と同じ 10 分にし、上限の値を 1 つにそろえる。

構文と整合の検査（`scripts/check.sh`・`scripts/manifest.sh`・MANIFEST の差分）は、テストと関わらず、同じ OS ならどのシャードでも結果が同じである。各 OS で 1 回だけ流す。macOS の bash 3.2 での構文の確認を残すため、OS ごとには流す。

macOS の `jq` と `python3` は、イメージに入っているものを使う。イメージから外れたら、テストが「command not found」で失敗し、それで気づける。入れ直しで隠すより早く分かる。

## 配布物の検証

`check.yml` に、ジョブ `assets` を足す。PR の head の木から、発行と同じ `scripts/build-assets.sh` で配布物を作り、名前の決まりと配布物の検証を流す。設計の全体は `docs/asset-names.md` の[確認する場所](asset-names.md#確認する場所)に書く。

```yaml
  assets:
    timeout-minutes: 10
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          persist-credentials: false
      - name: Build and check the assets
        run: bash scripts/build-assets.sh --commit HEAD "$RUNNER_TEMP/assets"
```

- 取り出すのは、PR では head のコミット、`main` への push ではそのコミットにする。既定のマージのコミットではなく、PR の作者が直す木を検証するため
- 動かす場所は、発行のワークフローと同じ `ubuntu-24.04` にする。GNU tar で、発行と同じ一覧の出方にするため。macOS の bsdtar での答えは、`scripts` のジョブの `tests/build-assets-test.sh` の同じ答えのケースで照合する
- 道具を入れる手順と、そのキャッシュは置かない。使うのは `git`、`tar`、`shasum` で、イメージに入っているため
- 権限はワークフローの全体の `contents: read` のまま、ジョブに足さない。`persist-credentials: false` で、取り出したあとの手順に認証を残さない
- 時間の上限は、ほかのジョブと同じ 10 分にする。配布物を作るのは数秒で、[時間の予算](#時間の予算)の 7 分に効かない
- 止まったときは、ジョブのログに、`scripts/build-assets.sh` の出した名前、理由、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」が出る

ジョブの定義の決まりは、`tests/release-workflow-test.sh` で確認する。`check.yml` に `assets` のジョブがあり、`runs-on` が `ubuntu-24.04` で、取り出しの `ref` が上の式で、`scripts/build-assets.sh --commit HEAD` を流すことである。発行のワークフローの定義と同じファイルで、ワークフローの決まりを読むテストを 1 つにまとめる。

## テストを分けて流す

`tests/run.sh` に、選んだファイルを N 個に分け、その k 番目だけを流す指定を足す。指定がなければ、今までどおりすべてを流す。CI は、シャードごとのジョブで k を変えて呼ぶ。

```bash
SQUAD_KIT_TEST_SHARD=2/4 bash tests/run.sh   # 4 つに分けた 2 つ目だけを流す
```

- 値は `k/N` の形で、`1 ≦ k ≦ N` の正の整数にする。合わなければ、使い方を出して 2 で終わる
- 引数でファイルを選んだときは、選んだファイルを分ける
- 分けた結果、流すファイルがないシャードは、`PASS suite` に 0 本と書いて 0 で終わる
- 結果の最後の行に、シャードの指定を添える。たとえば `PASS suite: すべてのテスト（12 本、並列 3、シャード 2/4）`

分け方は、各ファイルの重みから決める。重みは macOS の CI での秒数の目安で、`tests/test-weights` に 1 行 1 ファイルで、名前と秒を空白で区切って書く。`#` で始まる行と空の行は読み飛ばす。

```text
# ファイル 秒（macOS の CI での目安）
tests/project-test.sh 140
tests/setup-test.sh 121
```

1. 重みの大きい順（同じ重みは名前の順）に並べる
2. 先頭から順に、それまでの重みの合計がいちばん小さいシャードへ入れる。合計が同じなら番号の小さいシャードへ入れる
3. 一覧にないファイルは、重みを 30 秒として扱う

同じファイルの一覧と重みからは、どの実行でも同じ分け方になる。各ファイルはちょうど 1 つのシャードに入るので、すべてのシャードを合わせると、指定のないときと同じファイルを流す。

シャードの中で起こす順も、重みの大きい順にする。今の `slow` の一覧（遅いファイルを先に起こす）は、この重みで置き換える。重みは、テストの結果（どのファイルが通るか）を変えず、分け方と起こす順だけを変える。

重みの一覧が実物とずれないよう、テストで次を確認する。

- `tests/*-test.sh` のすべてに重みがある。重みのないファイルを足すと、テストが失敗して、追記に気づける
- 一覧に、存在しないファイルがない
- すべての重みが 150 秒以下である。超えた行は、ファイルの名前と理由を出して失敗する
- 同じ選んだファイルで、N を 1〜6 にしたとき、各シャードのファイルが重ならず、合わせると選んだファイルと一致する

重みは、分けたファイルを足したときと、CI の秒数が目安から 2 倍以上ずれたときに直す。`tests/run.sh` の `==== PASS` の行に秒数が出るので、それを写す。

シャードの数は、各ジョブの `Tests` の手順が 300 秒以下になる最小の数にする。見積もりでは、呼び出しを減らしたあとの macOS の合計は約 3,000 秒になる。1 つのシャードは、3 並列 × 300 秒のうち、詰め方の無駄を除いた約 760 秒を受け持てる。そのため、macOS は 4 つ、ubuntu（合計約 1,300 秒、4 並列）は 2 つから始めた。テストが増えて 4 つでは収まらなくなり、macOS を 5 つにした（[シャードの数](#シャードの数)）。

## 呼び出しを減らす

テストのケースと確認する内容は変えず、1 回の読み取りで起こすプロセスを減らす。テストの側と、見張りのライブラリの側の両方を直す。

### テストのスタブ

スタブ 1 回の呼び出しで起こす `python3` を 1 つまでにする。

- 呼び出しの記録と、見本を重ねて返す処理を、1 つの補助（`tests/cli-stub.py`）にまとめる。スタブは、記録だけの呼び出しと、記録して見本を返す呼び出しのどちらも、この補助を 1 回だけ呼ぶ
- 記録の形（`cli-test-trace.py` の行）と、見本を重ねる規則（`gh-fixture.py`・`multica-fixture.py`）は変えない
- `calls.jsonl` への記録も、補助の中で書き、`jq` を起こさない。各テストが読む形は変えない

`cli-test-trace.py`・`gh-fixture.py`・`multica-fixture.py` は、補助から読み込む関数のファイルにする。ケースの組み立てで呼ぶ `gh_fixture`・`cli_fixture` の使い方は変えない。

### 見張りのライブラリ

`common/monitor/squad-cli-lib` の読み取りの関数を、出力を変えずに次のように直す。

| 今 | 変えたあと |
| --- | --- |
| `squad_cli_read` と `squad_cli_normalize` が、それぞれ約束を `jq` で読み、コマンドを `jq` で取り出す（`jq` 4 回） | 約束の項目とコマンドを、1 回の `jq` でまとめて取り出し、確認して整える処理へ渡す |
| 確認する前に、毎回 CLI のバージョンを読む | バージョンは、欄が欠けて失敗するときだけ読む。メッセージの形と内容は変えない |

バージョンは、失敗のメッセージにだけ使う（[確認して整える](review-wait.md#確認して整える)）。成功するときに読まなくても、出力は変わらない。本物のホストでも、読み取りごとの `gh --version` と `multica version` がなくなる。

`squad_cli_normalize` を外から直接呼ぶ使い方（引数 1 つと 2 つ）は残す。`squad-preflight` とテストが使うため。

条件付きの欄の条件（`jq -e` を条件と要素ごとに起こす）は、今回は変えない。`jq` には文字列の式を評価する方法がなく、まとめて評価するには、約束の式から `jq` のプログラムを組み立てることになる。約束の評価の仕組みを変える大きな変更になるので、上の変更で目安に届かないときに、別のタスクで扱う。

見張りのスクリプトは配布するものなので、`CHANGELOG.md` の次のバージョンの節に、読み取りの呼び出しを減らしたことを 1 文で書く。動作は変わらないので、更新の案内は足さない。

## 長いファイルを分ける

macOS で 150 秒を超えるファイルは、ケースのまとまりごとに別のファイルへ分ける。最も遅い 1 ファイルより、ジョブは短くならないため。分けたあとも、すべてのケースを流し、`PASS` の行の文は変えない。

| ファイル | 分け方 |
| --- | --- |
| `tests/squad-dependabot-merge-test.sh` | `list`・マージ・人間に回す処理など、見張りのサブコマンドごと |
| `tests/project-test.sh` | 新しいプロジェクトの作成、既存のプロジェクトの選び直し、リポジトリの確認など、ケースのまとまりごと |
| `tests/setup-runtimes-test.sh` | ランタイムの組み合わせごと |
| `tests/squad-pr-watch-test.sh`・`tests/squad-review-wait-test.sh` | 呼び出しを減らしたあとも 150 秒を超えるときだけ、サブコマンドごと |

- 分けたファイルが共有するスタブと準備は、`-test.sh` で終わらない補助のファイル（例: `tests/dependabot-merge-test-lib.sh`）に置き、各ファイルが読み込む。`tests/run.sh` に、補助をテストとして拾わせないため
- 分けたファイルの名前は、元の名前に、まとまりの名前を足した形（例: `squad-dependabot-merge-list-test.sh`）にする
- 見張りのテストは、分けたファイルごとに、整形の後の 1 通りだけを流す（[整形の前と後の 2 回流しをやめる](#整形の前と後の-2-回流しをやめる)）

ファイルの名前が変わるので、`tests/run.sh` の `==== PASS` の行の名前も変わる。ケースの `PASS` の行は変わらない。

## 揺れに耐える余裕を取る

重いテストを減らし、macOS のシャードを 5 つにして、各シャードの `Tests` の手順を 300 秒以下に戻す。ジョブの上限は 10 分のままにし、ランナーが 1.5 倍ほど遅くなっても時間切れにしない。

### 時間切れになった原因

テストが 94 本に増え、macOS のシャードの余裕がなくなった。文書だけの PR で、`scripts (macos-latest, 1/4)` が 631 秒で時間切れになった。同じ時間帯の同じシャードは 414 秒で、ランナー全体が 1.5 倍ほど遅かった。

main の d919e2c の実行（run 43360258409）の macOS は次のとおりである。`Tests` の手順は、秒数の合計の 2.5〜3.0 分の 1 ほどになる。

| シャード | 秒数の合計 | `Tests` の手順 |
| --- | --- | --- |
| 1/4 | 967 秒 | 325 秒 |
| 2/4 | 795 秒 | 315 秒 |
| 3/4 | 1,608 秒 | 539 秒 |
| 4/4 | 1,240 秒 | 419 秒 |

揺れのない実行でも、すべてのシャードが 300 秒の目安を超えている。原因は次の 3 つである。

1. 見張りのテスト 27 本が、整形の前と後の 2 回、ファイル全体を流す。この 27 本で 1,712 秒ある
2. `setup-runtimes-*` が、claude・codex・both のそれぞれで `setup.sh` を最後まで通す。claude と codex の 2 本で 186 秒ある
3. `tests/test-weights` の合計は 3,904 秒で、実測の 4,610 秒より小さい。そのため、シャードの長さがそろわない

### ケースを減らす決まり

テストのケースは、同じ動作を別のテストで確認しているときに限り、減らしてよい。減らしたりまとめたりしたケースは、すべて対応表で示す。

対応表は PR のコメントに置き、減らすかまとめた確認ごとに 1 行を書く。列は次のとおりにする。

| 区分 | 元のファイル | 元のケース | 同じ動作を確認するファイル | そのケース |
| --- | --- | --- | --- | --- |
| 2 回流し・ランタイム・まとめた・名前を変えた のどれか | 今の main のファイル | `PASS` の行の文 | 残すファイル | `PASS` の行の文 |

- 1 つの `PASS` の行が複数の確認を含むときは、確認ごとに行を分ける
- 同じ動作を確認するケースがなければ、先にそのケースを足してから減らす。足したケースも表に書く
- `PASS` の行は、重みを写す push の CI のログと合わせる
- ファイルを分けて名前だけが変わったケースも、区分を「名前を変えた」にして書く

### 整形の前と後の 2 回流しをやめる

`cli_test_compare_modes` で、同じケースを整形の前と後の 2 回流すのをやめる。代わりに、欄がないと確認を飛ばす読み方ごとに、欄があって確認が効くケースを置く。

2 回流しが見つけるのは、見張りが約束にない欄を読む誤りである（[確認して整える](review-wait.md#確認して整える)）。この誤りは、形ごとに次の場所で見つけられる。

| 誤りの形 | 2 回流しをやめたあとに見つける場所 |
| --- | --- |
| ライブラリが、約束にない欄を除かない。除き方が変わる | `tests/squad-cli-lib-contract.py`。整形の前と後を、ライブラリの単位で比べる |
| 見張りが、約束にない欄の値を使う | 同じファイルのケース。値が `null` になり、期待した出力や呼び出しと合わなくなる |
| 見張りが、欄がないときに確認を飛ばす | 欄があって確認が効くケース。欄が除かれると確認が効かず、期待した結果と合わなくなる |

3 つめの形は、2 回流しでも、欄がある見本で確認が効くケースがなければ見つからない。そのケースがあれば、整形の後の 1 回で見つかる。そこで、そのケースがあることを、見張りごとに確認する。

1. `common/monitor` の見張りから、欄がないか `null` のときに動作を変える読み方を洗い出す。`squad-cli-lib` は約束のテストで確認するので除く
2. 読み方ごとに、欄があって確認が効くケースが、その見張りのテストにあるかを見る
3. なければ、2 回流しを除く前に足す。足したケースは対応表に書く

今の見張りでは、`squad-dispatch-pick` と `squad-pr-watch` に 9 か所ずつ、全体で 30 か所ほどある。洗い出しの一覧は、対応表と同じ PR のコメントに置く。

除くものと残すものは次のとおりである。

- 27 本のファイルの冒頭の、`SQUAD_CLI_TEST_COMPARING` で 2 回流しへ回す分岐を除く
- `tests/cli-mode-test-lib.sh` の `cli_test_compare_modes` を除く。比べるためだけの記録（`SQUAD_CLI_TEST_TRACE_FILE` に書く処理）も、ほかに読むテストがなければ除く
- ライブラリの `SQUAD_CLI_TEST_KEEP_FIELDS` の切り替えは残す。`tests/squad-cli-lib-contract.py` と `tests/capture-gh-fixtures.py` が使うため

27 本から `PASS modes:` の行が消える。対応表には、ファイルごとに 1 行を書き、上の表の 3 つの場所を示す。3 つめの場所には、洗い出しで見たケースの `PASS` の行を書く。

### Dependabot のマージのテストの本数

`squad-dependabot-merge-*` の 15 本は、まとめずに今の分け方のままにする。2 回流しをやめると時間がほぼ半分になり、まとめなくてもシャードに詰められるため。

`tests/setup-test.sh` を、ケースのまとまりで 3 つに分ける。直近の 3 回の実行のうち 2 回で、150 秒を超えたため。分け方は [長いファイルを分ける](#長いファイルを分ける) の決まりに従う。

### シャードの数

macOS は 5 つ、ubuntu は 2 つにする。macOS のシャードの数は、各シャードの重みの合計が 750 秒以下になる最小の数とし、5 つを上限にする。

750 秒は、`Tests` の手順の 300 秒に、秒数の合計と手順の比の小さいほう（2.5）を掛けた値である。上の 2 つの変更を入れたときの見積もりは次のとおり。見積もりには直近の 3 回の実行の秒数を使った。2 回流しのファイルは半分にし、claude と codex の 2 本は除いた。新しいテストは 30 秒とした。

| シャードの数 | 最も重いシャードの合計 | `Tests` の手順の見込み |
| --- | --- | --- |
| 4 | 789〜902 秒 | 263〜361 秒 |
| 5 | 631〜721 秒 | 210〜288 秒 |
| 6 | 526〜601 秒 | 175〜240 秒 |

4 つでは、揺れのない実行でも 300 秒を超えることがある。5 つなら 300 秒以下に収まり、1.5 倍に揺れても 450 秒ほどで、10 分の上限に届かない。6 つにしないのは、無料のプランで macOS のジョブを同時に流せる数が 5 つのためである。6 つ目は、同じ実行の中で空きを待つ。

ubuntu は、今も `Tests` の手順が 248〜285 秒で、テストを減らすとさらに短くなる。そのため 2 つのままにする。

### 重みを写し直す

`tests/test-weights` のすべての行を、一度だけ、macOS の CI の実測で写し直す。重みは分け方を変え、分け方は実測を変える。そのため、重みだけを直す push を最後に分けて置く。

| push | 変えるもの | 役目 |
| --- | --- | --- |
| A（実測を取る push） | テストとワークフローの最後の変更 | この push の CI の `==== PASS` の行の秒数を写す |
| B（最後の push） | `tests/test-weights` だけ。シャードの数を変えるときは、`check.yml` の matrix も | 写した重みで、`Tests` の手順の時間と全シャードの通過を確認する |

受け入れ条件の「最終の push の実測」は、A の実測と読む。B では重みが変わり、ファイルの秒数も変わるため、B の実測と一致させることはできない。

1. A を push し、その CI の macOS の全シャードのログから、`==== PASS` の行の秒数を集める。ジョブを流し直したときは、全ジョブを流し直し、全ジョブの最後の試行を使う。ジョブごとに速い試行を選んで混ぜない
2. 集めた行の数が、`tests/*-test.sh` の数と同じことを確認する
3. 150 秒を超えたファイルがあれば、[150 秒を超えるファイル](#150-秒を超えるファイル) の決まりで分け、A を作り直して 1 に戻る
4. すべての行を、ファイルの名前の順に、実測の秒数で書き直す。先頭のコメントに、実測を取ったコミットを書く
5. 新しい重みで、[シャードの数](#シャードの数) の決まりから数を求める。5 つでなければ、`check.yml` の matrix も直す
6. B を push する。B の CI で macOS のどれかのシャードの `Tests` の手順が 300 秒を超えたら、実装を止める。各シャードの秒数を添えて人間に返す

B の CI が揺れで遅かったときに、重みを B の実測で写し直すことはしない。写し直すたびに分け方が変わり、終わらないため。

## 利用者向けの文書の変更

## 確認の方法

| 確認すること | 方法 |
| --- | --- |
| すべてのジョブが 7 分以内 | 変更の PR で Checks を 3 回流す（再実行を含む）。各ジョブの開始から終了までを見る |
| 減らしたケースが対応表にある | 変更前の main と変更後の両 OS のテストのログを比べる。変更前の `PASS` の行のうち、変更後にない行が、すべて対応表にある。シャードに分かれたログは、OS ごとに合わせて比べる |
| 古い実行の取り消し | 同じ PR に 2 回続けて push し、前の実行が取り消され、後の実行だけが完走する |
| main の実行を取り消さない | main へ続けて 2 回 push し、両方の実行が完走する |
| 時間の上限 | ワークフローの定義で、各ジョブに `timeout-minutes: 10` がある |
| 結果を変えない手順がない | PR の本文に、消した手順と理由を書く |
| 手元ですべて流れる | 手元の macOS か Linux で、`bash tests/run.sh` がすべて通る |
| 揺れに耐える余裕 | 最後の push（B）の CI で、macOS の各シャードの `Tests` の手順が 300 秒以下で、macOS と ubuntu の全シャードが通る |
| 2 回流しが残っていない | `tests/` に、`cli_test_compare_modes` と `SQUAD_CLI_TEST_COMPARING` がない |
| `setup.sh` を最後まで通すのは both だけ | `tests/setup-runtimes-*-test.sh` が both の 3 本だけで、通る。`tests/project-runtimes-first-test.sh` も通る |
| 重みが実測と同じ | `tests/test-weights` の各行が、A の CI の `==== PASS` の行の秒数と一致する。`tests/test-runner-test.sh` が通る |
| 文書だけの PR も流す | `check.yml` に `paths-ignore` などがなく、`scripts` のジョブは `timeout-minutes: 10` のまま |

main への push の確認は、マージのあとでしか行えない。人間がマージした直後の 2 回の push で確認する。

## 残る危うさ

- macOS のジョブが、1 回の実行で 5 つになる。GitHub の無料のプランでは、アカウント全体で macOS のジョブを同時に 5 つまでしか流せない。2 つの PR が同時に流れると、後の実行の macOS のジョブは空きを待つ。それでも、1 回の実行で使う macOS の時間の合計は、テストを減らした分だけ短くなる
- 見張りに欄の有無で動作を変える読み方を足し、欄があるケースを足し忘れると、欄が約束から落ちても気づけない。`CONTRIBUTING.md` の決まりとレビューで防ぐ
- ランナーが 2 倍ほど遅くなると、重いシャードは 10 分に近づく。そのときは時間切れとして見えるので、流し直す
- 重みを写すのは一度だけで、その後の実測とはずれていく。今までどおり、2 倍以上ずれたら直す
- 重みの一覧が古くなると、シャードの長さがそろわず、1 つのジョブだけが長くなる。上限の 10 分で失敗として見えるので、重みを直して気づける
- ランナーのイメージから `jq` や `python3` が外れると、macOS のテストが失敗する。そのときは、入れる手順を戻す

## 検討した案

### 7 分に届かせる方法

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| テストを複数のジョブへ分け、呼び出しを減らし、長いファイルを分ける | 確認する内容を減らさない。macOS も PR で流し続ける | macOS のジョブの数が増え、同時に流せる数を取り合う | 選んだ |
| テストを速くするだけで、1 つのジョブに収める | ジョブの数が増えない | PR 34 の前でも、3 並列で 684 秒かかる。テストの作り直しだけでは届かない | 選ばない |
| 1 つのジョブの並列数を上げる | 変更が小さい | テストはプロセスの起動が多く、3 コアのランナーでは並列数を上げても速くならない | 選ばない。実測で効くときだけ、シャードの数を減らすのに使う |

### 分け方

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 重みの一覧から、決まった規則で分ける | 実行ごとに分け方が変わらない。手元でも同じ分け方を再現できる | 重みの一覧を直し続ける必要がある。テストで追記を強いる | 選んだ |
| 名前の順に、順番に配る | 一覧が要らない | 長いファイルが同じシャードに集まると、そのジョブだけ長くなる | 選ばない |
| 前の実行の秒数を、キャッシュから読んで分ける | 一覧を直さなくてよい | キャッシュがないときに分け方が変わり、手元で再現できない | 選ばない |

### 整形の前と後の 2 通りの比べ方

2 通りを 1 つのファイルの中で同時に流す案も考えた。ファイルの長さは半分になるが、`tests/run.sh` が数える並列数を超えてプロセスが動き、ほかのファイルが遅くなる。ファイルを分ければ、並列数の中で同じ効果が出るので、分けるほうを選んだ。

### 2 回流しの代わり

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 2 回流しをやめ、欄がないと確認を飛ばす読み方ごとに、確認が効くケースを置く | 見張りのテストの時間が半分になる。2 回流しも、このケースがなければ誤りを見つけられない | 見張りを変えるたびに、読み方とケースを合わせ続ける必要がある | 選んだ |
| 代表のケースだけを 2 回流す | 2 回流しの仕組みを残せる | 誤りは、欄があって確認が効くケースでしか出ない。代表のケースがそれに当たる保証がない | 選ばない |
| 約束にない欄の読み取りを、実行せずに検査する | 実行しないので速い | 見張りは `jq`・bash・Python で欄を読み、漏れなく拾う検査を作るのが重い | 選ばない |

### Dependabot のマージのテストをまとめるか

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 15 本のままにする | 準備のくり返しは 15 秒ほどで小さい。150 秒の上限から遠い | 本数が多く、見通しが悪い | 選んだ |
| サブコマンドごとに 3〜4 本にまとめる | 本数と、準備のくり返しが減る | 1 本が 100〜180 秒になり、揺れで上限を超える | 選ばない |

### 余裕の取り方

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| テストを減らし、macOS のシャードを 5 つにする | 揺れのない実行で 300 秒以下に収まる | 1 回の実行で、無料のプランの同時の上限を使い切る | 選んだ |
| テストを減らし、macOS のシャードを 4 つのままにする | 同時に流せる数が 1 つ空く | 揺れのない実行でも、300 秒を超えることがある | 選ばない |
| ジョブの上限を 15 分に上げる | 変更が小さい | 大きく遅くなったテストに気づくのが遅れる | 選ばない。要件で除いた |

### 重みを写す実測

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| テストを変える最後の push（A）の実測を写し、重みだけの push（B）を最後に置く | 一度で終わる | B の実測とは一致しない | 選んだ |
| 最後の push の実測で写し直し、一致するまでくり返す | 最後の push の実測と一致する | 重みが変わるたびに分け方と秒数が変わり、終わらない | 選ばない |
| 重みも A に含める | push が 1 つ減る | A より前に、変えたテストの実測がない | 選ばない |
