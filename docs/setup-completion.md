# 導入後の自動の作業と起票の設計

セットアップの最後に行う Dependabot の Webhook の登録と、人間に残る作業の起票について、仕組みとその理由を書く。  
使う人への手順は `manual.md` の「導入後に自動で行うことと、起票するタスク」に書く。

## Webhook の URL の扱い

トリガーの URL は token を含む認証情報なので、表示、ログ、タスクの本文、一時ファイルに出さない。  
セットアップは、URL を変数やファイルに置かず、パイプの中だけで受け渡す。

- URL は `multica autopilot get --show-secrets --output json` でだけ取り出す。
  - 出力はそのまま `jq` で GitHub への要求の JSON にし、`gh api … --input -` へ渡す。
  - コマンドの引数と環境変数にも置かない。
- 既存の Webhook との照合は、両方の JSON を一つのパイプで `jq -s` に渡し、一致した Webhook の ID だけを出す。
  - `gh api` の出力も `--jq` で ID だけにする。
- `--show-secrets` の警告と、`gh api` の失敗時の応答の本文は捨てる。
  - 失敗は HTTP の状態コードか、決まった文で表示する。
  - この処理は `set -x` で流さない。

テストでは、見張り用の URL を返す CLI の偽物を使う。  
その文字列が、標準出力、標準エラー、起票の本文、一時ファイル、記録したコマンドの引数のどこにもないことを確認する。

## イベントフィルターを自動にしない理由

イベントフィルターは今の Multica の CLI では設定できないので、自動にせずタスクで頼む。  
`multica autopilot trigger-add` と `trigger-update` にはフィルターの指定がなく、トリガーの JSON にもフィルターの項目がない。  
GitHub の Webhook で絞れるのはイベントの種類までで、アクションや送信者では絞れない。

そのため、セットアップは GitHub 側をイベント `pull_request` だけに絞る。  
アクションと Dependabot の PR への絞り込みは、Multica の画面で人間が行う。

CLI にフィルターの指定が入ったら、自動の作業に移す。

## 二重に作らないための判定

起票の前に対象のプロジェクトのタスクを状態を問わずに読み、すでに起票した対象を除く。  
判定はタスクの metadata の印で行い、タイトルの一致には頼らない。

- 起票するタスクの metadata の `squad_kit_task` に種類を、`squad_kit_targets` に対象の一覧を JSON の配列の文字列で書く。
  - リポジトリごとのタスクには、`repository` にも OWNER/REPO を書く。
- 起票の前に、`multica issue list --project <ID> --metadata squad_kit_task=<種類>` を最後のページまで読む。
  - 完了と取り下げも含める。
  - 見つかったタスクの対象を合わせ、まだない対象だけを起票する。
- 作るときは backlog で作り、metadata、ラベル、最後の状態の順に書く。
  - 途中で止まって印のないタスクが残ったら、同じプロジェクトの同じタイトルで印のないものを探す。
  - 見つかれば作り直さず、印を書いて使う。
  - 対象の一覧を本文に持つタスクの採用では、増えた対象の作業を本文へ追記してから印を書く。
  - 元の本文は残し、同じ追記は重ねない。

起票するかは今回の実行の記憶ではなく、読み直した現在の状態で決める。  
途中で止まった実行の分も、次に流したときに起票するため。

同じ対象は一度だけ起票し、やり直しが要るときは人がタスクを開き直す。

| 種類 | 対象 | 起票するかの判定 |
| --- | --- | --- |
| フィルターの設定 | OWNER/REPO | Dependabot の役を残し、Webhook を使う、選んだリポジトリ |
| Webhook の登録 | OWNER/REPO | 今回の実行で登録を飛ばしたか、失敗したリポジトリ |
| Webhook を外す | OWNER/REPO | Dependabot の役を残し、Webhook を使わない答えで、Webhook のトリガーが残っているリポジトリ |
| AGENTS.md の配置 | OWNER/REPO | 選んだリポジトリ |
| 説明と検証スキルの記入 | `project` | プロジェクトに 1 つ |
| 動きの試し | `project` | プロジェクトに 1 つ |
| 共通スキルの更新 | `squad-handoff@<タグ>` | 今回の実行で、共通スキルの更新を飛ばした |
| 外した役 | エージェントとオートパイロットの名前 | 外した役の自分の管理するエージェントと、外したために一時停止した自分の対象のオートパイロット |
| リポジトリの増減 | `added:OWNER/REPO` か `removed:OWNER/REPO` | 実行の前からある検証スキルの `` ## `OWNER/REPO` `` の節と、選んだリポジトリの差 |
| 導入の確認 | 項目の名前 | 今回の確認で要確認か、読み直しに失敗した項目 |

外した役のタスクは、まだない対象をまとめて 1 件にする。  
リポジトリの増減は、検証スキルを今回ひな形から作ったときは起票しない。

自動の作業も同じ考えで、既存のトリガーと Webhook を再利用し、既存の Webhook には ping を送り直さない。
