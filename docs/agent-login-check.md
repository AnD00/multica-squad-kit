# エージェント用の Claude のログインの確認

ホストの準備（`prepare_host`）は、エージェント用の Claude にログインしているかを `claude auth status` で確かめる。この文書は、その呼び方と、結果ごとの止まり方の設計と、その理由を書く。使う人への案内は `manual.md` に書く（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 目的と範囲

ログイン済みの人が、入口（`install.sh`）を標準入力から流すと、ホストの準備でログインを求められて止まっていた。流し直しても毎回同じところで止まるので、導入も更新も進めない。ログイン済みならログインの確認を通過し、ログインしていないときだけログインを案内するようにする。

原因は、次の二つが重なったことである。

1. 入口を標準入力から流すと、セットアップは標準入力を端末（`/dev/tty`）にして動く（[標準入力から流すとき](install.md#標準入力から流すとき)）。ログインの確認の `claude auth status` もこの標準入力を受け継ぐ。macOS では、標準入力が `/dev/tty` のとき、Claude の CLI（Bun）が `EINVAL: invalid argument, kqueue` を出して終了コード 1 で落ちる
2. ログインの確認は、`claude auth status` の終了コードが 0 以外なら、理由を見ずにログインを案内して止まる。そのため、CLI の異常終了がログイン切れとして案内される

1 は、macOS、Claude Code 2.1.322、Bun v1.4.4 で再現した。疑似端末の中で `claude auth status </dev/tty` は同じエラーで終了コード 1 になる。標準入力を `/dev/null` にすると、同じ疑似端末の中でも JSON を返す。

次は対象にしない。

- Claude の CLI（Bun）の kqueue の不具合そのものの修正。原本の外の製品のため。原本は呼び方で避ける
- Codex のログインの確認（`codex login status`）。今回の不具合が見られておらず、Rust 製で同じ原因に当たらないため。呼び方も止まり方も今のままにする
- 入口が質問を端末から読む方式。質問に答えるのに要り、今回の原因はログインの確認の呼び方で避けられるため。`install.sh` と、`setup.sh` が質問を読む方法は変えない
- セットアップのほかの外部の CLI の呼び方。今回の不具合が見られていないため

## 呼び方

`claude auth status` の標準入力を `/dev/null` にして呼ぶ。標準出力と標準エラーは、どちらも画面に流さずに受け取り、[結果の分け方](#結果の分け方)で読む。終了コードも受け取る。

確認のコマンドは何も読まないので、標準入力を `/dev/null` にしても動きは変わらない。こうすると、セットアップの標準入力が端末・パイプ・ファイルのどれでも、CLI が受け取る標準入力は同じになる。入口の流し方によらず、同じ呼び方で確かめられる（[入口の流し方と動作](#入口の流し方と動作)）。

標準エラーを受け取るのは、確認に失敗したときに示すためである（[確認に失敗したときの表示](#確認に失敗したときの表示)）。今は標準エラーをそのまま画面に流しているが、作成の進みの一覧（[作成の進み](screens.md#作成の進み)）の途中に出ると表示が崩れる。受け取りに一時ファイルを使うときは、確認のあとすぐ消す。

検討した案と選ばなかった理由は次のとおり。

| 案 | 選ばなかった理由 |
| --- | --- |
| 入口が、セットアップの標準入力を `/dev/tty` にしない | セットアップが質問を端末から読めなくなる。質問の読み方を変えると、`setup.sh` の質問のすべてに及ぶ |
| セットアップの最初で、子のプロセスの標準入力をまとめて `/dev/null` にする | 質問を読む処理と分ける必要があり、変更が広い。ほかの CLI では不具合が見られていない |
| 疑似端末（`script` など）の中で CLI を呼ぶ | 道具と OS ごとの違いが増える。端末を渡す理由がない |

## 結果の分け方

標準出力の最初の JSON の値と、終了コードで分ける。ログインしていないかは、CLI が `loggedIn: false` と答えたかだけで決め、終了コードでは決めない。

| 標準出力の最初の値 | 終了コード | 動作 |
| --- | --- | --- |
| オブジェクトで、`loggedIn` が `true` | 0 | 通過する。今までどおり、何も出さずに次へ進む |
| オブジェクトで、`loggedIn` が `false` | 問わない | 今までと同じ「エージェント用の Claude にログインしてください」の案内で止まる |
| オブジェクトで、`loggedIn` が `true` | 0 以外 | 確認に失敗したとして止まる |
| 上のどれでもない（空、JSON でない、オブジェクトでない、`loggedIn` が真偽値でない） | 問わない | 確認に失敗したとして止まる |

`loggedIn: false` を終了コードで分けないのは、同じ CLI でも、ログインしていないときの終了コードが呼び方で変わるためである。Claude Code 2.1.322 では、端末のないところで呼ぶと終了コード 0、疑似端末の中で呼ぶと終了コード 1 で、どちらも `loggedIn: false` を返した。

`loggedIn: true` でも終了コードが 0 以外なら通過させない。CLI が失敗したと言っているので、出力が途中までのおそれがあり、確かめたことにならないため。出力は[確認に失敗したときの表示](#確認に失敗したときの表示)で示すので、人間が判断できる。

最初の JSON の値だけを読むのは、端末のないところで呼ぶと、CLI が JSON のあとに端末の制御文字（`ESC [ ? 1 l` など）を出すためである。今の確認は出力の全体を JSON として読むので、制御文字があると読めずにログインを案内する。最初の値のあとに続くものは読まず、捨てる。最初の値の前に何かあるときは、読めない出力として扱う。

## 確認に失敗したときの表示

確認に失敗したときは、ログインを案内しない。確認そのものに失敗したことと、CLI の出力を示して、終了コード 1 で止まる。止まる前に、デーモンの操作など、ログインの確認のあとの処理は行わない。今のログインの案内と同じである。

表示は、今の止まり方（作成の進みの一覧の手順を `✖` にし、`エラー:` の行を出す）に、CLI の出力を続ける。CLI の出力は、`エラー:` の行のあと、標準エラーに出す。

```text
  ✖ ホストを準備
エラー: エージェント用の Claude のログインを確かめられませんでした（claude auth status の終了コード 1）。ログインが切れているとは限りません。下の出力を確かめ、端末から CLAUDE_CONFIG_DIR=/Users/me/.multica-agent/claude claude auth status を流して、ログインの状態を確かめてから流し直してください。
  claude auth status の標準出力:
    （なし）
  claude auth status の標準エラー:
    error: EINVAL: invalid argument, kqueue
          at emitError (node:events:65:13)
    Bun v1.4.4 (macOS arm64)
```

- `エラー:` の行には、終了コード、ログイン切れとは限らないこと、単独で確かめるコマンドを書く。コマンドの `CLAUDE_CONFIG_DIR` は、今の案内と同じく実際のパスにする
- 標準出力と標準エラーは、見出しの下に、4 つの空白で字下げしてそのまま出す。空なら `（なし）` と出す。出力を切り詰めない
- 作成の進みの一覧を書き換えないとき（`✔ 手順  値` の行を順に出す画面）も、`エラー:` の行と出力は同じに出す

文は、`manual.md` の止まったときの表と合わせる（[利用者向けの文書の変更](#利用者向けの文書の変更)）。

## 入口の流し方と動作

入口をファイルに取って流す場合と、`bash setup.sh` で流す場合の動作は変えない。直すのはログインの確認の呼び方だけで、`install.sh` と、`setup.sh` が質問を読む方法は変えないためである。

| 流し方 | セットアップの標準入力 | ログインの確認の CLI の標準入力 |
| --- | --- | --- |
| 入口を標準入力から流す（`curl ... \| bash -s --`） | `/dev/tty`（今のまま） | `/dev/null`（今は `/dev/tty`） |
| 入口をファイルに取って流す（`bash install.sh`） | 入口の標準入力（今のまま） | `/dev/null`（今は入口の標準入力） |
| `bash setup.sh` | 流した人の標準入力（今のまま） | `/dev/null`（今は流した人の標準入力） |

ファイルと `bash setup.sh` の場合も、CLI の標準入力は `/dev/null` に変わる。確認のコマンドは標準入力を読まないので、結果は変わらない。ログイン済みなら通過し、ログインしていなければ今と同じ案内で止まる。

変わらないことは、次で確かめる。

1. `install.sh` と `setup.sh` の差分がないこと。PR の差分で確かめる
2. 入口のテスト（`tests/install-test.sh`）を変えずに通すこと。ファイルとして流す場合は、セットアップが入口の標準入力を受け継いで答えを読むことを確かめている。標準入力から流す場合は、端末から答えを読むことを確かめている
3. ホストの準備のテスト（`tests/host-test.sh`）で、セットアップの標準入力を端末・パイプ・ファイルにした 3 通りで、同じ結果になること（[テスト](#テスト)）
4. 人間が macOS の実機で、ログイン済みの環境から、入口を標準入力から流す場合と `bash setup.sh` で流す場合の両方を流し、ホストの準備を通過すること

## テスト

`tests/host-test.sh` の `claude` のスタブを広げ、ログインの確認の呼び方と分け方を確かめる。スタブで行うので、本物の CLI もネットワークも要らず、macOS と Ubuntu の CI で通る。

スタブは、受け取った標準入力が端末なら（`[[ -t 0 ]]`）、kqueue のエラーと同じ文を標準エラーに出して終了コード 1 で終わる。macOS の CLI の不具合の代わりである。本物は `/dev/tty` のときだけ落ちるが、スタブは端末ならいつも落ちるので、本物より厳しく確かめる。

| 確かめること | スタブの動作 | 期待すること |
| --- | --- | --- |
| 標準入力が端末でも落ちない | セットアップの標準入力を `/dev/tty` にして流す。疑似端末は `tests/stdin-tty-run.py` の `tty` で作る | 通過し、次の処理（デーモンの確認）へ進む |
| 流し方によらず同じ | セットアップの標準入力を端末・パイプ・ファイルにする | 3 通りとも通過する。スタブが受け取った標準入力が端末でない |
| ログインしていない | `{"loggedIn":false}` を、終了コード 0 と 1 で返す | どちらも今と同じログインの案内で止まり、デーモンを操作しない |
| CLI が異常終了する | 標準出力は空、標準エラーに文を出し、終了コード 1 | ログインを案内しない。確認に失敗したこと、終了コード、標準エラーの文を出して止まる |
| 読めない出力で終了コード 0 | JSON でない文、`loggedIn` のないオブジェクト、`loggedIn` が文字列 | 上と同じに止まり、ログインを案内しない |
| ログイン済みでも終了コードが 0 以外 | `{"loggedIn":true}` と終了コード 1 | 確認に失敗したとして止まる |
| JSON のあとの制御文字 | `{"loggedIn":true}` のあとに `ESC [ ? 1 l` などを出し、終了コード 0 | 通過する |

ログインの案内で止まる場合と、確認に失敗した場合は、互いの文が出ていないことも確かめる。取り違えを戻さないため。今のテストの、Claude だけ・Codex だけを使う場合の確認（使わない側のログインを求めない）は、そのまま通す。

## 利用者向けの文書の変更

`manual.md` の「止まったときに見ること」の表に、確認に失敗したときの行を足す。ログイン切れの案内とは別の行にし、取り違えないようにする。

| 表示・状態 | 確認と再開 |
| --- | --- |
| 「エージェント用の Claude のログインを確かめられませんでした」と出て止まった | ログインが切れているとは限らない。表示された CLI の出力を読み、端末から表示されたコマンドを流してログインの状態を確かめる。CLI が落ちているときは Claude Code を更新して流し直す。直らなければ、出力を添えて配布者へ返す |

`docs/install.md` の[標準入力から流すとき](install.md#標準入力から流すとき)には、セットアップの子のプロセスも `/dev/tty` を受け継ぐことと、ログインの確認ではそれを避けることを書き、この文書へつないだ。
