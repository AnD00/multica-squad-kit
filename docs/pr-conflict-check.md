# マージへ回す前に PR のコンフリクトの状態を確かめる

リーダーが人間のマージへ回す直前に、PR の今の head と `mergeable` を `squad-pr-watch` で読み、その値と head の SHA を 1 行で出す。リーダーはその行に従って次の動きを決め、人間やほかの役へは読んだ値と head をそのまま書く。

この文書は、スクリプトの新しいサブコマンド、リーダーの指示、`squad-handoff` の決まりの設計と、その理由を書く。リーダーの指示に置いた手順は、のちに squad-handoff の参照のファイルへ移した（[leader-principles.md](leader-principles.md) の「手順の移し先」）。

## 目的と範囲

今のリーダーの指示は、人間のマージを待つ前に `squad-pr-watch conflicts <タスク>` で規則を入れ直すとだけ書いている。このサブコマンドは wakeup の規則を作り直すだけで、PR の head も `mergeable` も読まない。そのため、すでに `main` とコンフリクトしている PR でも、リーダーは出力を「なし」と読み違えて人間へ回せてしまう。状態を自分で読んだときも、読んだのが 1 つ前の head のことがある。

確認をスクリプトに持たせ、結果を必ず値と head の 1 行で出す。読めないときや値が決まらないときは「未確認」と出し、空の出力で終えない。次は対象にしない。

- レビュー・E2E・テストの結果など、PR の状態以外の確認に同じ決まりを広げること。今回の失敗に直結する PR の状態に絞り、守る場面をはっきりさせるため
- `mergeable` が決まるまで、人間へ回さずに見張りで待つ仕組み。待つ仕組みが新たに要り、値が決まらないとタスクが止まり続けるため。読み直しと「未確認」で扱う
- CI の見張り（`ci`・`ci-check`・`ci-held`）の動き。今回はコンフリクトの確認と、報告の書き方だけを扱う
- コンフリクトの見張り（`conflicts`）の動きと、見張りが起こしたときの指示の文。今までどおり残す

## コマンドの I/F

`conflicts` に足さず、別のサブコマンドにする。`ci` と `ci-check` と同じく、規則を作るものと今の状態を読むものを分ける。

```bash
squad-pr-watch conflicts-check <タスク>
```

`<タスク>` は、タスクの ID か識別子で、`multica issue get` が受け取る形ならよい。

| 終了コード | 意味 | 標準出力 |
| --- | --- | --- |
| 0 | 確かめた。読めなかったときも含む | 結果の 1 行 |
| 2 | 引数の数の誤り。使い方を標準エラーに出す | なし |

`multica`・`gh`・`jq` の失敗やコマンドが見つからないときも、終了コード 1 で止めず、「未確認」の行を出して 0 で終える。リーダーが空の出力や終了コードを読み違える余地を残さないため。失敗の詳細は標準エラーに出す。

## 結果の行

標準出力には、どの場合も次の形の 1 行だけを出す。値は `MERGEABLE`・`CONFLICTING`・`未確認` のどれかにする。

```text
コンフリクト: <値> head: <SHA> [理由: <理由>]
```

- head の SHA は、値を読んだのと同じ読み取りの `headRefOid` を、40 文字のまま書く。人間が PR の画面の head と照合でき、短縮による取り違えがないため
- PR を一度も読めなかったときは、SHA の代わりに `不明` と書く。読み直しの途中で読めなくなったときは、最後に読めた head を書く
- `理由:` は「未確認」のときだけ付ける。値が `MERGEABLE`・`CONFLICTING` のときは付けない
- 行と理由の文には、「なし」の語を使わない。リーダーや人間が「コンフリクトなし」と読み違えないため

| 場合 | 出す行 |
| --- | --- |
| `mergeable` が `MERGEABLE` | `コンフリクト: MERGEABLE head: <SHA>` |
| `mergeable` が `CONFLICTING` | `コンフリクト: CONFLICTING head: <SHA>` |
| 読み直しても `UNKNOWN` のまま | `コンフリクト: 未確認 head: <SHA> 理由: mergeable が 60 秒たっても UNKNOWN` |
| `UNKNOWN` 以外の想定外の値 | `コンフリクト: 未確認 head: <SHA> 理由: mergeable が想定外の値 <値>` |
| PR がマージ済みか閉じている | `コンフリクト: 未確認 head: <SHA> 理由: PR がマージ済みか閉じている` |
| タスクを読めない | `コンフリクト: 未確認 head: 不明 理由: タスクを読めない` |
| metadata に `pr_url` がない | `コンフリクト: 未確認 head: 不明 理由: metadata に pr_url がない` |
| `gh` が失敗した、応答に `state`・`headRefOid`・`mergeable` のどれかがない | `コンフリクト: 未確認 head: <最後に読めた SHA か 不明> 理由: PR を読めない（gh の失敗か必須欄の欠落）` |
| `gh`・`jq`・`multica` が見つからない | `コンフリクト: 未確認 head: 不明 理由: <コマンド> が見つからない` |

## 処理の順序

1. 引数の数を確かめる。合わなければ、使い方を標準エラーに出して終了コード 2 で終える
2. `jq`・`multica`・`gh` があるかを確かめる。なければ「未確認」の行を出す
3. `multica issue get <タスク> --output json` でタスクを読み、metadata の `pr_url` を取る。読めないか、`pr_url` がなければ「未確認」の行を出す
4. `gh pr view <pr_url> --json state,headRefOid,mergeable` を、共通ライブラリの `squad_cli_read gh-pr-mergeable` で読む。3 つの欄は必須で、`null` も認めない。失敗したか、欄が欠けたか、`headRefOid` が空なら「未確認」の行を出す
5. `state` が `MERGED` か `CLOSED` なら「未確認」の行を出す
6. `mergeable` が `MERGEABLE` か `CONFLICTING` なら、その値の行を出す
7. `UNKNOWN` なら、[読み直し](#読み直し)に従って 4 に戻る。上限に達したら「未確認」の行を出す
8. それ以外の値なら、読み直さずに「未確認」の行を出す

タスクの metadata、コメント、wakeup の規則には書き込まない。確認は何度流しても同じ結果になり、規則の入れ直しは `conflicts` に任せる。

## 読み直し

GitHub は `mergeable` をあとから計算するので、push の直後は `UNKNOWN` が返ることが多い。`UNKNOWN` の間は 10 秒おきに読み直し、最初に読み始めてから 60 秒を過ぎたら読み直しをやめる。

- 経過は `date +%s` で測り、待ちは `sleep` で行う。読み直す前に残り時間を確かめ、待ちは 10 秒と残り時間の短い方にする。残り時間がなければ待たずに「未確認」とする
- この決め方で、待ちの合計は 60 秒以内、読み取りは最初を含めて 7 回以内になる。新しい読み取りを始めるのは 60 秒までで、最後の 1 回の `gh` の時間だけ、全体が 60 秒を超えることがある
- 間隔を 10 秒にするのは、`mergeable` はふつう push から数秒で決まり、1 回か 2 回の読み直しで済むため。より短くしても決まる時刻は変わらず、GitHub への読み取りが増えるだけになる
- 上限は、要件の 60 秒をそのまま使う。リーダーの 1 回の実行は 30 分ほどに収めるので、その数 % にとどまる
- 値はスクリプトの中の定数にする。導入先ごとに変える要件がないため、設定にはしない。テストは `sleep` と `date` をスタブにして、実際には待たない

リーダーは、このコマンドの時間切れを 120 秒以上にする（[リーダーの指示](#リーダーの指示)）。

## リーダーの指示

`common/agents/orchestrator.md` の「CI とコンフリクト」で、コンフリクトの段落を「状態の確認」と「規則の入れ直し」の 2 つの手順に書き分ける。CI の段落と、`<!-- IF ci-monitor -->` の範囲は変えない。

状態の確認には、次を書く。

1. 人間のマージへ回す直前に `squad-pr-watch conflicts-check <タスク>` を流す。コマンドの時間切れは 120 秒以上にする。レビュー・E2E・CI を経て、または解消の引き継ぎを受けて、マージへ回すたびに流す
2. 出力の `コンフリクト:` の行に従う。行が出ないときや読めないときは「未確認」として扱う
3. `CONFLICTING` なら、人間を呼ばない。「実装・修正の振り分け」で有効な修正の役を選び、行を添えて `main` とのコンフリクトの解消を頼み、タスクを `in_progress` に戻す。解消の引き継ぎを受けたら、もう一度この確認から流す
4. 解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。「受け渡しと人間を待つところ」の、同じ差し戻しが 2 回続いたら人間を呼ぶ決まりに合わせる
5. `MERGEABLE` なら、規則を入れ直してから、行をそのまま添えて人間へ回す
6. 「未確認」なら、規則を入れ直してから、行をそのまま添えて人間へ回す。「なし」とは書かない

規則の入れ直しには、今の段落の内容を残し、次を足す。

- 人間のマージを待つ前に `squad-pr-watch conflicts <タスク>` で規則を入れ直す。この出力は規則の登録の結果で、PR の状態ではないので、人間への報告に使わない
- `CONFLICTING` で修正の役へ回すときは入れ直さない。解消の途中で見張りが起きても、タスクが `in_review` でないので何もしないため。次にマージへ回すときに入れ直す
- 見張りで起きたときの動き（`in_review`、前回はマージ待ち、返事を待つ回の途中でないときだけ解消を頼む）は今のままにする。「解消で設計や挙動が変わらなければ、レビューを回し直さず人間へ戻す」は、「状態の確認を流してから人間へ戻す」に改める

`squad-pr-watch` の中にある、見張りが起こしたときの指示の文は変えない。

## 受け渡しの決まり

`common/skills/squad-handoff/SKILL.md` の「PR にレビューやテストの結果を書く」の後に、節「PR の状態を書く」を足す。PR の状態を人間やほかの役へ書くすべての役に効かせるため、リーダーの指示だけでなく共通スキルに置く。

節には、次を書く。

- PR のコンフリクトや CI の結果を、タスクのコメントや PR のコメントで人間やほかの役へ書くときは、読んだ値と、読んだ時点の head の SHA を添える。SHA は 7 文字以上で書く
- 見張りのスクリプトが値と head の行を出したとき（`squad-pr-watch conflicts-check` の `コンフリクト:` の行、`ci-check` の `CI <SHA>:` の行）は、その行をそのまま写す
- 空の出力、読めなかった結果、`UNKNOWN` のように決まらなかった値は「未確認」と書く。「なし」や「通った」とは書かない

レビュー・E2E・テストの結果は、この節の対象にしない。それらは今の「`確かめたコミット:`」の決まりで扱う。

## 導入と更新

`squad-pr-watch` は `common/monitor/` の `squad-*` なので、ホストの準備がエージェントの `bin` に置き、流し直しで新しい中身に置き換える。セットアップの手順と、登録する名前は変えない。

リーダーの指示と `squad-handoff` は、セットアップの流し直しで更新される。見張りのスクリプトはホストごとの流し直しまで古いままなので、`CHANGELOG.md` には、ホストでセットアップを流し直すまで `conflicts-check` が使えないことを書く。古いスクリプトで `conflicts-check` を流すと使い方の誤り（終了コード 2）になり、リーダーは行が出ないので「未確認」として人間へ回す。誤って「なし」と回すことはない。

## テスト

`tests/squad-pr-watch-register-test.sh` に `conflicts-check` のテストを足す。スタブの `gh` は、決めた順に `pr view` の応答を返すか失敗する。スタブの `sleep` は受け取った秒を記録して待たずに返し、スタブの `date` は記録した秒の合計だけ進んだ時刻を返す。

| 確かめること | 受け入れ条件 |
| --- | --- |
| head が X、`CONFLICTING` のとき、行に X と `CONFLICTING` があり、「なし」がない | 1 |
| head が X、`MERGEABLE` のとき、行に X と `MERGEABLE` がある | 2 |
| 1 回目が `UNKNOWN`、2 回目が `CONFLICTING` のとき、`sleep 10` を 1 回呼び、行が `CONFLICTING` になる | 3 |
| `UNKNOWN` が続くとき、行に「未確認」と X があり、`sleep` の秒の合計が 60 以下である | 4 |
| `gh` が失敗するとき、`pr_url` がないとき、タスクを読めないとき、行に「未確認」があり、「なし」がない | 5 |
| 上のすべての場合で、標準出力がちょうど 1 行で、終了コードが 0 である | 6 |
| 既存の `conflicts` のテストが、変えずに通る | 7 |

あわせて、次も確かめる。

- PR がマージ済みか閉じているとき、「未確認」を出す
- 読み直しの間に head が変わったとき、行には最後に読んだ head を書く
- `conflicts-check` は wakeup の規則・metadata・コメントを書かない（スタブの `multica` の呼び出しが `issue get` だけである）
- 引数の数が違うとき、終了コード 2 で、標準出力が空である

`tests/agent-templates-test.sh` では、展開したリーダーの指示に `squad-pr-watch conflicts-check <タスク>` と `squad-pr-watch conflicts <タスク>` が別の段落にあること、`CONFLICTING`・`MERGEABLE`・「未確認」の扱いの文があることを確かめる。`squad-handoff` には、節「PR の状態を書く」と「未確認」の決まりがあることを確かめる。文面が要件どおりかは、検証する人が読んで確かめる。

## 検討した案

- `conflicts` に状態の読み取りを足す案。1 回の呼び出しで済むが、規則の登録と状態の報告が同じ出力に混ざり、今回と同じ読み違えが起きやすい。今の出力を前提にした既存のテストも変わるので、別のサブコマンドにした
- 確認をリーダーの指示だけに書き、リーダーが自分で `gh` を読む案。変更は少ないが、読み直しと「未確認」の扱いが実行ごとの判断に任され、テストで防げないので選ばなかった
- 読み取りの失敗を終了コード 1 で返す案。ほかのサブコマンドとそろうが、リーダーが空の出力を読み違える余地が残るので、どの場合も「未確認」の行を出して 0 で終えることにした
- head の SHA を `ci-check` と同じ 7 文字で書く案。行は短くなるが、人間がマージの前に照合する値なので、40 文字のまま書くことにした。`squad-handoff` の決まりは、`ci-check` の行も写せるよう 7 文字以上とした
- 読み直しを回数だけで決める案（例: 10 秒おきに 5 回）。`gh` の読み取りが遅いと全体が 60 秒を超えるので、経過時間で上限を決めた
