# プロジェクトごとの指示の書き方

ここは、プロジェクトに合わせて担当が記入して育てるひな形です。使用する言語、構成、検証コマンドは入っていません。`[記入: …]` は記入欄です。書き終えた欄は、かっこごと実際の内容に置き換えます。不要な項目は削除するか、対象外である理由を書きます。

セットアップは「プロジェクトの説明と検証スキルを記入する」と「スクワッドの動きを試す」を、実行した人を担当にして起票します。リポジトリごとの「OWNER/REPO に AGENTS.md と作業別のルールを置く」は、スクワッドを担当にして backlog で起票します。前の二つを終えてから、リポジトリのタスクを todo にしてスクワッドへ渡してください。作業の順と手順は、起票されたタスクの本文に従います。

## 置き場所

| この中のファイル | プロジェクトでの置き場所・用途 |
| --- | --- |
| [AGENTS.md](AGENTS.md) | リポジトリのルート。概要、構成、作業別のルールの入口、完了の条件 |
| [.agents/rules/code.md](.agents/rules/code.md) | 同じ相対パス。コードの作業で使うルールのひな形 |
| [.agents/rules/tests.md](.agents/rules/tests.md) | 同じ相対パス。テストの作業で使うルールのひな形 |
| [.agents/rules/docs.md](.agents/rules/docs.md) | 同じ相対パス。ドキュメントの作業で使うルールのひな形 |
| [.agents/skills/verify/SKILL.md](.agents/skills/verify/SKILL.md) | プロジェクトに一つ登録する検証スキルのひな形。リポジトリごとの節を持つ |
| [verify-repository.md](verify-repository.md) | 上のスキルへ、選んだリポジトリごとに差し込む記入欄 |
| [project.md](project.md) | Multica のプロジェクトの説明の初期値。以後の説明の正本はプロジェクトで決めた場所に置く |

既存のファイルがあれば、内容を読み、必要な項目だけを取り入れます。まとめて上書きしません。この案内は書く人用なので、エージェントの指示として登録する必要はありません。

## 記入すること

- リポジトリごとに、そのリポジトリの `AGENTS.md` に目的と利用者、設計の入口、実際のディレクトリと依存方向を書きます。外部との合意が要る契約、生成物とその正本、作業で守る制約を記入します。作業別のルールも各リポジトリのものを置きます。
- 作業別のルールを記入します。front matter の `paths` にある仮のパスを、リポジトリのルートから見た実際の glob に置き換えます。必要ならルールを分けたり名前を変えたりして、`AGENTS.md` の対応表とリンクも合わせます。不要なファイルは対応表からも削除します。
- プロジェクトに一つの検証スキルを用意し、リポジトリごとの節に、実行する場所、必要な道具・環境、変更別のコマンド、成功の基準を書きます。DB やサービスの専用環境と片付け、E2E と証拠、依存の監査も、そのリポジトリの方法を記入します。正本を育てる場所は一つに決めます。認証情報の値は書かず、取得手順を書きます。
- `project.md` に、タスクの実行が最初に知ることと、リポジトリごとに何が入り、どんな仕事を受けるかを書きます。リーダーが metadata の `repository` を決めるときに読みます。checkout 後にそのリポジトリの `AGENTS.md` とルールを読む案内を残し、hooks が自動で動くと仮定しません。
- 記入したパス、コマンド、検証環境と片付けを実際のプロジェクトで確かめます。使わない項目は対象外と分かるようにし、未記入を検証成功と扱わないようにします。

同じ決まりを複数のファイルへ写さず、詳細の正本へリンクします。役の指示や共通スキルにはプロジェクト固有のことを足さず、ここから育てたリポジトリの指示、プロジェクトだけのスキル、プロジェクトの説明に置きます。

## 差し込みと登録

`project.md` の `{{project_name}}`、`{{repositories}}`、`{{repository_roles}}`、`{{project_key}}` はセットアップが値を差し込みます。repositories は選んだ全リポジトリの一覧、repository_roles は各リポジトリの役割の記入表です。検証スキルの `{{repository_checks}}` には、`verify-repository.md` の `{{repository}}` を各リポジトリで展開し、見出しを一段下げた節を差し込みます。`[記入: …]` は自動で補いません。作業別のルールや AGENTS.md は担当者が記入するもので、役の条件の印は使いません。

検証スキルの元の名前は `verify` です。Multica への登録名は `<プロジェクトの区別>-verify` となり、役のひな形の `skills: verify` はその登録名へ割り当てます。ひな形の front matter を含めて名前と説明を持つ形にしてありますが、コマンドはまだ記入されていません。プロジェクトで内容を育ててから使います。

セットアップはプロジェクトの説明とプロジェクトだけのスキルがなければ作り、すでにあれば変えません。更新時は担当者が育てた内容を失わないようにします。リポジトリのファイルの記入・採用は人が行い、既存の説明や登録済みの検証スキルへの変更の反映も、プロジェクトの担当者が行います。セットアップの流し方と確認は [導入・更新の手順](../manual.md)を参照してください。

リポジトリを増減したときは、「OWNER/REPO の増減を説明と検証スキルに反映する」のタスクで、担当者が既存の説明と検証スキルに反映します。新しいリポジトリの記入欄がなければ、登録された役の最新の一覧を見て足します。外したリポジトリの古い節が残っていても、書き込みを許す一覧にはなりません。

プロジェクトの説明は、プロジェクトのタスクの実行には渡りますが、オートパイロットの `run_only` には渡りません。`run_only` で必要になるリポジトリや許可の値は、役の指示とオートパイロットの指示に置きます。プロジェクト・スクワッド・人の ID を、このひな形へ手書きする必要はありません。
