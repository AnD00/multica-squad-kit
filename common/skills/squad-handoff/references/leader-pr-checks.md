# リーダーの手順: PR の紐付け・CI・コンフリクト

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、PR を受け取ったとき、返事を待つ回の前後、人間へ回すとき、食い違いの知らせや PR のあるタスクで起きたときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## PR の紐付けの確認

PR があるタスクは、次のときに `squad-pr-watch link-check <タスク>` を流す。PR 一覧の JSON を自分で読んで判定しない。

- PR を受け取ったとき
- PR を人間のマージへ回す前。「コンフリクトの状態の確認」より先に流す
- レビューと E2E の返事を待つ回を始める前。`squad-review-wait watch` を流す前に確認する
- レビューと E2E の返事がそろったとき
- ほかの理由で人間を呼ぶコメントを書くとき
- 食い違いの知らせで起きたとき

出力の `紐付け:` の行で、次のように分ける。紐付いていないことだけでは、レビュー・E2E・CI・マージへ進むのを止めない。

| 判定 | 動き |
| --- | --- |
| 紐付いている | 今の手順で進める。ほかの PR が一緒に紐付いていてもよい。`unlinked` は登録しない |
| 紐付いていない | 「紐付いていない PR のその場の確認」を流して進め、マージ待ちでは `unlinked` も登録する |
| 食い違い | 先へ進めず、行の `pr:` と `紐付いた PR:` の両方を示して人間を呼び、どちらが正か決めてもらう。タスクを `in_review` にする。どちらにも合わせて書き換えない |
| 作業先と違う | 先へ進めず、判定の行にある正規形の PR URL と作業先を示して人間を呼ぶ。metadata の `pr_url` か `repository` の修正を頼み、タスクを `in_review` にする。自分でどちらかへ合わせない |
| 不正な `pr_url` | 先へ進めず、`pr: 表示しない` と理由の行だけを添えて人間を呼び、metadata の `pr_url` か `repository` の修正を頼む。元の値は写さず、タスクを `in_review` にする |
| `pr_url` なし | 一覧の有無によらず、成果物の不足として PR を作った役に `pr_url` を補ってもらう。一覧の PR を自動で採らない |
| 未確認 | 同じ実行で 1 回だけ流し直す。まだ未確認なら、先へ進めず、行を添えて人間を呼び、タスクを `in_review` にする |

未確認を紐付いていないとは読まない。`link-check` が使い方の誤り（終了コード 2）か見つからない（127）ときや、行が出ないときも未確認として扱う。2 または 127 のときはホストのスクリプトが古いので、セットアップを流し直してほしいことも添える。ほかの理由で人間を呼ぶコメントを書くときに未確認なら、そのコメントに「PR の紐付けを確認できませんでした（<理由>）。」を添え、未確認のためだけに別のコメントを書かない。

`repository` がない古いタスクは、squad-handoff の「タスクの作業先を決める」のとおり、リーダーが作業先を決めて書き、判定を流し直す。`pr_url` から作業先を書き写さない。決められなければ人間を呼んで止まる。

人間が未確認の知らせに「紐付けを確認せずに進めてよい」と返したときは、その返事を受けた回だけ紐付いていないものとして進め、次の区切りではもう一度判定する。作業先と違うときと不正なときは、この返事でも進めない。人間が metadata を直して返事をしたら、判定し直してから進める。食い違いで止まったあとも、人間が `pr_url` か紐付けを直して返事をしたら、判定し直してから進める。

`紐付け:` の行にある URL は、検証済みの正規形である。報告にはこの行を使い、metadata の `pr_url` や一覧の元の値を読み直して写さない。

`squad-pr-link` は、PR を作った直後の 1 回だけの呼び出しなので、呼び直さない。引き継ぎや出力に `紐付けていません:` の行があっても、紐付いているとは読まない。metadata の `pr_url` があるために紐付けを飛ばしただけなので、上の判定で決める。

## 紐付いていない PR のその場の確認

PR を受け取ったとき、返事を待つ回を始める前、返事がそろったとき、マージへ回す前に、CI とコンフリクトを確認する。CI の見張り役の有無によらず、どちらも確認する。

1. CI の見張り役があれば、「CI」の手順で `squad-pr-watch ci` を流す
2. `squad-pr-watch ci-now <タスク> <リーダーの ID> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、あるときだけ渡す
3. `squad-pr-watch conflicts-check <タスク>` を流す。コマンドの時間切れは 120 秒以上にし、`CONFLICTING` なら「コンフリクトの状態の確認」の 1 と 2 に従う

マージへ回す前の `conflicts-check` は「コンフリクトの状態の確認」と兼ね、同じ区切りで重ねて流さない。

`ci-now` の行は、次のように読む。

| 行 | 動き |
| --- | --- |
| `CI <SHA>: 失敗あり` で始まり、保留でない | 「CI」の失敗で起きたときと同じに扱う |
| `CI <SHA>: 失敗あり（… の作業中なので保留）` | 役の引き継ぎや揃った知らせを受けるまで保留し、`ci-held` で拾う |
| `CI <SHA>: 失敗は知らせ済み` | 前の知らせのとおり扱い、新たに頼まない |
| `紐付け:` で始まる | 「PR の紐付けの確認」の作業先と違うか不正な `pr_url` の行のとおり、人間を呼んで止まる。以降の確認や依頼へ進めない |
| 失敗なし、チェックなし、マージ済みか閉じている | 先へ進める |

`ci-now` が 0 以外で終わったときは CI を未確認とし、人間を呼ぶコメントに添える。見つけた失敗とコンフリクトは、紐付いているときと同じ条件で扱う。返事を待つ回の途中なら、全部がそろうまで直しを頼まない。修正へ回す条件、保留、同じワークフローの失敗と 2 回続いたコンフリクトの上限は変えない。

## 起きたときの確認

PR のあるタスクで起きたときは、きっかけを問わず、返事を待つ回の途中でない限り、次の順に確認する。コンフリクトの知らせで起きたときだけに限らない。返事を待つ回の途中かどうかは、`leader-review-wait.md` の手順で読んだ待ちの状態で決める。待ちの途中なら、作業中の対象を変えず、そちらの手順に従う。

1. 動いている実行を、`leader-run-status.md` の「起きたときの確認」の手順で確認する。その PR に触れる実行が動いているか、45 分を超えて動いている実行があるかを読む
2. `squad-pr-watch conflicts-check <タスク>` を流して、コンフリクトの状態を読む。出力の読み方は「コンフリクトの状態の確認」と同じにする。コマンドの時間切れは 120 秒以上にする
3. 次の条件がすべてそろったときだけ、解消を修正の役へ頼む。頼み方は、下の「コンフリクトの状態の確認」の 1 に従う
   - コンフリクトの行が `CONFLICTING` である
   - タスクが `in_review` で、前回はマージ待ちだった
   - 返事を待つ回の途中でない
   - その PR に触れる実行が動いていない

条件が 1 つでもそろわないときは、作業中の PR に修正の役を重ねて呼ばない。同じブランチに 2 つの実行が push するためである。作業中の対象を変えず、タスクの状態も変えない。

解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。この決まりは、起きたときの確認でも変えない。

## CI

紐付いている PR では、CI の見張りがあるときだけ確認する。見張りの ID は、リーダーの指示の「このスクワッドの役」にある。紐付いていない PR は、見張り役がなくても「紐付いていない PR のその場の確認」を流す。

metadata に `pr_url` があり、CI の見張り役がいれば、PR を受け取ったときと人間のマージへ回すときに `squad-pr-watch ci <タスク> <見張りの ID> <きっかけのコメント>` を流す。紐付いていないときも登録し、人間が待ちの途中で紐付けたあとに引き継ぐ。見張りが止まっていれば、次に人間を呼ぶコメントに添える。CI はその場で待たない。

CI の失敗で起きたとき、返事を待つ回の途中なら全部が揃うまで直しを頼まない。同じワークフローの失敗を一度修正へ回し、その push の後も失敗したなら、再び修正へ回さず人間へ返す。それ以外は有効な修正の役へ頼み、必要なら `in_progress` に戻す。修正の役の選び方は `leader-dispatch.md` に従う。

CI の見張り役がいるか、PR が紐付いていないときは、役の引き継ぎや揃った知らせを受けたら、次へ回す前に `squad-pr-watch ci-held <タスク> <きっかけのコメント>` で保留した失敗を拾う。見張り役がない場合も省かない。出たチェック名は同じ CI の失敗として扱う。取得が失敗したら人間へ返す。

## コンフリクトの状態の確認

人間のマージへ回す直前に、`squad-pr-watch conflicts-check <タスク>` を流して PR の今の状態を読む。コマンドの時間切れは 120 秒以上にする。レビュー・E2E・CI を経て、または解消の引き継ぎを受けて、マージへ回すたびに流す。

出力の `コンフリクト:` の行に従って、次の動きを決める。行が出ないときや読めないときは「未確認」として扱う。

1. `CONFLICTING` なら、人間を呼ばない。`leader-dispatch.md` で有効な修正の役を選び、行を添えて `main` とのコンフリクトの解消を頼み、タスクを `in_progress` に戻す。解消の引き継ぎを受けたら、もう一度この確認から流す
2. 解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。`leader-flow.md` の、同じ差し戻しが 2 回続いたら人間を呼ぶ決まりに合わせる
3. `MERGEABLE` なら、規則を入れ直してから、行をそのまま添えて人間へ回す
4. 「未確認」なら、規則を入れ直してから、行をそのまま添えて人間へ回す。「なし」とは書かない

## コンフリクトの規則の入れ直し

人間のマージを待つ前に `squad-pr-watch conflicts <タスク>` で規則を入れ直す。この出力は規則の登録の結果で、PR の状態ではないので、人間への報告に使わない。状態は上の確認の行だけで書く。

CI の見張り役がいれば `ci` も今のとおり流す。紐付いていないときは、それらに加えて `squad-pr-watch unlinked <タスク> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、あるときだけ渡す。紐付いているときは `unlinked` を流さない。待ちの途中で紐付けば、間隔を空けた確認は止まり、既存の CI とコンフリクトの見張りが引き継ぐ。

`unlinked` が `紐付け: 作業先と違う` か `紐付け: 不正な pr_url` の行を出したら、上の判定のとおり人間に metadata の修正を頼んで止まり、マージを頼まない。

`unlinked` の `見張り:` の行は、マージを頼むコメントにそのまま写す。0 以外で終わったときは、見張りなしでマージを頼み、登録できなかったことと、ホストでセットアップを流し直してほしいことを書く。

有効な修正の役へ解消を頼むのは、上の「起きたときの確認」の条件がそろったときだけにする。それ以外は作業中の対象を変えない。解消で設計や挙動が変わらなければ、レビューを回し直さず、状態の確認を流してから人間へ戻す。ただし印のあるタスクで、最上位の役の最終レビューのあとに解消の push で head が変わったときは、人間へ戻す前に、`leader-principal.md` の「最上位の役を呼ぶところ」の最終レビューを今の head でもう一度頼む。

`CONFLICTING` で修正の役へ回すときは、規則を入れ直さない。解消の途中で見張りが起きても、タスクが `in_review` でないので何もしないため。次にマージへ回すときに入れ直す。

## マージ待ちの定期確認で起きたとき

CI の見張り役がなく、規則でリーダー自身が起きたときは、規則の指示の `squad-pr-watch unlinked-check <タスク> <リーダーの ID>` を流す。`紐付け: 食い違い` は次の節、`紐付け: 作業先と違う` と `紐付け: 不正な pr_url` は上の判定と「人間を呼ぶコメントに添える行」のとおり扱う。

`CI <SHA>: 失敗あり` で始まり保留でない行は「CI」の失敗で起きたときと同じに扱い、`コンフリクト: CONFLICTING` で `知らせ: 書いた` なら「起きたときの確認」に進む。それ以外は、行を `/note` の記録にして終える。

0 以外で終わったときも、取得できた行を先にこの手順で扱ってから、規則の記録のスレッドに失敗を書く。CI の失敗の行が出たのに、通信エラーの報告だけで終えない。次の回は知らせ済みになり、修正への回しを取りこぼすためである。

## 食い違いの知らせで起きたとき

`unlinked-check` の「紐付けの食い違いを検出しました。」か「PR の URL を確認できませんでした。」の知らせで起きたら、`link-check` を流し直す。食い違いのままなら、両方の URL を示し、マージを頼んだあとで食い違いが分かったので、どちらが正かを決めるまでマージしないでほしいと書いて人間を呼ぶ。タスクは `in_review` のままにする。作業先と違うか不正なままなら、判定の行だけを添え、metadata の `pr_url` か `repository` を直すまでマージしないでほしいと書いて人間を呼ぶ。元の値は写さず、タスクは `in_review` のままにする。

紐付いているか紐付いていないに戻っていれば、人間を呼ばず、`/note` の記録にして終える。紐付いていないに戻ったときは `unlinked` を登録し直す。未確認なら「PR の紐付けの確認」の流し直しと停止の手順に従う。

## 人間を呼ぶコメントに添える行

紐付けの依頼だけのために人間を呼ばない。紐付いていないときは、ほかの理由で人間を呼ぶコメントに次の 1 行を添える。

| 呼ぶ理由 | 添える行 |
| --- | --- |
| マージを頼む | 紐付いていないので、マージのあとにタスクを `done` にしてほしい（または先に紐付けてほしい）。PR: `<正規形>` |
| 設計の承認、判断の依頼など、それ以外 | PR がタスクに紐付いていません。タスクの画面の PR の欄で `<正規形>` を紐付けてください。 |

`<正規形>` には、`link-check` の行の `pr:` の値を写す。metadata の `pr_url` を読み直して写さない。

作業先と違うときと不正なときは、紐付けの依頼ではなく、タスクの画面で metadata の `pr_url` か `repository` を直すよう頼む。判定の行だけを写し、不正な元の値はタスクの画面で見てもらう。タスクを `in_review` にし、返事のあとに判定し直す。

マージを頼むときは `見張り:` の行も続ける。どちらの行にも、役が PR の URL の下に残した `紐付けの失敗:` の段落を、空行の前までそのまま添える。警告に連携の案内があれば、ワークスペースの設定のコードの画面で、作業先のリポジトリが GitHub 連携につながっていることを確認する依頼も添える。連携がないと、タスクの画面からも紐付けられないためである。

更新前の引き継ぎの先頭にある紐付けの依頼と警告の文も、この段落と同じに扱う。失敗や先頭の依頼だけで止まらず、`link-check` の判定で決める。
