# リーダーの手順: PR の紐付け・CI・コンフリクト

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、PR を受け取ったとき、返事を待つ回を始めるとき、人間のマージへ回すとき、PR のあるタスクで起きたときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## PR の紐付けの確認

PR があるタスクは、次のときに `multica issue pull-requests <タスク> --output json` を流し、PR が紐付いているかを確認する。

- PR を受け取ったとき
- PR を人間のマージへ回す前。「コンフリクトの状態の確認」より先に流す
- レビューと E2E の返事を待つ回を始める前。`squad-review-wait watch` を流す前に確認する

出力の `pull_requests` が空なら、タスクに PR が紐付いていない。CI の見張りは、タスクに紐付いた PR を見るので、紐付いていないと動かない。レビュー・E2E・CI・マージへ進めず、人間を呼んでタスクの画面で PR の URL を紐付けてもらうよう頼んで止まる。`squad-pr-link` は、PR を作った直後の 1 回だけの呼び出しなので、呼び直さない。

役の引き継ぎのコメントの先頭に、紐付けられなかった旨があるときも、同じに扱う。コマンドが失敗して読めないときは、紐付いているとみなさず、失敗を人間に伝えて止まる。人間が紐付けたと返事をしたら、もう一度流して確認してから進める。

人間に紐付けを頼むときは、引き継ぎのコメントに写された警告の文を、そのまま添える。警告に、サーバーが PR を見つけられないという連携の案内があれば、ワークスペースの設定のコードの画面で、作業先のリポジトリが GitHub 連携につながっていることを先に確認するよう頼む。連携がないと、タスクの画面からも紐付けられないためである。

引き継ぎや出力に `紐付けていません:` の行があっても、紐付いているとは読まない。metadata の `pr_url` があるために紐付けを飛ばしただけで、紐付いているとは限らないためである。紐付いているかは、上の一覧で確認する。

## 起きたときの確認

PR のあるタスクで起きたときは、きっかけを問わず、返事を待つ回の途中でない限り、次の順に確認する。コンフリクトの知らせで起きたときだけに限らない。返事を待つ回の途中かどうかは、`leader-review-wait.md` の手順で読んだ待ちの状態で決める。待ちの途中なら、作業中の対象を変えず、そちらの手順に従う。

1. 動いている実行を、`leader-run-status.md` の「起きたときの確認」の手順で確認する。その PR に触れる実行が動いているか、45 分を超えて動いている実行があるかを読む
2. `squad-pr-watch conflicts-check <タスク>` を流して、コンフリクトの状態を読む。出力の読み方は「コンフリクトの状態の確認」と同じにする。コマンドの時間切れは 120 秒以上にする
3. 次の条件がすべてそろったときだけ、解消を修正の役へ頼む。頼み方は、下の「コンフリクトの状態の確認」の 1 に従う
   - コンフリクトの行が `CONFLICTING` である
   - タスクが `in_review` で、前回はマージ待ちだった
   - 返事を待つ回の途中でない
   - その PR に触れる実行が動いていない

条件が 1 つでもそろわないときは、作業中の PR に修正の役を重ねて呼ばない。同じブランチに 2 つの実行が push するためである。作業中の対象を変えず、タスクの状態も変えない。

解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。この決まりは、起きたときの確認でも変えない。

## CI

CI の見張りがあるときだけ、次の手順を使う。CI の見張りがないときは、見張りを呼ばず、この節を飛ばす。見張りの ID は、リーダーの指示の「このスクワッドの役」にある。

metadata に `pr_url` があれば、PR を受け取ったときと人間のマージへ回すときに `squad-pr-watch ci <タスク> <見張りの ID> <きっかけのコメント>` を流す。見張りが止まっていれば、次に人間を呼ぶコメントに添える。CI はその場で待たない。

CI の失敗で起きたとき、返事を待つ回の途中なら全部が揃うまで直しを頼まない。同じワークフローの失敗を一度修正へ回し、その push の後も失敗したなら、再び修正へ回さず人間へ返す。それ以外は有効な修正の役へ頼み、必要なら `in_progress` に戻す。修正の役の選び方は `leader-dispatch.md` に従う。

役の引き継ぎや揃った知らせを受けたら、次へ回す前に `squad-pr-watch ci-held <タスク> <きっかけのコメント>` で保留した失敗を拾う。出たチェック名は同じ CI の失敗として扱う。取得が失敗したら人間へ返す。

## コンフリクトの状態の確認

人間のマージへ回す直前に、`squad-pr-watch conflicts-check <タスク>` を流して PR の今の状態を読む。コマンドの時間切れは 120 秒以上にする。レビュー・E2E・CI を経て、または解消の引き継ぎを受けて、マージへ回すたびに流す。

出力の `コンフリクト:` の行に従って、次の動きを決める。行が出ないときや読めないときは「未確認」として扱う。

1. `CONFLICTING` なら、人間を呼ばない。`leader-dispatch.md` で有効な修正の役を選び、行を添えて `main` とのコンフリクトの解消を頼み、タスクを `in_progress` に戻す。解消の引き継ぎを受けたら、もう一度この確認から流す
2. 解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。`leader-flow.md` の、同じ差し戻しが 2 回続いたら人間を呼ぶ決まりに合わせる
3. `MERGEABLE` なら、規則を入れ直してから、行をそのまま添えて人間へ回す
4. 「未確認」なら、規則を入れ直してから、行をそのまま添えて人間へ回す。「なし」とは書かない

## コンフリクトの規則の入れ直し

人間のマージを待つ前に `squad-pr-watch conflicts <タスク>` で規則を入れ直す。この出力は規則の登録の結果で、PR の状態ではないので、人間への報告に使わない。状態は上の確認の行だけで書く。

有効な修正の役へ解消を頼むのは、上の「起きたときの確認」の条件がそろったときだけにする。それ以外は作業中の対象を変えない。解消で設計や挙動が変わらなければ、レビューを回し直さず、状態の確認を流してから人間へ戻す。ただし印のあるタスクで、最上位の役の最終レビューのあとに解消の push で head が変わったときは、人間へ戻す前に、`leader-principal.md` の「最上位の役を呼ぶところ」の最終レビューを今の head でもう一度頼む。

`CONFLICTING` で修正の役へ回すときは、規則を入れ直さない。解消の途中で見張りが起きても、タスクが `in_review` でないので何もしないため。次にマージへ回すときに入れ直す。
