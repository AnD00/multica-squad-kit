# リーダーの手順: 重要なタスクと最上位の役

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、重要の判断の時機に入ったとき、最上位の役を呼ぶときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

最上位の役の有無と系統で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。最上位の役がないときは、ラベル `重要` を付けず、最上位の役を呼ばない。このファイルの残りは使わない。

重要の基準は、リーダーの指示の「重要の基準」にある。

## 印と最上位の役

重要なタスクにだけ、最上位の役を呼ぶ。重要かどうかは、ラベル `重要` だけで表す。コメントの記録と metadata は理由と経緯を残すためのもので、印の正にしない。人間はいつでもラベルを付け外しできる。印のないタスクでも、下の「判断する時機」では基準と「印の記録」「修正の依頼の数え方」の記録を確かめて判定する。判定したあとも印がなければ、最上位の役を呼ばず、今のとおり進める。

最上位の役は、読んで指摘するだけで、直さない。設計の直しは設計の役、コードの直しは修正の役へ回す。

## 判断する時機

次の 3 つの時機にだけ判断する。ほかの時機には判断せず、ラベルを付けない。すでにラベルがあるタスクでは判断を飛ばし、次の「印の記録」だけを確かめる。

| 時機 | 当てはめる基準 | 新しく印を付けたとき |
| --- | --- | --- |
| 受け付けて最初に振り分けるとき | 共通 1〜3 と、プロジェクトの基準 | そのまま振り分ける。設計の見直しは設計が出たあとに頼む |
| 設計が承認されたとき | 共通 1〜4 と、プロジェクトの基準 | 実装のフェーズを頼まずに止め、設計と PR の見直しを頼む |
| 修正を振り分けるとき | 共通 4 だけ | 修正を頼まずに止め、設計と PR の見直しを頼む |

## 印の記録

印を付けるときは、`multica issue label add` でラベル `重要` を付け、その実行の最後のコメントに次の行を置く。当てはまった基準と理由を、人間があとから確かめられるようにするため。

```text
重要の印: 付けた。基準: <共通 N | プロジェクト N>（<基準の短い名前>）。理由: <このタスクが当てはまる理由を 1 文>
```

人間が付けたラベルを判断の時機に初めて見たときは、`重要の印: 人間が付けた印を確かめた。` の行を置く。どちらの行も、印を見た記録になる。行は最後のコメントに入れ、行だけのコメントを足さない。

自分からラベルを外さない。`重要の印:` の行がタスクにあるのにラベルがなければ、人間が外したとみなし、以後そのタスクには付け直さず、最上位の役も呼ばない。

## 修正の依頼の数え方

修正の依頼は、レビューの指摘・コンフリクト・CI の失敗のどれで修正の役へ回すときも、1 回と数える。修正の依頼のコメントに `修正の依頼: <N> 回目` の行を置く。N は、そのタスクにあるこの行の数に 1 を足したものにする。N が 4 になる依頼の前に、基準の共通 4 で印を付けて止める。

実装のフェーズを 1 つでも頼んだあとに、設計の役へ設計の変更を頼むときは、依頼に `設計の変更: 実装を始めたあと` の行を置く。変えた設計の承認と、次の修正の振り分けで、この行を見て基準の共通 4 に当てはめる。

## 最上位の役を呼ぶところ

呼ぶところは、次の 3 つだけにする。判断の時機に判定したあとも印がなければ、どれも飛ばす。

1. 設計の見直し: 印のあるタスクで、設計の役が設計を出したあと
2. 設計と PR の見直し: 印があるのに、PR に最上位の役の結果がないとき。判断の時機に新しく印を付けたときも、人間が承認のあとにラベルを付けたときも、同じに扱う
3. 最終レビュー: レビューの 4 役と E2E の結果がそろい、どれにも ❌ がなくなったあと、人間のマージへ回す前

依頼のコメントには、`見直しの種類: <設計の見直し | 設計と PR の見直し | 最終レビュー>` の行を置く。返事の待ち方は次の「返事の待ち方」に従う。

**設計の見直し**: 印のあるタスクでは、設計の役は設計を draft PR にしたあと、人間ではなくスクワッドへ返す。受け取ったら、最上位の役に設計の見直しを頼む。指摘がなければ（✅）、設計の役のコメントと最上位の役の結果を示して、人間に承認を頼み、`in_review` にする。指摘があれば（❌ か ⚠️）、設計の役に直しを頼む。設計の役は直したあと、人間に承認を頼む。直した設計を最上位の役にもう一度見せない。

**設計と PR の見直し**: 次の振り分けを止めて頼む。結果の扱いは次のとおりにする。そのあと、通常どおり最終レビューも行う。

- `設計` の指摘は、設計の役に直しを頼む。直した設計は人間にもう一度承認してもらい、止めた振り分けはそのあとに再開する
- `コード` の指摘は、止めた修正の依頼に加えて修正の役へ回す。実装のフェーズの前なら、該当するフェーズの依頼に添える
- 指摘がなければ、止めた振り分けをそのまま再開する

**最終レビュー**: 確かめるコミットは、ほかの役が確かめたものと同じにする。4 役と E2E の回とは別の回にし、同じ回で並べて頼まない。最終レビューのあとで、コンフリクトの状態の確認をしてから人間に回す。

- ❌ の指摘は、ほかのレビューと同じく修正の役へ回す。直したあとは、必要な観点のレビューを回し直し、最後に最上位の役に新しいコミットで最終レビューをもう一度頼む。人間に回すコミットを最上位の役が見たものにするため
- ⚠️ だけなら、マージを止めずに人間へ回す。同じ指摘が 2 回続けて差し戻されたときに人間を呼ぶ決まりは、最上位の役にも当てはめる
- 印のあるタスクでは、人間へ回す直前に、PR の今の head の SHA と、最上位の役の最終レビューの `確かめたコミット:` を照合する。一致しなければ、コンフリクトの解消など理由を問わず、今の head で最終レビューをもう一度頼み、その結果を受けてから人間へ回す。同じ head で人間へ回すのは、その head を最上位の役が見たあとだけにする。この再依頼は、ほかのレビューを回し直すかとは別に行う

## 返事の待ち方

最上位の役への依頼も、ほかのレビューと同じく `squad-review-wait` で返事を待つ。最上位の役は 1 体だけを頼む。依頼の前に `squad-review-wait watch <タスク> <きっかけのコメント> <頼む役の ID>` を流し、依頼のコメントに `返事を待つ役:` の行と `確かめるコミット: <完全な SHA>` の行を置き、その行だけでメンションする。`返事がそろいました` で起きたら、`squad-review-wait proceed <タスク> <きっかけのコメント>` を流し、`返事の待ち: 次に進む` を返した実行だけが進む。コマンドの時間切れは 90 秒以上にする。返ってきた `確かめたコミット:` が依頼と合わなければ、同じコミットで頼み直す。2 回続けて合わなければ人間を呼ぶ。

## 最上位の役の選び方

最上位の役を呼ぶたびに、その場の使用率を読み直して選ぶ。30 分より古い値は使わない。

### 両系統があるとき

`squad-dispatch-pick principal` で空いている方の 1 体を選ぶ。大きさの引数は付けない。終了コード 0 なら、`役:` の印に対応する最上位の役へ、`振り分け:` の行を添えて頼む。最上位の役の一覧は、リーダーの指示の「このスクワッドの役」にある。終了 2 は両方とも上限の近くなので、最上位の役を飛ばさずに人間を呼び、`in_review` にする。終了 1 は標準エラーの要約を添えて人間を呼ぶ。読めないときの代わりの決まりもスクリプトに任せる。

### Claude 系統だけのとき

`squad-usage-read` でその場の Claude の枠を読み、週または 5 時間の使用率が 80% 以上なら、人間を呼んで `in_review` にする。それ以外はこの系統の最上位の役へ頼む。読めなければこの役に固定して選んだことと理由を依頼に書く。使用率の取得に失敗したとき、古い値を使わない。

### Codex 系統だけのとき

`squad-usage-read` でその場の Codex の枠を読み、週の使用率が 80% 以上か利用不可なら、人間を呼んで `in_review` にする。それ以外はこの系統の最上位の役へ頼む。読めなければこの役に固定して選んだことと理由を依頼に書く。使用率の取得に失敗したとき、古い値を使わない。
