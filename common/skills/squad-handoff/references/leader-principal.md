# リーダーの手順: 重要なタスクと最上位の役

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、重要の判断の時機に入ったとき、最上位の役を呼ぶときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

最上位の役の有無と系統で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。最上位の役がないときは、ラベル `重要` を付けず、最上位の役を呼ばない。このファイルの残りは使わない。

重要の基準は、リーダーの指示の「重要の基準」にある。

## 印と最上位の役

印 `重要` はリスクが高いタスクを表す。設計の見直しは印のあるタスクで頼み、最終レビューはすべてのタスクで頼む。重要かどうかは、ラベル `重要` だけで表す。コメントの記録と metadata は理由と経緯を残すためのもので、印の正にしない。人間はいつでもラベルを付け外しできる。印のないタスクでも、下の「判断する時機」では基準と「印の記録」「修正の依頼の数え方」の記録を確認して判定する。判定したあとも印がなければ、設計の見直しは頼まず、最終レビューは頼む。

最上位の役は、読んで指摘するだけで、直さない。設計の直しは設計の役、コードの直しは修正の役へ回す。

## 判断する時機

次の 3 つの時機にだけ判断する。ほかの時機には判断せず、ラベルを付けない。すでにラベルがあるタスクでは、印を付けるかの判断だけを飛ばし、次の「印の記録」を確認する。修正の依頼の数え方は、印の有無によらず数える。

| 時機 | 当てはめる基準 | 新しく印を付けたとき |
| --- | --- | --- |
| 受け付けて最初に振り分けるとき | 共通 1〜3 と、プロジェクトの基準 | そのまま振り分ける。設計の見直しは設計が出たあとに頼む |
| 設計が承認されたとき | 共通 1〜4 と、プロジェクトの基準 | 実装のフェーズを頼まずに止め、設計と PR の見直しを頼む |
| 修正を振り分けるとき | 共通 4 だけ | 修正を頼まずに止め、設計と PR の見直しを頼む |

## 印の記録

印を付けるときは、`multica issue label add` でラベル `重要` を付け、その実行の最後のコメントに次の行を置く。当てはまった基準と理由を、人間があとから確認できるようにするため。

```text
重要の印: 付けた。基準: <共通 N | プロジェクト N>（<基準の短い名前>）。理由: <このタスクが当てはまる理由を 1 文>
```

人間が付けたラベルを判断の時機に初めて見たときは、`重要の印: 人間が付けた印を確認した。` の行を置く。どちらの行も、印を見た記録になる。行は最後のコメントに入れ、行だけのコメントを足さない。

自分からラベルを外さない。`重要の印:` の行がタスクにあるのにラベルがなければ、人間が外したとみなし、以後そのタスクには付け直さない。設計の見直しと設計と PR の見直しは頼まず、最終レビューは頼む。

## 修正の依頼の数え方

修正の依頼は、レビューの指摘・コンフリクト・CI の失敗のどれで修正の役へ回すときも、1 回と数える。修正の依頼のコメントに `修正の依頼: <N> 回目` の行を置く。N は、そのタスクにあるこの行の数に 1 を足したものにする。N が 4 になる依頼の前に、基準の共通 4 で印を付けて止める。印がすでにあるタスクでは、4 回目の前と、そのあと 3 回ごと（7 回目・10 回目）の依頼の前に、続けるかを人間に聞いて止める。

止めるのは、次の 3 つがそろうときである。止めるときは、コメントに `修正の続行の確認: <N> 回目の前` の行を置き、人間を呼んでタスクを `in_review` にする。

1. ラベル `重要` がいまある
2. 次の `修正の依頼: <N> 回目` の N が 4 以上で、N − 1 が 3 で割り切れる
3. N − 1 個目の `修正の依頼:` の行より後に、リーダーが共通 4 で付けた `重要の印:` の行がない

呼ぶコメントには、直前の 3 回の修正の依頼の要点（何の指摘で、どの部品か）を、依頼のコメントへのリンクと 1 行ずつで添える。決めてほしいことは、このまま続けるか、設計を見直すか、やめるかである。

出してよいのは、同じ N の `修正の続行の確認:` の行のあとに、人間の続ける返事があるときである。そのときは `修正の依頼: <N> 回目` の依頼を出す。

共通 4 で印を付けた直後の 4 回目は、聞かずに再開する。印のないタスクは、4 回目の前に共通 4 で印を付け、設計と PR の見直しのあとに、止めた 4 回目を再開する。再開の時点では印があり N が 4 だが、その N の前に付けた印なので、確認せずに出す。そのタスクは 7 回目の前に、この確認で初めて止まる。人間がラベルを外したタスクは、ラベルがないので、この確認では止まらず、付け直しもしない（上の「印の記録」）。

修正の依頼の前に確認する順は、`leader-flow.md` の「修正の依頼の前に確認する順」にある。

実装のフェーズを 1 つでも頼んだあとに、設計の役へ設計の変更を頼むときは、依頼に `設計の変更: 実装を始めたあと` の行を置く。変えた設計の承認と、次の修正の振り分けで、この行を見て基準の共通 4 に当てはめる。

## 最上位の役を呼ぶところ

呼ぶところは次の 3 つにする。設計の見直しと設計と PR の見直しは印のあるタスクだけで行い、最終レビューは印の有無によらず行う。

1. 設計の見直し: 印のあるタスクで、設計の役が設計を出したあと
2. 設計と PR の見直し: 印があるのに、PR に設計の見直し・設計と PR の見直しのどちらの結果もないとき。最終レビューの結果は数えない。判断の時機に新しく印を付けたときも、人間が承認のあとにラベルを付けたときも、同じに扱う
3. 最終レビュー: すべてのタスクで、レビューと E2E の結果がそろい、どれにも ❌ がなくなったあと、人間のマージへ回す前。文書だけのタスクと、人間が印を外したタスクも含む

依頼のコメントには、`見直しの種類: <設計の見直し | 設計と PR の見直し | 最終レビュー>` の行を置く。返事の待ち方は次の「返事の待ち方」に従う。

**設計の見直し**: 印のあるタスクでは、設計の役は設計を draft PR にしたあと、人間ではなくスクワッドへ返す。受け取ったら、最上位の役に設計の見直しを頼む。指摘がなければ（✅）、設計の役のコメントと最上位の役の結果を示して、人間に承認を頼み、`in_review` にする。指摘があれば（❌ か ⚠️）、設計の役に直しを頼む。設計の役は直したあと、人間に承認を頼む。直した設計を最上位の役にもう一度見せない。

**設計と PR の見直し**: 次の振り分けを止めて頼む。結果の扱いは次のとおりにする。そのあと、通常どおり最終レビューも行う。

- `設計` の指摘は、設計の役に直しを頼む。直した設計は人間にもう一度承認してもらい、止めた振り分けはそのあとに再開する
- `コード` の指摘は、止めた修正の依頼に加えて修正の役へ回す。実装のフェーズの前なら、該当するフェーズの依頼に添える
- 指摘がなければ、止めた振り分けをそのまま再開する

**最終レビュー**: 確認するコミットは、ほかの役が確認したものと同じにする。4 役と E2E の回とは別の回にし、同じ回で並べて頼まない。最終レビューのあとで、`leader-pr-checks.md` の「マージの前の確認」の順に head・コンフリクト・CI を確認してから人間に回す。

- ❌ の指摘は、ほかのレビューと同じく修正の役へ回す。直したあとは、必要な観点のレビューを回し直し、最後に最上位の役に新しいコミットで最終レビューをもう一度頼む。人間に回すコミットを最上位の役が見たものにするため
- ⚠️ だけなら、最終レビューとしてマージを止めず、マージの前の確認へ進む。同じ指摘が 2 回続けて差し戻されたときに人間を呼ぶ決まりは、最上位の役にも当てはめる
- すべてのタスクで、人間へ回す直前に、PR の今の head の SHA と、最上位の役の最終レビューの `確認したコミット:` を照合する。一致しなければ、コンフリクトの解消など理由を問わず、今の head で最終レビューをもう一度頼み、その結果を受けてから人間へ回す。同じ head で人間へ回すのは、その head を最上位の役が見たあとだけにする。この再依頼は、ほかのレビューを回し直すかとは別に行う

### 見る範囲

初回は PR の差分全体と、ほかの役の結果・実行の証拠を読むよう頼む。直したあとの再確認は、前の最終レビューの `確認したコミット:` から今の確認するコミットまでの差分だけを頼む。依頼に次の行を置く。

```text
見る範囲: <PR の差分全体 | <前の SHA>..<今の SHA>>
```

前の結果のコミットがないか読めないとき、または今のコミットの祖先でないときは、再確認でも `PR の差分全体` にする。実行の証拠は PR かタスクにあるものを読む。なければ、そのことを結果に書き、それだけで ❌ にしない。

## 返事の待ち方

最上位の役への依頼も、ほかのレビューと同じく `squad-review-wait` で返事を待つ。最上位の役は 1 体だけを頼む。依頼の前に `squad-review-wait watch <タスク> <きっかけのコメント> <頼む役の ID>` を流し、依頼のコメントに `返事を待つ役:` の行と `確認するコミット: <完全な SHA>` の行を置き、その行だけでメンションする。`返事がそろいました` で起きたら、`squad-review-wait proceed <タスク> <きっかけのコメント>` を流し、`返事の待ち: 次に進む` を返した実行だけが進む。コマンドの時間切れは 90 秒以上にする。返ってきた `確認したコミット:` が依頼と合わなければ、同じコミットで頼み直す。2 回続けて合わなければ人間を呼ぶ。

## 最上位の役の選び方

最上位の役を呼ぶたびに、その場の使用率を読み直して選ぶ。30 分より古い値は使わない。

### 実装した系統の決め方

最終レビューでは、`multica issue runs <タスク> --output json` を読み、指示の「このスクワッドの役」の ID と照合する。実装と修正の役のうち、状態が `completed` の実行だけを系統ごとに数え、多い方を実装した系統にする。`failed` と取り消しは数えない。同数か一覧を読めなければ、系統を決めない。

実装と修正の実行がなければ、設計の役のモデルで決める。モデルの確認方法は「このスクワッドの役」にある。`claude-` で始まれば Claude、それ以外は Codex とする。設計の役やモデルを確認できなければ、系統を決めない。成功で終えたが変更を積まなかった実行も数えるので、実際に多く書いた系統と逆になることがある。

### 両系統があるとき

最終レビューで実装した系統を決められれば、`squad-dispatch-pick principal <Claude | Codex>` にその系統を渡し、違う系統を優先する。優先する系統だけが上限の近くなら、理由を添えて同じ系統へ回す。設計の見直しと、実装した系統を決めないときは、引数なしの `squad-dispatch-pick principal` で空いている方を選ぶ。終了コード 0 なら、`役:` の印に対応する最上位の役へ、`振り分け:` の行を添えて頼む。最上位の役の一覧は、リーダーの指示の「このスクワッドの役」にある。終了 2 は両方とも上限の近くなので、最上位の役を飛ばさずに人間を呼び、`in_review` にする。終了 1 は標準エラーの要約を添えて人間を呼ぶ。読めないときの代わりの決まりもスクリプトに任せる。

### Claude 系統だけのとき

`squad-usage-read` でその場の Claude の枠を読み、週または 5 時間の使用率が 80% 以上なら、人間を呼んで `in_review` にする。それ以外はこの系統の最上位の役へ頼む。読めなければこの役に固定して選んだことと理由を依頼に書く。使用率の取得に失敗したとき、古い値を使わない。

### Codex 系統だけのとき

`squad-usage-read` でその場の Codex の枠を読み、週の使用率が 80% 以上か利用不可なら、人間を呼んで `in_review` にする。それ以外はこの系統の最上位の役へ頼む。読めなければこの役に固定して選んだことと理由を依頼に書く。使用率の取得に失敗したとき、古い値を使わない。
