# リーダーの手順: 進捗を聞かれたときと、実行を止めるとき

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、進捗や遅れを聞かれたとき、依頼の中身を変える追加をするとき、実行を止めるとき、PR のあるタスクで起きたときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

進捗・遅延・止まっているかを聞かれたら、答える前に実行の状態と記録を確認する。実行を止めるのは、人間の指示か承認があるときだけにする。

## 実行の状態を確認して答える

記憶や前のコメントから答えない。実行の状態は変わるので、確認せずに答えると古い状態や誤った「見えない」を返すため。

1. 聞かれたタスクで `multica issue runs <タスク> --active --output json` を流す。タスクに親か子があるときは `--siblings` も流して、親と子の実行も確認する
2. 一覧から、この返事を書いている自分の実行を除く。自分の実行も `--active` に出るため
3. 残った実行ごとに `multica issue run-messages <実行の ID> --issue <タスク> --output json` を流し、末尾の数件の記録を読む
4. 答えには、実行ごとに次の 5 つを書く

| 項目 | 読む欄 |
| --- | --- |
| 実行の ID | `runs` の `id`（`--siblings` では `task_id`） |
| 役 | `agent_id` を「このプロジェクトの値」の各役の ID と照らした名前 |
| 状態 | `status`（`queued`、`dispatched`、`running` など） |
| 始まった時刻 | `started_at`。まだ始まっていなければ、その旨 |
| 直近にしていたことと、その時刻 | 記録の末尾の `tool` と `input` の要約、または `content`。時刻はその記録の `created_at` |

`agent_id` が「このプロジェクトの値」のどの ID にも当たらないときは、`multica agent get <ID>` の名前を書く。それでも分からなければ ID だけを書き、役は「未確認」と書く。記録が空のときや読めなかったときは、その旨とコマンドを書き、直近にしていたことを推測で埋めない。`--siblings` は動いている実行を 20 件までしか返さない。打ち切りが標準エラーに出たときは、一覧が全部ではないことを答えに書く。

動いている実行がないときは、その旨と、最後の実行の結果を書く。最後の実行は `multica issue runs <タスク> --output json` の先頭（新しい順）にある、自分の実行を除いたものである。`completed` は「終わった」、`failed` は「失敗した」（`error` があれば添える）、`cancelled` は「止められた」と書く。それ以外の `status` は値をそのまま書く。結果に、その実行の役と終わった時刻（`completed_at`）を添える。実行の履歴が一つもなければ、その旨を書く。

「見えない」「できない」と答える前に、`multica issue --help` と、使えそうなコマンドの `--help` で、使えるコマンドを確認する。それでもできないときは、確認したコマンドを添えて答える。

進捗を答えるだけのときは、タスクの状態を変えず、ほかの役もメンションしない。

## 起きたときの確認

PR のあるタスクで起きたときは、きっかけを問わず、返事を待つ回の途中でない限り、動いている実行の長さを確認する。進捗を聞かれていなくても確認する。コンフリクトの状態の確認は、`leader-pr-checks.md` の「起きたときの確認」にあり、この確認の結果をその手順へ渡す。

1. 上の「実行の状態を確認して答える」の 1 と 2 のとおり、`multica issue runs <タスク> --active --output json` を流し、自分の実行を除く。親か子があるときは `--siblings` も流す
2. 残った実行のうち、その PR に触れる実行があるかを読む。実装・修正の役の実行は、触れるものとして数える。役が分からない実行も、触れるものとして数える。重ねて呼ぶ方に倒さないためである。この結果は `leader-pr-checks.md` の条件に使う
3. `started_at` から 45 分を超えて動いている実行があれば、その実行の記録を `multica issue run-messages <実行の ID> --issue <タスク> --output json` で、末尾の数件読む

45 分を超えて動いている実行は、同じ実行につき 1 回だけ人間に知らせる。知らせる前に、タスクの前のコメントに、同じ実行の ID の `実行の遅れ:` の行があるかを確認する。あれば、もう知らせない。起きるたびに同じ知らせを繰り返さないためである。

知らせるコメントには、`実行の遅れ: <実行の ID>` の行を置く。あわせて、「実行の状態を確認して答える」の 5 項目と、記録の要約、読めなかったものは「未確認」と書く。呼ぶ人間をメンションし、実行を止めるかどうかは人間が決めると書く。止めた方がよいと考えたときは、次の「実行を止める」の提案に従う。

知らせても、実行は止めない。タスクの状態も変えない。45 分を超えていない実行は、知らせない。

## 依頼の中身を変える追加をするとき

動いている実行へ方針を変える追加をするときは、古い依頼のまま作業が進まないよう、次の手順で頼み直す。

1. 役へ依頼の撤回や方針の変更を足す前に、`multica issue runs <タスク> --active --output json` で、その役の実行を確認する。自分の実行は除く
2. 追加がその実行の方針を変えるもの（検証の方法の撤回、範囲の変更など）なら、実行を止めて、元の依頼と追加を 1 本にまとめて出し直す。人間の指示がなければ、下の「実行を止める」の確認の 4 項目を添えて提案し、承認を待つ
3. 方針に影響しない補足だけなら、実行を止めずに足す
4. 人間が方針を変える追加を求めたときは、「止めて」と明示しなくても、停止と頼み直しの指示として扱う。止める提案や確認の 4 項目を挟まず、止めて頼み直す

止める対象の特定と停止の直前・直後の確認は、下の「実行を止める」に従う。対象が一つに決まらないときは、候補を示して人間に聞く。

## 実行を止める

`multica issue cancel-task` で実行を止めるのは、人間の指示か承認があるときだけにする。自分の判断では止めない。止まって見えるだけの長い実行もあり、止めると未 push の作業を失うことがあるので、その判断を人間に残す。

止めた方がよいと考えたときは、止めずに人間に提案する。状況と理由に、次の確認の 4 項目を添える。

1. 止める実行の ID と役
2. タスクのブランチに最後に push されたコミット
3. そのコミットより後の編集・コミットが、実行の記録にあるか
4. 止めると未 push の作業を失うおそれがあること

確認の項目で分からないものは「未確認」と書く。「なし」とは書かない。「なし」と読んだ人間が、失う作業がないと判断して承認するおそれがあるため。提案では、呼ぶ人間をメンションし、タスクの状態は変えない。提案の間も実行は動いており、エージェントの番が続いているため。

最後に push されたコミットは、metadata の `pr_url` があれば `gh pr view <PR の URL> --json headRefOid,headRefName` の `headRefOid`、`branch` だけがあれば `gh api repos/<repository>/branches/<branch> --jq .commit.sha` で読む。どちらもない、または読めないときは「未確認」と書き、理由を添える。SHA は 7 文字以上で書く。

後の編集・コミットは、止める実行の記録を `run-messages` で読み、最後に成功した `git push` より後に、ファイルの編集（`Edit`・`Write`・`apply_patch` などのツールの呼び出し）か `git commit` があるかで確認する。記録に `git push` がなければ、その実行のすべての編集とコミットが対象になる。あれば「あり」と書き、最初と最後の記録の `seq` と時刻を添える。記録を末尾まで読み、編集もコミットもなければ「なし」と書く。記録を読めなかった、一部しか読めなかった、push の成否が分からないときは「未確認」と書く。記録からの読み取りなので見落としはありうる。そのため、項目 4 の失うおそれは、項目 3 の結果によらず必ず書く。

人間が明示して「止めて」と指示したときは、それを承認として扱い、確認の 4 項目を挟まずに止める。上の「依頼の中身を変える追加をするとき」の 4 も、この扱いにする。止める実行は、指示の中の実行の ID・役・タスクから決める。候補が一つに決まらないとき（同じタスクで役の違う実行が二つ動いているなど）は、止めずに候補の実行の ID と役を並べて、どれを止めるかを聞く。取り違えて別の実行を止めないためである。

止める直前に `multica issue runs <タスク> --active` を流し直し、その実行がまだ動いているかを確認する。終わっていれば止めず、最後の結果を人間に書く。まだ動いていれば `multica issue cancel-task <実行の ID> --issue <タスク>` で止め、`multica issue runs <タスク> --output json` でその実行が `cancelled` になったことを確認する。自分の実行は止めない。

## 止めたあと

止めたら、止めた実行の ID と役、確認した結果、最後に push されたコミットを人間に書く。方針を変える追加のために止め、頼み直しの指示か承認もあるときは、次の「やり直す」に従い、まとめた依頼を出し直す。やり直すかを改めて聞かず、タスクは `in_progress` のままにする。

それ以外は、やり直す・別の役に振り直す・待つのどれにするかを聞く。人間の判断を待つときは、squad-handoff の「人間を呼んで止まるとき」に従って `in_review` にする。人間の返事には、次のとおり従う。

- やり直す: 止めた役をメンションで呼び、元の依頼の内容を写す。止めた実行の ID と最後に push されたコミットを添え、そこから続けるよう頼む。タスクを `in_progress` にする
- 別の役に振り直す: 振り直す役をメンションで呼び、やり直すときと同じ内容を添える。タスクを `in_progress` にする
- 待つ: 何もしない。状態は `in_review` のまま

元の依頼は、止めた実行の `trigger_comment_id` のコメントから読み、要約せずに写す。ただし、方針を変える追加で頼み直すときは、撤回・変更する箇所を置き換え、変更しない箇所は写して 1 本にまとめる。最後に push されたコミットが「未確認」のままなら、そのまま「未確認」と書き、ブランチの最新から確認して続けるよう頼む。`multica issue rerun` は使わない。担当がスクワッドのタスクでは、止めた役ではなくリーダーの実行が起きるおそれがあり、続きの起点も新しい実行に伝わらないため。

レビューや E2E の返事を待つ回の役を止めたときは、やり直しも `leader-review-wait.md` の手順で頼む。`返事を待つ役:` の行を写しただけでは、待ちの登録と照合がずれるため。
