# リーダーの手順: レビューと E2E の返事

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、レビューと E2E を頼むとき、その返事で起きたときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## レビューと E2E の役がないとき

自動のレビュー・E2E を依頼したことにせず、完了した検証と未確認の観点を添えて人間の確認へ回す。このファイルの残りは使わない。

## レビューと E2E の依頼

依頼は `squad-review-next request <タスク> <きっかけのコメント> <確認するコミット>` が書く。変えたファイルの場所から必要な観点を選び、`squad-review-wait watch` を流してから、`返事を待つ役:` の行と `確認するコミット: <完全な SHA>` の行のある依頼のコメントを、きっかけのコメントへの返信で書く。出力の `依頼:` の行が書いたコメントの ID、`観点:` の行が選んだ観点である。リーダーは役を選ばず、依頼の文も自分で書かない。

確認するコミットは、PR の head か、依頼されたブランチの確定したコミットを指定する。ZIP が成果物なら、`request` を使わず、役の ID を渡して `squad-review-wait watch <タスク> <きっかけのコメント> <頼む役の ID>...` を流し、依頼のコメントの行頭に `確認するコミット:` と名前と sha256 を置く。`返事を待つ役:` の行は、1 役でも置き、その行だけでメンションする。全員の返事が揃う前に、検証中の対象を変更する依頼を出さない。

QA の役があるときは、画面に触れる変更を人間のマージへ回す前に、PR に E2E の結果とスクリーンショットがあるか確認し、なければ QA の役に頼む。QA の役のメンションのリンクは、リーダーの指示の「このスクワッドの役」にある。QA の役がないときは、この確認を飛ばす。

## 返事で起きたとき

`返事がそろいました` で起きたら、開始時の確認が通ったあと、すぐに `squad-review-wait proceed <タスク> <きっかけのコメント>` を流す。最大 40 秒待って記録を読み直すので、コマンドの時間切れは 90 秒以上にする。

`<きっかけのコメント>` には、この実行を起こした知らせのコメントの ID を渡す。結合した場合は結合したコメントの ID にする。元の依頼コメントの ID は通らない。

どの実行が呼んでも、判定はスクリプトが持つ。実行の種類を確認せずに呼んでよい。

`返事の待ち: 次に進む` を返した実行だけが進み、`返事の待ち: 回ごと済み` なら何もしない。それ以外の結果はそのまま最後の返答にする。スクリプトが失敗したら、出力を添えて人間へ返す。

役が `squad-review-wait report` で結果を返すと、全員がそろった回は `report` を流した役が `squad-review-next decide` で次の依頼を決めて書く。リーダーが起きるのは、`decide` が決められなかったときだけで、知らせの 2 行目に `次の依頼を決められません: <理由>` の行がある。理由に応じて、次のとおりに扱う。

| 理由の行 | すること |
| --- | --- |
| `紐付け:`、CI、`コンフリクト:` の行 | [leader-pr-checks.md](leader-pr-checks.md) の手順を流し直して扱う。紐付けの食い違い・作業先と違う・読めない値、CI の失敗、コンフリクトの手順はそちらにある。決めた先が修正やマージの依頼なら、その手順で書く |
| `設計の見直しの回はリーダーが扱う` | 設計の見直しと設計と PR の見直しの回である。結果の `設計への指摘:` の行と指摘を読み、[leader-principal.md](leader-principal.md) の手順で、設計の役への直しの依頼か、人間への承認の依頼を扱う |
| 上のどれでもない | 理由の行を読み、役の状態や失敗の理由を確認して、今の手順で扱う。決められなければ理由を添えて人間を呼ぶ |

使用率の待ちと CI の待ちは、`decide` が起こしと待ちの記録を書き、リーダーを起こさずに終わる。待ちが明けると起こしや規則で起きるので、それぞれ [leader-dispatch.md](leader-dispatch.md) と [leader-pr-checks.md](leader-pr-checks.md) で扱う。

理由の行がない拾い直し（知らせがないまま全員がそろっていた回、`返事の待ち: 返事がそろっていて、まだ次へ回していない`）は、`proceed` の前に `squad-review-next decide <タスク> <回のコメント>` を流す。出力の `次の依頼:` の行を最後の返答にし、`次の依頼を決められません:` なら上の表で扱う。`proceed` が `次に進む` を返したあとは、`decide` が書いた依頼があるかを `前の回:` でこの回を指すコメントで確認してから進む。書き済みなら、同じ依頼を書き直さない。

## 確認したコミットの照合

次へ進む前に、全員の `確認したコミット:` を依頼と照合する。7 文字以上の 16 進で依頼の SHA の先頭と一致すればよい。合わない・行がない・なしの役だけを、同じコミットの新しい回で頼み直す。`コミットが合わず頼み直す役:` の行に名前だけを書き、合っていた役の結果は残す。同じ役が 2 回続けて合わなければ、3 回目は頼まず、依頼した値と返ってきた値を添えて人間を呼ぶ。ZIP なら指定した名前と sha256 を同じように照合する。

## 他のきっかけで起きたとき

他のきっかけでは、開始時の確認が通ったあと、ほかの処理より先に `squad-review-wait status <タスク>` を流す。見張りが `--timeout` を指示したときは付ける。

全員の返事がそろい、まだ次へ回していなければ、知らせの有無を問わず `proceed` へ進む。人間を呼ぶ判定なら役の状態と失敗理由を添えて止まる。ただし人間の返事で起きたときは同じ理由で呼び直さず、その返事に応じる。

見張りで起き、まだ待つ判定なら結果をそのまま返す。スクリプトの失敗は人間へ返す。
