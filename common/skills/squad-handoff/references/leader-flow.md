# リーダーの手順: 作業先・要件と設計・受け渡し

このファイルはリーダーの手順で、リーダーだけが読む。ほかの役は読まない。リーダーの指示の「場面と手順」から、新しい要望を受けたとき、作業先を決めるとき、要件と設計を進めるとき、実装のフェーズを頼むとき、依頼を書くときに読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## 作業先を決める

最初に振り分ける前に、タスクの metadata の `repository` を決めて書く。一覧が一つならそれを使い、二つ以上ならプロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、説明が未記入で決められないときは、人間を呼んで止まる。選択の先頭を自動で使わない。

振り分けのたびに、`repository` が「このプロジェクトの値」の一覧にあるかを確認する。人間が書いた値も同じく確認し、一覧にない値や外したリポジトリのタスクは、人間を呼んで止まる。書き方と各役の確認は、squad-handoff の「タスクの作業先を決める」に従う。

### 複数のリポジトリにまたがる要望

要件を決める役があるときは、その役が要件を合意するときにリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を確認し、設計からの流れを通す。

要件を決める役がないときは、人間と合意済みの要件をリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を設定して、設計からの流れを通す。要件を自分で定義しない。

## 要件と設計を進める

要件を決める役があるときは、新しい要望をその役に頼んで要件を合意してもらう。合意されていない要件を設計や実装へ回さない。

要件を決める役がないときは、合意済みの要件と受け入れ条件を確認して、次の有効な役へ直接回す。不足や未合意があれば、人間に準備と合意を頼んで止まる。自分で要件を定義しない。

設計の役があるときは、合意された要件の設計をその役に頼む。人間の設計とフェーズの分け方の承認を受けてから実装へ回す。ラベル `重要` のあるタスクは、`leader-principal.md` に従い、承認の前に最上位の役の見直しを挟む。

設計の役がないときは、必要な設計と承認が揃っているか確認し、次の有効な実装の役へ直接回す。設計が必要なのに未準備なら、人間に設計の手配と承認を頼んで止まる。自分で設計や draft PR を作らない。

## フェーズを頼む

承認された実装のフェーズは、一覧の順に、一度に 1 フェーズだけ頼む。前のフェーズの成果物が共有されてから次へ進む。全部のフェーズが揃うまでレビューを始めない。バグは再現手順と期待する動作を確認し、なければ起票した担当に補ってもらう。

実装のフェーズを頼む前の役の選び方は、`leader-dispatch.md` に従う。

## 依頼の書き方と受け渡し

- 依頼には対象・頼む範囲・返してほしいものを書く。実装のフェーズならフェーズ番号とそのフェーズの内容だけを写す。成果物と合意の記録はタスクのコメントと metadata を参照してもらう
- 担当はスクワッドのままにし、依頼先をメンションする。返事の先として自分をメンションしない。振り分けたら今回の実行を終える
- ステージのある sub-issue は、親の children を見て、次がすでに backlog から出ていれば重ねて進めない
- `multica squad activity` がリーダーの実行でないため失敗したら、流し直さず、追加コメントもせず、最後の返答に失敗を 1 行書く

### 同じ誤りや差し戻しが続くとき

修正の役へ差し戻すときは、この節の用語と数え方に従う。1 回目の失敗や差し戻しは、原因を確認し、依頼のコメントに原因を書いてから、同じ役へ頼み直してよい。原因が確認できなかったときは、確認した方法を添えて「未確認」と書く。

#### 用語

| 語 | 意味 |
| --- | --- |
| 部品 | 指摘の場所の、ファイルと関数、またはファイルと規則のまとまり。名前は `<ファイル>:<関数か規則の名前>` と書く。指摘に関数や規則の名前がなければ、ファイルの名前だけにする |
| 差し戻し | レビューの ❌、コンフリクト、CI の失敗で、修正の役へ戻すこと |
| 同じ誤り | 修正の役へ回した ❌ の指摘と、部品も、抜けていた入力や場合も同じ指摘が、その直しのあとにまた来ること。コンフリクトは、解消のあとにまた `CONFLICTING` になること。CI の失敗は、直しのあとに同じジョブが同じ原因で失敗すること |
| 同じ部品の指摘 | 前に修正の役へ回した ❌ の指摘と部品が同じで、抜けていた入力や場合が違う指摘 |
| 種類単位の依頼 | 1 件の入力の直しではなく、その部品が受ける入力の種類を列挙して扱いを決め、まとめて直す依頼 |

同じ誤りを先に当てはめる。同じ誤りに当たった指摘は、同じ部品の回数に数えない。コンフリクトと CI の失敗には部品がないので、同じ誤りの決まりだけで扱う。指摘は ❌ だけを数える。⚠️ は修正の役へ回さないので数えない。

#### 同じ誤りが続くとき

同じ誤りや差し戻しが 2 回続いたら、3 回目は頼まず、人間を呼んで止まる。この文が指すのは、同じ誤りの差し戻しだけである。部品が違う差し戻しが 2 回続いても、この文では止めない。呼ぶコメントには、原因と、再発を防ぐ手当てを添える。手当ては、手順の直し方か、指示の改善のタスクの起票である。人間が同じ失敗の原因を自分で調べ直さずに、手当てを選べるようにするためである。

同じ誤りの回数は、修正の役へ回したあとに同じ誤りが来た数で数える。最初の指摘やコンフリクトは数えない。同じ誤りを頼み直す依頼には、次の行を置く。

```text
同じ誤り: <部品の名前 | コンフリクト | CI の <ジョブの名前>> <N> 回目
```

N は、そのタスクのリーダーのコメントにある、同じ対象の `同じ誤り:` の行の数に 1 を足したものにする。N が 1 なら、原因を書いて頼み直す。N が 2 になる依頼は出さず、原因と再発を防ぐ手当てを添えて人間を呼ぶ。コンフリクトの解消のあとにまた `CONFLICTING` になったときは、`同じ誤り: コンフリクト 1 回目` と `修正の依頼: 2 回目` の行を置いて頼み直す。

同じ誤りを頼み直す依頼には、その指摘の `同じ部品:` の行を置かない。同じ部品の回数に数えないためである。

#### 同じ部品に指摘が続くとき

修正の依頼のコメントに、回す ❌ の指摘の部品ごとに、1 回目から次の行を置く。

```text
同じ部品: <部品の名前> <N> 回目
```

N は、そのタスクのリーダーのコメントにある、同じ部品の名前の `同じ部品:` の行の数に 1 を足したものにする。部品の名前は、前の行にあれば、その名前を一字も変えずに写す。数えるのはタスクの中の行のすべてで、連続した依頼だけではない。あいだに別の部品の依頼が挟まっても数え直さない。

N が 2 になる部品があれば、同じ依頼に次の行を置き、種類単位で頼む。人間は呼ばない。

```text
頼む範囲: 種類単位（<部品の名前>）
```

依頼の文では、修正の役に次を頼む。修正の役の指示は変えない。

- その部品が受ける入力の種類と規則を表にし、種類ごとの扱いを決める
- 表の行ごとにテストを置く。テストは表を入力とする形（表に沿ったテスト）にし、表の場所を結果に書く
- 指摘された 2 件の入力も、表の行に含める

直したあとの再確認の依頼には、その部品を指摘したレビューの役に向けて、次の行を置く。

```text
列挙を頼む部品: <部品の名前>
```

N が 3 以上になる部品があれば、修正を頼まず、人間を呼んで `in_review` にする。呼ぶコメントには次の行を置き、あわせて次を書く。

```text
同じ部品の確認: <部品の名前> <N> 回目の前
```

- その部品への指摘。それぞれの結果へのリンクと 1 行の要点
- 2 回目に種類単位で頼んだ範囲と、修正の役が書いた表の場所
- 決めてほしいこと。続けて 1 回頼むか、設計を見直すか、やめるか。推す案と理由を添える

出してよい条件は、同じ部品で同じ N の `同じ部品の確認:` の行のあとに、人間の続ける返事があることである。そのとき、`同じ部品: <部品の名前> <N> 回目` の行で 1 回だけ頼む。その部品に次の指摘が来たら、N + 1 の確認の行を置いて、また止まる。

部品が違う指摘が続くときは、指摘ごとの依頼にする。どの部品も `同じ部品: <部品の名前> 1 回目` の行にし、`頼む範囲:` は置かない。

#### 修正の依頼の前に確認する順

修正の役へ回す前に、次の 1〜3 をすべて確認する。当たるものが 1 つでもあれば、頼まずに人間を呼び、当たったものを 1 つのコメントにまとめて書く。1 回の実行で書くコメントは 1 つという決まりを保つためである。1〜3 のどれにも当たらなければ、4 と 5 を順に見る。

1. 同じ誤りの N が 2 になる: 原因と手当てを添える
2. 同じ部品の N が 3 以上で、その N の確認を人間が通していない: `同じ部品の確認:` の行を置く
3. 印のあるタスクの続行の確認に当たり、その N の確認を人間が通していない: `修正の続行の確認:` の行を置く（`leader-principal.md` の「修正の依頼の数え方」）
4. ラベルがなく、タスクに `重要の印:` の行がなく、修正の依頼の N が 4: `leader-principal.md` の決まりで印を付け、設計と PR の見直しを頼む
5. 1〜4 のどれにも当たらない: 頼む。N が 2 の部品は種類単位にする

2 と 3 が同じ実行で当たったときは、1 つのコメントで両方を聞く。人間の続ける返事は、そのコメントに置いたすべての確認の行を通す。人間を 2 回続けて呼ばないためである。1 に当たったときの人間の返事は、今の決まりどおり、手当てを選ぶか、続けて 1 回頼むかである。

人間を呼ぶ確認（1〜3）を、印を付ける 4 より先に見る。印のないタスクで 4 回目と同じ部品の 3 回目が重なったら、先に人間を呼ぶ。人間が続けると返した次の実行で、4 に当たって印を付ける。

指示の実物は勝手に変えない。指示の改善は、提案のタスクにする。
