# Multica での引き継ぎ

同じタスクのコメントで成果物を受け渡す。次の担当と人間が、コメントと状態から続きを始められるようにする。担当する範囲と権限は、依頼と自分の役の指示に従う。このスキルだけを根拠に、担当外の作業を始めない。

## このプロジェクトの値を使う

プロジェクトごとに違う値は、自分のエージェントの指示の末尾にある「このプロジェクトの値」を読む。このスキルの中に値を保存したり、名前から推測したりしない。

| 使う場面 | 写す値 |
| --- | --- |
| GitHub に書き込む | プロジェクトのリポジトリの一覧と、タスクまたは依頼の PR の作業先。紐付けだけの書き込みは、紐付け専用の一覧も照合する |
| タスクを作る | プロジェクトの ID、スクワッドの ID |
| リーダーに引き継ぐ | スクワッドのメンションのリンク |
| 人間に確認する | 呼ぶ人間のメンションのリンク |
| 見張りにリーダーを指定する | リーダーのエージェントの名前、または ID。呼ぶスクリプトの引数に合わせる |

メンションは、値にある完成したリンクをそのまま写す。名前だけでは通知できず、リンクの種類や ID を変えると別の相手を呼ぶことがある。必要な値がないときは、推測して作成・書き込み・メンションをせず、不足している値を報告する。

## 実行の始めの確認

GitHub に書き込む、または `squad-` の見張りを呼ぶ実行は、ほかの処理より先に `squad-preflight` を流す。タスクのある実行は `squad-preflight <タスク>`、タスクのない実行は引数なしにする。名前だけで呼び、絶対パスでは呼ばない。どちらもしない実行では、この確認は流さない。

終了コード 0 のときだけ、以降の処理へ進む。0 以外は、見つからないときの 127 も含め、次のとおりにして止まる。

1. GitHub の読み取り・書き込みも、見張りの呼び出しも行わない
2. 「人間を呼んで止まるとき」に従い、呼ぶ人間をメンションし、タスクを `in_review` にする
3. 報告に、使えなかったものと直し方を書く。`squad-preflight` の出力は、そのまま添える

`squad-preflight` が見つからないときは、「関所のディレクトリが PATH にありません。動いているタスクがないときに、同じプロジェクトでセットアップを流し直してください」と報告する。確認が通らなくても、報告と状態の変更には `multica` の CLI を使える。

タスクのない見張りは、オートパイロットの指示にある報告のしかたで、呼ぶ人間に知らせる。

## 書き込んでよいリポジトリ

GitHub の issue、PR、コメント、push などの書き込みは、「このプロジェクトの値」にあるリポジトリの一覧に含まれるものだけにする。次の紐付け専用の例外を除き、同じワークスペースに紐付いている別のリポジトリも読むだけにする。`multica repo list` に出ることや、人間の GitHub の認証で書けることは、このプロジェクトから書き込む許可にならない。

「紐付け専用のリポジトリ」が指示にある場合は、その一覧の既存の GitHub の issue にも紐付けコメントと Assignees の同期を書ける。具体的な同期の方法はプロジェクトのスキルに従う。この例外から GitHub の issue の作成、コード変更、PR の作成・コメント・レビュー、push を許可しない。一覧がなければ、紐付けにもこの例外を使わない。

一覧の中でも、タスクの作業は次の「タスクの作業先を決める」の一つのリポジトリで行う。PR へのコメントとレビュー結果は、その PR があるリポジトリへ書く。

ホストの `gh` と `git push` の関所に止められたら、関所を避ける呼び方や設定の変更をせず、呼ぶ人間に知らせる。

## タスクの作業先を決める

リポジトリで作業するタスクは、1 タスクにつき 1 リポジトリ・1 PR にする。作業先はタスクの metadata の `repository` に `OWNER/REPO` で残す。役ごとに本文から推測し直さない。紐付け専用の一覧は、タスクの作業先や定期処理の対象には使わない。

| 担当する仕事 | 確かめることと作業 |
| --- | --- |
| リーダー | 最初に振り分ける前に `repository` を決めて書く。既存の値も人間が書いた値も、プロジェクトの一覧にあることを確かめてから振り分ける。 |
| 要件を決める | 作業先を確かめ、複数のリポジトリにまたがる要望は、要件を合意するときにリポジトリごとの sub-issue に分ける。 |
| 設計・実装・修正 | `repository` のリポジトリを checkout し、そのリポジトリの `AGENTS.md` と作業別のルールを読む。そこで PR を作るか既存の PR に積む。 |
| レビュー・QA | 依頼の PR の URL からリポジトリを決め、プロジェクトの一覧と照合して checkout する。metadata の読み取りは不要。 |
| 定期の確認や見張り | オートパイロットや依頼で明示された一つのリポジトリを一覧と照合して使う。リポジトリを使わない見張りのために checkout しない。 |

リーダーは、一覧が一つならそれを `repository` に書く。二つ以上なら、プロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、役割が未記入などで決められなければ、人間を呼んで止まる。選択の先頭を代わりに使わない。

metadata は `multica issue metadata set <タスク> --key repository --value <OWNER/REPO> --type string` で書く。既存の値が一覧になければ、勝手に別の値へ直さず人間を呼んで止まる。外したリポジトリを作業先に持つタスクも同じ扱いにする。

要件・設計・実装・修正の担当は、`repository` がないか一覧にないとき、作業を始めずリーダーに返す。既存の PR がその値と違うリポジトリにあれば、作業を進めず不一致を返す。レビュー・QA は PR の URL を使うが、一覧にない PR は同じくリーダーへ返す。PR 以外の検証は、依頼が明示した対象を一覧と照合し、作業先が分からなければ推測せず返す。

複数リポジトリの sub-issue には、それぞれの作業先を `repository` に書く。先に入れるリポジトリから順にステージを付け、リポジトリの間で合わせる I/F は親のタスクの要件として合意する。各 sub-issue は一つのリポジトリのタスクとして、設計からの流れを通す。要件を決める担当を置かないときは、リーダーがこの分割を行う。

## タスクの状態と担当

| 状態 | 意味 | 変える人 |
| --- | --- | --- |
| `in_progress` | エージェントの番 | リーダー。振り分けを始めるときと、人間の返事を受けて再開するとき |
| `in_review` | 人間の判断・承認・マージを待つ | 人間を呼んで止まるエージェント |
| `done` | PR がマージされた | Multica の GitHub 連携 |
| `cancelled` | やめた | 人間 |

状態は `multica issue status` で変える。マージと取り下げは人間が決めるので、エージェントの実行が終わっただけでは `done` にしない。結果を書けば完了する運用のタスクについて、自分の役の指示に例外が明記されていれば、その指示に従う。

タスクの担当は「このプロジェクトの値」のスクワッドにし、作業する役は担当にせずメンションで呼ぶ。担当がスクワッドなら、人間の返事はリーダーへ届く。オートパイロットが `create_issue` で作る運用のタスクは、オートパイロットが決めた担当のままにする。

## 呼ぶ人間

通常は、「このプロジェクトの値」にある呼ぶ人間のメンションのリンクを写す。そのスクワッドやエージェントの持ち主が、ランタイムと利用枠を提供し、作業を見て判断するため。起票しただけの人であることがあるので、タスクの作成者を代わりに呼ばない。

持ち主とオーナーは別の語である。オーナーは、ワークスペースの権限の名前（オーナー・管理者・メンバー）である。持ち主は、スクワッドやエージェントなどを作り、そのランタイムと利用枠を提供する人で、`creator_id` や `owner_id` で読む。呼ぶ相手は持ち主で、オーナーとは限らない。

複数の担当者のタスクを横断する運用では、役の指示に従い、対象のタスクの担当から持ち主をたどる。

- 担当がスクワッドなら、`multica squad get` の `creator_id`
- 担当がエージェントなら、`multica agent get` の `owner_id`
- 担当がメンバーなら、そのメンバー
- 担当がなければ親のタスクの担当。それでも分からなければ、メンションせず結果に書く

名前は `multica workspace member list` の `name`、人間のリンクの ID は `user_id` を使う。メンバーの登録行の ID と取り違えない。

## 本文の書き方

PR の本文とコメント、タスクの本文とコメントには、次の決まりを共通で使う。意味のまとまりで区切り、読み手が要点を追えるようにする。

- 1 文は短くする。目安は 60 字以内、読点は 2 つまでとし、長いときは 2 文に分ける
- 段落は意味のまとまり 1 つにつき 1 つにする。1 段落は 2〜4 文、200 字ほどまでとし、段落の間は空行にする
- 段落の中では改行しない。1 文ごとの改行もしない
- 箇条書きの 1 項目は 1〜2 文にする。3 文以上になるときは、項目を分けるか、段落の文章にする
- 箇条書きは、同じ種類のものが 3 つ以上並ぶときに使う。順序や優先があるときは番号付きにする
- 2 つ以下の項目や、理由でつながる話は文章で書く。箇条書きの入れ子は 1 段までにする
- 表は、いくつかの項目を 2 つ以上の同じ観点で比べるときに使う。セルは語句か 1 文にする
- 見出しのすぐ下に、その節の結論を 1〜2 文で書く。見出しだけを続けない

既存の定型は、形も置き場所も変えない。対象は PR テンプレートの見出し、タスクの metadata の `repository`・`branch`・`pr_url`、PR の結果の先頭の行である。`確認したコミット:`、`見直し:`、`返事を待つ役:` の行と、タスクに記録する実装の一覧の列も同じように扱う。

## PR を作る・実装を積む

コードを PR で渡す仕事は、1 タスクにつき 1 PR にする。最初に PR を作る担当が次を行う。

- ブランチ名とタイトルの種類は、最後に入る変更で決める。実装まで進むものは、設計だけの時点でも機能や修正の種類にする。ドキュメントだけで終わるものにだけドキュメントの種類を使う
- プロジェクトの PR テンプレートがあれば、その見出しに沿って本文を作り、`gh pr create --body-file` で渡す
- PR を作った直後に `squad-pr-link <タスク> <PR の URL>` を呼ぶ。`<タスク>` には実行に渡されたタスクの ID を渡し、呼ぶ前に metadata の `pr_url` を書かない
- 終了コードが 0 なら、metadata の `pr_url` はスクリプトが書いたので、`branch` だけを置く。次の担当と見張りが、対象を取り違えないようにするため
- 0 以外なら、止まらずに `branch` と `pr_url` を自分で置く。コマンドが見つからないとき（終了コード 127）も同じに扱う
- 失敗したときは、引き継ぎのコメントの先頭、結論の行のすぐ次の行に「PR をタスクに紐付けられなかったので、タスクの画面で紐付けてほしい」と書く。人間への依頼として扱い、後ろの成果物や確認したことに埋もれさせない。人間はタスクの画面で URL を指定して紐付ける。標準エラーの警告の文も、そのまま写す。404 で待ち切れたときの連携の案内を、人間に届けるため
- タスクの識別子・作業番号・進行の記録は Multica 側に置き、PR の本文やコミットメッセージへ持ち出さない

スクリプトを呼ぶのは PR を作った直後の 1 回だけにする。`pr_url` があると、紐付けずに飛ばすため、失敗後の紐付けは人間が画面で行う。

実装を push するたびに、`gh pr edit --title --body-file` でタイトルを実装に合わせ、本文を最新の状態の要約に書き直す。前の状態の記述に追記せず、フェーズごとの経緯も書かない。実装の分担と作業番号はタスクの本文・コメントに置き、PR には持ち出さない。PR は draft のまま渡し、通常の ready への切り替えとマージは人間に任せる。役の指示で明示された自動処理は、その許可と条件の範囲だけで行う。

### PR の本文の置き場所と順序

最初の本文も push 後の書き直しも、次の表で情報の置き場所を決める。正本がある情報は本文に写さず、読み手が正本へ進めるようにする。

| 情報 | 置き場所 | PR の本文での扱い |
| --- | --- | --- |
| 設計と、その理由・検討した案 | プロジェクトの設計文書（docs など） | 写さず、該当する節を名前で示す |
| 実装の分担・作業番号 | Multica のタスクの本文・コメント | 書かない |
| 作業の進行や経緯 | Multica のタスクの本文・コメント | 書かない。コミットメッセージは変更した動作と理由を書く |
| 検証のコマンドと結論 | PR の本文の確認 | 最新の push の結果だけを 1 件 1 行で書く |
| 通らなかった検証の出力、検出の一覧、対応表などの長い根拠 | PR のコメント | 写さず、確認の行からリンクする |
| レビューと E2E の結果 | PR のコメント | 書かない |

本文は、プロジェクトの PR テンプレートの見出しの順にする。テンプレートが概要・理由・確認・注意の見出しなら、それぞれ次を書く。

1. 概要: 1 文目で、この PR のマージで何が変わるかを書く
2. 理由: 設計文書に書かない判断（PR の進め方など）を書く。設計の理由と検討した案は、設計文書の節の名前で示す
3. 確認: 検証のコマンドと結論を書き、テンプレートのチェックを付ける。長い根拠は PR のコメントへリンクする
4. 注意: 先頭に、人間がマージの前に判断・作業することを書く。ないときは「なし」と書く

長さの目安は 3,000 字以内とする。超えるときは、表の置き場所に移せる情報がないか見直す。折りたたみで長さを隠さない。

ZIP などで渡すと依頼に決まっている仕事は、その成果物を確定して添付する。リポジトリや PR に積むと読み替えない。

## PR にレビューやテストの結果を書く

最初の行を `<マーク> <自分のエージェントの名前>: <結論>` にする。同じ GitHub の認証で書いても、担当した役と結果を読み分けられるようにするため。

| マーク | 意味 |
| --- | --- |
| ❌ | 直すまでマージしない。必須の指摘、セキュリティの高・中、設計の性能基準に届かないもの、E2E の失敗 |
| ⚠️ | 指摘はあるがマージは止めない。推奨、セキュリティの低など |
| ✅ | 指摘なし、またはテスト成功 |

結論には重大度ごとの件数を添える。指摘は、重大度・場所・影響（何が起きるか）・直し方を、1 件 5 行ほどで書く。指摘がないときは、見た範囲を 3 行以内で書く。QA の結果の表（ケース・手順・期待する結果・実際の結果・判定）とスクリーンショットは、今のままにする。スクリーンショットの載せ方は「画像を載せる」に従う。本文の観点や細部は自分の役の指示に従う。`gh pr review --approve` と `--request-changes` は使わない。承認は人間が行うため。

## PR の状態を書く

この節の対象は、PR のコンフリクトと CI の結果だけである。レビュー・E2E・テストの結果は、「確認したコミット:」の決まりで扱う。

- PR のコンフリクトや CI の結果を、タスクのコメントや PR のコメントに書くときは、読んだ値と、読んだ時点の head の SHA を添える。SHA は 7 文字以上で書く
- 見張りのスクリプトが値と head の行を出したとき（`squad-pr-watch conflicts-check` の `コンフリクト:` の行、`ci-check` の `CI <SHA>:` の行）は、その行をそのまま写す
- 空の出力、読めなかった結果、`UNKNOWN` のように決まらなかった値は「未確認」と書く。「なし」や「通った」とは書かない

## タスクのコメントを書く

結果は、実行の最後に 1 回だけ書く。途中経過や計画では次の担当を呼ばない。きっかけのコメントがあるときは、その実行で指定された親コメントへ返信し、前の実行の返信先を使い回さない。

本文を UTF-8 のファイルとして実行の作業ディレクトリ内に保存し、`multica issue comment add --content-file` で投稿する。本文を引数や標準入力に直接渡さず、文字列の改行エスケープで改行を作らない。一時ファイルはその作業ディレクトリの `tmp/` に置き、投稿が成功したあとだけ片付ける。コマンドを続けて書くときは、投稿の成功を条件に片付ける。

添付する成果物は `--attachment` で届ける。実行の中だけにあるファイルのパスを、読める成果物のリンクとして渡さない。

タスクのコメントの本文には、URL のパスや、省略の点から始まるパスを書かない。画面名・処理名・関数名で示す。Multica の WAF が本文を権限エラーで拒否することがあるため。正確なパスが必要なら、PR の本文やコメントへ書き、タスクには PR のリンクを置く。GitHub の PR へのリンクは書いてよい。

投稿が `You do not have permission to access this resource.` で拒否されたら、本文のパスやコードの断片を外して再投稿する。それでも届かなければ、詳細を PR の結果か添付ファイルに置き、呼ぶ人間にその場所と投稿できなかったことを知らせる。通らなかった検証の出力は、パスの有無によらず、PR があれば PR のコメントに、なければ添付ファイルに置く。タスクのコメントには、結論とそのリンクまたは添付の名前を書く。

## 画像を載せる

PR には `gh` の `--attach`、タスクには `multica issue comment add --attachment` を使う。画像を別の置き場に置いて URL を書く方法は使わない。

画像と本文のファイルは、作業ディレクトリの `tmp/` に置く。PR のコメントには、次の形で載せる。`gh pr create` と `gh pr edit` にも同じ `--attach` が使える。

```bash
gh pr comment <PR> --body-file tmp/result.md --attach 'tmp/shot.png#<説明>'
```

本文に `![説明](./shot.png)` のような参照を書き、同じ画像を `--attach` で渡すと、参照がアップロード先の URL に置き換わる。`--body-file` の本文の中のパスは、本文のファイルのディレクトリから探し、なければ作業ディレクトリから探す。

本文に参照のない画像は、コメントの末尾に足される。説明は `#` の後ろに書き、なければファイルの名前を使う。

載せたあとは、終了コードだけでなく、`gh pr view <PR> --json comments` でコメントの本文を確かめる。手元のパスが残っていないことと、参照がアップロード先の URL に置き換わったことを見る。

PR に載せられなかったときは、同じ画像をタスクのコメントに `multica issue comment add --attachment` で載せ、「人間に操作を頼む前に」に従う。PR に載せるまで作業を止めることはしない。

## 人間に操作を頼む前に

「できない」「口がない」として人間に操作を頼む前に、試した方法とコマンドの出力をコメントに残す。

1. 使う CLI の `--help` で、その操作のコマンドとフラグを探す。画像を PR に載せるなら `gh pr comment --help` の `--attach` を見る
2. 見つかった方法を実際に流す
3. 失敗したら、コマンド、終了コード、標準エラーを含む出力を残す。出力は下のとおりファイルにして添える
4. 人間に頼むコメントには、探したヘルプ、流したコマンド、理由を書く

`--help` に方法がなかったときも、その結果を残す。画像を PR に載せられなかったときは、次の表で理由と頼むことを分ける。

| 理由 | 見分け方の例 | 人間に頼むこと |
| --- | --- | --- |
| 認証 | `gh auth status` が未ログインを示す。401 で返る | ホストの `gh` のログイン |
| 権限 | 403 や 404 で返る。push の権限がない | リポジトリの権限、または PR への手での添付 |
| 関所 | 標準エラーが `gh の関所:` で始まる | 関所を避けない。古い `gh` なら `gh` の更新 |
| ファイルの形 | 対応していない形式や大きさのエラー | なし。役が PNG に変えて載せ直す |

試したコマンドと出力は、`tmp/` のテキストのファイルに書き、タスクのコメントに `--attachment` で添える。本文には、試したコマンドの名前、終了コード、理由を書く。出力にはパスが混ざるため、「タスクのコメントを書く」に従って本文から分ける。

関所に止められたときは、「書き込んでよいリポジトリ」のとおり、関所を避ける呼び方をしない。本物の `gh` を絶対パスで呼ぶことや、`gh api` でアップロードを組み立てることも、避ける呼び方に入る。

## 引き継ぐとき

成果物を確定し、依頼どおりに共有したあと、最後のコメントの先頭に「このプロジェクトの値」のスクワッドのメンションのリンクを写してリーダーへ返す。リーダー個人のエージェントへのリンクに替えない。スクワッドのリンクが、スクワッドのリーダーとしての実行を起こすため。

コメントは、次の順に書く。目安は 1,000 字以内とし、根拠は正本へのリンクにする。

1. 結論: 1 行目で、何をして、次に何を頼むかを書く。メンションは先頭に置き、同じ行で結論を続ける。完了したフェーズや範囲もここに入れる
2. 成果物: PR なら push 済みのブランチと PR の URL。ZIP なら添付した名前と sha256
3. 確認したこと: コマンドと結果を 1 件 1 行で書く。通らなかったものの出力は、PR のコメントか添付ファイルに置き、そこへのリンクまたは名前を添える
4. 残っていることと、次の担当に頼むこと

`見直し:` など、役の指示や次の節で決まっている行の形と置き場所は変えない。

依頼や自分の役の指示が `/note` で返すと決めている報告は、その指示に従う。レビューや E2E の返事を待つ登録がある依頼は、次の手順を使う。

## レビューと E2E の返事を返す

依頼の `確認するコミット:` に指定されたコミットを手元に用意し、実際の HEAD が一致することを確認してから検証する。指定がなければ、PR の head、または依頼されたブランチの最新を使う。差分は PR の base からそのコミットまでを見る。前の実行の結果を確かめ直さずに返さない。

報告の先頭に `確認したコミット: <SHA>` を置き、実際の HEAD の完全な SHA を書く。用意できなければ `確認したコミット: なし` と理由を書く。依頼がコミットの代わりに ZIP などを指定しているときは、その名前と sha256 などの識別値を依頼と合わせて報告する。

`返事を待つ役:` の行がある依頼の結果は、`squad-review-wait report <タスク> <きっかけのコメント> <結果のファイル>` で投稿する。この場合は自分でリーダーをメンションせず、全員がそろったかも自分で判断しない。スクリプトが `/note` の結果を書き、そろった知らせを出す。

スクリプトは、投稿後に 20 秒ほど待って読み直すことがある。コマンドの時間切れは 60 秒以上にする。途中で実行が止まっても、結果が投稿済みなら `report` を流し直さない。重複した報告になるため。

`返事を待つ役:` の行がない依頼や、スクリプトが「返事を待つ役の登録がありません」と投稿前に止まった場合は、通常の「引き継ぐとき」で返す。登録のない結果を無通知で返すとリーダーに届かないため。

## 記入が足りずに止まるとき

検証スキルの節やプロジェクトの説明が未記入で止まるときは、セットアップが起票した記入のタスクを示す。未記入なら推測で検証しない。未記入や未実行は成功にしない。

止まると報告する前に、その実行で受け取った内容で未記入かを確かめる。前の報告、タスクのコメント、リーダーの依頼文にある「未記入」は根拠にしない。

| 確かめる対象 | 未記入とみなすとき |
| --- | --- |
| 検証スキル | その実行で受け取った本文に、作業先の `` ## `OWNER/REPO` `` の節がない。または、今回の検証に使う欄に `[記入:` が残る |
| プロジェクトの説明 | その実行で受け取った説明の、今回の作業に要る箇所に `[記入:` が残る |

今回の検証に使わない欄の `[記入:` では止まらない。記入済みなら止まらずに進める。リーダーと要件・設計の役は検証スキルを受け取らないので、説明についてだけ確かめる。スキルの割り当てや取り込みの不足は、記入とは分け、今までどおり不足を書いて止まる。

### 記入のタスクを探す

「このプロジェクトの値」のプロジェクト ID を使い、`multica issue list --project <プロジェクト ID> --metadata squad_kit_task=<種類> --output json` で探す。人がタイトルを直しても探せるよう、タイトルの一致では探さない。

| 足りないもの | 探す印 | 選び方 |
| --- | --- | --- |
| 検証スキルの、作業先の節がない | `squad_kit_task=repository-change` | `squad_kit_targets` に `added:<作業先>` を含むもの。なければ下の `project-instructions` |
| 検証スキルの欄、プロジェクトの説明 | `squad_kit_task=project-instructions` | プロジェクトに 1 つ |

前者は「OWNER/REPO の増減を説明と検証スキルに反映する」、後者は「プロジェクトの説明と検証スキルを記入する」として起票される。状態は絞らず、完了と取り下げも読む。複数あれば、当てはまるものをすべて報告に書く。一覧を読めなかったときは、見つからなかったときと分け、読めなかったことと理由を書く。

### 未記入の報告を返す

「人間を呼んで止まるとき」の形で、1 行目に未記入で止まったことと、先に片付ける記入のタスクを書く。報告には次を書く。

1. 足りない欄。検証スキルの節の見出しと欄の名前、またはプロジェクトの説明の箇所
2. 確かめた内容。その実行で受け取った検証スキルか説明で確かめたこと
3. 記入のタスク。識別子（タスクへのリンク）、タイトル、今の状態
4. 次の手。記入のタスクを先に片付け、記入を終えたらこのタスクに返事をすれば再開すること

記入のタスクが `done` か `cancelled` なのに未記入のときは、状態をそのまま書く。記入が反映されていないので確かめてほしいと添える。記入のタスクが見つからないときは、足りない欄と、見つからなかったこと、探した印を書いて止まる。

レビューや E2E の依頼で `返事を待つ役:` の行がある実行は、人間を直接呼ばない。上の 1〜4 を結果に書き、その検証は未実行として、「レビューと E2E の返事を返す」の手順で返す。

### リーダーが報告を受けたとき

未記入の報告を人間へ返すときや、人間の返事で再開するときは、記入のタスクをその実行で探し直す。前の報告にある状態を写さず、今の状態を書く。

報告のあとに記入のタスクが `done` になっていれば、人間を呼ばず、止まった役にもう一度確かめるよう頼む。報告より前から `done` だったときは、記入が反映されていないおそれがあるので、人間を呼んで止まる。同じ役が同じ理由で 2 回止まったときも、人間を呼んで止まる。

## 人間を呼んで止まるとき

「このプロジェクトの値」の呼ぶ人間のリンクを写し、何を決めてほしいかを書く。複数の案があるなら良い点・悪い点を添える。タスクを `in_review` にし、それ以上エージェントを呼ばずに実行を終える。

## 新しいタスクを作るとき

先に `multica issue search` で同じものがないか確かめる。`--project` には「このプロジェクトの値」のプロジェクト ID、`--assignee-id` にはスクワッドの ID を渡す。担当なしにすると次の担当が起きないため、作る時点で渡す。

ラベルは仕事に合わせて `開発`、`運用`、`指示の改善` のいずれかを 1 つ付ける。`検証` は、人が動作確認のためのタスクに使う。ラベルの ID は `multica label list` の名前から引き、作成後に `multica issue label add` で付ける。

元のタスクから分けるなら sub-issue にする。順番があるものは `--stage` でステージを揃える。最初より後のステージは、担当を付けず `backlog` で作り、前のステージが終わったらリーダーが担当と状態を設定する。担当を付けてすぐ起動し、前のステージを待たずに進むことを防ぐため。

## リーダーの手順

`references/leader-*.md` は、リーダーの手順である。リーダーだけが読み、ほかの役は読まない。

リーダーは、自分の指示の「場面と手順」の表から、その場面のファイルを選び、その実行の中で読む。手順の詳細はそれぞれのファイルにあり、このスキルには置かない。

## サブエージェントに分けるとき

依頼された範囲と権限の中で作業を分ける。親は、次の文をサブエージェントへの指示にそのまま写す。

```text
あなたはサブエージェントです。Multica のタスクにコメントもメンションもせず、タスクの状態も変えないでください。結果（変えたこと、コミットとブランチ、確かめたことと結果）は、最後の返答として親のエージェントに返してください。
```

親は全員の結果を受け取り、依頼どおりに共有できる成果物へまとめてから、最後に 1 回で引き継ぐ。サブエージェントはタスクの割り当てで起きた独立の実行と区別し、コメント・メンション・状態変更をせず、結果を親へ返す。
